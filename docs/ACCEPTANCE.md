# Acceptance Criteria – First Phase

The security criteria are defined only in `docs/SECURITY.md`, section 11; they are part of this acceptance (section 10). `[x]` means implemented and verified; `[ ]` means open, with the open part named under "Open". Never tick a criterion that was not verified on a real system.

## 1. Project and Setup

* [x] Minimum versions of Python, Django, MariaDB and all packages are documented with sources, still receive vendor security updates and are proven by tests (D-015). Migrations run reproducibly.

## 2. Login Page, Registration and Login

* [x] The login page is the entry point (login, password reset, registration, links to the privacy notice and the instance's website); every page accessible without login links to the privacy notice (D-022, D-025). No public home page: the root URL leads to the login page or, when logged in, to the start page (D-057), subject to the central second-factor check.
* [x] Registration with the email address only, verification link, sign-in method chosen and set up (password, password and app, or passkey; step 2 of 3), required profile data (step 3 of 3) activates the account; the customer number is assigned only when the last step succeeds (D-021, D-058). Login with the email address (not the customer number); logout; password change and reset.

## 3. Two-Factor Authentication

* [ ] Complete passkey lifecycle (D-106): shared method choice, username-free sign-in, current proof in sensitive actions, management, both switch directions, unified 24-hour recovery and narrow staff reset access. No feature flags. **Open:** human security review; genuine username-free and backup-only browser sign-in (not verified: the integrated browser returned `NotAllowedError` before the assertion POST).
* [x] Users can set up an authenticator app (TOTP) optionally and remove it after re-authentication; staff users and system administrators require password plus app or passkey-only mode before using normal functions (D-004, D-106). App setup issues recovery codes; passkey accounts have none.
* [x] Under D-106, any active staff user or system administrator may initiate recovery for any account, including their own and the last system administrator, after the official-ID name check; an ordinary account with no building, metering point or IBAN entered starts it itself by email. Old methods remain until the owner confirms the single-use 24-hour link by CSRF-protected POST. The resulting session has setup access only; normal permissions return only after complete method setup. Unrelated account/privilege editing stays protected.
* [x] Completion of the second factor is checked in one central place, TOTP-specific parts separate.
* [ ] Guidance for the login method (D-106): the shared choice explains requirements, recovery and recommendations. Registration (step 2), start tile, profile, password reset and administrator first login use the same component. Server options (`login_methods.available`) are password / password plus app / passkey for ordinary users and app / passkey for administrators; posted unoffered methods are refused. The router does not change credentials. Sensitive operations require the current method's proof. **Open:** screen-reader and 200 % zoom checks.
* [ ] Login page (D-106): one native shared persistence checkbox, consecutive password/passkey/register actions, one recovery entry to the GET-only situation chooser, accurate password-then-code guidance. **Open:** real authenticator cancellation/retry, mobile/zoom and no-JavaScript checks.
* [ ] Exactly one active passkey suffices uniformly for setup/activation, administrator promotion and retention; removing the last active key is refused, also concurrently. No two-device statement or checkbox. Atomic activation removes password, app and recovery codes. **Open:** independent security/human review.
* [ ] An active passkey account can add a passkey from the profile without selecting the method again. After current proof, "another device" and "this device" emit cross-platform/HYBRID and platform/CLIENT_DEVICE options; invalid or missing modes are refused. Creation stages the credential; explicit saving keeps the current session and existing keys, ends all other sessions and notifies all confirmed addresses. Localized guided help keeps the user on the authenticated computer, explains optional browser/OS QR/hybrid creation without an existing phone passkey or phone portal visit (loopback addresses are device-local), and cancellation or another method if unsupported. One key suffices; another is strongly recommended, not proof of physical independence. **Open (not covered by automated tests):** native browser behaviour, genuine cross-device creation, unsupported-client cancellation/retry, phone, screen reader and 200 % zoom.
* Open security-review trade-off: recovery dispatch holds the account lock during external mail delivery; a slow backend can delay writes to that account. The production Graph path has 30-second network timeouts. Human review required.

## 4. Profile and Account Lifecycle

* [x] Profile as five cards that change in place and work without a script (D-059); name and postal address required.
* [ ] Address suggestions and the not-found notice appear only while an address is edited, as in `docs/DESIGN.md`, section 6; nothing else about the directory is shown, no source named (D-066). **Open:** verified only with a stub and a synthetic directory; not accepted on a real system.
* [x] Email change as in `docs/PROJECT.md`, "Changing the Email Address"; second address, pending request and stop link as in D-059; every change of second factor, password or address is mailed to every address of the account.
* [x] Block, unblock, delete and reactivate (administrators), self-deletion (users) and re-registration of the same address follow D-016; the status (`docs/PROJECT.md`, "Account States") is displayed understandably.

## 5. First System Administrator

* [x] Created at the first start by `manage.py setup_instance` from `BOOTSTRAP_SYSTEM_ADMIN_EMAIL` and `BOOTSTRAP_SYSTEM_ADMIN_PASSWORD` (D-076; `setup_initial_administrator` is an alternative, D-005): password never printed or logged, ignored once an administrator exists; created only while the account table is empty (otherwise an error); two starts cannot create two administrators; the instance is not public until the first login is complete, because the initial password has no expiry (`docs/DEPLOYMENT.md`, section 9). At the first login the password must be changed and two-factor set up.

## 6. Roles and Permissions

* [x] A system administrator can create, rename and delete roles (groups), link them to permissions, assign roles and grant or remove `is_staff` and `is_superuser`. No role is hard-coded (no code, migration or fixture creates, names or checks roles).
* [ ] Administration tables of the management data work as in D-091: staff with the `view` right see read-only tables without free text, IBAN, emails and names and cannot write (403); a system administrator edits every column in the list with one "Save", adds a row in the new row and deletes one row; every write is in the admin log and in one security event without values (tests `community.tests.test_admin_tables`, `test_admin_raw_tables`). **Open:** browser check (input widths, new row, raw-id lookup popup, date inputs, 375 px) and security review.

## 7. Instance Configuration

* [x] No instance-specific value is hard-coded in code, templates or migrations; a second instance can be set up from the same code base with only the documented steps and its own configuration.
* [ ] The installation guide states that the application runs on its own host name, not under a path of another website, with the residual risk of a subdomain of the website's registrable domain (D-025), and describes the operator's manual branding checks (`docs/DESIGN.md`, sections 3.2 and 10).
* [ ] Portal settings work as in D-073 (rights, precedence of administration, environment and default, security settings read-only, 403 without the right, security events without file content). **Open:** browser checks of D-073 (SVG in `<img>` under the sandbox policy, live preview under the CSP, 375 px and 200 % zoom), security review, reverse proxy limit (V35 in `docs/DEPLOYMENT.md`).

## 8. Email

* [x] Central interface for outgoing email; the Graph configuration section of the admin never shows the private key, shows the certificate expiry with a warning, and its test send gives understandable feedback.
* [x] The editable email texts follow D-039 (unknown placeholders, missing personal link, typed addresses and template syntax refused; default, preview, test email only to the own address, versions; no access without the permission).
* [x] Security notifications tell the person to contact the operator (instance contact where configured), do not invite a reply, and greet by name only as in D-068 (`docs/DESIGN.md`, section 8; also in preview and test email); the name is blanked in queued notifications when the account is deleted; no other email greets by name.
* [ ] The installation guide explains how to restrict the Microsoft application to the sender mailbox ("RBAC for Applications") and that the sender mailbox must be monitored.
* [x] The ten onboarding mails (D-103) are notifications to every address of the account with the greeting of D-068 and one link to the login page; no address, IBAN or metering point number; each reminder and rollback mail is queued exactly once (automated tests; no real Graph run).

## 9. Security Logging

* [x] System administrators can view the security log; retention is configurable per instance (D-018). A long session ("Stay signed in") of a staff user or system administrator is written to the security log (no email, D-100), and a system administrator can end all sessions of another account (D-100; automated tests).
