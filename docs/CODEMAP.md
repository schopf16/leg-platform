# Code Map

What is where, and where to change what. Read this instead of searching the code. It lists entry points, not every function (use grep for the rest). Paths are relative to `leg_platform/` (the package) unless they start with `docs/`, `scripts/`, `locale/` or `.claude/`. `D-nnn` are decision IDs in `docs/DECISIONS.md`. A wrong pointer is a defect of this file: fix it in the same change.

## 1. Architecture

* One Django project (`settings.py`, `ROOT_URLCONF = "leg_platform.urls"`), one instance per municipality. MariaDB (`default`) plus a read-only SQLite file for the address directory (alias `addresses`).
* Apps in `INSTALLED_APPS` order:
  * `accounts`: user model, login, registration, second factor, profile, mail queue, security log, administration.
  * `addresses`: address directory and import.
  * `community`: domain of the management area (models, rules, services; no pages).
  * `customer`: the pages of the customer's participation under `/participation/` (D-105; no models, no permissions: see section 6a).
  * `management`: pages under `/management/` (lists, dialogs, PDF printing).
  * `admin_site.PortalAdminConfig`: replaces `django.contrib.admin`.
* Third party: `axes` (login lockout), `django_otp` (device functions only), `django_countries`, `phonenumber_field`. Tabler is self-hosted in `static/vendor/`.
* `MIDDLEWARE` in order: `SecurityMiddleware`, `ContentSecurityPolicyMiddleware`, `middleware.NoStoreForManagementMiddleware`, `middleware.RequestBodyLimitMiddleware`, sessions, `language.ChosenLanguageMiddleware` (the language cookie, D-056), common, CSRF, authentication, `OTPMiddleware`, messages, `accounts.session_timeout.SessionTimeoutMiddleware`, `accounts.second_factor.SecondFactorMiddleware` (a privileged account without a second factor can only set it up or log out), `XFrameOptionsMiddleware`, `AxesMiddleware`.
* `urls.py`: `instance.css`, `branding/logo/<variant>/` and `branding/favicon/` (`presentation`), `language/` (`language.set_language`, name `set_language`), `addresses/`, `management/`, `participation/` (`customer.urls`, namespace `customer`), `""` (`accounts.views.HomeView`, name `home`), `""` (`accounts.urls`, namespace `accounts`), `admin/`.
* Templates: `templates/` (shells `base.html`, `entry_base.html`, `error_base.html`, error pages, `_frame_menu.html`, `_corner_controls.html` (language menu form and theme button), `admin/` overrides; `admin/base_site.html` is the shell of the Django administration: the staff-area title prefix, the chip, the links "Management" and "My area" instead of "View site", D-113) plus `<app>/templates/`. Global context: `context_processors.instance`. Static: `static/`, `management/static/management/` and `customer/static/customer/`. The CSP allows only the own origin: no inline script or style.
* Background work:
  * `manage.py process_mail_queue --loop`: separate process, outbox `MailJob` (D-037).
  * The address import for the button runs in a thread of the web process (`addresses/runner.py`, claim in `addresses.ImportRequest`, D-090). Only that thread writes the SQLite file (`storage.mark_thread_writer`).
  * `manage.py process_address_imports`: optional worker alternative (`storage.mark_writer`).
  * `manage.py run_scheduled_tasks`: every cleanup command once, then the daily address directory run (`scheduled_address_import`: update flag, own process, `storage.mark_writer`); scheduled externally.
* Logs: standard error always, plus `application.log` and `security.log` in `LOG_DIRECTORY` (`logfiles.py`; viewed by system administrators, `log_views.py`, D-099).
* Email: `EMAIL_MODE` console / graph (D-116). Graph sender `mail.GraphEmailBackend`; the chapter "Email" of the administration (model `GraphConfiguration`: Graph settings, sender and contact address, D-116); sender and contact address are read by `accounts/mail_addresses.py`. Texts: default template plus optional administrator text (`EmailText`).
* Operations: `docs/STARTUP.md`, `docs/DEPLOYMENT.md`, `docs/INSTALLATION.md`, `docs/OPERATIONS.md`.

Logic (`accounts/*.py`):

`passkeys.py`: D-106 WebAuthn primitives (`begin`, `register`, `authenticate`, `relying_party`). `begin` requires an allowlisted registration mode: `another_device` emits cross-platform/HYBRID, `this_device` platform/CLIENT_DEVICE; authentication accepts no registration mode.
`passkey_methods.py`: current-proof setup grant, atomic `activate`, `remove` with a uniform permanent one-active-key minimum.
`activate` never reads or writes device confirmation. Activation and additional-key saving preserve only the current session, retain existing keys and notify confirmed addresses; removal ends all sessions.
`passkey_views.py`: JSON `OptionsView`, username-free `LoginView`, current-proof `SetupView`, `ManageView` under `/passkeys/`.
`SetupView` (`/passkeys/setup/`, `passkey_setup.html`) is the passkey wizard in the look of the building wizard (owner specification `profil/umsetzung/KAPITEL-PASSKEY.md`, chapters 8 and 9): one address, the screen in `?step=`: no valid proof grant always shows the proof (`SignInChangeProofForm`; a passkey account proves with a fresh passkey), then `name` (step 1 of 3, `CredentialNameForm`, kept in the session key `NAME_KEY`, display state only), `device` (step 2 of 3: "On this device" / "On another device"), the creation form `#passkey-create` that holds the panels "Confirm in the window" and "Did not work" (step 3; `static/js/passkey-setup.js` only shows them and passes the chosen device to the button `mode` that `passkeys.js` reads), `confirm` (step 3 "Activate passkey": the confirmation before `passkey_methods.activate`, shown whenever this session has staged keys, i.e. for a first passkey (red warning that the password and number code are deleted) and for recovery; a FURTHER passkey, from an account that already has an active passkey, is activated by `SetupView.post` itself right after the successful ceremony, in the same JSON request, D-112), `done` (result from the session key `DONE_KEY`, set after the activation, with the flag `further` for the heading). The choice "Passkey" of the flow "Change sign-in" has no screen of its own: `SignInChangeView.post_choice` converts the grant (`post_passkey`) and redirects to this setup. The JSON register POST, the `activate` POST and `passkey_methods` are unchanged; the POST `cancel` ends the grant and deletes only the unactivated keys of this session binding (`staged`). `ManageView` (`/passkeys/`, `passkeys.html`, chapter 10): one card per active key (name, created, last used, "Remove" only with two or more keys; the last key shows the reason instead), the removal as its own screen `?remove=<id>` (only among the account's active keys, opening changes nothing) whose POST needs a fresh passkey proof (`RemovalProofForm`, widget `show_lead` off) and ends all sessions. No device information, no help sections, no renaming (not released). `CredentialNameForm` is also the server-side check of the name at registration. Styles `.wizard-form`, `.key-facts`, `.step-ok`, `.step-hint`, `.page-actions` in `customer.css`. The passkey card of the profile (`_two_factor.html`, state view) shows the status "Passkey", one sentence, the primary button "Manage passkeys", the secondary button "Set up another passkey" and the small link "Change sign-in" (`.profile-link`, 44 px; the password card of a passkey account has no button). The profile entry of the menu is active on `/passkeys/` and `/passkeys/setup/` (`context_processors.PROFILE_VIEWS`). After a removal the login page shows "The passkey was removed. You were signed out." through the messages (no name). `passkey_methods.allow_setup(request, started=)` keeps the time of the original proof when the flow hands its grant over; `setup_allowed` treats a non-dict grant as none. `SetupView` closes the flow-wide guards of D-112; tests of the refusals: `A.test_proof_entry_points`. `_password.html` routes passkey accounts directly to the shared choice. Setup/removal reach `OptionsView` with an allowlisted registration mode (no automatic platform fallback; an explicitly browser-reported platform result for another-device creation is not submitted: UX guard only, no signed device proof). `admin/users.py` recovery eligibility is active-account-based, including password-only/first-login accounts; recovery-only settings display the formatted customer number and native admin action.
`admin/users.py`: `UserAdminForm` and locked `save_model` recheck a completed factor for promotion; one active passkey suffices. No device-statement field or legacy flag gates promotion. Foreign system-administrator authority and unrelated privilege protections remain. Tests use actual admin GET/POST in `test_method_changes.py` and `test_passkeys.py`.
`method_changes.py`: staged hash/app, `start`, `confirm_app`, outbox `process_return_link`, atomic `complete`.
`method_views.py`: `PasswordMethodView`, `AppMethodView` / `AppMethodQrView`, scanner-safe `ReturnVerifyView` / `ReturnConfirmView`, anonymous GET-only `LoginHelpView` (`/login/help/`, `login_help.html`) and public `RecoveryRequestView`. Routes `/sign-in-method/`, `/recovery/`. `_recovery_clarification.html` explains the second-passkey and password-then-recovery-code alternatives in both help pages.

`second_factor_reset.process_reset_link` locks the account for address-bound issuance and rechecks the recipient/current token under that lock at dispatch. `find_link` / `find_link_by_digest` and locked `confirm_link` require the token's `target_email` to match the current normalized login address. `email_change.confirm_change` revokes recovery tokens on a confirmed login-address change. `test_second_factor_reset.py` covers issued/opened links, delayed dispatch, and real MariaDB issuance/address-change and parallel-worker races.

## 8. Conventions a change must follow

* English everywhere in the repository; every user-facing text is translatable (English source) with a Swiss German translation in `django.po`; never "ß" (`AGENTS.md`, section 2).
* No instance-specific value in code, templates or migrations; email links only from `INSTANCE_BASE_URL` (`settings`, `emails.absolute_url`; environment again, D-116 amendment); never read `Host` from `request.META`.
* Roles (D-012): three fixed access levels; never create, name or check a group in code; permissions with English codenames; only system administrators change `is_staff`, `is_superuser`, groups, permissions (enforced in `UserAdmin` / `UserAdminForm`).
* Metering point numbers (D-109): every page shows one only through the filter `{{ number|metering_point }}` (`{% load metering_points %}`; attributes and sentences `|metering_point_text`, Python `numbers.format_metering_point_number`), never raw and never with `<wbr>`; white space is never part of a number (`numbers.compact_number`).
* Customer pages (D-105): every `/participation/` URL is served by a view with `CustomerAccessMixin` (active customer with a customer number; staff accounts and system administrators take part too, D-113); every id is resolved through the account; no `csrf_exempt`; every POST is counted by `customer.limits`; no address, IBAN or number in a log; `customer/tests/test_access.py` walks the routes. A confirmation on a customer page (the deregistration) uses `accounts.forms.ReauthenticationForm` (one proof, D-062), masks `current_password` / `otp_token` and ends a session like `ProfileCardView`; a way back in an address is accepted only through `customer.returns.safe_return_path`.
* Management area (D-086, the approved exception to D-012): no Django permission; every `/management/` URL is served by a view with `ManagementAccessMixin` or `@management_view`; never show or hide a page, column, filter, count, print scope or menu entry by permission; `management/tests/test_access.py` walks the URL configuration and fails for an unprotected route; no `csrf_exempt`, no `put` / `patch` / `delete` handler; `test_acceptance_matrix.py` (`test_every_route_has_a_case`) needs a case per route.
* Guarded `User` writes (D-034): status, `is_active`, email, `retention_obligation`, `is_staff`, `is_superuser`, `customer_number`, password and `session_version` change only through `User` methods; `UserQuerySet.update`, `delete`, `bulk_create` refuse them (`AccountIntegrityError`).
* Two logs: the security log (`security_log.record`) holds security events with internal numbers and no personal data (D-018). The History (`community.history.record`) holds who changed which management object, with ids and field names, never note, IBAN, operator customer number, email or password (D-077, D-087).
* Security: checks only on the server; never trust ids or roles from the browser; no secret in code, logs or error responses; no inline script or style; responses with customer data are `no-store`.
* Schema changes only through migrations; exact identifier columns use `EXACT_COLLATION`. UI changes follow `docs/DESIGN.md`.
* Documentation style: short sentences, bullets, facts and sources only, no narration, one place per fact, point to D-numbers instead of repeating (`AGENTS.md`, section 7). Decision entries: `docs/DECISIONS.md`, header "How to add a decision".
* Tests (D-071, `docs/DECISIONS.md` section 14): tests for new code incl. negative authorization; class data in `setUpTestData`; `TransactionTestCase` only where needed; threaded tests only on MariaDB (tag `mariadb`); messages are compared with the `de-ch` translation; one test process at a time; run the area, not the full suite.
