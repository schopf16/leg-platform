# Security Policy – Security Keeper

## 1. Binding Principle

Security by design and security by default apply to all architecture, development, configuration and operational decisions. The AI takes on the role of Security Keeper: it actively identifies risks, explains them clearly and proposes secure alternatives. Security must never be silently weakened in favour of convenience or development speed. The software must be securely operable by municipalities without in-depth IT knowledge: secure defaults, few manual security steps, clear instructions.

## 2. Security Decisions

For security-relevant changes: (1) identify protection needs and possible attacks; (2) determine protective measures; (3) choose a secure implementation, preferably an established, maintained solution instead of a custom development; (4) add automated tests; (5) document the checks actually performed; (6) openly name remaining risks. In case of significant uncertainty, ask before implementing.

Security decisions are not based on assumptions. Measures, configurations and statements about threats are verified against official sources (vendors' security documentation, e.g. Django and Microsoft; recognised standards, e.g. OWASP; official government requirements). Blogs, forums, news and tabloid content are not a basis (`AGENTS.md`, section 3).

## 3. Authentication

* Use Django's password functions and established mechanisms. No custom hashing: Django's default hasher with the default work factor of the installed version, never below the OWASP recommendation (D-023).
* Login is possible only with the email address (D-021). The customer number is not a login identifier (counting failed attempts per account across two identifiers would reveal which address and customer number belong together).
  * Addresses are looked up only through the normalised unique column of accounts that are not deactivated, so exactly one account is found. The normalisation (at least trimming and lower case) is defined in one place and used for storage and for every lookup and per-address counter.
  * A login with a nonexistent address returns the same response and lockout behaviour as a wrong password and keeps Django's protection against timing differences for nonexistent users (`ModelBackend` behaviour).
* Password rules (Django validators): minimum length 15 for all accounts (OWASP: 15 without MFA, 8 with MFA; two-factor is optional and removable, so 15 applies to all; D-004), at least 64 characters accepted, all characters allowed, no composition rules.
* An account can log in only once its email address is verified and a password is set. Blocked and deactivated accounts cannot log in.
* **Registration (three steps, D-055, D-058).**
  * Step 1 takes only the email address. The password is set only after verification, on the page reached through the link (step 2): checked and kept **only as a hash** in the browser's session, bound to the digest of that link. The account is **activated only by the last step** (name, address, consent), which writes status, customer number and password in one transaction under the locks of the account and of the link. Consent is stored with its time and the privacy notice address shown.
  * Later steps ignore every field except the password (step 2) and the profile fields with the consent (step 3: name, street, house number, postal code, town; country Switzerland). New accounts have no rights (no `is_staff`, `is_superuser`, groups, permissions; retention flag, status and customer number are server-assigned).
  * The link stays valid until the last step is completed (scanners, back button); opening it rotates the session key; the registration session keys are removed after completion and when the link is invalid. A used, replaced or expired link cannot log anyone in. Completing logs the person in once (session ID renewed, no rights, no failed attempt recorded).
  * The page after the request names the address entered in this browser (from its own session, never from the URL) and offers "send again" only after a server-enforced pause of 60 seconds; the address cannot be chosen in the resend request; the limits below apply to every resend.
  * Unverified accounts and their data are deleted when the link expires. A new registration with the address of an unverified account replaces the pending one. Registration and email change respond in comparable time whether or not the address is in use (asynchronous mail).
* **Invitation by staff (D-087).** Staff create a person and invite them. The account is **unverified**, with an unusable password, no customer number, no rights, no groups and the controlled mark `invited_at` (no form or `create_user` accepts it); **staff never set or see a password**. The link is the registration link (purpose `registration`, single use, **7 days**); only the last step activates the account. A new link (resend, or the person registering the same address) replaces the earlier one; an anonymous registration of an invited address never deletes the invitation. Address and instance limits apply to every invitation, the client-address limit does not (offices create many persons); a limit of 60 per hour per staff account and a pause of 60 seconds per invited account do. A duplicate address is answered to staff with "already in use" only. Expiry deletes the account. Creation, resend and every change of customer data by staff are in the security log (actor, account number) and the person's history.
* **Two-factor authentication (TOTP app) is mandatory for staff users and system administrators and optional for users (D-004).**
  * `is_staff` and `is_superuser` are granted only to an account that has already set up two-factor (D-042), otherwise whoever knows its password could enrol their own app. An account with these rights but without a second factor (the initial administrator, or after a reset) must set it up at its next login before using any function; such sessions have no privileges.
  * Completion of the second factor is checked in one central place, independent of the method, so that a later switch to AGOV does not change the check (`docs/PROJECT.md`, "AGOV and Passkeys"); a switch must keep at least the current level. No function checks TOTP devices directly.
* Recovery codes are issued at setup, single-use, regenerated after re-authentication (the old ones become invalid). A recovery code counts as a second factor at the login and in "phone lost"; it is no proof in confirmations of the profile (D-062).
* **Budget of wrong codes at the second step of the login (D-040):** per account, a window of 24 hours from the first wrong code; at 10 wrong codes the owner is notified by email without a link (once per window); at 15 code entry is paused, also for a correct code, until the window ends or the password is reset (at most 10 counted failures remain). Only wrong codes that reach the check count (not attempts refused by a lockout, not wrong passwords), so someone who knows only the address can neither pause the account nor trigger the email. A successful login does not clear the budget. The budget applies to the second step of the login **only**. The pending login between password and code ends when the password changes.
* **Lost second factor (no recovery code):**
  * Users: a system administrator starts the removal; a time-limited (24 hours), single-use link goes to the registered address; opening it changes nothing, only the confirmation does. The sender address of an incoming email is no proof (RFC 7489).
  * Staff and system administrators: reset by a system administrator only after verifying the identity in person or by calling back a phone number known independently of the account (not from its editable profile), confirmed in the administration; never for the administrator's own account. The factor of the last system administrator is reset only by `manage.py emergency_access` on the server (resets any account).
  * Every reset ends all sessions, notifies the owner without a link, is logged and deletes the account's open address-change requests and links. A password reset never removes or bypasses the second factor.
* **Re-authentication (D-062, "2FA wins")** is required to change the email address or password, delete the account, remove two-factor and generate recovery codes. It asks for **exactly one proof**: the 6-digit app code if a second factor is set up (**a recovery code is no proof here**), otherwise the current password, never both (OWASP Authentication Cheat Sheet; NIST SP 800-63B-4). The form shows only the field it needs; a posted `current_password` is ignored when a code is required.
  * An input that is not exactly 6 digits (after removing spaces and hyphens) is refused **before** the check and **counts nowhere** (a password typed into the code field by habit must not lock anyone out). The code field never writes its value back. The code is checked and used up only after every other field is valid (**accepted consequence**: the password card consumes the code before the comparison "new equals current").
  * **Wrong entries in a confirmation (wrong code, or wrong password where the password is the proof) count for the session and the account and are never failed logins** (no effect on Axes, the IP counter or the budget above, so whoever only holds a session can neither pause nor lock the login): the 5th wrong entry ends that session (event `session_ended_wrong_codes`, one notice to every address); the 15th within 24 hours over all sessions ends **all** sessions (`all_sessions_ended`, one notice, count restarts, **no pause of the login**). The count is kept on the server under a random session identifier that survives `cycle_key` and is never visible to the browser; a request already running when the sessions end is refused under the lock. A correct proof restarts the session's count. A lockout of Axes and an existing pause still refuse the check. **Honest limit:** someone with a session and the password can still guess the code (5 per session, 15 per 24 hours) but cannot get a new session without password and code.
  * The new password of the card "Passwort" may not equal the stored one; compared **only after a valid proof** (`check_password`, no setter; otherwise a guessing oracle without abuse protection, security review H-1). The view compares the session hash under the account lock with the value at the start of the request and refuses the change if the account changed meanwhile (D-040).
  * **"Phone lost" (turn off 2FA with password and a recovery code)** needs both, right, checked in this order: format and required fields, password (counted like a code, not as failed login), code (used up only if everything before was right). Wrong password, wrong code and another account's code give the same message. State check, both checks and removal are **one transaction under the account row lock** (a refusal gives the code back; of two parallel posts with the same code one wins). Not offered to staff and administrators; no effect without a second factor. Afterwards the factor is removed, other sessions end, every address is told, and the event `two_factor_removed_phone_lost` is kept for the long period. Whoever has neither app nor code goes through the operator (D-004).
* **Abuse protection (D-017, D-038):** Axes for account lockouts plus a separate transactional IP counter (Axes account resets also delete records that feed its IP bucket).
  * Failed attempts are limited per account and per IP. Lockouts are temporary, so attackers cannot lock others out permanently. A password reset stays possible during a lockout and ends only that account's temporary lockout (counters and lockouts per IP remain, so an attacker cannot lift their IP lockout by resetting their own account). Remaining risk (D-017): attackers who know an address can repeatedly cause temporary lockouts and use up the per-address email limit; the owner can still use links already in the mailbox.
  * Behind reverse proxies the exact trusted proxy count is `AXES_IPWARE_PROXY_COUNT` (default `0`: `REMOTE_ADDR`, forwarded headers ignored). A positive count enables strict proxy-chain validation; a mismatch yields no client IP and the login is refused. Client IP headers are otherwise forgeable.
  * Axes stores only a keyed digest of the normalised address and no raw IP; the IP lockout table stores an HMAC-SHA256 digest with a purpose-specific key derived from `SECRET_KEY` via HKDF (D-017, D-023). Password and OTP fields are masked; Axes access logs are off.
  * **Registration, password reset and email change** are rate-limited per IP and per normalised target address. A request above the per-address limit is not processed: no email, no replaced pending registration or change; the most recent verification link and reset links already sent stay valid. Below the limit a new registration replaces the pending one and a new reset request invalidates earlier reset links (D-042). Exceeding a limit changes neither response nor response time. Counters hold only keyed hashes (HMAC-SHA256, HKDF key; D-023) for the window.
  * **Mechanism (D-038):** the request stores only a counter entry and one job in a database outbox and makes no account lookup; a worker looks up the address, decides and sends. Three budgets count a request only if all have room: per address (12 per hour, 3 per 10 minutes, 24 per day; never shown), per client IP (IPv6 by /64) and instance wide. Over the client or instance budget: HTTP 429 ("Zu viele Anfragen"), no job, counter row or session. A request for the address this browser entered less than the pause ago, or a bot-check hit, creates no job; such silent requests are counted per client address (30 per hour) and above that get the same 429 (security review phase 4, M4). **Bot check, stage 0 (D-058):** hidden field and signed time stamp (at least 2 seconds) on step 1 and the reset request; a hit gets the same page without a job. Proof of work is only a recommendation (not built). The information email to an existing address is sent at most once per address per 24 hours. Jobs and counters store keyed digests; an unprocessed job holds the address for at most one hour; tokens are never stored in a job.
  * **A notification job holds the cleaned name for the greeting (D-068)** (empty for the neutral greeting, a deleted account and an address not belonging to the account at queue time): personal data with the life of the job (deleted after sending, after the third failed attempt, after 24 hours by the clean-up, with the account for jobs carrying the account key; blanked at once in every queued job when an account is deleted or deactivated, review M1); never logged.
  * **Editable email texts (D-039)** are plain text with fixed `{placeholder}` markers, never evaluated by the template engine. A text is accepted only if all placeholders are valid for that email, the personal link is present and no web or email address is typed in (deny-list, also in the subject). `{greeting}` exists only in the 14 notifications to the addresses of an account and is refused elsewhere, so a name never reaches a registration, reset or other mail to an unverified or foreign address; the name passes an allow-list (letters, combining marks only after a letter and at most three in a row, space, hyphen, apostrophe, period; no digits, symbols, line breaks, format characters, invisible marks or address-like text; at most 64 characters), is checked again when the email is built, otherwise the greeting is neutral. Changing a text needs the permission "change email text" (runtime role), is recorded in the administration log without the text; the history is visible to system administrators only. A test email goes only to the logged-in account's address; earlier versions can be restored after validation.
* Error responses give no hint about the existence of accounts (including blocked and deactivated ones); registration and email change use generic responses (`docs/PROJECT.md`, "Registration", "Changing the Email Address"). Reset links are random, single-use, time-limited, abuse-protected; reset is impossible for unverified, blocked and deactivated accounts with an identical response and comparable time.
* **Email address change** requires re-authentication and takes effect only after the new address is verified via a time-limited (24 hours), single-use link. The old address stays valid until then and is notified afterwards. Only the most recent pending change can be confirmed (D-059). A request stores a pending row for every target address whatever it belongs to (the answer does not tell whether it is in use); the person can cancel. Confirming a change or reactivating an account deletes a pending unverified registration with the same address.
  * A **second address** (own confirmation and status) is a recipient of every notification, **never an identifier** (no login, reset or lookup); removable at once after re-authentication.
  * **Stop link (D-059).** A request for a new login or second address sends a notice with a link "stop it at once" to the old login address and the confirmed second address (queued before the confirmation link; a new request deletes the earlier stop links). The link works without a login in two steps (a page, then a POST with CSRF token), so a mail scanner stops nothing; it cancels all pending changes, deletes all confirmation and stop tokens, ends every session of the account and logs the event. It has a meaning only while a request is open: stop links are deleted when the change was confirmed, cancelled or expired, and a link is refused without ending a session when no unexpired request exists (review phase 4, H1). Open requests and all confirmation and stop links are deleted when the password is reset or changed, when the status becomes anything but active and when the second factor is reset (final review, M-A). **Residual risk, not covered:** an attacker with password and session who confirms the new address in their own mailbox at once leaves no window to stop it; the owner only gets the notice "changed" and contacts the operator (open question for the project owner, D-059: a short undo window).
* **Notifications** of changes of email address, password and two-factor go to **every address of the account** (for an address change also the old one), also when a system administrator changes another account's password or address. Except for the stop link they contain no link that could undo or confirm anything and tell the person (default text, editable, D-039) to contact the operator immediately if they did not request it; no reply is invited (noreply sender). After such a report the procedure of the installation guide applies: block the account, verify the identity, restore address or password, log the incident.
* **Sessions, cookies, CSRF** (OWASP Session Management Cheat Sheet):
  * The session ID is renewed at login, after the second factor and after password and privilege changes. All other sessions of an account end after a password change or reset, email change, second-factor reset, blocking, deactivation and removal of rights.
  * **Session end (D-041, D-100).** The session ends at the idle timeout (server-side; users 30 minutes, staff and system administrators 15 minutes; every request except a background poll extends it) or at logout. No absolute limit for an ordinary session (owner decision 2026-10-17; OWASP recommends one). A session without a stored start time ends (fails closed). A background poll (import status, live log) neither extends the idle timeout nor survives it (401). **Residual risk:** a stolen session cookie stays usable while it is used within the idle timeout. Mitigations: HttpOnly/Secure/host-only cookies, session ID renewal, the idle timeout, the shorter staff timeout, end of all sessions on password change, rights removal and blocking, "End all sessions" for system administrators (D-100).
  * **Stay signed in (D-056, D-100).** Off by default; for everyone including staff and system administrators (owner 2026-10-17). Ticked: a session of 14 days (`STAY_SIGNED_IN_DURATION`) with a fixed absolute end; activity does not extend it. The second factor is asked once, at login. The persistent session exists only after the code was accepted; the wish waits only in the pending login. A privileged account without a second factor gets none. A removed right or second factor ends all sessions of the account. Sensitive actions still ask for one proof (D-062). Logout ends the persistent session. **Residual risk (owner-accepted):** a stolen 14-day session of a privileged account has its privileges for up to 14 days without a new code. **Mitigations (D-100):** security event `persistent_session_started` (long retention) and an email to every address of the account for each such session; "End all sessions" (event `account_sessions_ended_by_admin`) for system administrators; password reset and rights change end sessions. **No step-up code** before IBAN, PDF lists or any other action (owner, D-102): whoever is signed in is authenticated; an unattended device is the operator's responsibility.
  * **Proof of identity for the portal settings (D-100, D-062; replaces the five-minute rule of D-055/D-073).** Saving asks for one proof: the app code (staff always have one), else the password. Wrong entries count per session and per account (five end the session). The upload is validated, and its rejection logged, before the code is checked (a code works once); a password proof is checked first. `RECENT_AUTHENTICATION_WINDOW` (five minutes) stays only for setting up the second factor (D-055).
  * Session and CSRF cookies are `Secure` in stage and production and `HttpOnly` where possible; `SESSION_COOKIE_DOMAIN` and `CSRF_COOKIE_DOMAIN` are not set (host-only, D-025); `CSRF_TRUSTED_ORIGINS` never contains the instance's website or a wildcard for its parent domain. In stage and production the cookie names use the `__Host-` prefix (accepted only if `Secure`, `Path=/`, no `Domain`), so a cookie set by the website for the parent domain (cookie tossing) cannot replace the application's cookies (D-025; draft-ietf-httpbis-rfc6265bis).
  * After login a redirect target (`next`) is followed only on the application's own host.
* Security settings are secure by default and relaxed only for `APP_ENV=local`. A missing or unknown `APP_ENV` prevents the start. `DEBUG` can only be enabled with `APP_ENV=local`.
* **The initial system administrator** must change the initial password and set up two-factor at the first login (D-005, D-041). Its email address is entered by the operator on the server and counts as verified. The setup command treats any account with `is_superuser`, also blocked and deactivated ones, as an existing administrator. Until the password is changed the session can only change it (to a different one) and log out; then the factor must be set up before anything else.
* Introduce AGOV and passkeys only after their integration and security requirements have been reviewed. Account linking must reliably confirm the identity.

## 4. Authorization

* Permissions are checked on the server on every request. Hidden menus or buttons are no access control. Direct URLs, manipulated IDs, API endpoints and exports are covered by tests.
* New users are authenticated users without groups, permissions, `is_staff` or `is_superuser`; they read and edit only their own profile. Checks use permissions, never role (group) names; roles are runtime data (D-012).
* Only system administrators create and change roles and their permissions, assign roles, grant or remove direct permissions and grant or remove `is_staff` and `is_superuser`; enforced technically, also against staff who may add or change users ("If you give a non-superuser the ability to edit users, this is ultimately the same as giving them superuser status because they will be able to elevate permissions of users including themselves!", Django documentation, "Using the Django authentication system"). Delegating role assignment to other roles needs a separate reviewed decision.
* Staff can never change, block, deactivate or delete accounts of staff or system administrators (including their own in the admin) and never change the password, email address or second factor of another account. Changes by an administrator to another account's password or email address are logged and notified.
* **Customer data changed by staff (D-087, approved deviation from "the customer changes the data"; D-012 stays for everything else).** Every staff account may change the **profile data** of a customer account for support: salutation, company, names, second person, phone, billing address, IBAN, paper invoice, and the second email address through the flow of D-059 (the link goes to the new address only; the addresses valid now get the notice with the stop link; nothing changes before the confirmation). **Never** by this path: the login email address (without the owner's proof that is the takeover D-012 rules out, D-087 item 10), password, second factor, status, `is_staff`, `is_superuser`, groups, permissions, retention flag and customer number. The data of a **staff user or administrator (also one's own) is changed only by a system administrator; that of a deactivated account by nobody** (`persons.may_change_customer_data`; the service reads the actor from the database again; dialogs answer 403). The write goes through the account model (`save(update_fields=...)`, guards of D-034 compare controlled fields with the locked row), validates with the model's rules, writes the history entry and the security event `account_data_changed_by_staff` with **field names only**, and sends **no email to the customer** (owner decision). The same actor rule applies to accepting the address suggestion of a person (review M-1); a staff-initiated request or removal of the second address writes the event with the field `secondary_email`; the owner's confirmation is logged as "requested by staff account N". `User.invited_at` is controlled (no save, bulk update or plain creation can write it).
* The customer number, the retention flag (set only by application functions, never unset) and the normalised email column cannot be changed in the admin by anyone including system administrators; the first two are read-only there, the third is not shown (D-035).
* Every path that deletes, deactivates, reactivates, blocks, unblocks, promotes or demotes accounts, changes the email address or normalised column or the retention flag (objects, admin bulk actions, `list_editable`, `QuerySet.update()`/`delete()`, management commands) goes through the central account logic. "Delete selected objects" uses `QuerySet.delete()` and bypasses the model's `delete()`; it is disabled for the user model or replaced (Django documentation, "Admin actions").
* Promotion beyond the authenticated user needs an explicit action by an authorized superior; nobody promotes their own account; `is_superuser` is granted only by another system administrator; every promotion is logged. `is_staff` and `is_superuser` are granted only to accounts with a confirmed authenticator app (not an unconfirmed app or recovery codes); the administration refuses otherwise, rechecked on the locked row at save (D-042); the only exception is the initial administrator (D-005). The rule proves only that a confirmed app exists, so the administrator confirms with the person that they set it up themselves. Removing rights is always possible.
* System administrators can block other administrators and remove their rights. At least one active, not blocked administrator always remains; emergency access is restored only via the server command. Keep their number minimal; they bypass all permission checks and their actions are logged. Superuser status is no general role model.
* **Management area (`/management/`; D-077 to D-086).** Every page checks on the server, on every request, in `leg_platform/management/access.py`: logged in (else login), active and `is_staff` (else 404), second factor completed (else redirect to setup). **Since D-086 (owner decision 2026-10-17, approved deviation from D-012) there is no per-area permission: every active staff account may use every page**, and nothing in the area is shown or hidden by a Django permission. **Accepted risk:** every staff account can see and change all customer data in the area. Mitigations: mandatory second factor for staff (D-040, D-042), checked once per login; a "Stay signed in" session needs no new code (owner-accepted, section 3, D-100); each persistent staff session is logged and announced by email; system administrators can "End all sessions" of an account (D-100); only administrators create and change staff accounts and rights; every change is in the history with actor and time; the security log records printing and the retention flag; customers and normal users get 404. The community models have no Django permissions; the Django administration keeps its permission model; the grid operator model is maintained by administrators only. No response under `/management/` is cached (`NoStoreForManagementMiddleware`, also 403, 404 and CSRF pages).
  * Rules for every management function: ids and states are rechecked on the server under a row lock (no step twice or out of order); the person search is bounded (10 results, at most five words of 100 characters), finds only active accounts with a customer number and never shows the email address; list state is parsed again from the address on the server, selected ids are matched against that list's entries, an unknown print scope or more than 2000 ids is a 400; bounds: 1000 entries, 100 detail pages, 20000 printout rows; a LEG can be deleted only if no metering point was ever assigned (rechecked under a lock) and never when archived, and restore is the only action on an archived LEG or location, also by direct POST; assigning a person whose assignment is in force sets the retention obligation of the account and writes a security log entry (account and actor numbers only), and an account with any assignment is deactivated, never deleted; history names event, actor and time, never the text of a remark, note or IBAN. IBAN, note and customer number at the grid operator appear only on the person's detail page and are never searched, logged or written to history or security events. A staff change of an account's address writes only street, house number, town and Swiss postal code with the profile's `update_fields`; the directory suggestion is asked again under the row lock and must be the one shown (a digest travels with the buttons).
  * **Forms of the management area (D-097, D-098):** a value the page gives to a form (location at a location; number, direction, LEG of a point being changed) is a disabled field: Django ignores the posted value and uses the page's object. Drop-down choices (point to assign, circuit) are built from the database per request, so a posted id that is not offered (archived, already there, unknown, forged) is refused. Services check again under row locks in one order (location, then point; LEG, then point), refuse archived objects and write ids and field names only to the history. A circuit created in the same form is created in the same transaction. The redirect after a create uses only a safe return address (`returns.after_create`, `with_parameter`: paths of this site); `origin_point_url` is built from view name and number. Page scripts only help (no `innerHTML`, no dynamic code, answers as text). Suggestion endpoints are GET only, staff only, at most ten texts for at least two characters, never an email address. The person search is counted per staff account (300 per minute, then 429 with `Retry-After`), cut to 100 characters and five words; the scripts wait after a 429. A `DoesNotExist` of a service is the normal refusal (`management.access.gone`, D-101).
  * **PDF printing:** no typed text reaches ReportLab as markup (escape, remove control characters, cut the length); the PDF is made in memory and sent with `Cache-Control: no-store, private`, `Content-Disposition: attachment` and a fixed file name; a failure logs only the kind of error; the bundled font is read only from the package directory.
* `ALLOWED_HOSTS` lists only the application's host names (not the instance's website; D-025). Never read the `Host` header from `request.META` (use `request.get_host()`). Links in emails come from the canonical base URL of the instance configuration, never from the request.

## 5. Data Protection

* Collect only necessary data. The purpose of each profile field is documented (`docs/PROJECT.md`, "Profile Data and Purpose"); the phone number is optional. Persons are informed through the instance's privacy notice, linked at registration and on all pages accessible without login (DSG Art. 19; D-022).
* Account deletion removes all data of the account unless a retention obligation is set; then the account is deactivated (D-016). The retention flag can never be unset. Security log entries are kept without personal reference until they expire (D-018).
* **The IBAN of a person is stored encrypted (D-087):** a Fernet token (`PersonRecord.iban_encrypted`) under a key derived from `SECRET_KEY` by HKDF with the label `LEG-Platform person IBAN v1` (section 7); only the checksum-validated normal form is encrypted (`python-stdnum`, any country). It is **not searchable and not sortable**, appears only on the person's detail page, the card dialog and the PDF of the details, and **never** in a list, search, history, security log, log line or error message. The account number is part of the encrypted text (`v2|<account>|<IBAN>`, L-7): a text copied to another person's record is refused and shown empty. An IBAN that cannot be decrypted is shown empty and **an empty submission leaves it as it is** (M-2). The log line of printing says "with IBAN" (L-9). Note, customer number at the grid operator and address are plain columns, likewise never in history or logs.
* Do not write personal data to logs unnecessarily. Backups are the operator's responsibility; deleted data can remain in backups until they expire. Error pages disclose no secrets, stack traces or internal configuration. Development and test environments use no real production personal data.
* Assess legal data protection and retention requirements only against official sources (e.g. fedlex.admin.ch); legally unclear points are clarified with the project owner, not assumed.

## 6. Web Security

Consider at least CSRF, XSS, SQL injection, insecure direct object references, session and cookie security, rate limiting, secure error handling and protection against accidental disclosure of files and configuration. Django's security features must not be disabled without a documented, reviewed justification.

* **Headers:** HSTS in stage and production, CSP, `X-Content-Type-Options`, `Referrer-Policy: same-origin` or stricter, protection against framing.
* **CSP (D-028):** no inline scripts or styles that would need `'unsafe-inline'`; set with Django's `ContentSecurityPolicyMiddleware` and `SECURE_CSP` (at least `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`), never relaxed globally.
* **Token URLs (D-067):** pages whose URL carries a token (verification, reset, other emailed links) never render under it: the link only remembers the digest of a valid token in the session and redirects to a URL without the token; an invalid, expired, used or replaced link and a confirmation page without valid state redirect (302, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`) to a fixed page of the flow. Status, headers and body are identical for every cause and contain neither token nor account information. **Limit (review unit A, L-6):** the response time is not equalised and was not measured; tokens are looked up by a keyed digest, so no token prefix is compared in application code, and the length (43 characters, 256 bits) is public. The 429 lockout page is `no-store`.
* Static assets (Tabler, fonts, icons) are served by the instance in fixed versions, not from third-party CDNs. The application runs on its own host name, never under a path of another website (D-025); on a subdomain of the website's registrable domain it is still the same site, so the cookie rules of section 3 apply and the installation guide states the residual risk.
* Colour mode and language live only in the tab's `sessionStorage` (no cookie, nothing sent to the server); the scripts are external files, accept only allowlisted values (`light`, `dark`; `de`, `fr`, `it`, `en`) and evaluate no URL parameters (`docs/DESIGN.md`, section 7; D-056).
* **Branding values are validated:** colours match `^#[0-9A-Fa-f]{6}$`; configured URLs (privacy notice, legal notice, website) are absolute `https://` URLs without credentials, white space, control, format or line/paragraph separator characters, otherwise no link; environment logo references point to a file inside the instance's static files with an allowlisted extension (no absolute paths, traversal or external URLs). Validated at startup, when saved and again when read from the database (`docs/DESIGN.md`, section 3.2; D-073).
* **Logos (D-073):** static files provided by the operator (fallback) or uploads by an administrator with the right to change the portal settings; embedded as `<img>`, never inlined. Static SVG logos are checked for scripts and external references before deployment and served with a restrictive CSP (`docs/DESIGN.md`, section 10).
* **Uploads (D-073):** the only web uploads are the two Microsoft Graph files (D-048) and the two logo files of the portal settings. For logos: the right to change the portal settings is needed (a role gets it at runtime, never by default); the type is decided from the content, never from the name or content type; the file name is never stored or used; a rejected file is never rewritten. PNG (at most 1 MB, 64 to 4000 pixels per side, at most 4 million pixels) only if chunks, CRC-32, ancillary chunks (only `tRNS`, `gAMA`, `cHRM`, `sRGB`, `pHYs`, `bKGD`, once each, before the data), the data stream (exactly the header's size, inflated in steps of at most 1 MiB) and the end are valid. SVG (200 KB, at most 20 levels and 2000 elements) only through a strict allow-list: UTF-8, no DOCTYPE, ENTITY, CDATA or processing instruction (checked on the bytes before any parser), SVG namespace only, fixed lists of elements, attributes and value characters, `url()` only to an id of the same file, no script, style, image, foreignObject, link, use, animation or filter. Details: `leg_platform/accounts/logo_images.py` and its tests. The file is stored in the database with type and SHA-256 digest and served only by the view `instance_logo` for the two fixed variants with a fixed content type, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox; default-src 'none'`, `Cross-Origin-Resource-Policy: same-origin` and an ETag; the view reads no session (no `Set-Cookie`, no `Vary: Cookie`); `Cache-Control` is `max-age` (content hash in the address) or `no-cache`, never `public`; `MEDIA_URL` serves nothing. Every request below `/admin/accounts/portalsettings` is limited to 3 MiB before the form is read, by path prefix (the admin routes the object id as `<path:object_id>`, so `01`, `+1`, `%201`, `_31`, `add`, `history` reach the same admin). Saving needs one proof of identity (code of the authenticator app, else the password; D-100, replacing the former "login within the last five minutes" rule). A rejected upload is a security event with a reason code only (`portal_upload_rejected`); a change is a long-kept event with a line per field (never file content). The risk of the right (it changes what every visitor sees, like the email texts, D-039) is accepted and limited by the audit trail and by no role having it by default. **Open:** the rendering of an SVG with style attributes under the sandbox policy and the effect of CSSOM changes under `style-src 'self'` were not checked in a browser.

* **Address directory import in the web process (D-090):** the web application downloads the official address file in a background thread of one web worker (no extra service). The thread connects only to the two fixed HTTPS addresses of `data.geo.admin.ch` (host allowlist, no redirect, no proxy or `.netrc`), verifies the official SHA-256 before parsing, keeps size, time and row limits, and is the only code of the web process that may write the SQLite file (`storage.mark_thread_writer`; request threads stay read-only). Start: the administrator's button (right `addresses.request_directory_import`, CSRF, 5 per minute per IP, security event) or the automatic refresh (every 90 days, every 24 hours while there is no directory) triggered by an authenticated staff request to the administration start page or the management overview, at most one check per five minutes per process. One import at a time over all workers (the job row is the claim); a dead one is found by its stale heartbeat. The status endpoint (`admin/addresses/importrequest/status/`) needs a session and the same right, GET only, JSON, `no-store`; failures show only the fixed sentences of the importer (`jobs.SAFE_FAILURES`). **Residual risk:** a compromised web process can already write the file (D-075) and can now also start the download (fixed addresses only); a long import uses CPU and memory of one worker (a recycle or restart ends it; the directory in use stays).
* **Admin tables (D-091):** plain read-only tables of the management data follow Django model permissions (`view` only, handed out by a system administrator to a role); nobody can add, change or delete; free text of staff, IBAN, emails and names never appear as column or field.

Sources: Django 6.0 docs (`SECURE_REFERRER_POLICY`, CSRF "Limitations", CSP reference and howto), W3C CSP3, draft-ietf-httpbis-rfc6265bis, W3C SVG integration.

## 7. Secrets

* No secrets in Git, source code, documentation, logs or error messages. Local secrets in ignored files or environment variables; server secrets via protected environment variables or a suitable secret store. Never display secrets in plain text again. Separate credentials for local, stage and production and per instance (stage has its own database and secrets, D-070). No production or stage secrets on development machines. The read deny rules in `.claude/settings.json` additionally keep AI tools away from secret files; they do not apply to scripts that open files themselves and are not a complete protection (D-020).
* **Encryption of stored secrets (D-006, D-040):** the Microsoft Graph private key (written in the admin, never displayed again), the TOTP key and the IBANs (D-087) are encrypted with Fernet under a key derived from `SECRET_KEY` by HKDF with an own purpose-specific label (established `cryptography` library, no custom primitives). Keys from `SECRET_KEY_FALLBACKS` are tried for decryption and the secret is then encrypted again with the current key. Recovery codes are stored only as keyed digests, also checked against the digests of the fallback keys.
* **IBANs after a `SECRET_KEY` rotation:** run `manage.py reencrypt_ibans` on the server before the old key leaves `SECRET_KEY_FALLBACKS`; it prints numbers only and **fails with an error code if any IBAN could not be decrypted** (L-6). If the old key is removed first, those IBANs cannot be read any more (pages show none, the log names the account number, staff enter it again). Backups hold the encrypted values, so a restore needs the same `SECRET_KEY` (or the fallback). **Old plain values remain in backups made before migration `community/0005_encrypted_iban`, in the binary log and in freed database pages until overwritten** (`docs/DEPLOYMENT.md`, section 12.3, step 6; L-5).
* In case of accidental disclosure, revoke or rotate the affected secrets. If `SECRET_KEY` is changed without keeping the old key in `SECRET_KEY_FALLBACKS`, the Microsoft Graph certificate and private key must be uploaded again.
* **One database account for everything in MariaDB (D-075, approved deviation from D-033, D-049, D-052; risk assessment there).** The address directory is public data without reference to a profile, kept in its own SQLite file (mode 0600 for the service user, not part of any backup). Every process opens it read-only (`PRAGMA query_only`) unless it declares itself a writer (worker, operator commands, `migrate`; never the web processes). **This protects against a mistake in the code only, not against a compromised web process** (web process and worker run as the same service user): the worst effect is wrong address suggestions, never access to an account. Download and import run only in the worker (`process_address_imports`); no import credential exists. A manual import request is logged with the account number only; an import is refused below 4 GB of free disk space (directory disk and temporary-download disk; D-076).
* **Initial system administrator password:** entered interactively (`setup_initial_administrator`) and stored nowhere, or (D-076, owner requirement, deviation from D-005 and D-041) taken from `BOOTSTRAP_SYSTEM_ADMIN_PASSWORD` of the first start, a secret in the protected environment file (mode 0600, root), masked on debug pages and in error reports, never printed or logged. **It has no expiry: it stays valid as long as nobody has logged in.** Whoever knows it and reaches the login page before the real owner can log in, choose their own password, enrol their own second factor and lock the owner out. The runbook therefore requires that the instance is not publicly reachable until the owner has logged in, changed the password and enrolled the second factor; a take-over shows as the owner's failed first login and a `PASSWORD_CHANGED` entry nobody on the owner's side caused (`docs/DEPLOYMENT.md`, section 9). The variable is ignored once a system administrator exists, and the account is created only while the account table is completely empty (a restored backup or old environment file can never create a privileged account later). The operator removes the variable after the first login and restarts the services. A time limit for the initial password is **not implemented** (possible hardening, owner's decision, D-076).

## 8. Microsoft Graph

* Only the required permissions. The application permission `Mail.Send` by default allows sending as any user of the organisation, so the application must be restricted to the sender mailbox with "RBAC for Applications" in Exchange Online and no organisation-wide `Mail.Send` may remain in Microsoft Entra ID (https://learn.microsoft.com/en-us/exchange/permissions-exo/application-rbac). The installation guide explains this for operators without in-depth IT knowledge.
* Authentication uses a certificate, not a client secret (D-006). The private key is write-only in the admin and stored encrypted; only the public certificate and its expiry are displayed; the admin warns before expiry. The configuration is accessible only to system administrators; every change is logged. The test send never displays secrets. Email logs contain no tokens, passwords or complete security links.
* **Delivery by environment (D-070, approved deviation from the stage allow-list of D-006 and D-028; risks and mitigations there):** locally, console output (default) or Microsoft Graph restricted to allowed recipients; stage and production allow only unrestricted Graph delivery, so security links never reach console or server logs and stage does not differ from production. A stage instance is production-grade: same security configuration, separate database and secrets, no copy of production data, no real personal data of third parties without need; a mistyped test address receives real email.
* Local Graph delivery uses a dedicated development app registration and sender mailbox, separate from stage and production (section 7; D-020). Allowed local recipients live only in `EMAIL_ALLOWED_RECIPIENTS` on the developer machine, never in the repository; `allowlist` without recipients refuses to start; each entry is one complete address; debug pages and error reports mask them. A non-empty `EMAIL_ALLOWED_RECIPIENTS` is refused in stage and production (D-070).
* Automated tests never send real email (in-memory backend) and use only reserved domains (RFC 2606: `example.com`, `example.net`, `example.org`, `.test`, `.invalid`). Automatic emails do not invite a reply (noreply sender by default); a mailbox that receives replies anyway can contain personal data.

## 9. Database and Operations

* Database access with the minimum required privileges; no publicly accessible database administration; encrypted transport in stage and production.
* Keep migrations traceable and reviewable. Test backups and restore before going into production.
* Regularly check security updates and dependencies; only versions that still receive vendor security updates are declared as minimum versions (D-015). Check the production configuration with the Django checks (`check --deploy`).

## 10. Security Logging

* Logged events include at least: failed logins and lockouts, password changes and resets, email changes, setup, removal and reset of two-factor, use of recovery codes, role, permission, `is_staff` and `is_superuser` changes, blocking, unblocking, deletion, deactivation and reactivation of accounts, setting of the retention obligation, use of emergency commands, creation and invitation of a person by staff, resend of an invitation, every change of customer data by staff (D-087: actor and account number; field names, never a value), changes of the grid operator of the instance (D-087, L-8: actor only), changes to the Graph configuration and the portal settings (name, website, privacy and legal notice addresses, colours, logos; one entry per changed field: old and new name, host names of old and new address, colours, for a logo type, size and start of its SHA-256 digest, never content; D-056, D-073), and rejected portal-settings uploads (reason code only), the outcome of every address directory import (completed or failed with the fixed reason, D-090) and every opening of a log page and every log download (D-099).
* Logs never contain passwords, tokens, secrets or complete security links, and only as much personal data as necessary (basis: OWASP Logging Cheat Sheet). The logging filter (`log_filters.TokenRedactionFilter`) removes tokens of links, email addresses, IBANs and the values that MariaDB names in duplicate-entry and invalid-value errors from every message and exception text before it is written. **What can remain (D-099):** a path with an internal id or a customer number, internal account numbers (by design), the class and text of an exception that carries no database value, host names of the configured server and of the official address source; a free-text field of an exception message of a third-party package that the patterns do not know. The log pages apply the same redaction again when a line is shown or downloaded.
* **Log files and log page (D-099).** With `LOG_DIRECTORY` the portal also writes `application.log` and `security.log` (10 MB and 5 older files each, mode 0600 in a 0700 folder). **System administrators only** (`is_superuser`, like the security log; no right gives it to staff). The administration lists the files, shows one live (polls `logs/<log>/tail/` every 2 seconds; at most 128 KiB for the first answer, 64 KiB for later ones; pause and follow) and streams a download (redacted line by line). The client names only a fixed key and a backup number 0 to 5; the file name is built on the server; no symbolic link is followed (`O_NOFOLLOW`, check on the descriptor). Opening a list or viewer and every download is a security event (`log_viewed`, `log_downloaded`, long retention, actor only; the same page again within 300 seconds in one session is not a new event); polls are not events. Responses are `no-store`; the poll does not extend the idle timeout. Log lines escape CR, LF and other control characters, so a request path cannot forge a line; redaction works across read chunks (512-character overlap). Residual risk: a system administrator can read everything the logs contain, including what the filter does not know.
* Only system administrators can view security logs. The security log is append-only within the application: nobody, including administrators, can create, change or delete entries; entries are deleted only by the automatic retention. The same holds for the failed-attempt and lockout records of the abuse protection package. The log files are not the security log: they are operating logs that rotate and are not evidence.
* Log entries of deleted accounts are kept without personal reference, with an internal number, never the customer number (it appears on invoices). Admin log entries of accounts store only a neutral text with the internal number; after deletion the mapping is intentionally lost unless another kept record maps the number to a person (D-036). The admin history of accounts (it shows the acting account's address) is visible to administrators only.
* **Retention (D-018)** is set per instance in the server configuration (`SECURITY_LOG_RETENTION_DAYS`, `SECURITY_LOG_LONG_RETENTION_DAYS`; a value below the minimum prevents the start), not in the admin. Default: 1 year for changes of roles, permissions, `is_staff`, `is_superuser`, resets of the second factor of staff and administrators, blocking and unblocking of staff and administrators, changes by administrators to another account's password or address, deletion, deactivation and reactivation by administrators, emergency commands, customer data changes by staff (D-087) and changes to the Graph configuration and portal settings; 30 days for all other entries including failed-attempt records. Expired entries are deleted automatically.

## 11. Tests

Security-critical functions require positive and negative tests. This list is the only list of security-relevant acceptance criteria; `docs/ACCEPTANCE.md` refers to it and does not repeat it. Every rule of sections 3 to 10 needs a test; the tests prove at least the following cross-cutting points. Tests create the groups and permissions they need themselves and do not rely on predefined roles.

* **Accounts and login:** no login without verified email and password; blocked and deactivated accounts cannot log in or reset and no response reveals them; login is case- and whitespace-insensitive, resolves the one non-deactivated account, rejects the customer number, and a nonexistent address behaves like a wrong password; registration reads only the documented fields, creates accounts without rights, activates only at the last step, and used, expired or replaced links lead to "Link nicht mehr gültig"; customer numbers are assigned only at completion, unique and never reused; email addresses are unique among non-deactivated accounts, also under concurrency and case variants.
* **Sessions and cookies:** other sessions end on password change or reset, email change, second-factor reset, blocking, deactivation and removal of rights; the session ID is renewed at login, after the second factor and after password and privilege changes; idle timeouts (shorter for staff), activity extending them, no forced end of an active ordinary session, polls that neither extend nor survive the idle timeout (D-100); stay-signed-in rules for everyone incl. staff and the exclusion of a privileged account without a second factor (D-056, D-100); one proof for the portal settings (D-100); cookies `Secure`, without `Domain`, `__Host-` in stage and production; `CSRF_TRUSTED_ORIGINS` without website or wildcard; an external `next` is ignored.
* **Abuse protection and mail forms:** throttling per account and IP, expiring lockouts, reset during lockout ending only that account's lockout (an attacker's IP stays locked); client IP only from a configured trusted proxy; budget of wrong codes (notice, pause also for a correct code, reset ends pause, refused attempts and wrong passwords do not count, parallel wrong codes cannot exceed the limit); limits of registration, reset and email change per IP and normalised address without changing response or time; HTTP 429 without job, bucket or session over client and instance limits; bot-check and pause behaviour; earlier links keep working above the address limit.
* **Links and email change:** links are time-limited, single-use and never render under the token URL; email change needs re-authentication, is not performed for an address of an active, temporarily locked or blocked account (same response, rechecked at confirmation), only the latest pending change can be confirmed; notifications about completed changes contain no link, about a requested change the stop link only; the stop link, second address and profile cards behave as in section 3 (login and CSRF for every card action, uniform answers, no login or reset by the second address, dead stop links, `no-store`).
* **Two-factor:** staff and administrators can use no function without a completed second factor and rights cannot be granted without one (also not between form check and save); re-authentication asks for exactly one proof (code field without password field and the reverse; a recovery code or a malformed code is refused and never counted or used up; the code is never written back); wrong entries in confirmations count only per session and account (5 and 15, no effect on Axes, the IP counter or the login budget, not client-manipulable, parallel requests cannot exceed the caps); "phone lost" works only with password and recovery code, is one transaction and is refused for staff; recovery codes are single-use; resets only by administrators and never for their own account; for users nothing changes before the owner confirms; a password reset does not remove the factor.
* **Initial administrator (D-005, D-076):** the commands refuse while any administrator exists (also blocked or deactivated), print no secret and log; `setup_initial_administrator` reads the password only interactively, `setup_instance` only from `BOOTSTRAP_SYSTEM_ADMIN_PASSWORD` and only while none exists; no setup function on the website; the first login can only change the password and log out, then only set up the second factor; the frame after login (D-057) leads such accounts to nothing else and writes nothing.
* **Authorization:** user A cannot read or modify user B's profile; no self-promotion, no grant of groups or rights without permission, `is_superuser` only by another administrator; authorization survives renaming a group; a staff user who may add or change users cannot change `is_staff`, `is_superuser`, groups, permissions or accounts of staff and administrators (also their own), nor another account's password, email or second factor; customer number, retention flag and normalised email column are unchangeable in the admin; every management URL is tested for anonymous, non-staff, staff without second factor and staff; invitation and staff data changes (D-087) as in sections 3 and 4 (forged ids 404, CSRF, `next` never leaves the site, field names but no values in history and security log, IBAN never in logs); portal settings permissions (no right: 403 for page, post, preview and history; anonymous refused; add, delete and history never for staff), the logo validation matrix and serving headers.
* **Account lifecycle:** deletion needs re-authentication; without retention obligation all data is removed, with one the account is deactivated, shown as "Deleted (retention obligation)", the flag cannot be unset and the person sees the same page and message (D-055); a deactivated account is not reactivated by the user or by an administrator while an active, temporarily locked or blocked account with the same address exists; the last active, not blocked administrator can neither be deleted, deactivated, blocked nor lose superuser status; bulk actions respect the retention obligation and the last-administrator rule.
* **Email and Graph:** Graph configuration only for administrators, every change logged, private key never displayed and decryptable with a fallback key (otherwise the admin asks for a new upload); delivery modes refused in stage and production as in section 8, including a non-empty `EMAIL_ALLOWED_RECIPIENTS` (message names variable and `APP_ENV`, no address); tests send no real email; links use the canonical base URL; a `Host` header not in `ALLOWED_HOSTS` is rejected.
* **Logging and configuration:** security events are logged without secrets; the security log is append-only and deletes only by retention (minimums enforced); a missing or unknown `APP_ENV` prevents the start and `DEBUG` needs `APP_ENV=local`; error pages show no stack traces; secure headers are set (`Referrer-Policy` `same-origin` or stricter); static assets come from the instance; no template inlines an SVG logo; the colour-mode and language scripts ignore URL parameters; branding values are validated at startup, on save and on read; the Django security checks (including the deployment checks) run; no secrets in the repository.

## 12. Handling Insecure Requests

If a requirement would significantly weaken security, the AI must not implement it silently. It explains the risk, proposes a secure alternative and asks in case of significant conflicting goals. Deviations must be documented traceably; documentation alone does not make an insecure solution acceptable.

## 13. No Unsubstantiated Security Claims

The AI must distinguish between: implemented, automatically tested, manually checked, still open, not verified. Every security statement names the verification step or official source it is based on; anything not substantiated is considered not verified.

A passing test suite does not prove that the application is completely secure. Critical risks must be reported accordingly.

The subagents defined in `.claude/agents/` do not guarantee an independent security review (D-019). Critical changes additionally require a human review.
