# Security Policy – Security Keeper

## 1. Binding Principle

* Security by design and by default apply to all architecture, development, configuration and operations decisions.
* The AI is the Security Keeper: it finds risks, explains them and proposes secure alternatives. Security is never silently weakened for convenience or speed.
* Municipalities without in-depth IT knowledge must be able to operate the software securely: secure defaults, few manual security steps, clear instructions.

## 2. Security Decisions

* For a security-relevant change: (1) identify protection needs and attacks; (2) determine measures; (3) prefer an established, maintained solution over a custom one; (4) add automated tests; (5) document the checks actually performed; (6) name remaining risks. Ask before implementing when significantly uncertain.
* No assumptions. Verify measures, configurations and threat statements against official sources: vendor security documentation (Django, Microsoft), standards (OWASP), government requirements. Blogs, forums, news and tabloid content are no basis (`AGENTS.md`, section 3).

## 3. Authentication

* Use Django's password functions. No custom hashing: Django's default hasher with the default work factor of the installed version, never below the OWASP recommendation (D-023).
* Login only with the email address (D-021). The customer number is no login identifier.
  * Lookup only through the normalised unique column of accounts that are not deactivated, so exactly one account is found.
  * The normalisation (at least trimming and lower case) is defined in one place. Storage, every lookup and every per-address counter use it.
  * A nonexistent address gets the same response and lockout behaviour as a wrong password. Django's protection against timing differences for nonexistent users (`ModelBackend`) is kept.
* Password rules (Django validators, D-004): minimum length 15 for all accounts (OWASP: 15 without MFA, 8 with; two-factor is optional and removable), at least 64 characters accepted, all characters allowed, no composition rules.
* Login needs a verified email address and a set sign-in method: a password, a password with an authenticator app, or a passkey (D-106). Blocked and deactivated accounts cannot log in.
* **Registration (three steps, D-055, D-058).**
  * Step 1 takes only the email address.
  * Step 2 (pages reached through the link) chooses and sets up the sign-in method: password, password and app, or passkey. The account is unverified and cannot sign in, so everything set up is **staged** and bound to the digest of the link (`registration_methods`): a password only as a hash in the session; an authenticator device unconfirmed until the first code is confirmed (recovery codes are made and shown only at activation); a passkey as an inactive credential bound to the session (`passkeys.begin(registering=True)`, same ceremony rules as everywhere). Staged data signs nobody in, sends no mail and writes no log entry. A new choice deletes what an earlier one staged; the last step keeps only the chosen method.
  * The **last step** (name, address, consent) alone activates the account. It writes status, customer number and password (or, for a passkey, switches the staged keys on and sets no password) in one transaction under the locks of the account and of the link; it refuses a method whose setup is not complete. Consent is stored with its time and the privacy notice address shown.
  * Later steps ignore every field except their own.
  * New accounts have no rights: no `is_staff`, `is_superuser`, groups or permissions. Retention flag, status and customer number are server-assigned.
  * The link stays valid until the last step is done (scanners, back button). Opening it rotates the session key. Registration session keys are removed after completion and when the link is invalid.
  * A used, replaced or expired link cannot log anyone in. Completing logs the person in once: session ID renewed, no rights, no failed attempt recorded.
  * Resend: only after a server-enforced pause of 60 seconds; the request cannot choose the address (the page names the address from the browser's own session, never the URL); the limits below apply.
  * Unverified accounts and their data are deleted when the link expires. A new registration with the address of an unverified account replaces the pending one.
  * Registration and email change respond in comparable time whether or not the address is in use (asynchronous mail).
* **Invitation by staff (D-087).**
  * Staff create a person and invite them. The account is **unverified**, with an unusable password, no customer number, no rights, no groups and the controlled mark `invited_at`. No form or `create_user` accepts that mark. **Staff never set or see a password.**
  * The link is the registration link (purpose `registration`, single use, **7 days**). Only the last step activates the account.
  * A new link (resend, or the person registering the same address) replaces the earlier one. An anonymous registration of an invited address never deletes the invitation.
  * Address and instance limits apply to every invitation; the client-address limit does not (offices create many persons). A limit of 60 per hour per staff account and a pause of 60 seconds per invited account apply.
  * A duplicate address is answered to staff with "already in use" only. Expiry deletes the account.
  * Creation, resend and every change of customer data by staff are in the security log (actor, account number) and the person's history.
* **Two-factor authentication (TOTP app) is mandatory for staff users and system administrators, optional for users (D-004).** Any account may use a passkey instead of a password and an app (D-106); for a staff user or system administrator the passkey is the second factor.
  * `is_staff` and `is_superuser` go only to an account that has already set up two-factor (D-042).
  * An account with these rights but no second factor (the initial administrator, or after a reset) must set it up at its next login before using any function. Such sessions have no privileges.
  * Completion is checked in one central place, independent of the method. A new method must keep at least the current level. No function checks TOTP devices directly.
* Passkey-only accounts have no recovery codes (D-106). Recovery codes are issued at setup, single-use, regenerated after re-authentication (old ones become invalid). A recovery code counts as a second factor at login and in "phone lost". It is no proof in confirmations of the profile (D-062).
* **Budget of wrong codes at the second login step (D-040).**
  * Per account, a window of 24 hours from the first wrong code.
  * At 10 wrong codes the owner is notified by email without a link (once per window).
  * At 15, code entry is paused, also for a correct code, until the window ends or the password is reset (at most 10 counted failures remain).
  * Only wrong codes that reach the check count: not attempts refused by a lockout, not wrong passwords.
  * A successful login does not clear the budget. It applies to the second login step **only**. The pending login between password and code ends when the password changes.
* **Unified recovery (D-106).** Any active staff user or system administrator may start the same recovery for any account, including their own and the last system administrator. It grants no other account or privilege editing and adds no menu (it lives in the user detail settings). Staff without normal view/edit access see only the identity needed for the check and the recovery action. Account querysets and write protections stay unchanged.
  * Eligibility requires an active target, not an existing second factor: password-only accounts and an initial administrator still awaiting factor setup use the same approved procedure. Ordinary password reset remains a separate flow.
  * **Recovery by email without staff.** An ordinary account (no staff user, no system administrator) that has no building, metering point or IBAN entered starts the same recovery itself, whatever its sign-in method: "Forgot your password?" (a password account gets the password link as before; any other account gets this answer) or "App or passkey unavailable?". "Entered" is decided by `community.account_entries`: a building of an application (a draft or pending application counts), a name for a building, a metering point assigned by the LEG, an IBAN; a deleted entry is none. Cooperative shares and the acceptance of the contract do not count. The link is the same one (token purpose `self_recovery`), with the same confirmation and the same restricted session. The rule is checked under the account lock when the link is issued, when it is sent, when it is opened and when it is confirmed, and every writer of an entry in the application code locks the same row (the raw editing of the administration tables by system administrators does not). The check is correct under the isolation level READ COMMITTED of the settings. Every other active account gets the instructions mail; an address without an active account gets nothing; the page is the same for all (differences of timing are accepted, D-067). Accepted residual risk (owner, 2026-10-24): whoever controls the mailbox of an account with nothing entered can replace its sign-in methods; the notice goes to every address of the account.
  * Without a second passkey or usable app/recovery code, and for an account with something entered, a staff user or a system administrator, the person sends an official ID by email to the operator. The acting staff member compares the name with the account and explicitly confirms that check. Public instructions use the existing rate-limited outbox and configured website/operator contact guidance; the portal accepts no ID upload. Residual risk: emailed ID and a matching name do not prove physical identity; accepted by the owner.
  * The single-use link lasts 24 hours, goes to the registered login address and changes nothing on GET. An explicit CSRF-protected POST removes old password, passkeys, app/codes, pending method/address changes and old tokens, ends all previous sessions, logs and notifies all addresses.
  * Recovery tokens carry the normalized current login address in `target_email`. Lookup and locked confirmation reject missing or changed bindings. Issuance and delivery recheck the active account/address under its row lock; a newer issuance replaces earlier links. Confirming a login-address change revokes outstanding recovery tokens under the same account lock.
  * Confirmation grants a restricted setup session only, even for ordinary users. No normal profile, customer or administrative access. The same method-choice component offers users password/app/passkey, administrators app/passkey. Existing idle timeouts and five-minute setup proof apply; after expiry a fresh recovery link is needed. Server emergency access remains available.
* **Passkeys (D-106).** Public credentials only, discoverable credentials and user verification required, canonical RP/origin from configuration, no cross-origin ceremonies, opaque handles checked at sign-in, staged credentials excluded from sign-in, five-minute challenge expiry and single use. Synced keys are allowed; physical device independence cannot be proven.
  * All access levels use the same minimum: one active credential suffices for setup completion, activation, promotion and retention. The model rejects an active passkey account without an active credential; locked removal refuses the last key. An additional passkey on another device is strongly recommended for recovery protection, never required. Loss of the sole key: recovery by email while nothing is entered, otherwise operator-assisted recovery (owner-approved residual risk, D-106).
  * Promotion still requires an authorized system administrator editing another account. The form and locked save recheck an active second factor; staged or foreign keys do not count. No two-device statement/checkbox or legacy flag gates promotion. `PasskeyIdentity.two_devices_confirmed` is unused; no code reads or writes it.
  * Labels are user-chosen, never verified device identities. Adding a key uses fresh current proof and the existing setup grant. Saving it preserves existing keys, ends other sessions, retains the current one and notifies every confirmed address. Removing a key ends all sessions and notifies every address.
  * Registration requires the allowlisted `this_device` / `another_device` mode in `OptionsView` and `passkeys.begin` (D-106). Attachment and hints are constructed on the server; arbitrary client WebAuthn options are not trusted. Cross-platform/HYBRID is no proof of a physical device. No automatic fallback to platform registration; proof, binding, exclusion, staging, CSRF and rate limits apply to both modes.
  * Password return uses a pending hash only. Old passkeys stay active until the new method is complete, including app setup where chosen/required, and a single-use 24-hour email link is confirmed by POST. The atomic switch deletes passkeys, ends all sessions and notifies every address. Password-reset links cannot enter or bypass passkey/recovery mode: a reset request of such an account gets the answer of the recovery request. Passkey accounts have no recovery codes.
  * **A further passkey is activated in the request of its ceremony (D-112).** For an account that already has an active passkey nothing is deleted or replaced, so `SetupView` calls the atomic `passkey_methods.activate` right after the verified registration (other sessions end, every confirmed address is notified, security event). Accepted residual risk: somebody holding a stolen, unlocked session can add a passkey. Mitigations: fresh passkey proof before the setup, notice mail, end of all other sessions, and removing a passkey needs a fresh proof of another passkey. A first passkey and recovery keep the confirmation screen.
  * **The grant of the flow "Change sign-in" (`sign_in_change`).** Step 1 asks for exactly one proof by the order passkey, then number code, then password (a recovery code is no proof); the grant lives in the session only, is bound to the account and to its session authentication hash (another session of the same user has none), lasts five minutes, is used up by the step that acts and is revoked when the first step is opened again. The hand-over to the passkey setup keeps the time of the original proof (the window is not doubled), and the setup grant is checked again on every step. Wrong proofs count toward the session limit of D-062 on every entry point (flow, setup, removal).
  * **Open:** independent review and browser/human-review gates (`docs/ACCEPTANCE.md`, section 3). Tests: `accounts.tests.test_passkeys`, `test_passkey_wizard`, `test_method_changes`, `test_login_methods`, `test_second_factor_reset`, `test_proof_entry_points`.
* **Sign-in method choice (D-106, "Guidance").** The choice is a router into the existing flows and decides nothing the browser says.
  * The posted `method` is validated on the server against `login_methods.available(user)`, the same list that renders the page; a value not offered to this account is refused like a missing choice. Staff users and system administrators are never offered "password only" (D-004), whatever is posted.
  * The choice adds no proof and no bypass: the flows it leads into ask for the password or code, a wrong password sent to the choice URL counts like one sent to the setup (D-062), and the central rules (second-factor completion, password change first, no session for blocked or deactivated accounts) apply to the choice URL.
* **Re-authentication (D-062, "2FA wins")** is required to change the email address or password, delete the account, remove two-factor and generate recovery codes.
  * It asks for **exactly one proof**: a fresh action-bound assertion in passkey mode; otherwise the 6-digit app code if set up (**a recovery code is no proof here**), otherwise the current password (OWASP Authentication Cheat Sheet; NIST SP 800-63B-4). The form shows only the needed field. Unused password/code fields are ignored.
  * An input that is not exactly 6 digits (after removing spaces and hyphens) is refused **before** the check and **counts nowhere**. The code field never writes its value back.
  * The code is checked and used up only after every other field is valid. **Accepted consequence:** the password card consumes the code before the comparison "new equals current".
  * **Wrong entries** (wrong code, or wrong password where the password is the proof) count for the session and the account. They are never failed logins: no effect on Axes, the IP counter or the budget above, so a session holder can neither pause nor lock the login.
  * The 5th wrong entry ends that session (event `session_ended_wrong_codes`, one notice to every address). The 15th within 24 hours over all sessions ends **all** sessions (`all_sessions_ended`, one notice, count restarts, **no pause of the login**).
  * The count is kept on the server under a random session identifier that survives `cycle_key` and is never visible to the browser. A request already running when the sessions end is refused under the lock. A correct proof restarts the session's count. An Axes lockout and an existing pause still refuse the check.
  * **Residual risk:** someone with a session and the password can still guess the code (5 per session, 15 per 24 hours) but cannot get a new session without password and code.
  * The new password of the card "Passwort" may not equal the stored one, compared **only after a valid proof** (`check_password`, no setter; otherwise a guessing oracle without abuse protection). The view compares the session hash under the account lock with the value at the start of the request and refuses the change if the account changed meanwhile (D-040).
  * **"Phone lost" (turn off 2FA with password and a recovery code)** needs both, checked in this order: format and required fields, password (counted like a code, not as failed login), code (used up only if everything before was right).
  * Wrong password, wrong code and another account's code give the same message.
  * State check, both checks and removal are **one transaction under the account row lock**. A refusal gives the code back; of two parallel posts with the same code one wins.
  * Not offered to staff and administrators; no effect without a second factor.
  * Afterwards the factor is removed, other sessions end, every address is told, and the event `two_factor_removed_phone_lost` is kept for the long period. Whoever has neither app nor code goes through the operator (D-004).
* **Abuse protection (D-017, D-038):** Axes for account lockouts plus a separate transactional IP counter. Axes account resets also delete records that feed its IP bucket.
  * Failed attempts are limited per account and per IP. Lockouts are temporary, so attackers cannot lock others out permanently.
  * A password reset stays possible during a lockout and ends only that account's temporary lockout. Counters and lockouts per IP remain.
  * Remaining risk (D-017): attackers who know an address can repeatedly cause temporary lockouts and use up the per-address email limit. The owner can still use links already in the mailbox.
  * Behind reverse proxies the exact trusted proxy count is `AXES_IPWARE_PROXY_COUNT` (default `0`: `REMOTE_ADDR`, forwarded headers ignored). A positive count enables strict proxy-chain validation; a mismatch yields no client IP and the login is refused.
  * Axes stores only a keyed digest of the normalised address and no raw IP. The IP lockout table stores an HMAC-SHA256 digest with a purpose-specific key derived from `SECRET_KEY` via HKDF (D-017, D-023). Password and OTP fields are masked; Axes access logs are off.
  * **Registration, password reset and email change** are rate-limited per IP and per normalised target address.
    * Above the per-address limit nothing is processed: no email, no replaced pending registration or change. The most recent verification link and reset links already sent stay valid.
    * Below the limit a new registration replaces the pending one and a new reset request invalidates earlier reset links (D-042).
    * Exceeding a limit changes neither response nor response time. Counters hold only keyed hashes (HMAC-SHA256, HKDF key; D-023) for the window.
  * **Mechanism (D-038).** The request stores only a counter entry and one job in a database outbox and makes no account lookup. A worker looks up the address, decides and sends.
    * A request counts only if all three budgets have room: per address (12 per hour, 3 per 10 minutes, 24 per day; never shown), per client IP (IPv6 by /64), instance wide.
    * Over the client or instance budget: HTTP 429 ("Zu viele Anfragen"), no job, counter row or session.
    * A request for the address this browser entered less than the pause ago, or a bot-check hit, creates no job. Such silent requests are counted per client address (30 per hour); above that they get the same 429.
    * **Bot check, stage 0 (D-058):** hidden field and signed time stamp (at least 2 seconds) on step 1 and the reset request. A hit gets the same page without a job. Open: proof of work is recommended, not built.
    * The information email to an existing address is sent at most once per address per 24 hours.
    * Jobs and counters store keyed digests. An unprocessed job holds the address for at most one hour. Tokens are never stored in a job.
  * **A notification job holds the cleaned name for the greeting (D-068)**, empty for the neutral greeting, for a deleted account and for an address not belonging to the account at queue time. It is deleted after sending, after the third failed attempt, after 24 hours by the clean-up and with the account; it is blanked at once in every queued job when an account is deleted or deactivated. Never logged.
  * **Editable email texts (D-039)** are plain text with fixed `{placeholder}` markers, never evaluated by the template engine.
    * Accepted only if all placeholders are valid for that email, the personal link is present and no web or email address is typed in (deny-list, also in the subject).
    * `{greeting}` exists only in the 14 notifications to the addresses of an account and is refused elsewhere. A name never reaches a registration, reset or other mail to an unverified or foreign address.
    * The name passes an allow-list: letters, combining marks only after a letter and at most three in a row, space, hyphen, apostrophe, period; no digits, symbols, line breaks, format characters, invisible marks or address-like text; at most 64 characters. It is checked again when the email is built; otherwise the greeting is neutral.
    * Changing a text needs the permission "change email text" (runtime role) and is recorded in the administration log without the text. The history is visible to system administrators only.
    * A test email goes only to the logged-in account's address.
* Error responses give no hint about the existence of accounts (including blocked and deactivated ones). Registration and email change use generic responses (`docs/PROJECT.md`, "Registration", "Changing the Email Address").
* Reset links are random, single-use, time-limited, abuse-protected. Reset is impossible for unverified, blocked and deactivated accounts, with an identical response and comparable time.
* **Email address change** needs re-authentication and takes effect only after the new address is verified via a time-limited (24 hours), single-use link.
  * The old address stays valid until then and is notified afterwards. Only the most recent pending change can be confirmed (D-059).
  * A request stores a pending row for every target address whatever it belongs to (the answer does not tell whether it is in use). The person can cancel.
  * Confirming a change or reactivating an account deletes a pending unverified registration with the same address.
  * A **second address** (own confirmation and status) receives every notification and is **never an identifier** (no login, reset or lookup). It is removable at once after re-authentication.
  * **Stop link (D-059).** A request for a new login or second address sends a notice with a link "stop it at once" to the old login address and the confirmed second address. It is queued before the confirmation link; a new request deletes the earlier stop links.
  * The stop link works without a login in two steps (a page, then a POST with CSRF token), so a mail scanner stops nothing. It cancels all pending changes, deletes all confirmation and stop tokens, ends every session of the account and logs the event.
  * It has a meaning only while a request is open: stop links are deleted when the change was confirmed, cancelled or expired. Without an unexpired request a link is refused without ending a session.
  * Open requests and all confirmation and stop links are deleted when the password is reset or changed, when the status becomes anything but active and when the second factor is reset.
  * **Residual risk, not covered:** an attacker with password and session who confirms the new address in their own mailbox at once leaves no window to stop it. The owner only gets the notice "changed" and contacts the operator (open question, D-059: a short undo window).
* **Notifications** of changes of email address, password and two-factor go to **every address of the account** (for an address change also the old one), also when a system administrator changes another account's password or address.
  * Except for the stop link they contain no link that could undo or confirm anything. They tell the person (default text, editable, D-039) to contact the operator immediately if they did not request it. No reply is invited (noreply sender).
  * After such a report the operator follows the installation guide.
* **Sessions, cookies, CSRF** (OWASP Session Management Cheat Sheet).
  * The session ID is renewed at login, after the second factor and after password and privilege changes.
  * All other sessions of an account end after a password change or reset, email change, second-factor reset, blocking, deactivation and removal of rights.
  * **Session end (D-041, D-100).** Idle timeout (server-side): users 30 minutes, staff and system administrators 15 minutes. Every request except a background poll extends it. Logout also ends the session.
    * No absolute limit for an ordinary session (owner decision 2026-10-17; OWASP recommends one). A session without a stored start time ends (fails closed).
    * A background poll (import status, live log) neither extends the idle timeout nor survives it (401).
    * **Residual risk:** a stolen session cookie stays usable while it is used within the idle timeout.
    * Mitigations: HttpOnly/Secure/host-only cookies, session ID renewal, the idle timeout, the shorter staff timeout, end of all sessions on password change, rights removal and blocking, "End all sessions" for system administrators (D-100).
  * **Stay signed in (D-056, D-100).** Off by default; for everyone including staff and system administrators (owner 2026-10-17).
    * Ticked: a session of 14 days (`STAY_SIGNED_IN_DURATION`) with a fixed absolute end; activity does not extend it.
    * The second factor is asked once, at login. The persistent session exists only after the code was accepted; the wish waits only in the pending login. A privileged account without a second factor gets none.
    * A removed right or second factor ends all sessions of the account. Sensitive actions still ask for one proof (D-062). Logout ends the persistent session.
    * **Residual risk (owner-accepted):** a stolen 14-day session of a privileged account has its privileges for up to 14 days without a new code.
    * **Mitigations (D-100):** security event `persistent_session_started` (long retention), no email (owner 2026-10-19: normal security level); "End all sessions" (event `account_sessions_ended_by_admin`) for system administrators; password reset and rights change end sessions.
    * **No step-up code** before IBAN, PDF lists or any other action (owner, D-102): whoever is signed in is authenticated. An unattended device is the operator's responsibility.
  * **Portal settings (owner decision 2026-10-26).** Saving in the administration needs no further proof; the administration is only for system administrators behind the second factor at login. The proof for the profile (D-062) is unchanged.
    * `RECENT_AUTHENTICATION_WINDOW` (five minutes) stays only for setting up the second factor (D-055).
  * Session and CSRF cookies are `Secure` in stage and production and `HttpOnly` where possible. `SESSION_COOKIE_DOMAIN` and `CSRF_COOKIE_DOMAIN` are not set (host-only, D-025). `CSRF_TRUSTED_ORIGINS` never contains the instance's website or a wildcard for its parent domain.
  * In stage and production the cookie names use the `__Host-` prefix (accepted only if `Secure`, `Path=/`, no `Domain`). A cookie set by the website for the parent domain (cookie tossing) cannot replace the application's cookies (D-025; draft-ietf-httpbis-rfc6265bis).
  * After login a redirect target (`next`) is followed only on the application's own host.
* Security settings are secure by default and relaxed only for `APP_ENV=local`. A missing or unknown `APP_ENV` prevents the start. `DEBUG` can only be enabled with `APP_ENV=local`.
* **The initial system administrator** must change the initial password and set up two-factor at the first login (D-005, D-041).
  * Its email address is entered by the operator on the server and counts as verified.
  * The setup command treats any account with `is_superuser`, also blocked and deactivated ones, as an existing administrator.
  * Until the password is changed the session can only change it (to a different one) and log out. Then the factor must be set up before anything else.

## 4. Authorization

* Permissions are checked on the server on every request. Hidden menus or buttons are no access control. Tests cover direct URLs, manipulated IDs, API endpoints and exports.
* New users are authenticated users without groups, permissions, `is_staff` or `is_superuser`. They read and edit only their own profile.
* Checks use permissions, never role (group) names. Roles are runtime data (D-012).
* Only system administrators create and change roles and their permissions, assign roles, grant or remove direct permissions and grant or remove `is_staff` and `is_superuser`.
  * Enforced technically, also against staff who may add or change users. Django documentation ("Using the Django authentication system"): such a right "is ultimately the same as giving them superuser status because they will be able to elevate permissions of users including themselves".
  * Delegating role assignment to other roles needs a separate reviewed decision.
* Staff can never change, block, deactivate or delete accounts of staff or system administrators (including their own in the admin). Staff never change the password, email address or second factor of another account, except by starting a reset under D-106.
* **Staff accounts that take part (D-113).** A staff account or system administrator with a customer number is also a customer: the customer pages (D-105) treat it like every account (ids resolved through the account, budgets, deletion rules; the last system administrator stays protected, D-016). The staff area (`/management/`, `/admin/`) opens from an entry that authorises nothing (`target="_blank" rel="noopener noreferrer"`, no named window), and every request is checked on the server as before. Accepted by the owner: such an account can approve its own application in the management area (the application services check only an active staff actor; D-086, no four-eyes block). Not changed: the customer data of a staff account, also one's own, is changed by a system administrator only (`persons.may_change_customer_data`, D-087). The customer pages have the same second-factor check as the management area and the administration (`customer.access.check_access`, D-004; the middleware is the first line).
* Changes by an administrator to another account's password or email address are logged and notified.
* **Customer onboarding (D-103; `community.applications`, `application_staff`, `deregistrations`, `contracts`, `own_iban`).**
  * Authorization is in the services. A customer service takes the account and reads every object through it (`Application` with `person=`, rows of the application, assignments): an id of another account is "not found", the same answer as a missing one. A staff service re-reads the actor from the database (active `is_staff`); a customer, a blocked or a demoted account is refused.
  * No oracle for foreign data: a metering point number of another account (stored or in an application in flight), an archived building and an EGID that contradicts the entered address give one neutral refusal ("cannot be created, contact the LEG") with no detail; the staff gets an `ApplicationNotice` (deduplicated, capped per account). A building (EGID) is shared by all customers of it (owner decision 2026-10-19): choosing it always attaches, and a customer reads and edits only the own points, drafts and own words (`CustomerBuilding`, found through the account). One customer never changes the address of a building that other accounts use. Drafts of other accounts block nobody.
  * Caps against row creation: drafts, open applications, buildings per application, open deregistrations, open notices per account; one draw and one feed-in per building; IBAN changes per hour. Per-request rate limits belong to the pages.
  * Locks are taken in the order account, then application in the customer and staff services. The scheduler locks only the application (or deregistration) row, except `_operator_lapses` (account first). A holder of an ENDED assignment has no access to a point, a building or its address (`buildings.owns`, `own_building`, `own_metering_point` take the current assignment only) and does not count as a user of a building. Two accounts that name the same metering point number are separated at the staff's review and again at the registration at the grid operator (the earlier submission keeps it), not only at completion; concurrent completions lock buildings by EGID, then id.
  * History holds ids, dates, field names and fixed reason keys, never a name, address, number or IBAN. The scheduler logs counts and times only.

Staff dialog data (`completion_defaults`, `confirmation_defaults`) are staff services that re-read the actor.

CSRF token, POST only, 4 KiB, values bounded and validated (`clean_input`), at least three characters for the typing modes (`TYPEAHEAD_MINIMUM`), at most ten results, `no-store, private`. The walk `customer/tests/test_access.py` fails for a route without the mixin, for a `csrf_exempt` route and for a `put`/`patch`/`delete` handler. The second-factor middleware applies. Every response is `never_cache`; every POST has a CSRF token and a request budget per account (60 a minute and 600 an hour; the building search 12 a minute and 60 an hour; 429 with `Retry-After`; fails closed on a database error); the POST body is limited to 16 KiB. The building search asks only the local directory; the swisstopo budget stays with `addresses.limits` (D-066). Pages never echo anything of another account; refusals about foreign data are the neutral texts of the services. No inline script, style or handler (CSP). The IBAN is shown only to its owner on the bank-connection step; no address, IBAN or metering point number is written to a log (tested with `assertNoLogs`). The page "submitted" is shown once by a flag in the session of the account.
* **Customer data changed by staff (D-087, approved deviation from "the customer changes the data"; D-012 stays for everything else).**
  * Every staff account may change the **profile data** of a customer account for support: salutation, company, names, second person, phone, billing address, IBAN, paper invoice, and the second email address through the flow of D-059.
  * Second-address flow: the link goes to the new address only; the addresses valid now get the notice with the stop link; nothing changes before the confirmation.

  * The write goes through the account model (`save(update_fields=...)`; the guards of D-034 compare controlled fields with the locked row). It validates with the model's rules, writes the history entry and the security event `account_data_changed_by_staff` with **field names only**. It sends **no email to the customer** (owner decision).
  * The same actor rule applies to accepting the address suggestion of a person.
  * A staff-initiated request or removal of the second address writes the event with the field `secondary_email`. The owner's confirmation is logged as "requested by staff account N".
  * `User.invited_at` is controlled: no save, bulk update or plain creation can write it.
* The customer number, the retention flag (set only by application functions, never unset) and the normalised email column cannot be changed in the admin by anyone, including system administrators. The first two are read-only there, the third is not shown (D-035).
* Every path that deletes, deactivates, reactivates, blocks, unblocks, promotes or demotes accounts, or changes the email address, the normalised column or the retention flag, goes through the central account logic. Paths: objects, admin bulk actions, `list_editable`, `QuerySet.update()`/`delete()`, management commands.
  * "Delete selected objects" uses `QuerySet.delete()` and bypasses the model's `delete()`. It is disabled for the user model or replaced (Django documentation, "Admin actions").
* Promotion beyond the authenticated user needs an explicit action by an authorized superior. Nobody promotes their own account. `is_superuser` is granted only by another system administrator. Every promotion is logged.
  * `is_staff` and `is_superuser` are granted only to accounts with a confirmed authenticator app or an active passkey; recovery codes alone do not count (D-042, amended by D-106).
  * The administration refuses otherwise, rechecked on the locked row at save. The only exception is the initial administrator (D-005).
  * For passkey accounts, one active credential is sufficient; no separate two-device statement is required. Removing rights is always possible.
* System administrators can block other administrators and remove their rights. At least one active, not blocked administrator always remains; emergency access is restored only via the server command.
* Keep the number of administrators minimal: they bypass all permission checks and their actions are logged. Superuser status is no general role model.
* **Management area (`/management/`; D-077 to D-086).** Every page checks on the server, on every request, in `leg_platform/management/access.py`: logged in (else login), active and `is_staff` (else 404), second factor completed (else redirect to setup).
  * **Per D-086 (approved deviation from D-012) there is no per-area permission: every active staff account may use every page.**
  * **Accepted risk:** every staff account can see and change all customer data in the area.
  * Mitigations: mandatory second factor for staff (D-040, D-042), checked once per login; persistent sessions and "End all sessions" (section 3, D-100); only administrators create and change staff accounts and rights; every change is in the history with actor and time; the security log records printing and the retention flag; customers and normal users get 404.
  * The management area uses no Django permissions (the community models carry only the `view` right of the administration tables, D-091). The Django administration keeps its permission model. The grid operator model and the editing of the administration tables are for system administrators only.
  * No response under `/management/` is cached (`NoStoreForManagementMiddleware`, also 403, 404 and CSRF pages).
  * **Rules for every management function.**
    * Ids and states are rechecked on the server under a row lock (no step twice or out of order).
    * The person search is bounded (10 results, at most five words of 100 characters), finds only active accounts with a customer number and never shows the email address.
    * List state is parsed again from the address on the server. Selected ids are matched against that list's entries. An unknown print scope or more than 2000 ids is a 400.
    * Bounds: 1000 entries, 100 detail pages, 20000 printout rows.
    * A LEG can be deleted only if no metering point was ever assigned (rechecked under a lock) and never when archived. Restore is the only action on an archived LEG or location, also by direct POST.
    * Assigning a person whose assignment is in force sets the retention obligation of the account and writes a security log entry (account and actor numbers only); accepting the contract does the same (D-103). An account with any assignment or acceptance is deactivated, never deleted.
    * History names event, actor and time, never the text of a remark, note or IBAN.
    * IBAN, note and customer number at the grid operator appear only on the person's detail page. They are never searched, logged or written to history or security events.
    * A staff change of an account's address writes only street, house number, town and Swiss postal code with the profile's `update_fields`. The directory suggestion is asked again under the row lock and must be the one shown (a digest travels with the buttons).
  * **Forms of the management area (D-097, D-098).**
    * A value the page gives to a form (location at a location; number, direction, LEG of a point being changed) is a disabled field: Django ignores the posted value and uses the page's object.
    * Drop-down choices (point to assign, circuit) are built from the database per request. A posted id that is not offered (archived, already there, unknown, forged) is refused.
    * Services check again under row locks in one order (location, then point; LEG, then point), refuse archived objects and write ids and field names only to the history. A circuit created in the same form is created in the same transaction.
    * The redirect after a create uses only a safe return address (`returns.after_create`, `with_parameter`: paths of this site). `origin_point_url` is built from view name and number.
    * Page scripts only help (no `innerHTML`, no dynamic code, answers as text).
    * Suggestion endpoints are GET only, staff only, at most ten texts for at least two characters, never an email address.
    * The person search is counted per staff account (300 per minute, then 429 with `Retry-After`), cut to 100 characters and five words.
    * A `DoesNotExist` of a service is the normal refusal (`management.access.gone`, D-101).
  * **PDF printing.** No typed text reaches ReportLab as markup (escape, remove control characters, cut the length). The PDF is made in memory and sent with `Cache-Control: no-store, private`, `Content-Disposition: attachment` and a fixed file name. A failure logs only the kind of error. The bundled font is read only from the package directory.
* `ALLOWED_HOSTS` lists only the application's host names (not the instance's website; D-025). Never read the `Host` header from `request.META` (use `request.get_host()`). Links in emails come from the canonical base URL of the instance configuration, never from the request.

## 5. Data Protection

* Collect only necessary data. The purpose of each profile field is documented (`docs/PROJECT.md`, "Profile Data and Purpose"). The phone number is optional.
* Persons are informed through the instance's privacy notice, linked at registration and on all pages accessible without login (DSG Art. 19; D-022).
* Account deletion removes all data of the account unless a retention obligation is set; then the account is deactivated (D-016). The retention flag can never be unset.
* Security log entries are kept without personal reference until they expire (D-018).
* **The IBAN of a person is stored encrypted (D-087).**
  * A Fernet token (`PersonRecord.iban_encrypted`) under a key derived from `SECRET_KEY` by HKDF with the label `LEG-Platform person IBAN v1` (section 7). Only the checksum-validated normal form is encrypted (`python-stdnum`, any country).
  * It is **not searchable and not sortable**. It appears only on the person's detail page, the card dialog and the PDF of the details, and, in full, to the account itself (D-103: `community.own_iban`; the account changes it without password or second factor, with full validation, at most 5 changes per hour, a security event `iban_changed` and a history entry without the value on every change, and a mail to every address of the account on a change of an existing IBAN or its removal, not on the first entry from empty). **Never** in a list, search, history, security log, log line, mail text or error message.
  * The account number is part of the encrypted text (`v2|<account>|<IBAN>`): a text copied to another person's record is refused and shown empty.
  * An IBAN that cannot be decrypted is shown empty, and **an empty submission leaves it as it is**.
  * The log line of printing says "with IBAN".
  * Note, customer number at the grid operator and address are plain columns, likewise never in history or logs.
* Do not write personal data to logs unnecessarily.
* Backups are the operator's responsibility. Deleted data can remain in backups until they expire.
* Error pages disclose no secrets, stack traces or internal configuration. Development data and test accounts use no real personal data.
* Assess legal data protection and retention requirements only against official sources (e.g. fedlex.admin.ch). Clarify legally unclear points with the project owner.

* **Import error log (D-121, D-122).** Rows older than 180 days are deleted by the scheduled task `cleanup_import_log`. Notice mails carry no log line, no reason text and no file name.

## 6. Web Security and Uploads

* Consider at least CSRF, XSS, SQL injection, insecure direct object references, session and cookie security, rate limiting, secure error handling and protection against accidental disclosure of files and configuration. Do not disable Django's security features without a documented, reviewed justification.
* **Headers:** HSTS in stage and production, CSP, `X-Content-Type-Options`, `Referrer-Policy: same-origin` or stricter, protection against framing (`X-Frame-Options: DENY`, `frame-ancestors 'none'`; the one exception is the contract's reading view, D-108, section 6 "Contract PDF").
* **CSP (D-028):** no inline scripts or styles that would need `'unsafe-inline'`. Set with Django's `ContentSecurityPolicyMiddleware` and `SECURE_CSP`, never relaxed globally. At least: `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`.
* **CSP exception (D-123):** `img-src` of the page Nachbarschaft alone also allows `https://wmts.geo.admin.ch` (view override `csp_override`, `customer/views.py`; `docs/SERVICES.md`, N-10). Every other page keeps `img-src 'self'`. No other external host, no `unsafe-inline`, no `frame-src`.
* **Token URLs (D-067).** Pages whose URL carries a token (verification, reset, other emailed links) never render under it.
  * The link only remembers the digest of a valid token in the session and redirects to a URL without the token.
  * An invalid, expired, used or replaced link, and a confirmation page without valid state, redirect (302, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`) to a fixed page of the flow.
  * Status, headers and body are identical for every cause and contain neither token nor account information.
  * **Limit:** the response time is not equalised. Tokens are looked up by a keyed digest, so no token prefix is compared in application code. The length (43 characters, 256 bits) is public.
  * The 429 lockout page is `no-store`.
* Static assets (Tabler, fonts, icons) are served by the instance in fixed versions, not from third-party CDNs.
* The application runs on its own host name, never under a path of another website (D-025). On a subdomain of the website's registrable domain it is still the same site, so the cookie rules of section 3 apply and the installation guide states the residual risk.
* Colour mode lives only in the tab's `sessionStorage` (no cookie, nothing sent to the server). The scripts are external files, accept only allowlisted values (`light`, `dark`) and evaluate no URL parameters (`docs/DESIGN.md`, section 7; D-056).
* **Language cookie (D-056).** The language is chosen on the server; the one cookie it needs is functional and holds no personal data.
  * `language` (`__Host-language` in stage and production, like the other cookies, section 3): only the code of an allowed language (`de-ch`, `fr`, `it`, `en`), `Max-Age` one year, `Path=/`, no `Domain`, `HttpOnly`, `SameSite=Lax`, `Secure` outside local (settings `LANGUAGE_COOKIE_*`).
  * Only `set_language` sets it: POST only, CSRF token, a code outside `LANGUAGES` is refused (400, no cookie), `next` and then the Referer are checked with `url_has_allowed_host_and_scheme` (own host, https on https), otherwise `/` (no open redirect). The route is public and session-free (`SESSION_FREE_VIEWS`, `UNRESTRICTED_VIEWS`, `PASSWORD_CHANGE_VIEWS`): it neither reads nor extends a session, and works without the second factor. The body is limited to 8 KiB (`BODY_LIMITS`).
  * Only the cookie chooses the language, never `Accept-Language` (`leg_platform.language.ChosenLanguageMiddleware`). A wrong cookie value gives the instance default. Responses carry `Vary: Cookie` and `Content-Language`.
  * The menu form carries no address: nothing of the request is written into the page again.
* **Branding values are validated** at startup, when saved and when read from the database (`docs/DESIGN.md`, section 3.2; D-073).
  * Colours match `^#[0-9A-Fa-f]{6}$`.
  * Configured URLs (privacy notice, legal notice, website) are absolute `https://` URLs without credentials, white space, control, format or line/paragraph separator characters; otherwise no link.
  * Environment logo references point to a file inside the instance's static files with an allowlisted extension (no absolute paths, traversal or external URLs).
* **Logos (D-073):** static files from the operator (fallback) or uploads by an administrator with the right to change the portal settings. Embedded as `<img>`, never inlined. Static SVG logos are checked for scripts and external references before deployment and served with a restrictive CSP (`docs/DESIGN.md`, section 10).
* **Uploads (D-073, D-103).** The only web uploads are the two Microsoft Graph files (D-048), the two logo files and the favicon of the portal settings, and the contract PDF (below).
  * The right to change the portal settings is needed (a role gets it at runtime, never by default).
  * The type is decided from the content, never from the name or content type. The file name is never stored or used. A rejected file is never rewritten.
  * PNG: at most 1 MB, 64 to 4000 pixels per side, at most 4 million pixels; strict chunk, CRC, ancillary-chunk allow-list, bounded inflation (`leg_platform/accounts/logo_images.py` and its tests).
  * SVG: 200 KB, at most 20 levels and 2000 elements, strict allow-list: UTF-8; no DOCTYPE, ENTITY, CDATA or processing instruction (checked on the bytes before any parser); SVG namespace only, fixed lists of elements, attributes and value characters; `url()` only to an id of the same file; no script, style, image, foreignObject, link, use, animation or filter.
  * The file is stored in the database with type and SHA-256 digest. Only the views `instance_logo` (the two fixed variants) and `instance_favicon` serve it, with a fixed content type, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox; default-src 'none'`, `Cross-Origin-Resource-Policy: same-origin` and an ETag.
  * The favicon (browser tab icon) follows the same rules and the same validator: PNG or SVG only, by content; smaller limits (PNG 128 KB, SVG 64 KB). One file for both colour modes, independent of the logos; removing it returns to the built-in icon. Allowed by `img-src 'self'`; a change is `PORTAL_SETTINGS_CHANGED` (type, bytes, short digest), a rejected file `portal_upload_rejected` (reason `favicon <code>`).
  * The view reads no session (no `Set-Cookie`, no `Vary: Cookie`). `Cache-Control` is `max-age` (content hash in the address) or `no-cache`, never `public`. `MEDIA_URL` serves nothing.
  * Every request below `/admin/accounts/portalsettings` is limited to 3 MiB before the form is read, by path prefix (the admin routes the object id as `<path:object_id>`, so `01`, `+1`, `%201`, `_31`, `add`, `history` reach the same admin).
  * A rejected upload is a security event with a reason code only (`portal_upload_rejected`); a change is a long-kept event with a line per field, never file content (section 10).
  * The risk of the right (it changes what every visitor sees, like the email texts, D-039) is accepted and limited by the audit trail and by no role having it by default.
  * **Open:** the rendering of an SVG with style attributes under the sandbox policy and the effect of CSSOM changes under `style-src 'self'` were not checked in a browser.
* **Contract PDF (D-103).** Uploaded by an active staff account in the management area (no Django permission, D-086); the page has to limit the request body (10 MiB plus form data, `BODY_LIMITS`) before the form is read.
  * Checked by content in `community/contract_pdf.py`, never by name or content type, never rewritten: size 64 bytes to 10 MiB, `%PDF-1.x` / `%PDF-2.x` at byte 0, `%%EOF` in the last 1024 bytes, no `/Encrypt`, `/JavaScript`, `/JS`, `/AA`, `/OpenAction`, `/Launch`, `/EmbeddedFile(s)`, `/RichMedia`, `/XFA`, `/SubmitForm`, `/ImportData`, `/GoToR`, `/GoToE` (names with `#xx` escapes are decoded; every `stream` that inflates with zlib is scanned, within a per-stream and a total budget).
  * **Not checked:** streams with other filters (LZW, ASCII85, crypt), streams beyond the budget, and the meaning of the document (no PDF parser). A hostile PDF that avoids these names can pass. Mitigation: the customer download (`customer.views.ContractDownloadView`, D-105) is an attachment from the own server with `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox; default-src 'none'`, `Cross-Origin-Resource-Policy: same-origin`, `Referrer-Policy: no-referrer`, a fixed name and no caching; the upload is for staff only. **Reading view (D-108):** the current version is also shown in a frame of the contract pages (`customer.views.ContractReadingView`, `downloads.pdf_inline`): `Content-Disposition: inline`, `nosniff`, `Cross-Origin-Resource-Policy: same-origin`, `Referrer-Policy: no-referrer`, `no-store`, customer access check like the download, GET only, and **no `sandbox`** (the browsers' PDF viewers refuse a sandboxed document). It is the only response with a framing exception: `X-Frame-Options: SAMEORIGIN` and `Content-Security-Policy: default-src 'none'; frame-ancestors 'self'`; the site-wide `DENY` / `frame-ancestors 'none'` and the page CSP (`object-src 'none'`, no `frame-src`) are unchanged. Residual risk: section 4 (D-108); not verified in a real browser.
  * Stored in the database with SHA-256 and size; the file name is never stored (the download name is `contract-<version date>.pdf`). One current version; deletable only if never current and never accepted. A customer downloads the current version and the versions the account itself accepted (`contracts.customer_download`; any other version is "not found"). A contract acceptance sets the retention obligation of the account (security event `retention_obligation_set`), so the evidence outlives an account deletion. Every upload, change of the current version and deletion is the security event `contract_version_changed` (long retention, actor only).
* **Address directory import in the web process (D-090).** The web application downloads the official address file in a background thread of one web worker (no extra service).
  * The thread connects only to the two fixed HTTPS addresses of `data.geo.admin.ch` (host allowlist, no redirect, no proxy or `.netrc`). It verifies the official SHA-256 before parsing and keeps size, time and row limits.
  * It is the only code of the web process that may write the SQLite file (`storage.mark_thread_writer`; request threads stay read-only).
  * Start: the administrator's button (right `addresses.request_directory_import`, CSRF, 5 per minute per IP, security event; thread of the web process), or the daily run of the scheduled tasks (`scheduled_address_import`, own process, no web request; regular refresh every 90 days; at most one download per day; same claim as the button). A visit of a staff member starts nothing.
  * One import at a time over all workers (the job row is the claim). A dead one is found by its stale heartbeat.
  * The status endpoint (`admin/addresses/importrequest/status/`) needs a session and the same right, GET only, JSON, `no-store`. Failures show only the fixed sentences of the importer (`jobs.SAFE_FAILURES`).
  * **Residual risk:** a compromised web process can already write the file (D-075) and can also start the download (fixed addresses only). A long import uses CPU and memory of one worker; the directory in use stays.
* **Plant register download (D-117, owner decision 2026-10-24).** A second source of the address file: the plant register of the Federal Office of Energy (BFE). It is downloaded only by the daily run (`scheduled_address_import`, own process, no web request, no administration button), after the address import of the same run and under the same claim (section 7).
  * One fixed address, `importer.PLANT_URL` (`https://data.geo.admin.ch/ch.bfe.elektrizitaetsproduktionsanlagen/csv/2056/ch.bfe.elektrizitaetsproduktionsanlagen.zip`), in the download allowlist of `importer._chunks` next to the two addresses of the address import; no other address is accepted. HTTPS with a verified certificate (`verify=True`), no proxy variables or `.netrc` (`trust_env=False`), **no redirect** (`allow_redirects=False`).
  * **Deadline:** one total time limit of 1,800 seconds (`importer.MAX_DOWNLOAD_SECONDS`) for connection, headers and body together. At the deadline every socket of the request is shut down (`http_budget.Budget`).
  * **Content type:** `application/zip` or `application/octet-stream`; any other type is refused.
  * **Limits:** the ZIP at most 64 MiB; at most 16 members, none encrypted, compression ratio at most 100, all declared sizes together at most 192 MiB; the plant file at most 128 MiB and 1,000,000 rows, each line at most 16 KiB. The ZIP holds the plant file `ElectricityProductionPlant.csv` exactly once and five catalogue and detail files. These are checked like the others but never read or extracted; any other name is refused. Open: the owner still has to confirm this member rule (D-117).
  * Each row is checked field by field. A failed row is counted and not stored. A publication is refused only when the file holds no plant or its row count moves by more than a factor of two (D-117).
  * **No official checksum.** The BFE publishes no checksum. The SHA-256 of the downloaded ZIP is computed and stored for the statistic and compared with nothing. A transmission error is caught by the ZIP and CSV checks only.
  * **Residual risk, accepted by the owner:** a wrong but well-formed file is published without notice. Reason: the data is not sensitive and feeds no bill; a wrong value would only distort a chart (D-117).
* **Outbound request with an address: building search at swisstopo (D-066, `docs/SERVICES.md` S-4).** The only request of the web process that carries an address to a third party.
  * Only after the local directory and the stored answers found nothing, only for a signed-in active account (`addresses/buildings.find_buildings(user=)`; anonymous callers never trigger it), only to determine the EGID. Budgets in the transactional rate limiter: 6 per minute and 10 per hour per account, 30 per minute and 300 per hour per instance (`limits.allow_external_lookup`; fails closed on a database error). The answer is stored (negative 7 days, positive 90 days); a repeat costs no request. A refused or failed search is `unavailable` with a reason; `BuildingSearch.needs_review` lets the caller note the address for the LEG instead of leaving the person stuck.
  * `addresses/swisstopo.py`: one fixed https address (`https://api3.geo.admin.ch/rest/services/api/MapServer/find`), no redirect, 256 KiB, no proxy variables or `.netrc`, JSON content type, strict schema checks (nested JSON is a failure), at most 200 features. Only the postal code (search text) and the house number and street (filter) are sent; the filter input is restricted to a safe character set, never concatenated from free text.
  * **Time and breaker:** waits of 3 s (connect) and 4 s (read), and a **hard total deadline of 8 s**: the request runs in a helper thread, the caller stops waiting after 8 s and every socket of the request is shut down. A circuit breaker (5 failures in 5 minutes, shared by all workers through the rate-limit tables, cleared by a success) pauses the search without using any budget.
  * **Never logged or stored in clear text:** the address, the answer, the exception text of the HTTP client (it contains the query). The stored negative answer is a keyed digest; found buildings are public directory data. The update flag holds no address.
  * Tests (`addresses/tests/test_buildings.py`): fixed URL, redirect and error statuses, oversized, nested and invalid JSON, a trickling server cut off at the deadline, the circuit breaker, anonymous and inactive callers, budgets, nothing logged.
  * **Residual risk:** a signed-in account chooses the address that is sent (within the budgets); the answer is public data. Swisstopo sees the address and the instance's address (a server, not a person). The privacy notice must name the request (operator's text, D-022, D-074).
* **Admin tables (D-091):** the tables of the management data have two faces, chosen on the server by `is_active and is_superuser` (never by a group name).
  * **Plain face** (staff with the `view` right of a table, handed out by a system administrator to a role): read-only, only the explicit `staff_list_display` / `staff_fields`. Add, change, delete and every POST (also `add-row/`) are refused with 403. Free text of staff, IBAN, emails and names never appear as column or field.
  * **Raw face** (system administrators only; owner order 2026-10-19, approved deviation): every column that is a model field is an input of the list (one "Save"), a "new row" adds a row, one row can be deleted; no bulk action. Not an input: primary key, automatic timestamps, the encrypted IBAN (editing the ciphertext destroys it), the address digest. No validator of the model, no `Model.clean`, no service rule, no history entry written by the application: only what the database and Django's field types need (a database refusal is a message, never a 500).
  * **Audit:** `LogEntry` per row, one security event `management_data_edited` per request (long retention; log line with table, row ids and field names, never a value); a write path without that note fails closed. CSRF and the second-factor check apply as everywhere in the administration.
  * **Accepted risk (owner 2026-10-19):** the system administrator edits raw rows without checks; wrong values can break rules and pages of the management area. Users, groups and the protected `User` fields are not in these tables (D-034).

Sources: Django 6.0 docs (`SECURE_REFERRER_POLICY`, CSRF "Limitations", CSP reference and howto), W3C CSP3, draft-ietf-httpbis-rfc6265bis, W3C SVG integration.

* **Transformer station scan (D-118).** The weekly run (`schedule.run_transformer_weekly`, Saturdays) and the command `scan_transformer_stations` read the public map server of BKW Netz, host `qgisserver-extern.bkw.ch` (one fixed address, `transformers.WMS_URL`, which must be in `importer.APPROVED_WMS_URLS`). No other address, no redirect, certificate verified, no proxy variables, no `.netrc`, no credentials. Only the tiles of the service area are requested, one at a time, at least one second apart. The owner states verbal permission to use the server (recorded 2026-10-25; source: owner statement).
  * **Deadline:** each tile request runs in a helper thread with a hard total limit of 60 seconds (`transformers.REQUEST_SECONDS`, also cut at the rest of the run's 3,600 seconds) for connection, headers and body together. At the deadline every socket of the request is shut down (`http_budget.Budget`), as for the downloads.
  * **Content:** the answer must be a PNG of the requested size and at most 16 MiB; any other answer is a fixed failure. Nothing of the answer is stored or logged.
  * Only the scheduled run and the command start the scan. No web view and no administration action does (test `NoWebStartTests`).

## 7. Secrets

* No secrets in Git, source code, documentation, logs or error messages. Local secrets live in ignored files or environment variables; server secrets in protected environment variables or a suitable secret store. Never display secrets in plain text again.
* Separate credentials for local, stage and production and per instance (stage has its own database and secrets, D-070). No production or stage secrets on development machines.
* The read deny rules in `.claude/settings.json` additionally keep AI tools away from secret files. They do not apply to scripts that open files themselves and are no complete protection (D-020).
* **Encryption of stored secrets (D-006, D-040).**
  * The Microsoft Graph private key (written in the admin, never displayed again), the TOTP key and the IBANs (D-087) are encrypted with Fernet under a key derived from `SECRET_KEY` by HKDF with an own purpose-specific label (established `cryptography` library, no custom primitives).
  * Keys from `SECRET_KEY_FALLBACKS` are tried for decryption. The secret is then encrypted again with the current key.
  * Recovery codes are stored only as keyed digests, also checked against the digests of the fallback keys.
* **IBANs after a `SECRET_KEY` rotation:** run `manage.py reencrypt_ibans` on the server before the old key leaves `SECRET_KEY_FALLBACKS`.
  * It prints numbers only and **fails with an error code if any IBAN could not be decrypted**.
  * If the old key is removed first, those IBANs cannot be read any more (pages show none, the log names the account number, staff enter it again).
  * Backups hold the encrypted values, so a restore needs the same `SECRET_KEY` (or the fallback).
  * **Residual risk:** old plain values remain in backups made before migration `community/0005_encrypted_iban`, in the binary log and in freed database pages until overwritten (`docs/DEPLOYMENT.md`, section 12.3, step 6).
* After accidental disclosure, revoke or rotate the affected secrets. If `SECRET_KEY` is changed without keeping the old key in `SECRET_KEY_FALLBACKS`, the Microsoft Graph certificate and private key must be uploaded again.
* **One database account for everything in MariaDB (D-075, approved deviation from D-033, D-049, D-052; risk assessment there).**
  * The address directory is public data without reference to a profile. It is kept in its own SQLite file (mode 0600 for the service user, not part of any backup).
  * Every process opens it read-only (`PRAGMA query_only`) unless it declares itself a writer (worker, operator commands, `migrate`; the web processes only through the import thread of section 6).
  * **This protects against a mistake in the code only, not against a compromised web process** (web process and worker run as the same service user). The worst effect is wrong address suggestions, never access to an account.
  * A manual import request is logged with the account number only. An import is refused below 4 GB of free disk space (the disk of the directory file, which also holds the downloaded archive; D-076).
* **Plant table in the address file (D-117; D-075, D-090).** The tables `Plant` and `PlantRegister` are in the address file and follow its rules: own SQLite file, routed only through the directory alias (`AddressRouter`), read-only for every process that is not a writer. The plant rows hold no address, owner or account; they are public register data (EGID, power, LV95 coordinates).
* **One claim and a serial chain (D-090, D-117).** The plant import takes the same claim as the address import (`jobs.claim`; the field `source` of the job row shows the holder). One writer of the address file at a time over all processes: no plant import while an address request is queued or running, and no address import while a plant import holds the claim. In the daily run the plant import runs after the address import, also when that failed (owner decision). It does not change the address schedule.
* **Statistic (D-117).** `PlantRegister` keeps the values of the last successful import only (address count, plant file rows, plants taken over, rows ignored by reason, time). A failed, refused or unchanged import keeps them. A missing or failed plant register does not affect the address directory.
* **Initial system administrator password:** entered interactively (`setup_initial_administrator`) and stored nowhere, or (D-076, owner requirement, deviation from D-005 and D-041) taken from `BOOTSTRAP_SYSTEM_ADMIN_PASSWORD` of the first start.
  * That variable is a secret in the protected environment file (mode 0600, root), masked on debug pages and in error reports, never printed or logged.
  * **Residual risk:** the variable has no expiry: it stays valid as long as nobody has logged in. Whoever knows it and reaches the login page before the owner can log in, set their own password and second factor and lock the owner out.
  * The runbook therefore requires that the instance is not publicly reachable until the owner has logged in, changed the password and enrolled the second factor (`docs/DEPLOYMENT.md`, section 9). A take-over shows as the owner's failed first login and a `PASSWORD_CHANGED` entry nobody on the owner's side caused.
  * The variable is ignored once a system administrator exists. The account is created only while the account table is completely empty (a restored backup or old environment file can never create a privileged account later).
  * The operator removes the variable after the first login and restarts the services.
  * A time limit for the initial password is **open** (possible hardening, owner's decision, D-076).

## 10. Security Logging

* Logged events include at least:
  * failed logins and lockouts; password changes and resets; email changes;
  * setup, removal and reset of two-factor; use of recovery codes;
  * role, permission, `is_staff` and `is_superuser` changes;
  * blocking, unblocking, deletion, deactivation and reactivation of accounts; setting of the retention obligation; use of emergency commands;
  * creation and invitation of a person by staff; resend of an invitation;
  * every change of customer data by staff (D-087: actor and account number; field names, never a value);
  * every change of the IBAN by the account itself (`iban_changed`, D-103: account number only, never a value; long retention) and every upload, change of the current version and deletion of a contract version (`contract_version_changed`, long retention);
  * changes of the grid operator of the instance (D-087: actor only);
  * every add, change and delete of a row in the raw administration tables of the management data, one event per request (`management_data_edited`, long retention; table, row ids and field names in the log line, never a value; D-091);
  * changes to the Graph configuration and the portal settings (name, website, privacy and legal notice addresses, colours, logos): one entry per changed field with old and new name, host names of old and new address, colours, for a logo type, size and start of its SHA-256 digest, never content (D-056, D-073);
  * rejected portal-settings uploads (reason code only);
  * the outcome of every address directory import (completed, or failed with the fixed reason; D-090);
  * the outcome of every plant register import (D-117): `pv_import_succeeded` with the kind (manual or automatic) and the number of stored plants; `pv_import_failed` with the kind and one fixed reason (a sentence of `jobs.PLANT_FAILURES`, of `jobs.SAFE_FAILURES`, or the generic text for an unexpected failure).   Never a row, a value, a file name or upstream text.
   * the outcome of every transformer station scan (D-118): `transformer_scan_succeeded` with the kind and the number of buildings; `transformer_scan_failed` with the kind and one fixed reason (`jobs.TRANSFORMER_FAILURES`). Never a row, a name, a label, a tile or upstream text.
   * every run of the housekeeping of the databases (D-119): `housekeeping_run`, once per run, with the account of a manual start; fixed text, no SQL, no table content, no file name.
   * the change of the log notification setting (`log_notification_changed`, D-120; no address in the event) and the acknowledgement of open housekeeping errors (`housekeeping_errors_acknowledged`, D-119).
   * every change of the postal codes of the service area (`service_area_changed`, D-118): the actor only in the entry; the postal codes after the change in the log line, nothing else.
  * every opening of a log page and every log download (D-099); the log menu (D-120) writes the same events (`log_viewed`, `log_downloaded`) with the source name as detail.
* Logs never contain passwords, tokens, secrets or complete security links, and only as much personal data as necessary (basis: OWASP Logging Cheat Sheet).
  * The logging filter (`log_filters.TokenRedactionFilter`) removes tokens of links, email addresses, IBANs and the values that MariaDB names in duplicate-entry and invalid-value errors from every message and exception text before it is written.
  * **What can remain (D-099):** a path with an internal id or a customer number; internal account numbers (by design); the class and text of an exception that carries no database value; host names of the configured server and of the official address source; a free-text field of an exception message of a third-party package that the patterns do not know.
  * The log pages apply the same redaction again when a line is shown or downloaded.
* **Log files and log page (D-099).** With `LOG_DIRECTORY` the portal also writes `application.log` and `security.log` (10 MB and 5 older files each, mode 0600 in a 0700 folder).
  * **System administrators only** (`is_superuser`, like the security log; no right gives it to staff).
  * The administration lists the files, shows one live (polls `logs/<log>/tail/` every 2 seconds; at most 128 KiB for the first answer, 64 KiB for later ones; pause and follow) and streams a download (redacted line by line).
  * The client names only a fixed key and a backup number 0 to 5; the file name is built on the server; no symbolic link is followed (`O_NOFOLLOW`, check on the descriptor).
  * Opening a list or viewer and every download is a security event (`log_viewed`, `log_downloaded`, long retention, actor only; the same page again within 300 seconds in one session is no new event; polls are none). Responses are `no-store`; the poll does not extend the idle timeout.
  * Log lines escape CR, LF and other control characters, so a request path cannot forge a line. Redaction works across read chunks (512-character overlap).
  * Residual risk: a system administrator can read everything the logs contain, including what the filter does not know.
* Only system administrators can view security logs.
* The security log is append-only within the application: nobody, including administrators, can create, change or delete entries. Entries are deleted only by the automatic retention. The same holds for the failed-attempt and lockout records of the abuse protection package.
* The log files are not the security log: they are operating logs that rotate and are not evidence.
* Log entries of deleted accounts are kept without personal reference, with an internal number, never the customer number (it appears on invoices).
* Admin log entries of accounts store only a neutral text with the internal number. After deletion the mapping is intentionally lost unless another kept record maps the number to a person (D-036). The admin history of accounts (it shows the acting account's address) is visible to administrators only.
* **Retention (D-018)** is set per instance in the server configuration (`SECURITY_LOG_RETENTION_DAYS`, `SECURITY_LOG_LONG_RETENTION_DAYS`; a value below the minimum prevents the start), not in the admin.
  * Default 1 year: changes of roles, permissions, `is_staff`, `is_superuser`; resets of the second factor of staff and administrators; blocking and unblocking of staff and administrators; changes by administrators to another account's password or address; deletion, deactivation and reactivation by administrators; emergency commands; customer data changes by staff (D-087); changes of the IBAN by the account and of the contract versions (D-103); changes to the Graph configuration and portal settings.
  * Default 30 days: all other entries including failed-attempt records.
  * Expired entries are deleted automatically.

## 11. Tests

* Security-critical functions need positive and negative tests. Every rule of sections 3 to 10 needs a test. Tests create the groups and permissions they need and rely on no predefined roles.
* This section is the only list of security-relevant acceptance criteria (`docs/ACCEPTANCE.md` refers to it). Tests prove at least these cross-cutting points; the individual cases are in the test modules (`docs/CODEMAP.md`, section 9).
* **Accounts (section 3):** no login without verified email and a set sign-in method; blocked and deactivated accounts neither log in nor reset and no response reveals them; the customer number is rejected as login; a nonexistent address behaves like a wrong password; registration activates only at the last step; used, expired or replaced links lead to "Link nicht mehr gültig"; customer numbers are unique, assigned only at completion, never reused; addresses are unique among non-deactivated accounts, also under concurrency and case variants.
* **Sessions, abuse protection, links, two-factor (section 3):** test every rule and its negative cases: session renewal/end, idle timeouts, stay signed in, cookie flags and `next`; trusted proxies, lockouts, proof budgets and rate limits; single-use scanner-safe links; no normal privileges without completed authentication, including during mutation races; exactly one current proof with atomic counter settlement; unified recovery and restricted setup. Method-choice tests cover server-offered choices, refusal of password-only for administrators, shared entry points and account-state guards. Passkey tests additionally cover canonical RP/origin, user verification, challenge/action/session binding, replay, counters, malformed input, the uniform one-active-credential minimum (including promotion and concurrent removal), add-key session consequences, atomic method transitions and no password-reset bypass. Independent review and final acceptance are separate gates.
* **Initial administrator (D-005, D-076):** the commands refuse while any administrator exists (also blocked or deactivated), print no secret and log; the password comes only interactively (`setup_initial_administrator`) or from `BOOTSTRAP_SYSTEM_ADMIN_PASSWORD` while none exists (`setup_instance`); no setup function on the website; the first login can only change the password and log out, then only set up the second factor (D-057).
* **Onboarding (D-103; `community/tests/test_applications.py`, `test_application_staff.py`, `test_deregistrations.py`, `test_contracts.py`, `test_own_iban.py`, `test_application_deadlines.py`, `test_buildings.py`; staff pages D-104: `management/tests/test_process_pages.py`, `test_contract_pages.py`, `test_deadline_settings_page.py`, `test_acceptance_matrix.py`):** ids of another account are "not found" for every service; a customer, a blocked and a demoted staff account cannot use a staff service; neutral refusals are equal for an archived building, a contradicting EGID and a foreign number; a shared building attaches and nobody sees or changes another account's points, drafts or words; a rollback (customer, idle, contract deadline, operator lapse, staff) deletes only draft rows; the scheduler never rolls back anything submitted or completed; each mail once, a second run changes nothing; no address, IBAN or number in mails, history and log lines; PDF matrix (signature, size, active content, escapes, compressed streams, bomb); one current version, append-only acceptance, only the current version downloadable; own IBAN validation, mail to every address, rate limit; no step on a draft (read-only page, D-107), every step out of order refused with a message, no IBAN on the application page; upload matrix (not a PDF, too large, active content, empty, duplicate, double submit, name never used, body limit before the login); download only as an attachment with the protective headers and logged; delete only a never-current and never-accepted version, also by a forged post; whole-number matrix of the deadlines, second step bound to the shown number; every route closed to a customer, an anonymous visitor and a staff account without the second factor.
* **Authorization:** user A cannot read or modify user B's profile; no self-promotion; authorization survives renaming a group; a staff account or system administrator with a customer number reaches the customer pages only for its own data and a customer gets 404 under `/management/` and sees no entry to the staff area (D-113; `customer/tests/test_access.py`, `test_staff_customer.py`, `accounts/tests/test_workspaces.py`); staff who may change users cannot change `is_staff`, `is_superuser`, groups, permissions or accounts of staff and administrators (also their own), nor another account's password, email or second factor; customer number, retention flag and normalised email column are unchangeable in the admin; every management URL is tested for anonymous, non-staff, staff without second factor and staff; staff data changes (D-087): forged ids 404, CSRF, no values in history and security log, IBAN never in logs; portal settings: 403 without the right (page, post, preview, history), the logo validation matrix, serving headers.
* **Account lifecycle:** deletion needs re-authentication; retention obligation gives a deactivated account shown as "Deleted (retention obligation)" with the same page and message (D-055); no reactivation while an active, temporarily locked or blocked account with the same address exists; the last active, not blocked administrator cannot be deleted, deactivated, blocked or demoted; bulk actions respect both rules.
* **Language (section 6, D-056):** the language comes from the cookie only (`Accept-Language` does not change the default; a wrong cookie value gives the default); a code outside `LANGUAGES` is refused (400, no cookie); the cookie flags; `next` and the Referer cannot cause an open redirect; the form needs the CSRF token and a GET changes nothing; the route works for an anonymous visitor, staff without the second factor and an account that must change its password, reads no session and has a body limit; a text without a translation is English, never German; the pages (entry, error, signed in, management, administration) and the JavaScript catalogue switch; no inline script or style (`leg_platform/tests/test_language.py`, `accounts/tests/test_translations.py`).
* **Email, Graph, logging, configuration:** Graph configuration only for administrators, every change logged, private key never displayed and decryptable with a fallback key; delivery modes refused in stage and production as in section 8 (the message names variable and `APP_ENV`, no address); tests send no real email; links use the canonical base URL; a `Host` header not in `ALLOWED_HOSTS` is rejected; events are logged without secrets; the security log deletes only by retention (minimums enforced); a missing or unknown `APP_ENV` prevents the start; error pages show no stack traces; no template inlines an SVG logo; the colour-mode script ignores URL parameters; branding values are validated at startup, on save and on read; the Django deployment checks run; no secrets in the repository.

## 12. Handling Insecure Requests

* If a requirement would significantly weaken security, the AI does not implement it silently. It explains the risk, proposes a secure alternative and asks when goals conflict significantly.
* Deviations are documented traceably. Documentation alone does not make an insecure solution acceptable.

## 13. No Unsubstantiated Security Claims

* The AI distinguishes: implemented, automatically tested, manually checked, still open, not verified.
* Every security statement names the verification step or official source it is based on. Anything not substantiated is not verified.
* A passing test suite does not prove that the application is completely secure. Report critical risks accordingly.
* The subagents in `.claude/agents/` do not guarantee an independent security review (D-019). Critical changes additionally require a human review.
