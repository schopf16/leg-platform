# Architecture Decisions

This document holds the CURRENT binding decisions of LEG-Platform, grouped by topic. It is not a log: implemented work, review histories, test counts and replaced intermediate states are deliberately not kept (history: `git log -- docs/DECISIONS.md`). Decision IDs in brackets, such as `(D-012, D-086)`, are cited by code comments and other documents; every ID D-001..D-101 appears at least once. Where two decisions conflict, the later or owner decision wins and the older one is marked "superseded".

How to add a decision: take the next free ID, put the current rule (present tense, imperative) into the matching topic with the ID in brackets, name the owner and date for owner decisions, name the source (official documentation, law, vendor) for facts about libraries, laws and vendors, and list open points in section 15. Decisions rest on verified facts (D-011): no assumptions, no blogs or forums as basis.

Contents: 1 Stack, versions, licence; 2 Language and translation; 3 Instances, configuration, hosting; 4 Roles and access; 5 Accounts and lifecycle; 6 Authentication, second factor, confirmation links; 7 Security log and sessions; 8 Mail; 9 Web security baseline; 10 Address directory; 11 Design language and UI; 12 Portal settings; 13 Management area; 14 Operations, deployment, tests; 15 Open points and pending owner decisions; 16 Agent workflow and conduct; 17 Index of superseded or merged IDs.

## 1. Stack, versions, licence

* **Backend and database** (D-001, D-002, D-030): Python and Django. MariaDB through Django's MySQL backend with `mysqlclient`; minimum 10.11, the newest LTS (12.3) is used. MySQL is not supported; supporting it again needs a new decision (owner, 2026-10-11). `utf8mb4_uca1400_ai_ci` exists in 10.11 and 12.3; do not use `utf8mb4_0900_ai_ci` (alias only from 11.4.5). `REFERENCES` is unused in MariaDB and not granted. MariaDB 12.3 end of life 2029-06-12, 10.11 2028-02-16 (vendor policy, not binding). Source: Django "Databases", https://mariadb.org/about/.
* **UI framework** (D-003): Tabler for the application, the Django admin for system administration; no second UI framework (two sets of templates, styles and security updates without gain). Tabler minimum browsers: Chrome/Edge 123, Firefox 128, Safari 17.5, Opera 109; older devices are unsupported (documented for operators and users). Fully usable on phones in phase 1.
* **Version policy** (D-015, D-026): specify only minimum versions: the oldest that still gets vendor security updates, from official sources, proven by automated tests (CI tests both ends: minimum and latest). Raise a minimum when vendor security support ends. Where a version is chosen for use (development, install, CI "latest", operator recommendation) use the newest compatible release, for LTS tracks the newest of the track (owner, 2026-10-11). Never support an old version through a package with known vulnerabilities. Semantic versioning.
* **Minimums** (owner 2026-10-11; `pyproject.toml`, `requirements/minimum-constraints.txt`): Python 3.12 (security until 2028-10), Django 6.0 (`>=6.0.9,<6.2`, built-in CSP; Django 6.0 security fixes end April 2027, raise by then), MariaDB 10.11, `mysqlclient` 2.3.0, `django-axes` 8.3.1, `django-ipware` 8.0.0, `django-otp` 1.7.4, `cryptography` 50.0.2, `segno` 1.6.6 (TOTP QR codes), `msal` 1.39.0, Tabler 1.6.1, `requests` 2.34.2 (D-048; no official source names a supported older line), `reportlab` 5.0.1 (D-083), `python-stdnum` 2.2 (D-087), `django-countries` 9.1.0, `django-phonenumber-field` 8.5.0, `phonenumberslite` 9.0.41, `idna` 3.15+ (below: CVE-2026-45409) (D-034). Development runs on Django 6.1 / Python 3.14 / newest packages; the code must also run on the minimums. Django 6.0 lacks `MAILERS`, so settings keep both branches (`MAILERS` on 6.1+, `EMAIL_BACKEND` on 6.0). `django-axes` 8.3.1 declares Django up to 6.0; fall back to 6.0 if 6.1 fails. `msal` caps `cryptography` below 51: a 51 security release installs only once `msal` allows it.
* **Rate limits** (D-026): a small tested component with the keyed hash of D-023 on a shared store, not `django-ratelimit` (last release 2023-07, Python to 3.11). Counters must be shared across workers (a local-memory cache is per process, so counters live in database tables, D-038).
* **PDF** (D-083): `reportlab` (BSD 3-clause, pure Python; brings Pillow, unused by the project, keep it in the dependency check). Do not use fpdf2 (LGPL-3.0-only) or WeasyPrint (HTML/CSS renderer, its own docs warn of long renderings and file/network access). Safe subset: never give typed or database text to a paragraph as markup (always `printing/pdf.markup()`), no `<img>`, `Image`, link, `rl_safe_eval` or colour strings from data; own markup only `<br/>` (paragraph-parser CVEs: CVE-2019-17626, -19450, CVE-2020-28463 SSRF via `<img>`, CVE-2023-33733). Font DejaVu Sans Condensed Regular/Bold 2.37 unmodified in `leg_platform/management/printing/fonts/` with `LICENSE-DejaVu.txt` (hashes in `docs/THIRD_PARTY_LICENSES.md`), read by `TTFont`, never served; listed in package data (an installation copying only Python files must copy `fonts/`). Arabic, Hebrew and Asian scripts print as boxes. Tests use no PDF reader.
* **IBAN validation** (D-087): `python-stdnum` (`stdnum.iban`; LGPL-2.1-or-later, pure Python), not `schwifty`.
* **Licence** (D-029): BSD-3-Clause (SPDX, owner 2026-10-11), "Copyright (c) 2026, the LEG-Platform contributors"; `pyproject.toml`: `license = "BSD-3-Clause"`, `license-files = ["LICENSE"]` (PEP 639). `docs/THIRD_PARTY_LICENSES.md` lists every dependency and bundled asset with its licence; add new ones. `mysqlclient` is GPL-2.0-or-later (compatible); dependencies are not distributed with the source, a distribution bundling them (e.g. a container image) must comply with their licences. Not legal advice. Source: https://spdx.org/licenses/BSD-3-Clause.json, https://www.gnu.org/licenses/license-list.en.html.
* **Name** (D-014): "LEG-Platform", package `leg_platform`; initiated by LEG Ittigen (named in README), developed neutrally; no instance values or operator personal data in the repository. No trademark search done.
* **Billing** (D-009): no billing or productive financial functions in phase 1.

## 2. Language and translation

* **All repository content is English** (D-010): code, identifiers, database schema, stored keys, migrations, permission codenames, comments, commits, logs, tests, configuration, URL paths, documents. Only the UI is language-dependent: `LANGUAGE_CODE = "de-ch"`; Swiss German only in phase 1. Owner communication is German; German instructions go into the repository in English.
* **UI texts** (D-010, D-036): every user-facing text is translatable (English source), Swiss German in `locale/de_CH/LC_MESSAGES/django.po` (`LOCALE_PATHS`). Never use the German sharp s (eszett): Django's `de_CH` falls back to `de`, which contains it, so the project catalogue overrides every such text (Django, contrib, third-party; e.g. the German country name of the UK, D-034); an automated check forbids it; recheck at each Django upgrade and new third-party package. Missing translations and sharp s are defects. Commit compiled `.mo` next to `.po`; CI runs `msgfmt --check` and compares `msgunfmt` (D-034); translations keep every placeholder. A literal "%" in `{% translate %}` needs "%%" in the catalogue: use placeholders (D-080).
* **Wording** (D-036, owner): user-facing texts use established everyday terms, never invented technical terms ("company name", "address addition", "post office box", "account", "system administrator"; admin titles "LEG Platform"/"Administration", never "Django"). Untranslated Django admin texts are overridden in the project catalogue. LEG-specific texts are catalogue content that another instance replaces.
* **Login page** (D-056, D-074): FR/IT/EN texts exist (`login-texts.js`, checked against the catalogue by a test); no native-speaker review is planned; do not say one is required or that the texts are drafts. All other pages are German only.
* **Fact-based work** (D-011): no assumptions; the basis is project state and official sources (vendor documentation, legal texts, OWASP/IETF/W3C, owner statements); blogs, forums, news, SEO and AI-generated text are no basis; when in doubt ask. Decisions state sources; reports separate verified from unverified (`AGENTS.md` section 3).

## 3. Instances, configuration, hosting

* **One instance per municipality** (D-013): not multi-tenant; each instance has its own database, configuration, secrets, users and system administrators; no shared data, no tenant concept, no central administration. The same person has a separate account per instance. One code base; instance values (names, domain, base URL, sender, contacts) are instance configuration, never hard-coded in code, templates or migrations. Operation, updates and backups are the operator's duty. Source: StromVG Art. 17d para. 3 (an LEG covers at most one municipality).
* **Host name** (D-013, D-025): `ALLOWED_HOSTS` lists only the application's own host names; never read `Host` from `request.META` (use `request.get_host()`); email links use the canonical `INSTANCE_BASE_URL`. The application runs on its own host name (e.g. `portal.leg-ittigen.ch`), never under a path of the website (shared origin, RFC 6454, RFC 6265 8.5/8.6); subdomain or separate registrable domain is the operator's choice (the latter avoids cookie tossing; the installation guide states the subdomain risk). `SESSION_COOKIE_DOMAIN`/`CSRF_COOKIE_DOMAIN` are not set (host-only); `CSRF_TRUSTED_ORIGINS` never contains the website or a parent wildcard; in stage/production session and CSRF cookies use the `__Host-` prefix. `SameSite` does not protect between subdomains.
* **Entry point** (D-025): no public home page; the entry is the login page (login, reset, registration, links to privacy notice and instance website). Public LEG figures belong to the instance's website; publishing figures from the application needs its own security design (not phase 1).
* **Environment configuration** (D-027, D-028, D-037): configuration comes from environment variables, validated in `leg_platform/environment.py`; invalid or unsafe values prevent the start. Outside `APP_ENV=local`: `DJANGO_SECRET_KEY` and fallback keys meet `security.W009` (>= 50 chars, >= 5 unique, no `django-insecure-`); `DJANGO_ALLOWED_HOSTS` required; `DJANGO_CSRF_TRUSTED_ORIGINS` only `https://`; wildcards (`*`, leading `.`) rejected everywhere; numbers accept only ASCII digits; ports 1..65535. `SECURE_PROXY_SSL_HEADER` only via `DJANGO_SECURE_PROXY_SSL_HEADER`, never by default. HSTS in stage/production, default one year (`DJANGO_SECURE_HSTS_SECONDS`, lowerable, not disableable); `SECURE_HSTS_INCLUDE_SUBDOMAINS` off unless `DJANGO_SECURE_HSTS_INCLUDE_SUBDOMAINS=True` (`security.W005` silenced only while off); `SECURE_HSTS_PRELOAD` never set (irreversible); `security.W021` always silenced. Logging: warnings and errors to stderr; no email to `ADMINS`. `DEFAULT_EXCEPTION_REPORTER_FILTER = "leg_platform.debug.ExceptionReporterFilter"` masks `EMAIL_ALLOWED_RECIPIENTS`.
* **Instance values** (D-037): `INSTANCE_NAME` (default "LEG Platform", max 100, no control or line-separator characters), `INSTANCE_BASE_URL` (`https://` origin without path or credentials; `http://` only with `APP_ENV=local`; required elsewhere; host in `DJANGO_ALLOWED_HOSTS`), `INSTANCE_PRIVACY_URL` (absolute `https://`, required outside local), `INSTANCE_WEBSITE_URL` (optional). The privacy notice is linked on every page without login, including the lockout page. Branding and portal settings: section 12.
* **Environments** (D-070): `APP_ENV=stage` is only a label; no code branches on it. Stage must not differ from production (owner 2026-10-16; approved deviation from `docs/SECURITY.md` section 8): HTTPS, cookies, HSTS, CSP, limits, validation and secret rules stay. Stage and production require `EMAIL_MODE=graph` and refuse `console`, `allowlist` and a non-empty `EMAIL_ALLOWED_RECIPIENTS` (startup error without the address). Stage has its own database, `DJANGO_SECRET_KEY`, Graph app registration and certificate, and no production data or secrets (D-013, D-020); real personal data on stage counts like production. Accepted risks: real mail to typed addresses (not recallable); the public registration form allows up to 300 mails/hour to third parties, protected by the production limits (section 8). Procedures (`docs/DEPLOYMENT.md` 5.3/5.4, `docs/OPERATIONS.md`): testers use own addresses; the operator marks stage in `INSTANCE_NAME` (e.g. "<municipality> STAGE (test system)"), restricts the stage host at the proxy (IP allow-list or basic auth, recommended), names who reads the stage sender mailbox, purges/checks queued `MailJob` rows before the first restart and reverts environment files with the code.
* **Hosting** (D-008, D-074): the Ittigen production instance runs on an Infomaniak "VPS Lite 1" with MariaDB; Infomaniak operates stage and production (owner statement; assume nothing else about product, access or contact). Other instances: the operator's choice. SSH is needed for management commands. Vendor facts: Infomaniak VPS Lite offers official images only, no security software, no SLA, no backup by Infomaniak, outgoing port 25 not openable, key authentication.
* **Deployment documents** (D-053, D-064, D-076): `docs/STARTUP.md` is the single document for the local environment (agents never print the environment, never read `.env`, never delete seeded accounts, stop processes only by process ID). `docs/DEPLOYMENT.md` (direct deployment without containers: venv, Gunicorn, nginx, MariaDB 12.3 from the MariaDB Foundation repository, Certbot, systemd units and timer; secrets only in root-owned 0600 environment files) is a proposal not yet run on a server; section 0.5 is the entry point for a deployment request. Distinguish update from initial install; keep a non-secret instance record; reuse earlier decisions and inspect technical facts instead of asking the owner; verify both CI variants for the exact SHA. Stage without explicit revision uses the configured release branch resolved once to a SHA; production uses the release accepted on stage (same full SHA) and needs explicit per-deployment approval. Update: quiesce all writers; wait for the importer, never interrupt it; take and validate a backup on stage too; apply ordinary migrations; refresh static files; restart all affected processes; verify. Destructive migrations, restores and security exceptions stay approval boundaries; a code-only rollback does not prove schema compatibility. Do not use an unattended-password pseudo-terminal script, a fake privacy URL default or an automatic self-signed TLS fallback; do not skip the stage backup or treat the importer as one-shot. Owner decisions O-1..O-23 are in `docs/DEPLOYMENT.md` section 1. Behind one reverse proxy on the same host `AXES_IPWARE_PROXY_COUNT=0` resolves every visitor to `127.0.0.1`; count 1 works only with a header of exactly two entries, so nginx overwrites `X-Forwarded-For` with `"$remote_addr, 127.0.0.1"`. Distribution facts: Ubuntu 26.04 LTS until May 2031 (python3 3.14.3), 24.04 until June 2029 (3.12.3); Debian 13 until 2028-08-09, LTS 2030-06-30; MariaDB repository key fingerprint `177F 4010 FE56 CA33 3630 0305 F165 6F24 C74C D1D8`.
* **First start** (D-005, D-076): owner 2026-10-16: no manual account creation; an empty database plus environment file plus start gives a working instance. `manage.py setup_instance` is idempotent and runs on every start under one named MariaDB lock (`GET_LOCK`, hashed name, waits at most 600 s): `migrate --noinput` (never `flush`); creates the initial system administrator via the locked `create_superuser()` from `BOOTSTRAP_SYSTEM_ADMIN_EMAIL`/`BOOTSTRAP_SYSTEM_ADMIN_PASSWORD` with `password_change_required=True` and a security log entry; `migrate addresses --database=addresses`; prints no secrets. Bootstrap only when `accounts_user` has no row at all. Accounts but no superuser: create nothing, write `System administrator: NONE EXISTS, but accounts exist ...` to stderr, exit 0 (advice: restore a backup or run interactive `setup_initial_administrator`; `emergency_access` grants no admin rights). Missing or weak password, email without password, password without email on an empty table: fail the unit. The password passes the project validators (min 15 chars), never appears in messages or command-line arguments, is not read while a superuser exists (the start prints a reminder to remove it), enters no Django settings (`environment.parse_bootstrap_administrator()`), has `PASS` in its name so error reports mask it, and may contain only letters, digits, `-`, `_`, `.` (systemd `EnvironmentFile=` quoting). The directory step never blocks the start (failure: stderr with class only, exit 0, retried next start); a failure of the main database or of a configured administrator fails the command. The initial password is typed by a human, never generated or seen by an AI. Deployment (`docs/DEPLOYMENT.md` 8.0): `Type=oneshot` `leg-setup.service` (`Restart=on-failure`, `RestartSec=60s`, `StartLimitIntervalSec=15min`, `StartLimitBurst=5`, systemd >= 244); web and mail worker `Requires=`+`After=`, importer `Wants=`+`After=`, cleanup `After=` only; never `systemctl stop|restart leg-setup` (`start` is safe; `reset-failed` after the limit); never `StartLimitIntervalSec=0`; migrations run at every start without backup, so change code only via the update runbook (12.3, backup first); alert on a failed `leg-setup` and on `journalctl -u leg-setup | grep -c 'NONE EXISTS'` (expect 0). Not automatable: empty MariaDB database and account, HTTPS/DNS/proxy, the environment file.
* **Initial administrator** (D-005, D-041): created only by a server command, never via the website (first visitor could take over); runs only while no system administrator exists, never overwrites or resets an account. `setup_initial_administrator` reads `BOOTSTRAP_SYSTEM_ADMIN_EMAIL`, asks twice for the password with `getpass` (refuses without a terminal that can hide input), refuses while any `is_superuser` account exists; `createsuperuser` stays disabled. The account gets `password_change_required`: only password change and logout are allowed (`SecondFactorMiddleware`), the admin is closed (also `PortalAdminSite.has_permission()`); the new password must differ; password change and reset by link clear the flag; then the second factor must be set up. Accepted risk (owner): the initial password sits in the environment file (0600 root), with no expiry: whoever knows it and reaches the login first can take over (change the password, enrol an own second factor). The instance must not be publicly reachable (nginx closed or `allow`/`deny`) until the owner has logged in, changed the password and enrolled the second factor; restart services after removing the variable. A take-over shows as a failed first login or an unexplained `PASSWORD_CHANGED`. Accepted: the security log entry is written after commit.
* **Emergency commands** (D-005, D-041, D-044): `manage.py emergency_access`: `reset-second-factor N` (any account, also the last system administrator), `unblock-account N`, `reencrypt-second-factor-keys`; typed confirmation (`--no-input` skips; owner 2026-10-13); prints only the internal number; every use is logged for the long retention. They run only on the server. Procedure: `docs/INSTALLATION.md`, "Emergency commands".
* **Seed accounts** (D-019, D-042): `seed_design_accounts` (owner 2026-10-13) creates throw-away accounts of every access level for local design work; refuses outside `APP_ENV=local`; writes credentials only to a file outside the repository, never prints them; creates no role or permission and creates the authenticator app before granting rights. Risk: that file is readable by anyone who can read the user's files.
* **Scheduled tasks** (D-041, D-068): `manage.py run_scheduled_tasks` runs `delete_expired_registrations`, `cleanup_mail_requests` (includes `delete_expired_reset_tokens` and `mail_queue.delete_stale_jobs`), `cleanup_login_ip_attempts`, `cleanup_security_log`, `cleanup_confirmation_failures`, `clearsessions`; a failing task does not stop the others and fails the command; a test requires every `cleanup_*`/`delete_expired_*` command to be included. The scheduler (systemd timer) is part of hosting and must be scheduled (`docs/INSTALLATION.md`).
* **Backups** (D-016, D-075): the operator's duty; deleted data may persist in backups until expiry (documented). The backup is MariaDB plus the environment file; the address directory is not in any backup. Replacing `SECRET_KEY` without `SECRET_KEY_FALLBACKS` invalidates pending links and makes encrypted values unreadable (second-factor keys, IBANs, Graph key; backups need the key).

## 4. Roles and access

* **Three fixed access levels** (D-012): system administrator (`is_superuser` + `is_staff`, all permissions), staff user (`is_staff`, only assigned permissions), authenticated user (own profile only). Other roles are Django groups created at runtime in the admin. Never hard-code roles: no code, migration or fixture creates, names or checks a group; authorization checks permissions, never group names; permission codenames are English; tests create their own groups and permissions. The portal ships no predefined role or rights set (D-061).
* New users have no groups, permissions, `is_staff` or `is_superuser`. Nobody promotes themselves; `is_superuser` only by another system administrator; every promotion is logged (D-012).
* Only system administrators manage roles, permissions, assignments, `is_staff`, `is_superuser`, enforced technically also against staff holding add/change-user permissions (Django: that equals superuser). Delegation needs a separate reviewed decision. Staff can never change, block, deactivate or delete staff or system administrator accounts (also not their own in the admin) nor change another account's password, email or second factor. System administrators can block each other and remove rights; at least one active, not blocked system administrator always remains (emergency: section 3). (D-012, D-016)
* **Rights only with a second factor** (D-042, D-043): the administration grants `is_staff`/`is_superuser` only to an account with a confirmed authenticator app (`second_factor.has_second_factor()`; an unconfirmed app or recovery codes alone do not count); the form refuses with a translated message and `save_model()` rechecks on the locked account row (403). Removing rights is always possible; groups and direct permissions are not restricted (they open nothing without `is_staff`). The rule lives only in the administration (`UserAdminForm._clean_privileges`, `UserAdmin.save_model`), by owner decision 2026-10-14; code outside the administration that grants `is_staff`/`is_superuser` must implement the same check with a test, and every review checks this. The administrator confirms with the person that they set up the factor themselves (`docs/SECURITY.md` section 4). Remaining gaps: the initial administrator and staff after a second-factor reset set up the factor at next login. A password reset keeps `is_staff`, `is_superuser`, groups and permissions. If permissions are later used outside the administration for non-staff, decide again whether they need a second factor.
* **Management area exception** (D-086, D-087; owner 2026-10-17, approved deviation from D-012; wins over D-077/D-079/D-080/D-081/D-084): the management area (`/management/`) uses NO Django permissions. Every active staff user or system administrator with a completed second factor may use every page and function there. The one policy is `leg_platform/management/access.py` (details in section 13). Everything else of D-012 stays; the Django admin keeps its permission model, and functions outside the area stay permission-protected. Staff may change customer profile data in the area, but never password, login email, second factor, status, `is_staff`, `is_superuser`, groups, permissions, retention flag or customer number of any account (D-087).
* Later financial functions may need four-eyes separation that conflicts with an all-powerful system administrator: assess before financial modules (D-012, D-086).

## 5. Accounts and lifecycle

* **Lifecycle** (D-016): login after email verification and password set; no approval. The password is set only via the verification link, never at registration (else attackers register a victim's address with a known password). Unverified accounts are deleted when the link expires; a new registration with the same address replaces a pending one. States: unverified, active, blocked, deactivated (plus temporary lockout, `docs/PROJECT.md`). System administrators block/unblock any account. Blocked accounts cannot log in or reset passwords; during a temporary lockout reset works.
* **Retention flag** (D-016, D-086): one-way (unset to set only; rejected otherwise, also in the admin; DB privileges restricted, `docs/SECURITY.md` section 9). Deleting an account without retention obligation removes all data (security log entries lose their personal reference, D-018). With the obligation the account is deactivated: no login or reset, responses never reveal existence, the user cannot reactivate; a system administrator can unless an active/locked/blocked account has the same email. Assigning a person to a metering point with an assignment in force sets the flag (section 13).
* **Email uniqueness** (D-016, D-034): unique among non-deactivated accounts via the nullable `normalized_email` plus a normal unique index (MariaDB has no conditional unique constraints; UNIQUE allows several NULLs); NULL while deactivated.
* **Protection rules** (D-016): the last active, not blocked system administrator cannot be deleted, deactivated, blocked or lose superuser status. Email change: effective after verifying the new address (old valid until then), needs re-authentication, old address notified. Registration or change to an address of an active, locked or blocked account does nothing; the response is identical to success and that address gets an information email. Confirming an email change or reactivation deletes a pending unverified registration for that address. Every delete/deactivate/reactivate/block/unblock/promote/demote/email-change/retention-flag path uses the central account logic, including admin bulk actions (Django's "delete selected" skips `delete()`).
* **Deletion by the user** (D-055): page and message are identical for every account and never reveal a retention obligation; no artificial delay. Without retention the account and data are erased; with it the account stays `deactivated`, the email is released; the admin shows "Deleted (retention obligation)" and offers "Restore account". The legal assessment of the wording (DSG Art. 6, 19, 25) is unverified, the owner's responsibility.
* **Customer number** (D-021, D-034, D-038): six random digits (`secrets.randbelow(10**6)`, max 100 retries), unique, never reused, text, shown `482 915`, read-only; assigned once at completion of registration (or by the setup command for the initial administrator) by `assign_customer_number()` for a saved, active account without one, kept on email change and reactivation; unverified accounts have none. Table `IssuedCustomerNumber` holds every number ever issued without person reference (immutable rows); `User.customer_number` is a one-to-one FK (`PROTECT`, `utf8mb4_bin`). Identifier, not a secret; at most 1,000,000 numbers: from 90 % issued (`CUSTOMER_NUMBER_WARNING_PERCENT`, owner 2026-10-13) each issue logs a warning and the admin user list shows a notice to system administrators only; at 100 % completion of registration fails (500; no error page defined). Login is by email only: counting failures across email and number would reveal whether they belong to one account.
* **Email canonical form** (D-021, D-035): local part ASCII only (no SMTPUTF8, RFC 6531 section 3.4); `email` stores NFKC, trimmed, whole address lower case, IDN domain as IDNA ASCII (UTS #46), derived in `save()`; `normalized_email` equals it unless deactivated. Lookups, counters and rate limits use `normalize_email_address()`. Validation rejects non-ASCII local parts, quoted local parts, domain literals, IPs, `localhost`, Unicode categories C/Z/M; `idna` is a direct dependency. Owner decision 2026-10-12 (re-confirmed 2026-10-13 with the risk): the local part is lower-cased although RFC 5321 section 2.4 calls it case sensitive; risk: on a case-distinguishing host mail could reach another mailbox, mitigated because all mail goes to the canonical stored address.
* **User model** (D-034, D-051): `leg_platform.accounts`, `accounts.User` from the first migration; profile fields live on it, no profile table; `USERNAME_FIELD = normalized_email` (unique, nullable, not editable, `utf8mb4_bin`; the redundant column stays because its NULL releases a deactivated account's address while the unique index protects other states). Invariants live in the model, not in views/admin: `is_active` derived from status; unverified accounts have no customer number or usable password; `create_superuser()` refuses while any `is_superuser` account exists; the customer number never changes; the retention flag only goes unset -> set. Status, `is_active`, email, normalised email, retention flag, `is_staff`, `is_superuser`, customer number and password change only via `set_status()`, `change_email()`, `set_privileges()`, `assign_customer_number()`, `set_retention_obligation()`/`create_user()`; `QuerySet.update()` of these fields, `QuerySet.delete()` and `bulk_create()` are rejected (also base manager, `Meta.base_manager_name = "objects"`); `save()` of an existing account compares them with the `FOR UPDATE`-locked row; `delete()` refuses accounts with a retention obligation and the last active system administrator. Not covered (rely on DB privileges, `docs/SECURITY.md` section 9): raw SQL, `QuerySet._update()`, `loaddata`, many-to-many managers (`user.groups.add()`); no fixtures with accounts. Deleting an account deletes its admin log entries (owner accepted 2026-10-12).
* **Profile data** (D-032, D-034, D-036): fields follow eCH-0010 8.1.0 (https://www.ech.ch/de/ech/ech-0010; lengths per `eCH-0010-8-0.xsd`); all fields exist even if hidden. Person: salutation (Mrs/Mr/Family/empty), title, first and last name; organisation: name + two add-ons; organisation name OR first+last name required. Address: two lines, street, house number (text), dwelling number, PO box number (integer up to 8 digits) and text, locality, town, postal code, country (`CountryField`, default `CH`). Swiss postal code integer 1000-9999, foreign text up to 15. Required: postal code, town, country, and street or PO box (owner 2026-10-12); use the postal town, not the political municipality. One account = one person or organisation, no shared accounts; a second person goes into an address line. Phone optional (`PhoneNumberField`, `PHONENUMBER_DEFAULT_REGION = "CH"`, `PHONENUMBER_DB_FORMAT = "E164"`; Swiss numbers shown nationally, others internationally; declare `phonenumberslite` directly). Cross-field rules live in `User.clean()`/`clean_fields()`. Forms hide title, organisation add-ons, address line 2, dwelling number, PO box text and locality; validation never requires a hidden field and saving keeps stored values; an eCH export must fill the PO box text (e.g. "Postfach") when a PO box number exists. Forms show one "postal code" field: `CH` -> `swiss_postal_code` (4 digits 1000-9999), other countries (also `LI`, until eCH/owner clarify) -> `foreign_postal_code` (required, up to 15); the other is cleared. Required at registration: email; the rest after the verification link (owner 2026-10-13).
* **Admin neutrality** (D-018, D-036): `User.__str__` = "Account 686 821" or "Unconfirmed account", never email or name. Admin log entries stay neutral: `LogEntry.object_repr` = "Account with internal number N", never customer number, email or name; `UserAdmin` overrides `log_addition`, `log_change`, `log_deletions` (not `log_actions()`); future admin code logging an account as related object must keep this, with a test. Account history is for system administrators only (`UserAdmin.history_view()` 403 before any lookup); "Recent actions" shows only the viewer's own. The project catalogue must contain the capitalised labels of all editable account/group fields (history translates at display time; test). The admin user list shows/sorts/searches by customer number, not internal ID. The duplicate-email message exists only for the later email change in the profile; public registration answers duplicates generically (`docs/SECURITY.md` section 3).
* **Collations** (D-028, D-031): create every instance database with `CHARACTER SET utf8mb4 COLLATE utf8mb4_uca1400_ai_ci` (MariaDB's default charset is `latin1` up to 11.5); Django test DB via `TEST["CHARSET"]`/`TEST["COLLATION"]`. Exactly compared identifier columns use `utf8mb4_bin` (`db_collation`): normalised email, tokens/keyed hashes, recovery codes, customer number; other text keeps the default. Connection: `isolation_level` "read committed" (repeatable read can lose data), `charset` utf8mb4, `sql_mode` per connection via `OPTIONS["init_command"]` = `STRICT_TRANS_TABLES,ERROR_FOR_DIVISION_BY_ZERO,NO_AUTO_CREATE_USER,NO_ENGINE_SUBSTITUTION`; check `mysql.W002` (CI `--database default`) and tests tagged `mariadb` verify it. Source: Django "Model field reference" (`db_collation`); MariaDB "Supported Character Sets and Collations".
* **Password hashing** (D-023): Django's default PBKDF2-HMAC-SHA256 at the installed version's default work factor; never below it or OWASP's 600,000 iterations; not raised for now (measure one hash on the real server, OWASP: under one second; a higher factor needs a new decision). Argon2id not chosen. Source: Django passwords docs; OWASP Password Storage Cheat Sheet.
* **Keyed hashes** (D-017, D-023): counters and tokens store HMAC-SHA256 digests with a key derived from `SECRET_KEY` via HKDF with its own label per purpose (`cryptography`; prefer documented functions such as `django.utils.crypto.salted_hmac`; `keyed_digest` reads also with `SECRET_KEY_FALLBACKS`). Rotation resets counters (accepted). A leaked `SECRET_KEY` lets hashes be reversed with address lists; short retention limits the impact. Raw IPs and identifiers exist only in request memory.
* **Encrypted secrets** (D-006, D-040, D-087): secrets that must be read back (Graph private key, TOTP key, IBAN) are Fernet-encrypted under an HKDF key from `SECRET_KEY` with an own label (`LEG-Platform Microsoft Graph certificate key v1`, `LEG-Platform person IBAN v1`; `leg_platform/accounts/encryption.py`); `SECRET_KEY_FALLBACKS` keys are tried and the value is re-encrypted on use or by the re-encrypt commands; an undecryptable value verifies/shows nothing and is logged without content.

## 6. Authentication, second factor, confirmation links

* **Login** (D-004, D-021, D-037): email + password; Django `LoginView`, one message for every failure; `EmailModelBackend` returns no user for inactive accounts; `redirect_authenticated_user` off; a nonexistent email behaves like a wrong password. Pages with forms, tokens or personal data send `Cache-Control: no-store`; `/logout/` is POST only. Password rules (OWASP Authentication Cheat Sheet; NIST SP 800-63B-4 Appendix A): Django validators, minimum 15 characters for ALL accounts (second factor is optional for users), maximum at least 64, no composition rules; the text shown to users states the real policy and never promises a rule the server does not enforce.
* **Second factor policy** (D-004): TOTP (authenticator app) is mandatory for staff users and system administrators, optional for users (they may turn it off; staff and administrators cannot). A password reset never removes or bypasses the second factor; recovery mechanisms must not bypass MFA (OWASP MFA Cheat Sheet). Library `django-otp` (its `OTPMiddleware` adds `user.is_verified()`; devices subclass `django_otp.models.Device`, so the verified state is not tied to TOTP). The completed factor is checked in one central place, independent of method; TOTP parts stay separate (`docs/PROJECT.md`, "AGOV and Passkeys"). AGOV (Swiss authorities' login service) is intended as second factor, TOTP until then; AGOV is connected only after the clarification. Passkeys are a security goal, assessed together with account recovery.
* **Central check** (D-040, D-041): `leg_platform/accounts/second_factor.py`: `requires_second_factor()` (staff users, system administrators), `has_second_factor()`, `is_second_factor_complete()` (fails closed without the middleware). `SecondFactorMiddleware` (after `OTPMiddleware` and messages): such a session has no privileges without the factor (only logout/setup open; factor but incomplete -> logout; no factor -> setup); promotion applies in an open session. `PortalAdminSite.has_permission()` checks it too; the admin has no own login page. The mandatory factor is set up in the restricted session at first login (owner 2026-10-13); accepted risk: anyone knowing the password of a newly promoted account or the initial administrator can enrol first (no privileges; the owner is notified by email; reset is the recovery).
* **Devices and secrets** (D-040, D-054, D-062): `AuthenticatorDevice` (TOTP 30 s, 6 digits, SHA-1, one step tolerance, a used code is not reusable; one app per account, DB-enforced; only a confirmed app counts) and `RecoveryCodeDevice`/`RecoveryCode`. `django-otp` device throttling is NOT used (it lets someone knowing the password lock the owner out). Issuer = `INSTANCE_NAME`. Devices are not in the administration. The TOTP key (160 bits) is Fernet-encrypted (section 5); ten recovery codes (8 chars `a-z2-7`, 40 bits, shown once, a new set invalidates the old) are stored only as keyed digests, unique per device (`accounts_recovery_code_unique_per_device`), single use by one `DELETE`. Setup asks for the password unless the session is recent (below); an unconfirmed secret is valid 15 min and bound to the starting session; the QR code is an own SVG (`no-store`, no `data:` image); the factor is on only after a correct code. Recovery codes are shown once in the POST answer that creates them (never stored in plain text or session; `no-store`, `sensitive_post_parameters`), a "I saved the codes" checkbox is checked by the server; the term is "recovery code" ("emergency code" was the old term). Notifications without link for setup, removal, renewed codes, used recovery code.
* **Two-step login** (D-040): no `login()` after the password if a factor exists; the pending login (account, time, safe redirect, password session hash) lives in the session for 5 minutes and ends if the account is inactive, the factor is gone or the password changed; `/login/two-factor/` takes an app or recovery code (field `otp_token`, masked by Axes). Each attempt passes the Axes lockout check (`AxesStandaloneBackend`), takes its own IP slot, and a wrong code is a failed attempt of account and IP, under the account row lock. `login()` only after verification; the session ID is renewed at each step; OTP errors count for account and IP. "Stay signed in" is in section 7.
* **Wrong-code budget at login** (D-040; owner 2026-10-13, small residual risk accepted): `AuthenticatorDevice` counts wrong codes in 24 h from the first (`failed_codes`, `failed_codes_since`); only wrong codes that reach the check count (code step, wrong recovery codes), not Axes/pause refusals or wrong passwords. At 10: one email without link per window plus a log line (outside the mail budgets). At 15: code entry is paused, also for a correct code, until the window ends (lockout page with reset link; does not extend the Axes lockout). A completed password reset relieves to at most 10, once per window. A successful login does not clear the budget (deviation from NIST SP 800-63B-4 section 3.2.2, accepted). No escalating cool-off (it would let someone knowing only the email lock an account). Accepted: anyone knowing only the password can pause code entry for 24 h.
* **Protection against automated attacks** (D-017; owner 2026-10-12): `django-axes` for temporary lockouts per normalised account identifier plus a separate transactional MariaDB counter per client IP (Axes shares rows, so account resets would lower IP counts). Limits: 5 failed attempts in a rolling 15 minutes for account and IP each; 15-minute cool-off (`LOGIN_COOLOFF`, the lockout page names the real duration). Completing all factors releases the IP slot; failures keep it until the window ends. An account reset clears only Axes account rows, never the IP counter. Identifiers and IPs are stored only as keyed digests; Axes success logs off; POST `password`, `otp_token`, `otp_device` are masked (`AXES_SENSITIVE_PARAMETERS`); the Axes admin is disabled until a read-only system-administrator-only view exists. The client IP is `REMOTE_ADDR`, forwarded headers ignored (`AXES_IPWARE_PROXY_COUNT=0`); behind proxies the operator sets the exact trusted proxy count first. A lockout is recorded only when the failure reaching the limit is counted (Axes 8.3.1 also signals refused attempts during a lockout). Accepted risk: someone knowing an email can repeatedly trigger temporary lockouts and use up the per-address mail limit. Source: django-axes 8.3.1 docs, django-ipware; OWASP (a lockout must not enable denial of service; recovery stays possible while locked). The lockout response is `AXES_LOCKOUT_CALLABLE = "leg_platform.accounts.axes_handler.lockout_response"` (lockout template, `AXES_HTTP_RESPONSE_CODE` 429, never-cache, same HTML for XHR, also for the second-factor pause; django-axes' JSON answer echoes the username and sets `Access-Control-Allow-Origin` from `AXES_ALLOWED_CORS_ORIGINS`, default `"*"`: do not use a middleware or `AxesMiddleware` subclass instead). The lockout template never shows the submitted value. `cleanup_login_ip_attempts` also deletes abandoned unconfirmed setups and expired Axes attempts, taking IP buckets one by one with `skip_locked`.
* **Lock order** (D-072): everywhere account row first, then counter rows (`LoginIpBucket`/`LoginIpAttempt`, `SessionCodeFailure`, `ConfirmationFailure`); an inverted order caused MariaDB 1213 deadlocks. `login_protection.settle_client_ip_attempt` locks the bucket row in a short transaction first; cleanup commands lock per account with `skip_locked` and never wait. Locks do not use `nowait`; waits end at `innodb_lock_wait_timeout`, then 1205/1213 = HTTP 500, nothing accepted, no oracle, no retry (it could hide a fault); a logout failing this way keeps the session. Do not widen the application DB account with `PROCESS`. The order is proven by the deterministic tests that fail without the lock (`ConcurrentLoginIpAttemptTests`, `ConfirmationCounterLockOrderTests`); operators check the `EXPLAIN DELETE` plans (`docs/DEPLOYMENT.md` 12.4).
* **Registration** (D-016, D-037, D-058; owner 2026-10-13: six-digit number): three steps. Step 1 asks the address only; new/unverified address -> unverified account + token + link (a pending registration is replaced and the old link dies); active, temporarily locked or blocked account -> no account, one identical information email without link (no IP/agent/time; no reply asked); deactivated accounts do not hold their address; duplicates never give a form error; the next page is identical for every address and names the address entered in this browser (session only, never in the URL); "send again" after a 60 s pause enforced on the server; D-038 limits apply to every resend and the address cannot be chosen in a resend request. Mail goes to the canonical stored address, never the entered spelling (IDNA 2003 vs UTS #46 mismatch could bind an account to a domain the attacker does not control). Step 2 sets the password (shown address as text plus a read-only `username` field for password managers; the password is held only as a hash in the session, bound to the link digest; `UserAttributeSimilarityValidator` sees only the address). Step 3 collects names, street, house number, postal code, town and the privacy checkbox (consent stored with time and notice address: `privacy_accepted_at`, `privacy_accepted_url`). Only the last step activates the account: status, customer number and password in one transaction with locks on account (first) and link, then login (below); `User.complete_registration()` is the only place a customer number is issued. The link stays valid until step 3 completes or 24 h pass (mail scanners, back button; no text may call it single use); opening it calls `cycle_key`; a logged-in person opening it goes to the start page. Registration form field list is explicit.
* **Token links** (D-037, D-038, D-058, D-067): token = `secrets.token_urlsafe(32)`, stored only as keyed digest (`VerificationToken`, own HKDF label). Opening a link stores the digest in the session and redirects to the form page (scanners cannot consume it); the token is consumed only when the form succeeds (row lock; form bound to the rendered request; `sensitive_post_parameters`). Token pages (`TokenPageMixin`) send `Referrer-Policy: no-referrer` and `never_cache`; no form is served under `no-referrer` (a form POST from there sends `Origin: null`, which CSRF refuses; the form views after the redirect use `same-origin`, `/register/complete/` too). Every invalid, expired, used or replaced token, non-active account, stop link without open request, or removal link without usable second factor answers `302` to a fixed page (`/email-change/expired/`, `/email-change/stop-expired/`, `/two-factor-reset/expired/`; registration and reset likewise to "link no longer valid" with an address field); status, `Location`, headers and body are identical for every cause, no token, no flash message; fixed paths must not match a token route. The confirmation views redirect likewise when the session state is missing and remove their session key. `TOKEN_URL_PATTERN` (`leg_platform/log_filters.py`, also used by the session-timeout middleware so tokens never reach `next`) matches every token route including `/email-change/stop/<token>/`; a logging filter redacts tokens on all handlers; `test_instance_configuration.token_routes()` walks the resolver so new token routes are covered (a regex route with `token` fails the test). Proxy/web-server access logs are the operator's job (nginx error logs can keep token URLs). Response time is not equalised or measured (`docs/SECURITY.md` section 11). Accepted: `APPEND_SLASH` 301 for a token URL without slash; a stale-session cookie returned; `SecondFactorMiddleware` redirects an incomplete staff session before a verify view. Rotating `SECRET_KEY` invalidates pending links (accepted).
* **Password reset** (D-038, D-044): "Forgot password?" -> single-use link valid 24 h (= the longest limit window; a completed reset removes all outstanding links) -> new password -> normal login, no automatic login. Mail only to accounts with status active (a temporarily locked account is active, so reset works during a lockout); other states get nothing. Reset ends all other sessions and that account's temporary lockout only (never IP counters or lockouts), leaves the second factor untouched and notifies the account. `process_reset_request()` locks the account row and checks status under the lock (an unknown address returns `None` without lock); `complete_reset()` accepts only purpose `PASSWORD_RESET`; a reset request below the per-address limit deletes the account's earlier reset links first (during a mail outage retries each replace the link: accepted). A blocked account gets no reset mail; unblock with `emergency_access unblock-account N`.
* **Password change** (D-040, D-062): `/profile/password/`; session ID renewed, other sessions end, notification sent, outstanding reset links removed; `PasswordChangeView.post` compares `get_session_auth_hash()` with its value at request start under the lock and refuses if changed. "New equals current" is checked only after a valid proof, with `check_password(new, user.password)` without setter; before a proof the answer is identical whatever the new password is (it was a guessing oracle).
* **Login after registration and recent authentication** (D-055, D-063): completing the registration calls `login()` with `second_factor.LOGIN_BACKEND` (key renewed, no Axes failure, timeouts via `user_logged_in`) and goes to the start page; no privileges; a used/expired/replaced link logs nobody in. `second_factor.recently_authenticated(request, max_age=timedelta(minutes=5))` is true only if the session holds the server-side `authenticated_at` (epoch seconds, a number not bool, not in the future, at most 5 min old), written only by the `user_logged_in` receiver `remember_authentication` (after password and 2FA, and registration completion); never by activity, key cycling, password change/reset or client input; it ends with the session. It is not bound to an account id and is safe only because a session never changes account without a flush (`login()` flushes; every path ending a session's user uses `logout()`): a future path changing a session's account must bind the time to the account. Accepted Low risks: within 5 min of a login an unattended browser can start 2FA setup without the password (consequence: owner locked out); `ENROLMENT_LIFETIME` 15 min; "Copy codes" uses the clipboard; the 5 minutes are the owner's choice, not an OWASP rule.
* **One proof per confirmation, "2FA wins"** (D-062; owner 2026-10-15): every profile re-authentication asks exactly one proof: the 6-digit app code if 2FA is active, otherwise the current password, never both (email changes incl. second address, password change, new recovery codes, turning off 2FA, account deletion, forced password change; staff without 2FA give the password; 2FA setup after more than 5 min asks the password). `OneProofMixin` (`forms.py`) removes the unneeded field; a posted `current_password` with 2FA is ignored; the code is checked after all other fields are valid. After `totp.normalize_code` only exactly six digits count; anything else is refused as "not a code" before `verify_second_factor`, not counted against the wrong-code budget (a habit-typed password cannot pause the account), never echoed. A recovery code is no proof in any profile confirmation (`totp.verify_code(..., recovery=False)`); it counts only at login and in "phone lost". `totp.verify_code()` requires the caller to hold the account row lock (`second_factor.verify_second_factor()` does).
* **"Phone lost"** (D-062): card "turn off 2FA", `POST /profile/two-factor/lost-phone/`, works without script: password AND a recovery code, both right; order: required fields and code shape, then password (`verify_password`), then code (`verify_second_factor(..., app=False)`, used up only if everything before was right); wrong password and wrong code give the same message. Success in one `transaction.atomic()` under the account row lock (state checked on the locked row; of two parallel posts one wins): `totp.disable(..., via_recovery_code=True)`, other sessions end, every address mailed, security events `recovery_code_used` and `two_factor_removed_phone_lost` (long retention). Not for staff/administrators, not without 2FA. People with neither app nor code go through the operator.
* **Wrong entries in confirmations** (D-062): count per session, not at the account budget, Axes or IP counter (`verify_second_factor(..., per_session=True)`, `verify_password` record no failure; an existing Axes lockout or pause still refuses). Table `SessionCodeFailure` keyed by a keyed digest (purpose `LEG-Platform session code failures v1`, read with fallback keys) of a random `confirmation_counter_id` written once into the session and kept across `cycle_key`; changed under the account row lock; `SESSION_CODE_LIMIT` = 5 ends the session (`logout` in `ProfileCardView.dispatch`), event `session_ended_wrong_codes`, one notice to every address; a correct code deletes the row; a right password restarts the count except in "phone lost"; format errors count nowhere. Account cap: table `ConfirmationFailure`; 15 wrong entries over all sessions in 24 h end all sessions (`end_all_sessions`), event `all_sessions_ended`, one notice, count restarts (the login is not paused); a running request finds the session hash changed under the lock and is refused (`confirmation_refused`). `cleanup_confirmation_failures` removes rows older than 30 days. Statement: a session holder cannot trigger the account budget or Axes; with session and password the code can still be guessed (5 per session, 15 per 24 h). Residual risk: with 2FA an app code alone suffices to change email/password or delete the account (phished code, unlocked phone); mitigations: notifications to all addresses, other sessions end, 24 h pending address change with stop link, budgets, Axes. Accepted low points (take up with the next change of this area): L-1 `verify_password`/`verify_second_factor(per_session=True)` do not check the caller is the logged-in person (a new caller without login needs `request.user.pk == user.pk`); L-2 under an existing Axes lockout the check still sends the failed-login signal (counts against the holder's IP only); L-3 a login in a logged-in session also restarts the session count for accounts without 2FA; L-4 session counts are cleaned only via `run_scheduled_tasks`.
* **Profile cards, second address, stop link** (D-059): `/profile/` has five cards (personal details, email addresses, password, 2FA, delete account); state is server-rendered and addressable (`?edit=...&step=...`); old paths stay POST targets; GET renders and changes nothing (a redirect would loop with the mandatory-2FA middleware); `ProfileForm.save` uses `update_fields`; mandatory-2FA accounts see only the 2FA card; the forced password change keeps its stand-alone page. Second address: `User.secondary_email`, `PendingEmailChange` (account, kind login/secondary, address, 24 h deadline, one per account and kind); a request stores a row for every target address whether or not it belongs to another account (same answer, no enumeration) and the worker re-checks; the link is two-step (page, then POST); a login-address change ends all other sessions and mails old and new address; the second address is never used to log in or reset a password, is not unique, is stored only after confirmation and removable at once. Notifications go to every address (`User.notification_addresses()`, `mail_queue.enqueue_for_account`): password changed, address changed/removed, 2FA on/off, new recovery codes, deletion; the notice is queued before the confirmation link. Stop link `/email-change/stop/<token>/`, sent to the old login address and a confirmed second address with every change request: works without login, two-step; cancels all pending changes, deletes all confirmation and stop tokens, ends every session of the account, records `email_change_stopped`, recommends a new password; refuses a link without an open request. `User.discard_email_change_requests()` runs after password reset/change, on any status change away from active and in `remove_second_factor`; confirming a login address deletes all stop links. Limits are checked for every posted kind before password/code (`request_changes` raises `RequestRefused`, HTTP 429 only for client-address and instance limits); bot hits and repeats count per client address (`SCOPE_MAIL_SILENT`, 30/h). Events `email_change_cancelled`, `email_change_stopped`, `secondary_email_changed`, `registration_completed` carry no personal data. All mail templates have `autoescape off` (one test covers every key). The delete card shows the legal notice (`legal/VORGABEN.md` section 7) with privacy link, re-authentication and a never pre-ticked checkbox; the notice goes to all addresses taken before deletion. Open owner question (not built): an attacker with password and session who confirms a new login address in their own mailbox at once leaves no window for the stop link; an undo window needs a product decision.
* **Lost second factor** (D-004, D-041, D-044): users: a system administrator requests removal in the administration (action "Reset two-factor authentication", system administrators only, 403 otherwise, also for the own account); the worker mails a single-use link (24 h, keyed digest, never in the job); opening it stores the token in the session and redirects; the owner confirms with a button; then devices are deleted, all sessions end, the owner is notified, the event is logged. A newer link replaces the older; it dies if the account is inactive, became staff or has no factor. Staff users and system administrators: immediate reset after the administrator ticks that identity was verified in person or by callback to a number known independently of the account; the factor is set up again at next login. The last system administrator: only `emergency_access reset-second-factor N`. An incoming email's sender is never proof (forgeable, RFC 7489); do not start a removal on an unverified channel. Rationale: users reach only their own profile and a mailbox reset already opens accounts without a second factor, so a confirmation through the registered mailbox is proportionate; staff have extensive access and need a strict identity check. Large providers restrict manual resets (e.g. GitHub Support does not restore access without credentials).
* **Bot protection stage 0** (D-058, D-069): hidden field `contact_fax_number` (class `hp-field`, `aria-hidden`, `tabindex="-1"`, `autocomplete="off"`) plus a signed `form_started` (`django.core.signing`, min age 2 s `MAIL_FORM_MINIMUM_SECONDS`, max 3 days) on step 1, the invalid-link form and the reset request; a hit shows the same confirmation without a job. A read-only pre-check of client-address and instance limits (`mail_queue.requests_refused`) runs before storing anything: refusal creates no `MailJob`/session and answers HTTP 429 with a visible message; only these two limits are ever shown (no account oracle); the per-address limit stays silent. Proof of work (ALTCHA) is not built; reconsider only if abuse is observed (needs designer approval and study of licence, data protection, self-hosted widget under the CSP).

## 7. Security log and sessions

* **Security log** (D-018, D-041): events are logged (`docs/SECURITY.md` section 10), never with passwords, tokens, secrets or complete security links, only necessary personal data, identified by internal number (not customer number); entries of deleted accounts lose their personal reference. Table `SecurityEvent` = time, event (fixed list), internal numbers of the account concerned and the acting account (no FKs), long-retention flag; no email, no free text. Append-only in the application: model/queryset refuse update, delete and bulk create (nobody, including system administrators, changes entries; this includes Axes failure/lockout records); the admin shows it read-only to system administrators only (not by permission); also written to logger `leg_platform.security`, in the change's transaction (exceptions: initial administrator, lockout, re-encryption). Retention is server configuration, not admin: `SECURITY_LOG_RETENTION_DAYS` / `SECURITY_LOG_LONG_RETENTION_DAYS`, defaults and minimums 30 / 365 days (a lower value prevents start); `cleanup_security_log` deletes expired entries. Long retention: changes of rights/roles/`is_staff`/`is_superuser`, initial administrator, emergency commands, 2FA reset of staff users and system administrators, blocking/unblocking of staff and administrators, administrator changes of another account's password/email, deletion/deactivation/reactivation by administrators, Graph configuration and portal settings changes, staff changes of customer data, grid operator changes, printing (section 13); 30 days for everything else. No stricter protection against persons with server/DB access (owner 2026-10-13). Basis: DSG (SR 235.1) Art. 6 para. 4; OWASP Logging Cheat Sheet. Events of not yet existing functions (blocking, deletion, deactivation, admin changes of another account's password/email, Graph configuration) are logged when those functions exist.
* **Session end** (D-041, D-088; owner 2026-10-13, changed by the owner 2026-10-17; OWASP Session Management Cheat Sheet recommends an absolute timeout as well, this is a deliberate deviation): server-side `SessionTimeoutMiddleware`: a session ends at the idle timeout (users 30 min, staff users and system administrators 15 min; every request extends it, written at most once a minute) or at the logout. No absolute limit for an ordinary session; "stay signed in" keeps its own. A background poll (`session_timeout.PASSIVE_VIEWS`: import status, live log) neither extends the idle timeout nor survives it (401, no redirect). After a timeout the session ends and the login page appears with a message; return after GET only, a POST changes nothing; the redirect never puts a link token into the login URL. A session without stored times ends (fails closed). `SESSION_COOKIE_AGE` (8 h) only bounds the cookie and row of an abandoned session; `clearsessions` removes expired sessions. The session hash covers the password and `User.session_version`; `User.end_all_sessions()` raises it (2FA reset, change of access or roles). **Cause of the complaint "logged out about every 5 minutes"** (owner, 2026-10-17): no timeout of the session; the portal settings page refused every save when the login was older than `RECENT_AUTHENTICATION_WINDOW` (5 min, D-055/D-073) and offered a logout. Replaced by one proof of identity at the save (app code, else password; wrong entries counted per session, D-062); the window remains for setting up the second factor only.
* **Stay signed in** (D-056, D-088, D-100; owner 2026-10-17: for everyone, accepted with the residual risk below): off by default; ticked gives `STAY_SIGNED_IN_DURATION` (14 days, owner may change) as absolute end (set with a `timedelta`, never an integer, so it does not slide) and as idle timeout; allowed also for staff users and system administrators. **What is checked when**: the second factor is checked ONCE per login, at the login (the persistent session exists only after the code was accepted); the 14 days then run without a new code, so a stolen persistent session of a staff account has the privileges of that account for up to 14 days (also IBAN and PDF lists) unless a system administrator ends it (below) or the password changes. A privileged account without a second factor yet gets none (`session_timeout.start_session` checks `has_second_factor`). The wish lives on the request object or in the pending login, never in the session. **Mitigations that cost no usability** (D-100): every persistent session of a staff or system administrator account writes the security event `persistent_session_started` (long retention) and sends an email to every address of the account (kind `persistent_session_started`, text editable in "Mailtexte"); a system administrator ends all sessions of another account in the administration, "End all sessions" on the account page (`end_all_sessions`, security event `account_sessions_ended_by_admin`, long retention; not for the own account: a new password ends those). A new code for the IBAN or the PDF lists (step-up) was NOT built (usability); it is an option for the owner. Residual risk: `docs/SECURITY.md` section 3.
* **Log files and log page** (D-092; owner 2026-10-17): the logs are written to standard error (journald in production) and, with `LOG_DIRECTORY`, to `application.log` and `security.log` (`logfiles.py`: rotating, 10 MB x 5, files 0600 in a 0700 folder; default local `~/.leg-platform-dev/logs`, default stage/production `/var/log/leg-platform` with `LogsDirectory=leg-platform`, `off` = standard error only; a folder that cannot be used means no files). The system administrator's page "Protokolldateien" in the administration (`log_views.py`, `admin:logs*`; `is_superuser` only, as the security log, no right) lists, shows live (poll of an offset, bounded answers, pause/follow) and downloads (streamed) the files; fixed keys `application`/`security` plus backup number 0-5, never a client path; every line is redacted when read; opening and downloading are security events `log_viewed`/`log_downloaded` (long retention). The filter also removes email addresses, IBANs and database error values. Several processes write one file: the standard `RotatingFileHandler` does not coordinate rotation (Python `logging` cookbook: logging from multiple processes), so a rotation can reorder or drop older lines; the size stays bounded.

* **Mail content** (D-037, D-038, D-054, D-058): plain text only in phase 1 (HTML mail adds link spoofing, tracking and rendering risk; acceptance after the real Graph test send: click a link mail in Outlook, Apple Mail, Gmail and a Swiss webmail; if a link breaks add a line asking to copy the whole line into the address bar). SPF/DKIM/DMARC are DNS settings (installation guide). A failing send is logged by exception class only. Pages after a request show identical conditional text for every address; a test compares them.
* **Queue** (D-038): registration, reset and invitation requests only count the request and store one `MailJob`; nothing is read or sent in the request, so response and timing do not depend on the address. At-least-once; given up after 3 attempts; `cleanup_mail_requests` deletes unprocessed request jobs after 1 h and notifications after 24 h; jobs of a deleted account go with it (CASCADE).
* **Limits** (D-038; owner confirmed the hourly address limit 2026-10-13; OWASP gives no numbers): per normalised address 12/hour, 24/24 h, 3/10 min, shared by registration, reset and email change; per client IP 20/hour (IPv6 by /64, RFC 6177; undeterminable: one shared bucket + warning); instance-wide 300/hour for registration and 300/hour for reset, separate. Information email to an existing address: at most once per address per 24 h. Accepted: addresses sit in unprocessed jobs up to 1 h (a dump contains them); a failed information email loses its retry; an attacker knowing an address can use up its budget; the IP limit needs a correct `AXES_IPWARE_PROXY_COUNT`; the reverse proxy must limit the page request rate; no queue-age monitoring; the daily/IP limits and the 24 h link lifetime were never confirmed by the owner.
* **Editable email texts** (D-039): editable: registration link, information for an existing address, reset link, password change notification, the notifications of the second-factor and security flows and the invitation; only in the instance default language; subject and body. Permission `accounts.change_emailtext` (system administrators and staff holding it; in no default role, only for people trusted with the instance's communication); history visible to system administrators only; no second-person approval. Refuse a text without its personal link placeholder (`{verification_url}`, `{reset_url}`). Addresses cannot be typed into text or subject: after NFKC/format-character removal reject schemes (`https:`, `mailto:`, `tel:`), `//`, backslashes, `@`, words with a dot followed by two letters (incomplete deny-list; the permission is the protection); addresses arrive only via placeholders. Placeholders `{name}`: `{instance_name}`, `{contact_url}`, `{privacy_url}`, `{login_url}`; link emails also `{lifetime_hours}` and their own link; invitation `{lifetime_days}`; subject only `{instance_name}`. Max 5000 characters text, 150 subject; no control/format/separator characters (C*, Zl, Zp; line breaks and tabs allowed in body). If a saved text no longer validates when sending, use the default and log a warning with the email name only. `EmailText` (empty = default); every change is logged with email name and field names, never the text; `EmailTextVersion` on each changing save/restore (latest 100 per email); "Restore" needs change permission, POST only, re-validated, logged; "Preview" saves/logs/sends nothing; "Send a test email" goes only to the own address, prefix "[Test]", no limit (owner).
* **Greeting** (D-068): placeholder `{greeting}` only for the 14 `MailJob.NOTIFICATION_KINDS` (refused for other mails and in subjects; a test asserts the set). "Guten Tag Vorname Nachname" for a person account with both names, else neutral "Guten Tag" (company-only or one name gives neutral); built in `accounts/greeting.py`. Name guard `greeting.clean_name`: NFKC; categories Cc, Cf, Cs, Co, Cn, Zl, Zp and invisible marks/fillers are removed, whitespace collapsed; allowed only letters, combining marks (after a letter/mark, max 3 in a row), space, hyphen-minus, apostrophe (`'`, U+2019), period; any other character, a part without a letter, a part accepted by `email_texts.looks_like_an_address`, or more than 64 characters (`GREETING_NAME_MAX_LENGTH`) gives neutral; every uncertainty gives neutral; do not widen the list. * **Storage** (D-075; owner 2026-10-16, approved deviation from D-033/D-049/D-052): the directory is rebuildable public data in an OWN SQLite file (alias `addresses`, backend `leg_platform.addresses.sqlite`: file 0600, folders 0700, symlink at the file path refused, `O_CREAT|O_EXCL`, existing file narrowed via `O_NOFOLLOW` + `fchmod`), not in the main database or any backup, not shared between environments or instances, no import account or second settings module (no `ADDRESS_DB_*`, `ADDRESS_IMPORT_DB_*`, `import.env`). `Directory` and `Address` live in the file; `ImportRequest` (and `last_failed_repair_at`) stays in `default`; router `addresses/router.py`; `migrate` creates only directory tables in the file (`migrate addresses --database=addresses`, run by `setup_instance`). Every directory connection is read-only (`PRAGMA query_only = ON`) unless the process called `storage.mark_writer()` (`process_address_imports`, `import_address_directory`, `seed_local_address_directory`, `setup_instance`, the project's `migrate`, test settings) or, for its own thread only, `storage.mark_thread_writer()` (the import thread of the web process, D-090); this protects only against code mistakes. Path: optional `ADDRESS_DIRECTORY_FILE` (absolute, outside the repository, no control characters, not a folder); defaults `/var/lib/leg-platform/address-directory.sqlite3` (`StateDirectory=leg-platform`), local `~/.leg-platform-dev/address-directory.sqlite3`; one host only, no file system without working locks. SQLite: WAL, `synchronous = NORMAL`, `busy_timeout` 20 s, `transaction_mode = IMMEDIATE`; search over folded key columns (`street_key`, `house_number_key`, `locality_key`, `addresses/keys.py`) and ranges, not `LIKE`; indexes `addr_generation_postal_street`, `addr_generation_street`; no `ORDER BY` in the candidate query; `ANALYZE` after import. A missing, empty or unreadable file means silently no suggestions. Corrupted file: stop the web service and the worker (if used), delete file + `-wal`/`-shm`, start the setup unit and the services, use the button or wait (`docs/DEPLOYMENT.md` 10.2). Since D-090 the web process runs the import in its own thread (`runner.py`) and that thread is the only code of the web process that writes the file; `DirectoryFileSettingsTests` still fails if request-reachable modules import the importer or `requests`. Accepted: a compromised web process can write the file (wrong suggestions only, fixed by re-import) and can start the download from the two fixed addresses. Tests use a temporary SQLite file outside the repository; classes touching the directory declare `databases = {"default", "addresses"}`. Local: `manage.py seed_local_address_directory` writes eight invented addresses only with `APP_ENV=local` and refuses to replace a directory whose checksum is not `synthetic-local-directory` (D-053).
* **Import** (D-050, D-052, D-075, D-076, D-090; owner 2026-10-14, option C; changed 2026-10-17): the operator's import command stays; an admin button (dedicated permission, D-012) starts the same job; the web request itself never downloads: since D-090 the import runs in a thread of the web process (next bullet), the worker `process_address_imports` stays an optional alternative. Outbound HTTPS to `data.geo.admin.ch` is required; download controls: host allowlist, SHA-256 check, size limit, CSRF, permission, rate limit, no secrets in logs, the live register unchanged until the new one is complete. Schedule: one automatic attempt every 90 days (persisted before the download starts, also failed ones; first one due when none exists); a failure is logged and not retried before another 90 days; manual attempts may be repeated and do not change the schedule; concurrent requests are coalesced; while the directory is missing/empty an attempt is due after 24 h (`jobs.EMPTY_DIRECTORY_INTERVAL`); warning when the data date is older than 92 days. A new generation is loaded in chunks (`importer.CHUNK_ROWS` = 20,000), invisible until one short transaction switches `Directory.generation`; a lease on `Directory` (6 h) blocks parallel importers; `wal_checkpoint(TRUNCATE)` after; keep the new and previous generation, prune older ones in batches of 900 (SQLite < 3.32 allows 999 variables); a failed prune is logged, not failing the import; nothing is deleted if the import fails, the catalogue date is older than the stored `Directory.data_date`, or the checksum is unchanged; the file never shrinks (no `VACUUM`). The import refuses (job `failed`, nothing written) with less than `MIN_FREE_DISK_BYTES` = 4 GiB free on the file's folder or `tempfile.gettempdir()` (fail closed on `OSError`). A `running` job of the worker without heartbeat older than `jobs.RUNNING_JOB_LEASE` (6 h, equal to the importer lease; `jobs.py` must not import the importer at the top) or without start time is set `failed`; a job of the web process is dead after `jobs.HEARTBEAT_STALE_AFTER` (90 s) without heartbeat (D-090). A manual request (button) calls `import_directory(repair=True)`: it ends before any download if the published directory is the official file (same checksum), `PRAGMA quick_check` is `ok` and `Directory.row_count` equals the published rows and is > 0; otherwise it downloads a new generation; the automatic attempt trusts the checksum. A repair that failed blocks the next repair for 6 h (`importer.REPAIR_RETRY_INTERVAL`). Manual requests: 5/min per IP, 20/min per instance; each one passing the limit writes security event `address_import_requested` (actor only, normal retention). `ImportRequest` states in the application database; `importer._is_published` needs `row_count > 0`. `process_address_imports` loops unless `--once`.
* **Import in the web process** (D-090; owner 2026-10-17: no extra service, no cron job, visible progress and errors; supersedes the D-075 rule that the web process never downloads): (1) **Cause of "nothing happens"**: the button only queued a request; the queue was consumed only by the separate worker `process_address_imports`, which the local setup never starts and which a new instance did not have, so the page showed "queued" for ever, nothing was downloaded and no log line or security event was written after the request (the outcome was logged to the standard error output of the worker only). (2) **Design**: the button (and the automatic refresh, below) claims the single `ImportRequest` row in the database (`jobs.claim`, row lock, so one import at a time over all web workers; `claim_token`) and starts a **daemon thread** (`runner.py`, Python `threading`; Django opens one database connection per thread and the thread closes its own). Gunicorn is run with sync workers (`docs/DEPLOYMENT.md` 8.1): the thread works in that process; a worker recycle (`--max-requests`), a restart or a kill ends the thread, `atexit` marks the job interrupted where the interpreter still runs it, otherwise the next claim finds the stale heartbeat. The thread has a heartbeat thread that writes the progress (phase, bytes, rows) every 2 s; without a heartbeat for 90 s the job counts as dead and the next claim takes over and frees the lease of the dead import. The live directory is never touched before the new generation is complete, so an interrupted import changes nothing. (3) **Writing the file**: only the import thread writes the SQLite file (`storage.mark_thread_writer`, thread-local; `mark_writer` stays forbidden in `wsgi.py`/`asgi.py` and the request threads stay read-only). (4) **Status**: `status.build()` (state incl. `interrupted`, phase, download percent, counts, directory data date, import time, row count, file size, reason of a failure, the sentence about the automatic refresh) renders the page and is the JSON of `admin/addresses/importrequest/status/` (session and `addresses.request_directory_import`, GET only, `no-store`); the script `static/js/import-status.js` polls every 2 s while queued or running, textContent only, `aria-live`, stops at a login redirect or 401. (5) **Reasons**: only the fixed sentences of `importer.ImportFailure` (`jobs.SAFE_FAILURES`; a test compares them with the importer) reach the row, the page, the log and the security log, translated by `status.REASONS`; anything else is "failed unexpectedly" (the trace goes to the application log). (6) **Logs**: start, end and failure are written to logger `leg_platform.addresses` (INFO/ERROR; application log file and standard error) and to the security log (`address_import_succeeded`/`address_import_failed`, detail = kind and fixed reason or count; the request keeps `address_import_requested`). (7) **Automatic refresh without a scheduler**: `runner.maybe_start_automatic()` is called by the administration start page and the management overview (authenticated staff only; at most one claim attempt per 5 minutes per process, `runner.AUTOMATIC_CHECK_INTERVAL`) and starts the import when it is due (90 days; 24 hours while there is no directory; the attempt is stored before the download). It needs no cron job or service; it only happens while somebody signs in, which the page says. `ADDRESS_IMPORT_AUTOMATIC=False` turns it off (then only the button or the worker update). Both the worker and the web thread claim the same row, so they cannot run twice. (8) Tests never start a real thread or download (test settings: no automatic import; thread tests use a stand-in for the importer). Sources (checked 2026-10-17): Python documentation, `threading` ("Daemon threads are abruptly stopped at shutdown", `threading.local`); Django source `django/db/utils.py` of the installed version (`ConnectionHandler.thread_critical = True`: one connection per thread, so a thread opens and closes its own); Gunicorn design page https://gunicorn.org/design/ (pre-fork workers, `sync` = one request per worker).
