  * Collation `utf8mb4_uca1400_ai_ci` exists in 10.11 and 12.3; never `utf8mb4_0900_ai_ci` (alias only from 11.4.5).   `REFERENCES` not granted. Source: Django "Databases".
* **UI framework** (D-003): Tabler for the application, Django admin for system administration; no second framework. Browsers: Chrome/Edge 123, Firefox 128, Safari 17.5, Opera 109. Phones fully usable in phase 1.
* **Version policy** (D-015, D-026): declare only minimums: the oldest version still receiving vendor security updates, from official sources, proven by tests (CI runs minimum and latest). Raise a minimum when vendor support ends. Versions chosen for use: newest compatible release, for LTS tracks the newest of the track (owner, 2026-10-11). Never support an old version through a package with known vulnerabilities.
* **Minimums** (owner 2026-10-11; `pyproject.toml`, `requirements/minimum-constraints.txt`): Python 3.12; Django 6.0 (`>=6.0.9,<6.2`, built-in CSP; fixes end April 2027: raise by then); MariaDB 10.11; `mysqlclient` 2.3.0; `django-axes` 8.3.1; `django-ipware` 8.0.0; `django-otp` 1.7.4; `cryptography` 50.0.2; `segno` 1.6.6 (TOTP QR); `msal` 1.39.0; Tabler 1.6.1; `requests` 2.34.2 (D-048); `reportlab` 5.0.1 (D-083); `python-stdnum` 2.2 (D-087); `django-countries` 9.1.0; `django-phonenumber-field` 8.5.0; `phonenumberslite` 9.0.41; `idna` 3.15+ (below: CVE-2026-45409) (D-034).

Django 6.0 lacks `MAILERS`: settings keep both branches (`MAILERS` 6.1+, `EMAIL_BACKEND` 6.0). `django-axes` 8.3.1 declares Django up to 6.0: fall back to 6.0 if 6.1 fails. `msal` caps `cryptography` below 51.

* **Billing** (D-009): none in phase 1.

## 2. Language and translation

* **English repository** (D-010): code, identifiers, schema, stored keys, migrations, permission codenames, comments, commits, logs, tests, configuration, URL paths, documents. Only the UI is localized: `LANGUAGE_CODE = "de-ch"` is the instance default; French, Italian and English can be chosen (D-056, below).
* **UI texts** (D-010, D-036): translatable (English source), Swiss German in `locale/de_CH/LC_MESSAGES/django.po` (`LOCALE_PATHS`).
  * Never the German sharp s (eszett): `de_CH` falls back to `de`, so the catalogue overrides every such text (Django, contrib, third-party; e.g. UK country name, D-034). Automated check; recheck at each Django upgrade and new package.
  * Missing translations and sharp s are defects. Commit `.mo` next to `.po`; CI: `msgfmt --check`, compare `msgunfmt` (D-034). Keep every placeholder. A literal "%" in `{% translate %}` needs "%%": use placeholders (D-080).
* **Wording** (D-036, owner): everyday terms ("company name", "address addition", "post office box", "account", "system administrator"), no invented technical terms; admin titles "LEG Platform"/"Administration", never "Django". LEG-specific texts are catalogue content that another instance replaces.
* **Languages** (D-056, D-074): `LANGUAGES` are `de-ch` (Deutsch, the instance default), `fr`, `it`, `en`; every server-rendered text follows the chosen language. `en` is the English source text and has no catalogue. `locale/fr` and `locale/it` hold `django.po` and `djangojs.po` with the entries of `locale/de_CH` (`REQUIRE_COMPLETE_CATALOGS` in `accounts/tests/test_translations.py` switches the completeness test on).
  * Only the language cookie chooses (`leg_platform.language.ChosenLanguageMiddleware`, subclass of `LocaleMiddleware`); never the `Accept-Language` header. A text without a translation is shown in English (`install_english_fallback`), never in German.
  * Emails, the mail worker and every text outside a request stay in the instance default language (`translation.override(settings.LANGUAGE_CODE)`).
* **Fact-based work** (D-011): no assumptions; sources are project state and official documents (vendor, law, OWASP/IETF/W3C, owner); never blogs, forums, news, SEO, AI text. Ask when in doubt (`AGENTS.md` section 3).

## 3. Instances, configuration, hosting

* **One instance per municipality** (D-013): not multi-tenant; own database, configuration, secrets, users, system administrators; no shared data or central administration; one account per person and instance. One code base; instance values (names, domain, base URL, sender, contacts) are configuration, never in code, templates or migrations. Source: StromVG Art. 17d para. 3 (an LEG covers at most one municipality).
* **Host name** (D-013, D-025): `ALLOWED_HOSTS` only own hosts; never read `Host` from `request.META` (use `request.get_host()`); email links from `INSTANCE_BASE_URL`.
  * Own host name, never a website path (shared origin, RFC 6454, RFC 6265 8.5/8.6). `SameSite` does not protect between subdomains.
  * `SESSION_COOKIE_DOMAIN`/`CSRF_COOKIE_DOMAIN` unset. `CSRF_TRUSTED_ORIGINS` never holds the website or a parent wildcard. Stage/production cookies use the `__Host-` prefix.
* **Entry point** (D-025): no public home page; the entry is the login page (login, reset, registration, links to privacy notice and instance website).
* **Environment configuration** (D-027, D-028, D-037): environment variables validated in `leg_platform/environment.py`; invalid or unsafe values stop the start.
  * Outside `APP_ENV=local`: `DJANGO_SECRET_KEY` and fallback keys meet `security.W009` (>= 50 chars, >= 5 unique, no `django-insecure-`); `DJANGO_ALLOWED_HOSTS` required; `DJANGO_CSRF_TRUSTED_ORIGINS` only `https://`. Wildcards (`*`, leading `.`) rejected; numbers ASCII digits only; ports 1..65535.
  * `SECURE_PROXY_SSL_HEADER` only via `DJANGO_SECURE_PROXY_SSL_HEADER`. HSTS in stage/production, default one year (`DJANGO_SECURE_HSTS_SECONDS`, lowerable, not disableable); `SECURE_HSTS_INCLUDE_SUBDOMAINS` only with `DJANGO_SECURE_HSTS_INCLUDE_SUBDOMAINS=True` (`security.W005` silenced only while off); `SECURE_HSTS_PRELOAD` never (irreversible); `security.W021` silenced.
  * Logging: warnings/errors to stderr; no email to `ADMINS`. `DEFAULT_EXCEPTION_REPORTER_FILTER = "leg_platform.debug.ExceptionReporterFilter"` masks `EMAIL_ALLOWED_RECIPIENTS`.
* **Instance values** (D-037): `INSTANCE_NAME` (default "LEG Platform", max 100, no control or line-separator characters); `INSTANCE_BASE_URL` (`https://` origin without path or credentials; `http://` only with `APP_ENV=local`; required elsewhere; host in `DJANGO_ALLOWED_HOSTS`); `INSTANCE_PRIVACY_URL` (absolute `https://`, required outside local); `INSTANCE_WEBSITE_URL` (optional). The privacy notice is linked on every page without login, also the lockout page. Branding: section 12.
* **Environments** (D-070): `APP_ENV=stage` is only a label; no code branches on it. Stage must not differ from production (owner 2026-10-16; approved deviation from `docs/SECURITY.md` section 8): HTTPS, cookies, HSTS, CSP, limits, validation, secret rules.
  * Stage and production require `EMAIL_MODE=graph` and refuse `console`, `allowlist` and a non-empty `EMAIL_ALLOWED_RECIPIENTS`. Stage has own database, `DJANGO_SECRET_KEY`, Graph app registration and certificate; no production data or secrets (D-013, D-020). Real personal data on stage counts like production.
  * Accepted risks: real mail to typed addresses (not recallable); the registration form allows up to 300 mails/hour to third parties (production limits apply, section 8).
  * Stage procedures: `docs/DEPLOYMENT.md` 5.3/5.4, `docs/OPERATIONS.md`.
* **Hosting** (D-008, D-074): Ittigen production runs on an Infomaniak "VPS Lite 1" with MariaDB (owner statement; assume nothing else). SSH is needed for management commands. Vendor facts: no security software, no SLA, no Infomaniak backup, outgoing port 25 not openable.
* **Deployment** (D-053, D-064, D-076): `docs/STARTUP.md` is the one local-environment document (agents never print the environment, never read `.env`, never delete seeded accounts, stop processes only by process ID). `docs/DEPLOYMENT.md`: direct deployment without containers (venv, Gunicorn, nginx, MariaDB 12.3 from the MariaDB Foundation repository, Certbot, systemd units and timer; secrets only in root-owned 0600 environment files); a proposal not yet run on a server; section 0.5 is the entry for a deployment request.
  * Stage: the release branch resolved once to a SHA. Production: the release accepted on stage (same full SHA) with explicit per-deployment approval. Verify both CI variants for the exact SHA.
  * Update: quiesce writers; wait for the importer, never interrupt it; back up (also on stage); migrate; refresh static files; restart; verify. Destructive migrations, restores and security exceptions stay approval boundaries.
  * Forbidden: unattended-password pseudo-terminal script, fake privacy URL default, automatic self-signed TLS fallback, skipping the stage backup, treating the importer as one-shot. Owner decisions O-1..O-23: `docs/DEPLOYMENT.md` section 1.
  * One reverse proxy on the same host: nginx overwrites `X-Forwarded-For` with `"$remote_addr, 127.0.0.1"` and `AXES_IPWARE_PROXY_COUNT=1` (count 0 resolves every visitor to `127.0.0.1`; count 1 works only with a header of exactly two entries).
* **First start** (D-005, D-076; owner 2026-10-16): no manual account creation; empty database + environment file + start = working instance.
  * `manage.py setup_instance` is idempotent, runs on every start under one named MariaDB lock (`GET_LOCK`, hashed name, waits at most 600 s): `migrate --noinput` (never `flush`); initial system administrator; `migrate addresses --database=addresses`. Prints no secrets.
  * Administrator: locked `create_superuser()` from `BOOTSTRAP_SYSTEM_ADMIN_EMAIL`/`BOOTSTRAP_SYSTEM_ADMIN_PASSWORD`, `password_change_required=True`, security log entry; only when `accounts_user` has no row. Accounts but no superuser: create nothing, write `System administrator: NONE EXISTS, but accounts exist ...` to stderr, exit 0 (advice: restore a backup or run interactive `setup_initial_administrator`; `emergency_access` grants no admin rights). Missing or weak password, email without password, password without email on an empty table: fail the unit.
  * Password: project validators (min 8 chars, owner decision 2026-11-01, D-004); never in messages or arguments; not read while a superuser exists; not a Django setting (`environment.parse_bootstrap_administrator()`); `PASS` in the name so reports mask it; only letters, digits, `-`, `_`, `.` (systemd `EnvironmentFile=` quoting). A human types it; an AI never generates or sees it.
  * The directory step never blocks the start (failure: stderr with class only, exit 0, retried next start); a failure of the main database or of a configured administrator fails the command.
  * Directory step (owner 2026-10-22): `addresses.setup.prepare_directory`. A missing or changed catalogue schema is created/rebuilt and its official import is queued durably in MariaDB before setup returns. Setup performs no network import and does not wait for the download. Current clean files do not requeue on each start, even when empty after an import failure.
  * Units: `docs/DEPLOYMENT.md` 8.0. Never `systemctl stop|restart leg-setup` and never `StartLimitIntervalSec=0`. Migrations run at every start without backup: change code only via the update runbook (`docs/DEPLOYMENT.md` 12.3, backup first).
* **Initial administrator** (D-005, D-041): only by server command, never via the website (a first visitor could take over); only while no system administrator exists; never overwrites or resets an account. `setup_initial_administrator` reads `BOOTSTRAP_SYSTEM_ADMIN_EMAIL`, asks twice for the password with `getpass` (refuses without a terminal that hides input), refuses while any `is_superuser` exists. `createsuperuser` stays disabled.
  * `password_change_required`: only password change and logout work (`SecondFactorMiddleware`); admin closed (also `PortalAdminSite.has_permission()`); the new password must differ. Password change or reset by link clears the flag; then the second factor must be set up.
  * Accepted risk (owner): the initial password sits in the environment file (0600 root), no expiry; whoever knows it and logs in first can take over. The instance must not be publicly reachable until the owner has logged in, changed the password and enrolled the second factor; restart services after removing the variable. A take-over shows as a failed first login or an unexplained `PASSWORD_CHANGED`. The security log entry is written after commit (accepted).
* **Emergency commands** (D-005, D-041, D-044): `manage.py emergency_access`: `reset-second-factor N` (any account, also the last system administrator), `unblock-account N`, `reencrypt-second-factor-keys`. Typed confirmation (`--no-input` skips); prints only the internal number; every use logged for the long retention; server only (`docs/INSTALLATION.md`).
* **Seed accounts** (D-019, D-042): `seed_design_accounts` creates throw-away accounts of every access level for local design work. Refuses outside `APP_ENV=local`; writes credentials only to a file outside the repository, never prints them; creates no role or permission.
* **Scheduled tasks** (D-041, D-068): `manage.py run_scheduled_tasks` runs the cleanup and deadline commands (list: `run_scheduled_tasks` in code) and, last, `scheduled_address_import` (section 10; it can take minutes). `process_application_deadlines` queues mails and deletes only drafts (D-103). A failing task does not stop the others and fails the command. A test requires every `cleanup_*`/`delete_expired_*` command of the accounts app to be included. The systemd timer is hosting (`docs/INSTALLATION.md`).
* **Backups** (D-016, D-075): operator's duty; deleted data may persist in backups until expiry. Backup = MariaDB + environment file; the address directory is in no backup. Replacing `SECRET_KEY` without `SECRET_KEY_FALLBACKS` invalidates pending links and makes encrypted values unreadable (second-factor keys, IBANs, Graph key).

## 4. Roles and access

* **Three fixed access levels** (D-012): system administrator (`is_superuser` + `is_staff`, all permissions), staff user (`is_staff`, assigned permissions only), authenticated user (own profile only). Other roles are Django groups created at runtime in the admin.
  * Never hard-code roles: no code, migration or fixture creates, names or checks a group. Authorization checks permissions, never group names; codenames English; tests create their own groups. No predefined role or rights set (D-061).
  * New users have no groups, permissions, `is_staff`, `is_superuser`. Nobody promotes themselves; `is_superuser` only by another system administrator; every promotion is logged.
  * Only system administrators manage roles, permissions, assignments, `is_staff`, `is_superuser`, enforced technically, also against staff holding add/change-user permissions (Django: equals superuser). Delegation needs a separate reviewed decision.
  * Staff never change, block, deactivate or delete staff or system administrator accounts (also not their own in the admin), nor another account's password, email or second factor. System administrators can block each other and remove rights; at least one active, unblocked system administrator always remains (emergency: section 3) (D-016).
* **Rights only with a second factor** (D-042, D-043, D-106; owner 2026-10-14): the administration grants `is_staff`/`is_superuser` only to an account with a confirmed authenticator app or an active passkey (`second_factor.has_second_factor()`; an unconfirmed app or recovery codes alone do not count). The form refuses with a translated message; `save_model()` rechecks on the locked account row (403). Removing rights is always possible; groups and direct permissions are not restricted.
  * The rule lives only in the administration (`UserAdminForm._clean_privileges`, `UserAdmin.save_model`). Other code granting `is_staff`/`is_superuser` must implement the same check with a test; every review checks this. A passkey label is not evidence of device identity; D-106 requires no separate device statement.
  * Gaps: the initial administrator and staff after a second-factor reset set up the factor at next login. A password reset keeps `is_staff`, `is_superuser`, groups, permissions. If permissions are later used outside the administration for non-staff, decide again whether they need a second factor.
* **Management area exception** (D-086, D-087; owner 2026-10-17; approved deviation from D-012; wins over D-077/D-079/D-080/D-081/D-084): `/management/` uses NO Django permissions. Every active staff user or system administrator with a completed second factor may use every page and function there (policy: `leg_platform/management/access.py`, section 13). The rest of D-012 stays; the Django admin and functions outside the area stay permission-protected.
  * Staff may change customer profile data there, never password, login email, second factor, status, `is_staff`, `is_superuser`, groups, permissions, retention flag or customer number of any account (D-087). A later financial module may need four-eyes separation: assess before building (D-012, D-086).

## 5. Accounts and lifecycle

* **Lifecycle** (D-016): login after email verification and a chosen sign-in method (password, password and app, or passkey); no approval. No sign-in method is set before the address is verified: the choice and its setup follow the verification link, never the first step (attackers could register a victim's address with a known password or key). States: unverified, active, blocked, deactivated (plus temporary lockout, `docs/PROJECT.md`).
  * Unverified accounts are deleted when the link expires; a new registration with the same address replaces a pending one. System administrators block/unblock any account. Blocked accounts cannot log in or reset passwords; during a temporary lockout reset works.
* **Retention flag** (D-016, D-086): one-way (unset to set only; otherwise rejected, also in the admin; DB privileges restricted, `docs/SECURITY.md` section 9). Deleting an account without it removes all data (security log entries lose the personal reference, D-018). With it the account is deactivated: no login or reset, responses never reveal existence, the user cannot reactivate; a system administrator can, unless an active/locked/blocked account has the same email. Assigning a person to a metering point with an assignment in force sets it (section 13); so does accepting the contract (D-103).
* **Email uniqueness** (D-016, D-034): unique among non-deactivated accounts via nullable `normalized_email` + a normal unique index (MariaDB has no conditional unique constraints; UNIQUE allows several NULLs); NULL while deactivated.
* **Protection rules** (D-016): the last active, unblocked system administrator cannot be deleted, deactivated, blocked or lose superuser status.
  * Email change: effective after verifying the new address (old valid until then), needs re-authentication, old address notified.
  * Registration or change to the address of an active, locked or blocked account does nothing; the response equals success and that address gets an information email. Confirming an email change or reactivation deletes a pending unverified registration for that address.
  * Every delete/deactivate/reactivate/block/unblock/promote/demote/email-change/retention-flag path uses the central account logic, also admin bulk actions (Django's "delete selected" skips `delete()`).
* **Deletion by the user** (D-055, D-105, D-127; owner 2026-10-19, 2026-10-24 and 2026-10-29): The account can always be deleted, at once and for good; nothing has to be deregistered first. The deletion withdraws or deletes the applications and deregisters every running and not yet active metering point in one deregistration (`community/account_deletion.py`). An application already registered at the grid operator is deleted too; the staff gets a notice (kind `account_deleted`, EGID and numbers) to withdraw the registration there. The sign-in (password, passkeys, app, recovery codes) is deleted in every case; an account under the retention duty (retention obligation or a metering point assignment) stays `deactivated` with the details the law requires (`User.delete_or_deactivate`). Page "Delete account" with the one proof; a customer who takes part first sees the fork (D-127). Legal assessment of the wording (DSG Art. 6, 19, 25) unverified, owner's responsibility.
* **Customer number** (D-021, D-034, D-038): six random digits (`secrets.randbelow(10**6)`, max 100 retries), unique, never reused, text, shown `482 915`, read-only. Assigned once at completion of registration (or by the setup command for the initial administrator) by `assign_customer_number()` for a saved, active account without one; kept on email change and reactivation; unverified accounts have none.
  * `IssuedCustomerNumber` holds every number ever issued without person reference (immutable). `User.customer_number` is a one-to-one FK (`PROTECT`, `utf8mb4_bin`). An identifier, not a secret.
  * Max 1,000,000 numbers: from 90 % issued (`CUSTOMER_NUMBER_WARNING_PERCENT`) each issue logs a warning and the admin user list shows a notice to system administrators only; at 100 % registration completion fails (500). Login is by email only: counting failures across email and number would reveal whether they belong to one account.
* **Email canonical form** (D-021, D-035): local part ASCII only (no SMTPUTF8, RFC 6531 section 3.4). `email` stores NFKC, trimmed, whole address lower case, IDN domain as IDNA ASCII (UTS #46), derived in `save()`; `normalized_email` equals it unless deactivated. Lookups, counters, rate limits use `normalize_email_address()`. Validation rejects non-ASCII local parts, quoted local parts, domain literals, IPs, `localhost`, Unicode categories C/Z/M. `idna` is a direct dependency.
  * Owner decision 2026-10-12: the local part is lower-cased although RFC 5321 section 2.4 calls it case sensitive. Risk: on a case-distinguishing host mail could reach another mailbox; mitigated because all mail goes to the canonical stored address.
* **User model** (D-034, D-051): `leg_platform.accounts`, `accounts.User` from the first migration; profile fields on it. `USERNAME_FIELD = normalized_email` (unique, nullable, not editable, `utf8mb4_bin`).
  * Invariants in the model: `is_active` derived from status; unverified accounts have no customer number or usable password; `create_superuser()` refuses while any `is_superuser` exists; customer number never changes; retention flag only unset -> set.
  * Status, `is_active`, email, normalised email, retention flag, `is_staff`, `is_superuser`, customer number and password change only via `set_status()`, `change_email()`, `set_privileges()`, `assign_customer_number()`, `set_retention_obligation()`/`create_user()`. `QuerySet.update()` of these fields, `delete()`, `bulk_create()` are rejected (also base manager, `Meta.base_manager_name = "objects"`). `save()` of an existing account compares them with the `FOR UPDATE`-locked row. `delete()` refuses accounts with a retention obligation and the last active system administrator.
  * Not covered (DB privileges, `docs/SECURITY.md` section 9): raw SQL, `QuerySet._update()`, `loaddata`, many-to-many managers (`user.groups.add()`); no fixtures with accounts. Deleting an account deletes its admin log entries (owner accepted 2026-10-12).
* **Profile data** (D-032, D-034, D-036): fields follow eCH-0010 8.1.0 (https://www.ech.ch/de/ech/ech-0010; lengths per `eCH-0010-8-0.xsd`); all fields exist even if hidden.
  * Person: salutation (Mrs/Mr/Family/empty), title, first and last name. Organisation: name + two add-ons. Organisation name OR first+last name required. One account = one person or organisation.
  * Address: two lines, street, house number (text), dwelling number, PO box number (integer up to 8 digits) and text, locality, town, postal code, country (`CountryField`, default `CH`). Required: postal code, town, country, and street or PO box (owner 2026-10-12); postal town, not political municipality. At registration only email; the rest after the verification link.
  * Phone optional (`PhoneNumberField`, `PHONENUMBER_DEFAULT_REGION = "CH"`, `PHONENUMBER_DB_FORMAT = "E164"`; declare `phonenumberslite`). Cross-field rules in `User.clean()`/`clean_fields()`.
  * Forms hide title, organisation add-ons, address line 2, dwelling number, PO box text, locality; validation never requires a hidden field, saving keeps stored values. An eCH export must fill the PO box text (e.g. "Postfach") when a PO box number exists. One "postal code" field: `CH` -> `swiss_postal_code` (4 digits 1000-9999); other countries (also `LI`, until eCH/owner clarify) -> `foreign_postal_code` (required, up to 15); the other is cleared.
* **Admin neutrality** (D-018, D-036): `User.__str__` = "Account 686 821" or "Unconfirmed account", never email or name. `LogEntry.object_repr` = "Account with internal number N" (`UserAdmin` overrides `log_addition`, `log_change`, `log_deletions`, not `log_actions()`); future admin code logging an account as related object keeps this, with a test. Account history: system administrators only (`UserAdmin.history_view()` 403 before any lookup). The user list shows/sorts/searches by customer number, not internal ID. The duplicate-email message exists only for the later email change; registration answers duplicates generically (`docs/SECURITY.md` section 3).
* **Collations and connection** (D-028, D-031): create every instance database with `CHARACTER SET utf8mb4 COLLATE utf8mb4_uca1400_ai_ci` (MariaDB default charset is `latin1` up to 11.5); Django test DB via `TEST["CHARSET"]`/`TEST["COLLATION"]`. Exactly compared identifier columns use `utf8mb4_bin` (`db_collation`): normalised email, tokens/keyed hashes, recovery codes, customer number.
  * Connection: `isolation_level` "read committed" (repeatable read can lose data), `charset` utf8mb4, `sql_mode` via `OPTIONS["init_command"]` = `STRICT_TRANS_TABLES,ERROR_FOR_DIVISION_BY_ZERO,NO_AUTO_CREATE_USER,NO_ENGINE_SUBSTITUTION`. Check `mysql.W002` (CI `--database default`); tests tagged `mariadb` verify it. Source: Django "Model field reference" (`db_collation`); MariaDB "Supported Character Sets and Collations".
* **Password hashing** (D-023): Django default PBKDF2-HMAC-SHA256 at the installed version's default work factor; never below it or OWASP's 600,000 iterations. Not raised for now (measure one hash on the real server; OWASP: under one second; higher needs a new decision). Argon2id not chosen. Source: Django passwords docs; OWASP Password Storage Cheat Sheet.
* **Keyed hashes** (D-017, D-023): counters and tokens store HMAC-SHA256 digests under a key derived from `SECRET_KEY` via HKDF with an own label per purpose (`cryptography`; prefer `django.utils.crypto.salted_hmac`; `keyed_digest` also reads with `SECRET_KEY_FALLBACKS`). Rotation resets counters (accepted). A leaked `SECRET_KEY` lets hashes be reversed with address lists; short retention limits the impact. Raw IPs and identifiers exist only in request memory.
* **Encrypted secrets** (D-006, D-040, D-087): secrets read back (Graph private key, TOTP key, IBAN) are Fernet-encrypted under an HKDF key from `SECRET_KEY` with an own label (`LEG-Platform Microsoft Graph certificate key v1`, `LEG-Platform person IBAN v1`; `leg_platform/accounts/encryption.py`). `SECRET_KEY_FALLBACKS` keys are tried; the value is re-encrypted on use or by the re-encrypt commands. An undecryptable value shows nothing and is logged without content.

## 6. Authentication, second factor, confirmation links

* **Login** (D-004, D-021, D-037): email + password via Django `LoginView`; one message for every failure; a nonexistent email behaves like a wrong password; no user for inactive accounts; `redirect_authenticated_user` off; `/logout/` POST only. Pages with forms, tokens or personal data send `Cache-Control: no-store`.
  * Passwords (OWASP Authentication Cheat Sheet; NIST SP 800-63B-4 Appendix A): Django validators, minimum 8 characters for ALL accounts (customers, staff, system administrators, the bootstrap administrator), maximum at least 64, no composition rules; the validators for user-attribute similarity, common passwords and all-numeric passwords stay. Texts shown to users state only the real policy. **Owner decision 2026-11-01 (amends the earlier minimum of 15):** usability over strictness; LEG is a simple platform of low value and older users could not cope with 15 characters. **Accepted risk:** OWASP asks for 15 characters when the password is the only factor and accepts 8 with multi-factor authentication; NIST SP 800-63B-4 asks for 15 (single factor) or 8 (as part of multi-factor). The owner accepts the deviation for customers, who may use the password alone, because the platform holds little of value. **Mitigations:** login lockout and rate limits (D-028), the common-password blocklist, optional app/passkey sign-in for everyone and mandatory second factor for staff and system administrators (D-016).
* **Second factor policy** (D-004): TOTP (authenticator app) mandatory for staff and system administrators, optional for users (they may turn it off; staff and administrators cannot). A password reset never removes or bypasses it; recovery must not bypass MFA (OWASP MFA Cheat Sheet). D-106: any account may use a passkey; for staff users and administrators it is the second factor.
  * Library `django-otp`; the completed factor is checked centrally, independent of method. Passkeys: D-106 (`docs/PROJECT.md`, "Passkeys").
* **Central check** (D-040, D-041): `leg_platform/accounts/second_factor.py` (`requires_second_factor()`, `has_second_factor()`, `is_second_factor_complete()`, fails closed without the middleware). `SecondFactorMiddleware`: such a session has no privileges without the factor (only logout/setup open); promotion applies in an open session; `PortalAdminSite.has_permission()` checks it too; the admin has no own login page.
  * The mandatory factor is set up in the restricted session at first login (owner 2026-10-13). Accepted: anyone knowing the password of a newly promoted account or the initial administrator can enrol first (no privileges; the owner is notified by email; reset is the recovery).
* **Devices and secrets** (D-040, D-054, D-062): `AuthenticatorDevice` (TOTP 30 s, 6 digits, SHA-1, one step tolerance, a used code is not reusable; one app per account, DB-enforced; only a confirmed app counts) and `RecoveryCodeDevice`/`RecoveryCode`. `django-otp` device throttling is NOT used (someone knowing the password could lock the owner out). Issuer = `INSTANCE_NAME`. Devices are not in the administration.
  * TOTP key (160 bits) Fernet-encrypted (section 5). Ten recovery codes (8 chars `a-z2-7`, 40 bits, shown once, a new set invalidates the old), keyed digests only, unique per device (`accounts_recovery_code_unique_per_device`), single use by one `DELETE`. The term is "recovery code".
  * Setup asks for the password unless the session is recent. An unconfirmed secret is valid 15 min, bound to the starting session. The QR code is an own SVG (`no-store`, no `data:` image). The factor is on only after a correct code. Recovery codes appear once in the POST answer that creates them (never stored plain or in the session; `no-store`, `sensitive_post_parameters`) with a server-checked "I saved the codes" checkbox. Notifications without link for setup, removal, renewed codes, used recovery code.
* **Two-step login** (D-040): no `login()` after the password if a factor exists. The pending login (account, time, safe redirect, password session hash) lives in the session for 5 minutes and ends if the account becomes inactive, the factor is gone or the password changed. `/login/two-factor/` takes an app or recovery code (`otp_token`, masked by Axes). Each attempt passes the Axes lockout check and takes its own IP slot; a wrong code is a failed attempt of account and IP, under the account row lock. Session ID renewed at each step. "Stay signed in": D-100.
* **Wrong-code budget at login** (D-040; owner 2026-10-13, small residual risk accepted): `AuthenticatorDevice` counts wrong codes in 24 h from the first (`failed_codes`, `failed_codes_since`); only wrong codes that reach the check count (not Axes/pause refusals or wrong passwords).
  * At 10: one email without link per window + log line (outside the mail budgets). At 15: code entry paused until the window ends, also for a correct code (lockout page with reset link; does not extend the Axes lockout). A completed password reset relieves to at most 10, once per window.
  * A successful login does not clear the budget (deviation from NIST SP 800-63B-4 section 3.2.2, accepted). No escalating cool-off (someone knowing only the email could lock an account). Accepted: anyone knowing only the password can pause code entry for 24 h.
* **Automated attacks** (D-017; owner 2026-10-12): `django-axes` for temporary lockouts per normalised account identifier + a separate transactional MariaDB counter per client IP (Axes shares rows, so account resets would lower IP counts).
  * Limits: 5 failed attempts in a rolling 15 minutes for account and IP each; 15-minute cool-off (`LOGIN_COOLOFF`; the lockout page names the real duration). Completing all factors releases the IP slot; failures keep it until the window ends. An account reset clears only Axes account rows, never the IP counter.
  * Identifiers and IPs only as keyed digests. POST `password`, `otp_token`, `otp_device` masked (`AXES_SENSITIVE_PARAMETERS`). Axes admin disabled until a read-only, system-administrator-only view exists.
  * Client IP = `REMOTE_ADDR`, forwarded headers ignored (`AXES_IPWARE_PROXY_COUNT=0`); behind proxies the operator sets the exact trusted proxy count first. A lockout is recorded only when the failure reaching the limit is counted (Axes 8.3.1 also signals refused attempts during a lockout).
  * Accepted risk: someone knowing an email can repeatedly trigger temporary lockouts and use up the per-address mail limit. Sources: django-axes 8.3.1 docs, django-ipware; OWASP (a lockout must not enable denial of service; recovery stays possible while locked).
  * Lockout response `AXES_LOCKOUT_CALLABLE = "leg_platform.accounts.axes_handler.lockout_response"` (lockout template, `AXES_HTTP_RESPONSE_CODE` 429, never-cache, same HTML for XHR and for the second-factor pause; never shows the submitted value). No middleware or `AxesMiddleware` subclass: django-axes' JSON answer echoes the username and sets `Access-Control-Allow-Origin` from `AXES_ALLOWED_CORS_ORIGINS` (default `"*"`).
* **Lock order** (D-072): account row first, then counter rows (`LoginIpBucket`/`LoginIpAttempt`, `SessionCodeFailure`, `ConfirmationFailure`); an inverted order causes MariaDB 1213 deadlocks. Cleanup commands lock per account with `skip_locked`, never wait. Never `nowait`: waits end at `innodb_lock_wait_timeout`, then 1205/1213 = HTTP 500, nothing accepted, no oracle, no retry. Do not widen the application DB account with `PROCESS`. Operators check the `EXPLAIN DELETE` plans (`docs/DEPLOYMENT.md` 12.4).
* **Registration** (D-016, D-037, D-058): three steps.
  * Step 1 asks the address only (D-136: a six-digit code instead of a link, entered on the page "Enter code" of the same tab; challenge row for every address, account created when the code is confirmed; the link below stays for invitations and the other flows). The next page is identical for every address. Active, temporarily locked or blocked account -> one identical information email without link or code (no IP/agent/time; no reply asked). Deactivated accounts do not hold their address. Duplicates never give a form error. "Send again" after a 60 s pause enforced on the server; D-038 limits apply to every resend.
  * Mail goes to the canonical stored address, never the entered spelling (IDNA 2003 vs UTS #46 mismatch could bind an account to a domain the attacker does not control).
  * Step 2: choice of the sign-in method (D-106) and its setup, staged and bound to the link digest (`accounts/registration_methods.py`). Password page: the verified address is plain text (no form control); a hidden read-only `username` field (`autocomplete="username"`, `aria-hidden`) gives the password manager the account context and the server ignores its posted value; both password fields are `new-password` (the same after a reset link, `accounts/_account_name.html`); the password is held only as a hash in the session. App: QR code and first code (device confirmed on the unverified account; its 10 recovery codes are made at step 3 and shown once). Passkey: the ceremony (inactive credential, fixed name "My passkey"). A new choice deletes what an earlier one staged; step 3 keeps only what belongs to the chosen method. Step 3: names, street, house number, postal code, town, privacy checkbox (stored: `privacy_accepted_at`, `privacy_accepted_url`).
  * Only the last step activates the account: status, customer number, password (a passkey account: the staged keys are switched on and no password is set) in one transaction with locks on account (first) and link, then login. `User.complete_registration()` is the only place a customer number is issued.
  * The proof of a new registration (the confirmed code, D-136) lasts 2 hours; the link of an invitation stays valid until step 3 completes or its lifetime passes (mail scanners, back button; no text may call it single use). Opening it calls `cycle_key`.
* **Token links** (D-037, D-038, D-058, D-067): token = `secrets.token_urlsafe(32)`, stored only as keyed digest (`VerificationToken`, own HKDF label). Opening a link stores the digest in the session and redirects to the form page (scanners cannot consume it); the token is consumed only when the form succeeds (row lock; `sensitive_post_parameters`).
  * Token pages send `Referrer-Policy: no-referrer` and `never_cache`; no form is served under `no-referrer` (POST would send `Origin: null`, which CSRF refuses); form views after the redirect use `same-origin`.
  * Every invalid, expired, used or replaced token, non-active account, stop link without open request, or removal link without usable second factor answers `302` to a fixed page (`/email-change/expired/`, `/email-change/stop-expired/`, `/two-factor-reset/expired/`; registration and reset to "link no longer valid" with an address field). Status, `Location`, headers, body identical for every cause; no token, no flash message; fixed paths must not match a token route.
  * `TOKEN_URL_PATTERN` (`leg_platform/log_filters.py`, also used by the session-timeout middleware so tokens never reach `next`) matches every token route incl. `/email-change/stop/<token>/`; a logging filter redacts tokens on all handlers; a test walks the resolver (a regex route with `token` fails). Proxy/web-server access logs are the operator's job (nginx error logs can keep token URLs). Response time is not equalised (`docs/SECURITY.md` section 11).
  * Accepted: `APPEND_SLASH` 301 for a token URL without slash; a stale-session cookie returned; `SecondFactorMiddleware` redirects an incomplete staff session before a verify view; rotating `SECRET_KEY` invalidates pending links.
* **Password reset** (D-038, D-044): "Forgot password?" -> single-use link valid 24 h (= the longest limit window; a completed reset removes all outstanding links) -> new password -> normal login, no automatic login. Mail only to status active (a temporarily locked account is active: reset works during a lockout); other states get nothing (unblock a blocked account with `emergency_access unblock-account N`).
  * Reset ends all other sessions and that account's temporary lockout only (never IP counters or lockouts), leaves the second factor untouched, notifies the account. `process_reset_request()` locks the account row and checks status under the lock; `complete_reset()` accepts only purpose `PASSWORD_RESET`. A request below the per-address limit deletes earlier reset links first (retries during a mail outage each replace the link: accepted).
* **Password change** (D-040, D-062): `/profile/password/`; session ID renewed, other sessions end, notification sent, outstanding reset links removed; refused under the lock if the session auth hash changed since request start. "New equals current" is checked only after a valid proof, via `check_password(new, user.password)`; before a proof the answer is identical whatever the new password is (otherwise a guessing oracle).
* **Login after registration, recent authentication** (D-055, D-063): completing registration calls `login()` with `second_factor.LOGIN_BACKEND` and goes to the start page; no privileges; a used/expired/replaced link logs nobody in.
  * `second_factor.recently_authenticated(request, max_age=timedelta(minutes=5))` is true only if the session holds the server-side `authenticated_at` (epoch seconds, number not bool, not in the future, at most 5 min old), written only by the `user_logged_in` receiver `remember_authentication` (after password and 2FA, and registration completion); never by activity, key cycling, password change/reset or client input; ends with the session. Not bound to an account id; safe only because a session never changes account without a flush; a future path changing a session's account must bind the time to the account.
  * Accepted Low risks: within 5 min of a login an unattended browser can start 2FA setup without the password (consequence: owner locked out); `ENROLMENT_LIFETIME` 15 min; "Copy codes" uses the clipboard.
* **One proof per confirmation, "2FA wins"** (D-062; owner 2026-10-15): every profile re-authentication asks exactly one proof: the 6-digit app code if 2FA is active, otherwise the current password, never both. Applies to email changes (incl. second address), password change, new recovery codes, turning off 2FA, account deletion, forced password change. Staff without 2FA give the password; 2FA setup after more than 5 min asks the password.
  * A posted `current_password` with 2FA is ignored; the code is checked after all other fields are valid. After `totp.normalize_code` only exactly six digits count; anything else is refused as "not a code", not counted against the wrong-code budget (a habit-typed password cannot pause the account), never echoed.
  * A recovery code is no proof in any profile confirmation; it counts only at login and in "phone lost". `totp.verify_code()` needs the caller to hold the account row lock.
* **"Phone lost"** (D-062): card "turn off 2FA", `POST /profile/two-factor/lost-phone/`, works without script: password AND a recovery code, both right; wrong password and wrong code give the same message; the code is used up only if everything before was right. Success in one transaction under the account row lock (of two parallel posts one wins): 2FA off, other sessions end, every address mailed, security events `recovery_code_used` and `two_factor_removed_phone_lost` (long retention). Not for staff/administrators, not without 2FA. People with neither app nor code go through the operator.
* **Wrong entries in confirmations** (D-062): counted per session, not at the account budget, Axes or IP counter (an existing Axes lockout or pause still refuses). `SessionCodeFailure`, keyed by a keyed digest (purpose `LEG-Platform session code failures v1`) of a random `confirmation_counter_id` kept in the session across `cycle_key`; changed under the account row lock.
  * `SESSION_CODE_LIMIT` = 5 ends the session, event `session_ended_wrong_codes`, one notice to every address. A correct code deletes the row; a right password restarts the count except in "phone lost"; format errors count nowhere.
  * Account cap (`ConfirmationFailure`): 15 wrong entries over all sessions in 24 h end all sessions (`end_all_sessions`), event `all_sessions_ended`, one notice, count restarts (login not paused); a running request is refused (`confirmation_refused`). `cleanup_confirmation_failures` removes rows older than 30 days.
  * A session holder cannot trigger the account budget or Axes; with session and password the code can still be guessed (5 per session, 15 per 24 h). Residual risk: with 2FA an app code alone suffices to change email/password or delete the account (phished code, unlocked phone). Mitigations: notifications to all addresses, other sessions end, 24 h pending address change with stop link, budgets, Axes.
  * Accepted low points (next change of this area): L-1 `verify_password`/`verify_second_factor(per_session=True)` do not check the caller is the logged-in person (a new caller without login needs `request.user.pk == user.pk`); L-2 under an Axes lockout the check still sends the failed-login signal (counts against the holder's IP only); L-3 a login in a logged-in session also restarts the session count for accounts without 2FA; L-4 session counts are cleaned only via `run_scheduled_tasks`.
* **Profile cards, second address, stop link** (D-059): `/profile/` has five cards (personal details, email addresses, password, 2FA, delete account); state server-rendered (`?edit=...&step=...`); GET changes nothing. Mandatory-2FA accounts see only the 2FA card; the forced password change keeps its own page.
  * Second address: `User.secondary_email`, `PendingEmailChange` (account, kind login/secondary, address, 24 h deadline, one per account and kind). A request stores a row for every target address whether or not it belongs to another account (same answer, no enumeration); the worker re-checks. Two-step link (page, then POST). A login-address change ends all other sessions and mails old and new address. The second address never logs in or resets a password, is not unique, is stored only after confirmation, removable at once.
  * Notifications go to every address (`User.notification_addresses()`, `mail_queue.enqueue_for_account`), queued before the confirmation link.
  * Stop link `/email-change/stop/<token>/`, sent to the old login address and a confirmed second address with every change request: works without login, two-step; cancels all pending changes, deletes all confirmation and stop tokens, ends every session, records `email_change_stopped`, recommends a new password; refuses a link without an open request. `User.discard_email_change_requests()` runs after password reset/change, on any status change away from active and in `remove_second_factor`; confirming a login address deletes all stop links.
  * Limits are checked for every posted kind before password/code (`RequestRefused`, HTTP 429 only for client-address and instance limits); bot hits and repeats count per client address (`SCOPE_MAIL_SILENT`, 30/h). Events of this area carry no personal data. All mail templates have `autoescape off`.
  * The delete card shows the legal notice (`legal/VORGABEN.md` section 7) with privacy link, re-authentication, a never pre-ticked checkbox. Open owner question (not built): an attacker with password and session who confirms a new login address in their own mailbox at once leaves no window for the stop link; an undo window needs a product decision.
* **Lost second factor** (D-004, D-041, D-044, D-106): details of the method choice and identity check: D-106.
  * Initiated in the administration (action "Reset two-factor authentication") by any active staff user or system administrator, for any account including their own and the last system administrator; or, by email, by an ordinary account with nothing entered (D-106). No immediate portal reset.
  * The worker mails a single-use link (24 h, keyed digest, never in the job); the owner confirms with a button; then devices are deleted, all sessions end, the owner is notified, the event is logged. A newer link replaces the older; it dies if the account is inactive.
  * An incoming email's sender alone is never proof (forgeable, RFC 7489).
  * Rationale: users reach only their own profile and a mailbox reset already opens accounts without a second factor, so confirmation through the registered mailbox is proportionate; staff need a strict identity check (D-106).
* **Bot protection stage 0** (D-058, D-069): hidden field `contact_fax_number` (class `hp-field`, `aria-hidden`, `tabindex="-1"`, `autocomplete="off"`) + signed `form_started` (`django.core.signing`, min age 2 s `MAIL_FORM_MINIMUM_SECONDS`, max 3 days) on step 1, the invalid-link form and the reset request; a hit shows the same confirmation without a job. A read-only pre-check of client-address and instance limits (`mail_queue.requests_refused`) runs before storing anything: refusal creates no `MailJob`/session and answers HTTP 429 with a visible message; only these two limits are shown (no account oracle); the per-address limit stays silent. Proof of work (ALTCHA) is not built; reconsider only if abuse is observed.

## 7. Security log and sessions

* **Security log** (D-018, D-041): events per `docs/SECURITY.md` section 10. Never passwords, tokens, secrets or complete links; only necessary personal data; accounts by internal number (not customer number); entries of deleted accounts lose the personal reference.
  * `SecurityEvent` = time, event (fixed list), internal numbers of the account concerned and the actor (no FKs), long-retention flag; no email, no free text. Append-only in the application (update, delete, bulk create refused, also for Axes failure/lockout records). Admin: read-only, system administrators only (not by permission). Also logged to `leg_platform.security`, in the change's transaction (exceptions: initial administrator, lockout, re-encryption).
  * Retention is server configuration: `SECURITY_LOG_RETENTION_DAYS` / `SECURITY_LOG_LONG_RETENTION_DAYS`, defaults and minimums 30 / 365 days (lower value stops the start); `cleanup_security_log` deletes expired entries.
  * Long retention: changes of rights/roles/`is_staff`/`is_superuser`, initial administrator, emergency commands, 2FA reset of staff and system administrators, blocking/unblocking of staff and administrators, administrator changes of another account's password/email, deletion/deactivation/reactivation by administrators, Graph configuration and portal settings changes, staff changes of customer data, grid operator changes, printing. Everything else 30 days.
  * No stricter protection against persons with server/DB access (owner 2026-10-13). Basis: DSG (SR 235.1) Art. 6 para. 4; OWASP Logging Cheat Sheet. Events of functions not yet built are logged when they exist.
* **Sessions** (D-041, D-056): see D-100 (idle timeout only; "stay signed in" 14 days; no step-up code). **Log files and log page** (D-099): see D-099.

## 8. Mail

* **Delivery** (D-006, D-028, D-070): all mail via Microsoft Graph with a certificate (client credentials, signed client assertion), not a client secret (owner 2026-10-14; Microsoft advises against secrets in production).
  * `EMAIL_MODE`: `console` (default, local), `allowlist` (local, `EMAIL_ALLOWED_RECIPIENTS`), `graph` (stage, production; section 3). Outside local a missing value stops the start.
  * Local `allowlist` (owner 2026-10-11): dedicated development app registration and mailbox with credentials separate from stage/production (`docs/SECURITY.md` section 7); recipients only in the user environment variable, never in the repository; empty list refuses the start; each entry one full lower-cased address (one `@`, domain with >= 2 labels, no wildcards); errors name only the entry position.
  * Tests never send real mail (locmem), use only reserved domains (RFC 2606: `example.com/.net/.org`, `.test`, `.invalid`); `leg_platform/tests/test_repository.py` scans text files for other addresses.
  * `leg_platform.mail.GraphNotImplementedEmailBackend` raises on every send until the real backend is configured; never silence `mail.E001`. Django 6.1 refuses `EMAIL_TIMEOUT` with `MAILERS`; the Graph backend sets its own timeout.
* **Graph configuration** (D-006, D-048): system administrators maintain tenant ID, client ID, sender, certificate, private key in a Django admin section with test send (`accounts.GraphConfiguration`; superusers only view/change, no add/delete). Changes logged; expiry shown (certificate-expiry warning not built).
  * Private key write-only, Fernet-encrypted (section 5); a non-ASCII key is refused; a stored one gives a generic `GraphEmailError` without token request; an `OSError` from MSAL tenant discovery becomes a generic error. Certificate: key size at least 2048 bits, expiry checked; `GRAPH_UPLOAD_MAX_BYTES` = 16 KiB, and the proxy must limit the body too (`docs/INSTALLATION.md`).
  * Test send: superuser only, only to the requester's own address, refused in console mode, every attempt logged (`GRAPH_TEST_EMAIL_REQUESTED`), reuses the per-address budget (D-051).
  * Loggers `msal.oauth2cli.oauth2` and `msal.oauth2cli.assertion` are CRITICAL, `propagate` False (MSAL logs token response bodies at ERROR).
* **Graph backend** (D-006, D-048): `msal`, `POST /v1.0/users/{sender}/sendMail` (202 = accepted, not delivered). Fail closed if the message sender differs from the configured sender. Never follow redirects (bearer token).
  * No `Auto-Submitted` header (Graph allows custom headers only on creation, named "x-"; SMTP sends `Auto-Submitted: auto-generated`, RFC 3834 section 5.2): switch off automatic replies of the sender mailbox (`docs/INSTALLATION.md` step 6).
  * Exchange Online: restrict the app to the sender mailbox with "RBAC for Applications" (filter `EmailAddresses -eq 'smtp:<sender>'`, verify with `Test-ServicePrincipalAuthorization`); no organisation-wide `Mail.Send` in Entra ID. Source: Microsoft Learn (application-rbac, v2-oauth2-client-creds-grant-flow, user-sendmail, message resource).
* **Mail content** (D-037, D-038, D-054, D-058): plain text only in phase 1 (HTML adds link spoofing, tracking, rendering risk); the one exception is the registration code mail (D-136: fixed HTML wrapper without link, image or script, plus a text variant). Acceptance after the real Graph test send: click a link mail in Outlook, Apple Mail, Gmail and a Swiss webmail; if a link breaks, add a line asking to copy the whole line into the address bar.
  * Links only from `INSTANCE_BASE_URL` (environment, D-116), never from the request (`docs/SECURITY.md` section 4), on their own line. Sender: the chapter "Email" of the administration (`GraphConfiguration.sender_address`, D-116), strict pattern.
  * Emails never say replies are read (owner 2026-10-13); notifications invite no reply and tell the person to contact the operator if not requested; link mails end with a contact line from `INSTANCE_WEBSITE_URL`. SPF/DKIM/DMARC are DNS settings. A failing send is logged by exception class only. Pages after a request show identical conditional text for every address.
* **Queue** (D-038): registration, reset and invitation requests only count the request and store one `MailJob`; nothing is read or sent in the request (no address-dependent response or timing). Worker `manage.py process_mail_queue` (`--loop`) claims under lock (retry after 2 min), sends outside any transaction, deletes the job; raw tokens are created by the worker, never stored. At-least-once; given up after 3 attempts. A registration job older than 5 minutes is dropped (D-136). `cleanup_mail_requests` deletes unprocessed request jobs after 1 h and notifications after 24 h; jobs of a deleted account go with it (CASCADE).
* **Limits** (D-038; owner confirmed the hourly address limit 2026-10-13; OWASP gives no numbers): per normalised address 12/hour, 24/24 h, 3/10 min, shared by registration, reset, email change; per client IP 20/hour (IPv6 by /64, RFC 6177; undeterminable: one shared bucket + warning); instance-wide 300/hour for registration and 300/hour for reset, separate.
  * A request counts only if every limit has room (one transaction, ordered row locks). Client-IP and instance limits refuse before anything is stored (HTTP 429, logged at most once a minute). The address limit is never shown: the request becomes a job without the address, processed as "send nothing". Information email to an existing address: at most once per address per 24 h.
  * Counters in `RateLimitBucket`/`RateLimitEvent` with keyed digests; unused buckets deleted after 24 h; DB table, not the Django cache (non-atomic counters).

## 10. Address directory

* **Purpose** (D-033, D-066, D-069, D-111): Swiss addresses are checked and autocompleted against a local copy of the swisstopo "Official directory of building addresses" (public federal data) where a postal address is edited: registration step 3 (country fixed to CH) and profile edit (owner 2026-10-15); **in every form with an address since D-111** (not in the read-only profile or the Django admin).

Missing, unreachable, old, rate limited, invalid directory or no JavaScript: no warning. No visible reference to swisstopo or "official directory" in the UI (owner 2026-10-15); no `attribution`. Logging: only DB errors and `ValueError` of the limit check, fixed texts.
* **Source and licence** (D-049, D-022, D-066, D-074): STAC collection `https://data.geo.admin.ch/api/stac/v0.9/collections/ch.swisstopo.amtliches-gebaeudeadressverzeichnis`, asset `amtliches-gebaeudeadressverzeichnis_ch_2056.csv.zip` (UTF-8 with BOM, `;`, 143 MB zipped, 3.3 million lines). The import verifies the SHA-256 multihash (prefix `1220`) from the catalogue.

The STAC label "proprietary" is not the legal basis.
* **Stored columns** (D-049): only `STN_LABEL` (street), `ADR_NUMBER`, `ZIP_LABEL` (split at the first space into postal code and locality; the postal locality, not `COM_NAME`), `BDG_EGID` (building identifier) and `ADR_EDID` (entrance identifier), and the LV95 coordinates `ADR_EASTING` and `ADR_NORTHING` (`Address.easting`, `Address.northing`: decimal, 3 places, nullable; all data downloadable from admin.ch is public federal data, and the transformer station match needs the position of each address, owner 2026-10-25); no others (`BDG_NAME` may contain names; data minimisation, FADP art. 6). Identifiers and entrance: owner approval 2026-10-19, see below. Tests use a small fixture CSV; never store the dataset in the repository.
* **Building identifier (EGID)** (owner 2026-10-19, KONZEPT 3a; D-049, D-066): a building is identified by its EGID, not by address text.
  * Column `BDG_EGID` (swisstopo product information table 1 "Attribute"; the published file starts `ADR_EGAID;STR_ESID;BDG_EGID;ADR_EDID;STN_LABEL;ADR_NUMBER;...`; KONZEPT 3a calls it "EGID"). Stored as `Address.egid` (nullable integer, 1 to 999,999,999, anything else refuses the file), `Address.entrance_id` (column `ADR_EDID`, product information table 1, SHORT; nullable, 0 to 32767, anything else refuses the file; owner approval 2026-10-19 for the "Hauseingang und EGID" choice) and `Directory.has_egid`. One `Address` row per row of the file: an address with several buildings has several rows, a building with several addresses shares its EGID over several rows. A file without a column is refused ("Missing EGID column.", "Missing entrance column.", `jobs.SAFE_FAILURES`), the published generation stays. A published generation without identifiers (`has_egid` false, also one imported before the entrance column existed) is replaced by the next import even if the checksum is unchanged.
  * Search `addresses/buildings.find_buildings(street, house_number, postal_code, town, user=)`: (1) the local directory, exact on the folded keys, no internet; (2) a stored answer (`BuildingLookup` in the application database, so an import does not replace it and request threads may write it; keyed digest of the normalised address, never its text; negative answers 7 days, positive 90 days, `cleanup_address_lookups`); (3) one request to swisstopo, only for a signed-in active account and within the budgets (6/min and 10/h per account, 30/min and 300/h per instance; `limits.allow_external_lookup`), and not while the circuit breaker is open (below). Result: `found` (candidates: one per EGID and entrance, each with `egid`, `entrance_id`, house number, street, postal code, locality; the wizard shows "Hauseingang und EGID" and lets the person choose when there are several), `not_found` (every attempt made), `unavailable` (`reason` not_signed_in, limit, circuit_open or failed: nothing stored, no flag) or `invalid`.
  * Outbound request (`addresses/swisstopo.py`, the only module besides the importer that imports `requests`; `docs/SERVICES.md` S-4): `GET https://api3.geo.admin.ch/rest/services/api/MapServer/find` (swisstopo product information chapter 3, https://docs.geo.admin.ch/access-data/find-features.html): layer `ch.swisstopo.amtliches-gebaeudeadressverzeichnis`, `searchField=zip_label`, `searchText` the postal code, `layerDefs` `adr_number ilike '<number>' and stn_label ilike '<street>'` (the service filters only these attributes). Only the house number (ASCII, `[0-9A-Za-z][0-9A-Za-z.\-/]{0,11}`) and street (anything outside letters, digits, space, point and hyphen becomes the wildcard `_`) reach the filter; hits are compared again on the folded text. Fixed https URL, no redirect, `Accept-Encoding: identity`, JSON content type, strict checks of every field (nested JSON that exhausts the parser is a failure), at most 200 features (a full answer without the address is no conclusion), no proxy variables or `.netrc`, 256 KiB. **Time:** one wait is limited to 3 s (connect) and 4 s (read), and the **whole request has a hard deadline of 8 s**: the request runs in a helper thread, the caller waits at most 8 s, and on expiry every socket of the request is shut down. A socket timeout alone would not do: a server sending one byte every few seconds never times out. **Circuit breaker:** 5 failures (timeout, error status, invalid answer; not a refused input) within 5 minutes pause the search for everybody (`limits.circuit_open`, counted in the transactional rate-limit tables, so every worker sees it); a success clears the count; while it is open nobody is asked and no budget is used up (the result is `unavailable`, reason `circuit_open`). A failure carries a fixed sentence; the address is never logged.
    * **Review path:** `BuildingSearch.needs_review` is true for `not_found` and for an `unavailable` search whose reason is `limit`, `circuit_open` or `failed`: the caller notes the address for the review by the LEG and lets the person go on (nobody is stuck by swisstopo or the budget). `community/buildings.find_candidates` raises `building_not_found` with `review=True` for such a search.

The caller notes the address for the review by the LEG (its own record; this module stores no address text). The daily run (below) downloads the directory when it is set; a successful import that started after it was set clears it. **Known property (owner-accepted):** any signed-in account that enters an address unknown to swisstopo sets the flag, so it can cause one 143 MB download per day, never more.

### D-090 Address import in the web process (2026-10-17)

* **Amended by D-133 (2026-10-31).** The import no longer runs in a thread of the web process but in the worker `process_import_queue`; `runner.start_manual`, the thread-local writer for it, `atexit` and the 2 s polling are gone. Claim, heartbeat, stale takeover and the status rules stand.

* Decision (owner wants visible progress and errors): the admin button starts the import in a daemon thread of the web process (`runner.start_manual`, `runner.py`). No extra service or cron job. Worker `process_address_imports` is an optional alternative.
* Claim: `jobs.claim` locks the single `ImportRequest` row (`claim_token`): one import over all web workers and the worker. The thread has its own DB connection. Gunicorn runs sync workers (`docs/DEPLOYMENT.md` 8.1). Recycle (`--max-requests`), restart or kill ends the thread; `atexit` marks the job interrupted where it still runs, else the next claim finds the stale heartbeat.
* Heartbeat: a second thread writes phase, bytes, rows every 2 s. Without it for 90 s (`jobs.HEARTBEAT_STALE_AFTER`) the job is dead; the next claim takes over and frees the lease. The old thread checks its claim at every phase (D-101). The live directory is untouched until the new generation is complete.
* Writer: only the import thread writes the SQLite file (`storage.mark_thread_writer`, thread-local). `mark_writer` stays forbidden in `wsgi.py`/`asgi.py`.
* Status: JSON at `admin/addresses/importrequest/status/` (session + `addresses.request_directory_import`, GET only, `no-store`); `static/js/import-status.js` polls every 2 s while queued or running (stops at a login redirect or 401); the poll is no session activity (D-100). Only the fixed sentences of `importer.ImportFailure` (`jobs.SAFE_FAILURES`) reach row, page and logs; anything else is "failed unexpectedly" (trace in the application log).
* Logs: logger `leg_platform.addresses`; security events `address_import_succeeded`/`address_import_failed` (kind and fixed reason or count); the request keeps `address_import_requested`.
* Automatic refresh: the daily run of the scheduled tasks (section 10, "Import", Schedule); it runs the import in its own process (`storage.mark_writer`). No page view starts an import.
* Sources: Python `threading` ("Daemon threads are abruptly stopped at shutdown", `threading.local`); Django `django/db/utils.py` (`ConnectionHandler.thread_critical = True`); Gunicorn design https://gunicorn.org/design/ (pre-fork, `sync` = one request per worker).

### D-098 Request budgets and back-off (2026-10-17)

* Decision: person search (`management:metering_points_person_search`) is counted per staff account (`rate_limits.PERSON_SEARCH_LIMITS`, 300 per minute); text under two characters is not counted. Beyond the limit: 429 with `Retry-After: 30` and `{"results": [], "limited": true}`.
* Why 300: at 120 ms, typing without a pause sends about 8 requests per second (the running request is cancelled); normal work stays far below; a hijacked session cannot keep the database busy for long.
* Bounds: text cut to 100 characters (`PersonAssignForm.person` `max_length=100`); only the first five words filter (`person_search.MAX_WORDS`).
* Back-off: `combobox.js` and `address-directory.js` send no request after a 429 until the `Retry-After` time has passed (30 s, at most 120 s; 60 s for the address lookup). The combobox says "Too many searches. Please wait a moment." and searches the text again after the pause.
* Address lookup budget: see D-111. At 200 ms with cancellation at most five requests per second. A refused request means "no suggestions". Not measured against real typing.

### D-099 Logs and log hardening (2026-10-17)

* Decision: logs go to standard error (journald in production) and, with `LOG_DIRECTORY`, to `application.log` and `security.log` (rotating, 10 MB x 5, files 0600 in a 0700 folder). Defaults: local `~/.leg-platform-dev/logs`; stage and production `/var/log/leg-platform` with `LogsDirectory=leg-platform`. `off` = standard error only. An unusable folder means no files.
* Page "Protokolldateien" in the administration (`admin:logs*`; `is_superuser` only, no right): lists files, shows one live (poll of an offset, pause/follow), streams a download. Fixed keys `application`/`security` plus backup number 0-5, never a client path. Every line is redacted when read (tokens, emails, IBANs, database error values). Events `log_viewed`/`log_downloaded` (long retention); the same page again within 300 s in one session is no new event; a download always is.
* Hardening: `log_filters.SafeFormatter` escapes CR, LF, other control characters and U+2028/U+2029, so a path like `%0a` cannot forge a line; tracebacks stay multi-line. Files open with `O_NOFOLLOW` and are checked as regular file on the descriptor (Windows has no `O_NOFOLLOW`; the descriptor check remains). Download redaction reads in pieces with a 512-character overlap cut at a blank; the local part of `EMAIL_PATTERN` is bounded to 64 characters.
* `portal_upload_rejected` is written once per session and minute with an app-code proof (the upload is judged before the code is checked); with a password proof every rejection is written.
* Residual risk: several processes write one file; `RotatingFileHandler` does not coordinate rotation (Python `logging` cookbook), so rotation can reorder or drop older lines; size stays bounded. Run `manage.py` as the service user (`docs/OPERATIONS.md` section 5).

### D-100 Sessions and long sessions (2026-10-17)

* Session end (owner 2026-10-17; deliberate deviation from OWASP's absolute timeout): server-side `SessionTimeoutMiddleware`. Idle timeout: users 30 min, staff and system administrators 15 min; every request extends it (written at most once a minute). No absolute limit for an ordinary session. A session without stored times ends (fails closed).
* Background polls (`session_timeout.PASSIVE_VIEWS`: import status, live log) neither extend nor survive the idle timeout (401, no redirect). After a timeout: login page with a message; return after GET only; a POST changes nothing; the redirect never puts a link token into the login URL.
* `SESSION_COOKIE_AGE` (8 h) only bounds the cookie and row of an abandoned session; `clearsessions` removes them. The session hash covers the password and `User.session_version`; `User.end_all_sessions()` raises it.
* No re-proof at a save in the administration (owner decision 2026-10-26; the old portal-settings proof is gone). `RECENT_AUTHENTICATION_WINDOW` (5 min) applies to setting up the second factor only.
* Stay signed in (owner: for everyone, also staff and system administrators): off by default. Ticked gives `STAY_SIGNED_IN_DURATION` (14 days, owner may change) as absolute end and idle timeout (a `timedelta`, so it does not slide). The wish lives on the request object or in the pending login, never in the session. A privileged account without a second factor gets none.
* Second factor: checked once per login; the persistent session exists only after the code was accepted; the 14 days then need no new code. Residual risk (owner-accepted): a stolen persistent session of a staff account has its privileges, incl. IBAN and PDF lists, for up to 14 days. Operator: staff log out on foreign devices.
* Mitigations: every persistent session of a staff or system administrator account writes security event `persistent_session_started` (long retention); no email (owner 2026-10-19: security proportionate to the effort of users, normal level; too many mails make users ignore all mails). A system administrator ends all sessions of another account ("End all sessions", `lifecycle/end_sessions/`, event `account_sessions_ended_by_admin`, long retention); the own account is excluded (as the 2FA reset, D-041).
* No step-up code (owner, D-102): whoever is signed in is authenticated; an unattended device is the operator's responsibility.

### D-102 Metering point number, menu, unchanged items (2026-10-17)

* Source: VSE/AES "Metering Code Schweiz (MC-CH 2025)", 4 December 2025, section 4.2.3 "Bildungsregel", tables 4 and 5 (<https://www.strom.ch/de/media/13608/download>, read 2026-10-17). Same composition: VSE/AES "Handbuch Messdatenmanagement HB-MDM-CH", November 2017, section 2.4 (<https://www.strom.ch/de/media/8287/download>).
* Composition: 33 characters. Positions 1-2: country (ISO 3166 alpha-2, "CH"). 3-13: identifier (grid number in 3-8, reserved placeholder in 9-13, assigned by VSE/AES). 14-33: the number the grid operator assigns (20 characters, unique in its area, not temporary). Empty positions are zero; optical separators only inside the 20.
* The 20 characters (table 5, ISO 8859-1: "Grossbuchstaben A-Z, die Ziffern 0-9 sowie der Bindestrich"): A-Z, 0-9 and "-", ASCII only. The owner follows the standard.
* Rule, one place `numbers.normalise_entered_number` (form class, check route `management:metering_points_check_number`, `field-check.js`): shorter than 20: zeros on the left (`zfill` would put them behind a hyphen); longer than 20: only leading zeros are removed, as many as needed, otherwise invalid ("The metering point number is invalid: it is too long. …" with the count); more than 200 characters (`MAX_ENTRY_LENGTH`): invalid; forbidden character and empty: own messages; no other character is ever removed; all zeros are valid.
* Small letters are accepted and stored as capitals (the column is binary and unique; `ab-12` and `AB-12` are one number). The character check runs before upper-casing (`ß` would become `SS`).
* Field: no `maxlength` (a paste is never cut), no `inputmode`, `autocapitalize="characters"`; internal name `number_digits`. Country (2 capitals) and identifier (11 capitals/digits, looser than grid number plus placeholder) come from `ManagementSettings` (D-077). Complete number `[A-Z]{2}[A-Z0-9]{11}[A-Z0-9-]{20}`, unique, nullable; duplicates found on the normalised value. The script pads on leaving the field, shows the complete number, looks it up.
* Column 33 characters, unique, binary collation. Lists and search use `contains` on the upper-cased word. History holds ids only. `format_metering_point_number` groups by four. The IBAN-like log redaction may over-redact a number (harmless).
* Power fields and LEG quota: `form_fields.DecimalInputField`: digits and one decimal point or comma (stored as point), no sign, at most two decimals, at most 999999.99 (`DECIMAL(8,2)`); quota `DECIMAL(5,2)`, at most 999.99 (D-089). Checked while typing and on the server.
* Menu "System administration": shown in the left and phone menu only to an active staff account for which `admin.site.get_app_list(request)` is not empty (`navigation.system_administration_visible`; Django's own check of view/add/change/delete rights, plus the log files for a system administrator). Superuser: always; staff with one admin right: yes; staff without any, customers: no. No group name or role is read. Hiding is not security: the administration refuses every request without the right. "Mail texts" needs `accounts.view_emailtext` or `accounts.change_emailtext` (`navigation.EMAIL_TEXT_PERMISSIONS`).
* Unchanged: the location of a metering point stays optional; the warning "This metering point is not assigned to a location." is in the list and the banner of the point with "Set location". An invited person stays unassignable (D-081: no person until it has a customer number); the text after inviting says so. The bottom bar is unchanged.

### D-106 Passkeys: registration, switching, recovery and reset (2026-10-21)

* **Administrators and the passkey minimum (owner 2026-10-22).** Administrators use the same passkey behavior as ordinary users: one active credential suffices for activation, promotion and continued access; every passkey account retains at least one. No two-device statement or checkbox is required. An additional passkey on another device is strongly recommended, never mandatory. Synced passkeys are allowed; WebAuthn cannot prove physical device independence. Residual risk accepted by the owner: loss of the sole passkey requires operator-assisted recovery. Source: explicit owner instruction of 2026-10-22.
* **Recovery (owner 2026-10-22).** The recovery procedure applies to both app and passkey accounts. Any active staff user or system administrator may initiate recovery for any account, including their own account and the last system administrator. D-044's self-reset and last-administrator exclusions do not apply to this procedure; unrelated privilege/editing protections stay. Recovery is reached in the existing user detail settings, without a new menu. Opening the email link changes nothing; explicit CSRF-protected POST consumes the single-use 24-hour link (D-040/D-067). Source: explicit owner clarification of 2026-10-22.
* **Implementation source.** Server verification: Duo Labs `webauthn` 3.0.1 (BSD-3-Clause). Require discoverable credentials and user verification; allow synced credentials. Browser helper: self-hosted `@simplewebauthn/browser` 14.0.0 (MIT). Sources: https://github.com/duo-labs/py_webauthn/tree/v3.0.1, https://github.com/MasterKale/SimpleWebAuthn/tree/v14.0.0/packages/browser, https://www.w3.org/TR/webauthn-3/.
* **Password return and labels (owner 2026-10-22).** A password return uses a single-use 24-hour email link and the same method-choice component as registration. The old passkeys stay valid until the chosen method is complete and confirmed, including app setup for administrators. Only the pending password hash is stored. Labels are user-chosen names, not proven device identities. Removing a passkey ends all sessions (existing security policy); add a replacement before removing the sole remaining key. Recovery uses the established idle timeout, restricted access and setup-proof expiry; contact guidance uses the configured instance website/operator patterns, with no new service. Source: explicit owner follow-up relayed by the main session.
* **Login methods.** A user chooses the method in step 2 of the registration: password, password and app, or passkey (staged until step 3, D-058). A password account may later add an authenticator app (2FA) and may switch to a passkey. A passkey account has no password and no app. The switch needs re-authentication with the current proof, ends all other sessions, notifies every address of the account and deletes the password, the app and the recovery codes. Password and passkey are never combined on one account.
* **Passkeys.** Passkeys are discoverable, so sign-in needs no username. The email address stays the account identifier for registration, notices and reset. Passkeys are voluntary. The portal refuses to remove the last active passkey, uniformly for all access levels.
* **Administrators.** `is_staff` and `is_superuser` may use a passkey-only account with the same one-credential minimum as users. One active passkey meets the second-factor requirement of D-004. Promotion remains restricted to an authorized foreign system administrator; form and locked save recheck the active factor. The model enforces an active credential for every active passkey account. No legacy device statement gates promotion.
* **Recovery codes.** Password accounts keep 10 codes of 8 characters, unchanged. Passkey accounts have no recovery codes.
* **Back to password.** Self-service with a current passkey as proof: the user sets a new password. The change takes effect only after the user clicks a link sent to every address. Until then the passkeys stay valid, afterwards they are deleted. The app is offered; it stays optional for users and is required for administrators (D-004).
* **Lost passkey.** With a second passkey the user signs in with that one. Without one, while no building, metering point or IBAN is entered for the account (a draft or pending application counts; a deleted entry does not; `community/account_entries.py`), the ordinary account starts the recovery by email itself: the same link as the reset below, issued only for such an account and checked again when it is sent, opened and confirmed (owner decision 2026-10-24; accepted residual risk: whoever controls the mailbox of an account with nothing entered can replace its methods; every address is notified). The same holds for a lost app or password and app together. Otherwise, and always for a staff user or a system administrator, the user receives instructions by email to contact the LEG administrator and prove identity with an official ID document, sent by email. The administrator checks it and starts the reset manually. The page "Forgot your password?" gives a passkey account the same answer. Owner decision: convenience over an in-person check, accepted and recorded.
* **Reset.** Started by a staff user or a system administrator (`is_staff` or `is_superuser`), or by the ordinary account itself while nothing is entered (Lost passkey). Staff may reset other staff, their own account and the last system administrator. The administration shows a red button and warning naming the consequences. Identity check: the person sends an official ID document by email; the administrator compares the name with the stored values. The identity check applies to all account levels except that recovery by email (simplicity chosen over an in-person check, owner decision). A single-use link (24 hours) goes to the registered address. Old methods stay valid on GET and are deleted only after explicit CSRF-protected POST confirmation. The restricted session then offers the same choice as registration (users: password, password and app, or passkey; administrators: password and app, or passkey). The confirmed link replaces registration email verification, not complete method setup. Every reset ends prior sessions, notifies all addresses and is logged.
* **Operator compatibility.** The server emergency command retains its existing interactive and last-administrator safeguards. For passkey/recovery accounts it requests the same confirmation link without deleting credentials or inventing a usable password; the request is logged for long retention. Password/app accounts retain their existing server emergency behavior. Expired pending password hashes, method-return links, challenges and staged inactive keys are removed by the existing scheduled mail/request cleanup.
* **Recovery eligibility (owner/main, 2026-10-22).** "Any account" includes active password-only accounts and the initial administrator before factor setup. Existing-factor checks must not exclude these accounts from request, delivery, link lookup or confirmation. Inactive-account exclusion, identity check, single-use confirmation, restricted setup and unrelated privilege protections remain unchanged.
* **Additional-passkey journey (owner 2026-10-22).** Stay on the authenticated computer: the profile links directly to setup, which requires current proof and offers distinct "Create passkey on another device" and "Create passkey on this device" creation actions. `OptionsView` / `passkeys.begin` require a registration-only allowlisted mode (`another_device` / `this_device`); missing, malformed or unrecognized modes are refused. The server sets cross-platform attachment plus `HYBRID` for another device, platform attachment plus `CLIENT_DEVICE` for this device. Client-supplied WebAuthn options never override those settings. Shared localized help describes the native browser/OS prompt, optional QR scanning, creation without an existing passkey on the phone, explicit saving, and cancellation when no suitable option appears. No portal navigation on the phone is needed: localhost/127.0.0.1 is device-local. Support is browser/provider-dependent; hints are not guarantees or physical-identity evidence. Sources: owner instruction; W3C WebAuthn Level 3, [user-agent hints](https://www.w3.org/TR/webauthn-3/#enum-hints) (HYBRID recommends cross-platform attachment for older clients) and [attachment](https://www.w3.org/TR/webauthn-3/#enum-attachment); installed Duo `webauthn` 3.0.1 `structs.py` / option serialization; self-hosted SimpleWebAuthn 14.0.0 option pass-through.
  * Other-device limits: WebAuthn has no QR-only creation switch: hints do not bind the user agent, so the local password manager may still open. The portal cannot force a native QR dialog; help discloses that limitation before creation. The browser helper suppresses submission of an explicitly reported `platform` result for `another_device`, without retry or platform fallback. This is a client-side UX guard, not signed device evidence or a server security rule; missing/unknown attachment remains compatible. A credential might already exist at the provider even when not submitted to the portal. Sources: [W3C reported attachment](https://www.w3.org/TR/webauthn-3/#dom-publickeycredential-authenticatorattachment); versioned [SimpleWebAuthn registration](https://github.com/MasterKale/SimpleWebAuthn/blob/v14.0.0/packages/browser/src/methods/startRegistration.ts) and [attachment normalization](https://github.com/MasterKale/SimpleWebAuthn/blob/v14.0.0/packages/browser/src/helpers/toAuthenticatorAttachment.ts). The shipped-helper headless test stubs the native API; actual Windows/provider/phone acceptance remains open.
  * Existing staged activation, proof, challenge/session binding, credential exclusion, CSRF and rate limits remain. Saving keeps the current session and existing keys, ends all other sessions and then sends notices to all confirmed addresses; context-specific copy beside saving discloses this. for the designer layout see `docs/DESIGN.md`. Removal still ends all sessions; switching retains only the current session. The legacy `PasskeyIdentity.two_devices_confirmed` column remains unused solely to avoid destructive schema change; later removal needs an owner decision. Real cross-device authenticator acceptance remains open.
* **Recovery binding.** Recovery authority remains bound to the current normalized login address (`VerificationToken.target_email`), checked at lookup and locked confirmation. Account-first locking serializes issuance/delivery with confirmed login-address changes, which revoke outstanding recovery tokens. Unbound old links require reissuance. Recovery eligibility and reset exceptions are unchanged.
* **Guidance (designer specification, D-056 "Clear register").** A person is helped to choose, in plain language, never with "2FA" in a heading:

One component (one card per method: the title and one sentence, and "More about this" with what it is, "You need", "If you lose it" and, for an account that exists, "What happens?"; no explainer above, no helper list) is shown at five places: step 2 of the registration, the start tile (which stays hideable and disappears once a second factor exists), the profile card, after a reset, and at the first login of an administrator (restricted session, then the page joins `second_factor.UNRESTRICTED_VIEWS`).
  * The options come from one server function (`accounts/login_methods.py`, `available(user)`): users are offered password only, password and app, passkey; administrators password and app, passkey (no password only, D-004). An administrator with only one option has no choice page. The posted method is validated against that list on the server; a method that is not offered, such as a forged `passkey`, is refused. The choice leads into the existing flows and adds no security logic.
  * Recommendation (the tag "Recommended" on a card): users "password and app" (the app has the most precise recovery path, the recovery codes); administrators the passkey. An additional passkey on another device is strongly recommended for everyone, not an activation condition. The texts name no app brands ("an authenticator app from your phone's app store").
  * Passkeys are offered without a feature flag.

The Open owner question is below.
* **Endpoint:** modes `suggest`, `check`, `locality` (postal code to towns, town to postal codes). Answer keys include `status`, `results`, `more`, `match`, `warning`, `reason`, `proposals`. **No login:** the registration details step is used before the account exists (D-066); the answer is public register data. POST only, CSRF, 4 KiB, `no-store, private`, no outbound request. `TYPEAHEAD_MINIMUM` = 3 on the server (the community's own advice keeps 2).
* **Request budgets** (`limits.allow_request`): a signed-in account 120/min per account and 300/min per client address; an anonymous client 60/min per address; everybody 600/min per instance. A `check` of an anonymous client counts as two requests. The approximate street search has its own budget (below).
* **Approximate (fuzzy) street search:** runs only when the prefix search found nothing, for a street of 3 to 64 characters, and only inside a complete postal code or, without one, a typed town. Bounds: at most `APPROXIMATE_STREET_LIMIT` = 20,000 streets (read from the small table `AddressStreet`), 300 comparisons, 0.25 s, similarity threshold 0.75; fail closed (no result). **Never done for an anonymous client.** Budget of a signed-in account 10/min and 60/h, of the instance 60/min, counted only when the search runs (`limits.allow_approximate`); a used-up or failing counter skips the search and answers the prefix result (no error). Server-side callers (`community.addressing`, `addresses.buildings.suggest`) keep it under their own request budgets. `approximate_matches(..., town=)` carries the town bound.
* **Mode `check` and proposals:** answers `reason` (`street`, `house_number`, `postal_code`, `town`) and up to 3 complete `proposals` computed by `fixes.fixes` (`addresses/fixes.py`; shared helpers in `addresses/matching.py`): fewest changed fields first (a street of similarity at least 0.9 counts as a typing mistake and costs none), then the typed house number, the nearer place (distance of the place centres `AddressPlace.easting/northing`, else the postal code difference), the closer house number, the LEG's area first; only candidates that change the same fields as the best one are offered. None for an old directory, an empty house number, when neither a complete postal code nor a town of 3 characters is typed, or when the address exists. Bounds that only protect against abuse: deadline `FIX_TIME_BUDGET` = 0.5 s (passed: no proposal), a street in at most `PLACES_CAP` 5000 places, `CANDIDATE_CAP` 3000, `HOUSE_CAP` 200 house numbers compared by text, `SIMILAR_CAP` 200 similar streets. * **In-place migration and locks:** the additive migrations 0020 and 0021 (`Migration.in_place = True`) are applied to an existing directory file by `setup.prepare_directory` without a re-download: under the exclusive directory lock, only while no import is alive, with a free-disk check (35 % of the file size twice plus 256 MB; without space the migration is skipped with a message and lookups answer "unavailable" until it runs), and a populated file is never wiped when the schema is incomplete afterwards (error instead). Readers take the directory lock shared (`storage.directory_open_guard(shared=True)`; `flock` / `LockFileEx`) so parallel lookups do not fail; reset and setup take it exclusive.
* **Directory not available:** a **staff** account (`request.user.is_staff`, in the markup `data-directory-missing`) is told "There are no address suggestions: the directory is not available or has not been imported yet …" when the answer says `missing` or `unavailable`; everybody else sees nothing (D-066 unchanged for them).
* **Residual risk / open:** the widget is tested only in a headless Chrome with a stubbed `fetch` (`test_widget_script.py`), not against a real directory in a browser; screen readers not tried; an overlay can be clipped by a container with `overflow: hidden` (none known; the administration's `.form-row` is overridden). * **Checks (values).** Download: the fixed URL only (`importer.PLANT_URL` in the allowlist of `_chunks`, no other URL), `verify=True`, `trust_env=False`, no redirects, one total time limit of `importer.MAX_DOWNLOAD_SECONDS` (1,800 s) for connect, headers and body together: the request runs in a helper thread, and at the deadline every socket of the request is shut down (`http_budget.Budget`; tests inject the clock), ZIP at most 64 MiB, Content-Type `application/zip` or `application/octet-stream`. The ZIP is hashed while streaming; the SHA-256 is stored and not compared. Members: the declared count is read from the end record before the archive is parsed (at most 16; the address archive: exactly one member, D-075); each is stored or deflated, not encrypted, ratio at most 100; the CSV `ElectricityProductionPlant.csv` exactly once; declared total at most 192 MiB; the CSV is read up to 128 MiB and 1,000,000 rows. Per row, every field is checked, also for a row without EGID: `xtf_id` 1 to 64 characters of `[0-9A-Za-z_.-]`, unique within the file; `EGID` empty (skipped) or `[1-9][0-9]{0,8}`; `SubCategory` `subcat_N`; `TotalPower` a plain decimal with at most 8 digits before and 3 after the point, finite, from 0 up to 10,000,000 kW; `_x` and `_y` both present (or both empty) within LV95 E 2,480,000 to 2,840,000 and N 1,070,000 to 1,300,000 (the file's own range 2,486,220 to 2,831,206 and 1,075,619 to 1,294,828, rounded outwards; not checked against an official extent).
* **Refusal (values).** A row that fails is counted as ignored (`rejected`) and not stored; a row without EGID counts as ignored (`skipped`) only when all its other fields are valid, otherwise as rejected. Owner decision 2026-10-24: no share of ignored rows refuses an import; the import assigns what it can and leaves out the rest. The generation is refused only when it is empty, or when its row count is below half or above twice the published count (the first publication has no comparison). A refused generation is deleted; the published one stays.
* **Format.** The file is comma-separated, UTF-8 with BOM, CRLF (checked on the sample of 2026-10-24).
* **Statistic (owner decision 2026-10-24).** `PlantRegister` keeps, from the last successful import only: `address_count` (`Directory.row_count` of the published address generation when the plants are published), `file_row_count` (data rows of the plant file), `row_count` (plants taken over: EGID and valid row), `rejected_count` and `skipped_count` (ignored rows by reason: failed check, no EGID) and `imported_at` (time of the run). A failed or refused import keeps the values of the last success; an unchanged file (same SHA-256) is not loaded again and keeps its plants and counts, but the statistic is rewritten after every successful plant run, so `address_count` and `imported_at` are current. The statistic is shown in the administration block below and blocks nothing: a missing plant register does not affect the address directory.
* **Switch.** The switch checks the claim (the job row with the claim token, locked) and the generation it started from (a compare-and-swap in the directory file). The job row and the plants lie in different databases (D-075), so one transaction cannot span both; the row lock holds a takeover off until the switch is committed (MariaDB). Every other generation is deleted after the switch.
* **One claim.** `ImportRequest` has the field `source` (address or plant), the day of the last plant run and its result (`last_plant_state`, `last_plant_finished_at`, `last_plant_error`). The claim (`jobs.claim`) is the only gate for both sources (D-090): the plant import never starts while an address import is queued or running, and the reverse. A plant claim does not touch the address schedule (`last_automatic_attempt_at`). Chain (owner decision 2026-10-24): `schedule.run_daily` runs the address import first and then, in the same process, `run_plant_daily`; the plant import does not start when the address import of that day failed (the next daily run tries again). Once a day, also on days without an address import (the address part reports `nothing due`). No button for the plant import in the administration (owner decision).
* **Administration block (2026-10-25, owner decisions).** The chapter "Data imports" (model `ImportRequest`, renamed from "Address directory imports") shows the address block and, read only, the block "PV-Anlagen (BFE)": the statistic of the last successful import (`PlantRegister`, Swiss thousands separator), the last result of the plant run with its date and time (owner decision 2026-10-25): a failure is shown on any day, with `role="alert"` and its fixed reason, until a later run replaces it; a success is shown as "Completed" only on the day of its run, otherwise "Not run today" (the date stays); after a failure, the date of the older data, which stays valid. A download step that fails has its own fixed text: `Official file not found.` for an HTTP 404 (the other download texts are those of `importer`). Source line: "Quelle: Bundesamt für Energie (BFE), Nutzung frei (Open Use)". No coverage note, no coordinates, no list of plants. Permission: `addresses.request_directory_import`, the right of the address page (no new right).
* **Security events.** `pv_import_succeeded` (detail: kind and count) and `pv_import_failed` (detail: kind and one fixed text of `plants` or `jobs.PLANT_FAILURES`). Never a row or a value. Two keys instead of one, as for the address import.
* **Owner decision on the member rule.** The downloaded ZIP holds six members (the plant file and five catalogues and details: `PlantDetail.csv`, `MainCategoryCatalogue.csv`, `OrientationCatalogue.csv`, `PlantCategoryCatalogue.csv`, `SubCategoryCatalogue.csv`). The rule "exactly one member" from the plan would make the source unusable. Chosen: the five names are listed, every member is checked (not encrypted, ratio, size), and only the plant file is read or extracted. To be confirmed by the owner.
* **Residual risk.** The SHA-256 is not verified: the BFE publishes no checksum (`.sha256` and `.md5` return 404 on 2026-10-24). A transmission error is caught by the ZIP and CSV checks, not by a checksum; a wrong but well-formed file would be published. The owner accepted this (data not sensitive, no billing; a wrong value would only distort a chart). The shared row keeps the last error of either source (address status page); the result of the last plant run has its own fields (below).
* **Consequence.** The plant register is loaded by the first daily run after the setup, about 20 MB per day (no skip by a HEAD request). The file grows by about 30 to 40 MB per generation (estimate of the plan, not measured); the old generation is deleted after the switch.
* **Not included.** No display in the building card (owner decision on the visibility to owners pending), no coverage note (owner decision: none), no request of plant data by a user.
* **Stale hint (owner decision 2026-10-25; both sources).** `Directory.content_changed_at` and `PlantRegister.content_changed_at` hold the day on which the published file last changed (instance time zone): set to the day of the run when the SHA-256 differs from the stored one, kept when it is equal. The owner expects each source to change at least once in 30 days; more than 30 days (`status.STALE_CONTENT_DAYS`) without a change shows the hint "The file has not changed since {date}. Check whether the source is still updated." (`role="status"`, dot `status-warn`) on the page "Data imports", in the address block and in the plant block. A hint only: no import outcome changes, no security event, independent of the run result, gone when the content changes; the page shows no address and no hash.

### D-118 Transformer stations from the public BKW map: weekly, server only, own table (2026-10-25; owner decisions 2026-10-25)

* **Decision.** A weekly read-only scan of the public high-discount map of BKW Netz (WMS `https://qgisserver-extern.bkw.ch/ogc/`, layer `high_discount`; the map and method of `bkw_leg_scanner.py` of the project owner) matches each building of the postal codes of the service area to its transformer station. Postal codes: `ServicePostalCode`, edited in the administration with the right `addresses.manage_service_areas`. Buildings: rows of the published address generation with an EGID and an LV95 position (D-049). Only the map tiles that contain such a building are requested. Coloured dots are matched to the nearest address point (exact within 3 m, fallback within 50 m, none otherwise); the transformer name is read from the label by OCR. Stored per building in `TransformerStation` (address directory file): EGID, postal code, cleaned name (`transformers.CLEAN_NAME`), match status and time. No raw label, image or URL is stored, logged or shown.
* **Design (owner decision 2026-10-25).** The stations are not part of the address generation: no foreign key, and the daily address import does not touch them. A complete scan replaces the rows of the postal codes it scanned in one transaction (`transformers.store`); a failed scan changes nothing. A lookup (`transformers.station_of`) joins by EGID with the current generation in two plain queries. Rows whose EGID left the generation are not shown and are removed by the next successful scan of their postal code.
* **Run.** On Saturdays, after the plant register of the day (`schedule.run_transformer_weekly`; once per Saturday; the same claim as the imports, D-090, D-117: a queued address request holds it back). Manual start: `scan_transformer_stations`. A failure is recorded with a fixed text (`jobs.TRANSFORMER_FAILURES`), shown in the block "Transformer stations" until a later success, and stops nothing else.
* **Limits and why.** One request at a time; at least 1 s from the end of one request to the start of the next; a total time limit of 3,600 s per run (each request is cut at the rest of it); at most 300 tiles per run, a larger area is refused and not cut (the owner decides on a larger area); a tile is at most 16 MiB and must be a PNG of the requested size; timeouts of 10 s to connect and 60 s to read, and a hard total time limit of 60 s per tile request (`REQUEST_SECONDS`; the helper thread and the socket budget of `http_budget.py`, as for the downloads of D-117); HTTPS only, certificate verified; no redirects; no proxy variables, no `.netrc`, no credentials; user agent `LEG-Platform/1.0` with the purpose. The only host besides the import code is `importer.APPROVED_WMS_URLS`.
* **Permission.** The project owner states verbal permission to use the public BKW map server (recorded 2026-10-25; source: owner statement; no written terms found).
* **Dependencies.** `requirements/transformers.txt` (numpy 2.5.4, scipy 1.18.1, Pillow 13.0.0, opencv-python-headless 5.0.0.93, onnxruntime 1.31.0, pyclipper, shapely, six, pyyaml; the first five pins are those of `bkw_leg_scanner.py`). rapidocr-onnxruntime 1.2.3 is installed separately with `--no-deps`, because it declares `opencv-python`, which conflicts with the headless build (both provide `cv2`). Chosen by the team lead 2026-10-25 (best practice; `pip check` reports only the expected missing `opencv-python`). Installed only on the server, imported where used. Tests use fake tiles and a fake reader. Licences: `docs/THIRD_PARTY_LICENSES.md`.
* **Residual risks.** OCR misreads (the place name is voted per number, the number itself can be misread); a change of the BKW map (layer, colours, label placement) gives fewer dots or names; load on a third-party server (accepted with the limits above); the permission of the owner is verbal (see Permission above; no written terms found); the script's filter on `ADR_STATUS` is not applied, because the directory keeps no such column (D-049); the results are not checked against ground truth.
* **Consequence.** The table `TransformerStation` lives in the address directory file. New security events `transformer_scan_succeeded`, `transformer_scan_failed` and `service_area_changed` (the postal codes after each change in the log line).

## 23. Decisions of 2026-10-26 (D-119)

### D-119 Weekly housekeeping of both databases: the address directory file is compacted, the application tables are optimised after a dump of the housekeeping itself (2026-10-26)

* **Decision.** A weekly housekeeping of both databases (`addresses/housekeeping.py`, command `housekeeping`, administration page "Housekeeping", right `addresses.run_housekeeping`). The scheduled run is the task `housekeeping` of `run_scheduled_tasks`: Sunday from 04:30 instance time, once per ISO week; a manual run counts for its week. Manual start: the button of the page (a thread of the web process, D-090) or `manage.py housekeeping --now`.
* **Address directory file.** `PRAGMA quick_check`, then `VACUUM` in place, then `quick_check` again. Only when no import holds the claim, no setup of the directory file runs, and the free disk space is at least twice the file size (main file plus `-wal`) plus 1 GiB; `VACUUM` writes a temporary copy into the folder of the file (SQLite's temporary folder; `SQLITE_TMPDIR` is set to that folder, `addresses/sqlite/base.py`). Otherwise the step is skipped with a fixed reason. No rebuild and no deletion: a rebuild stays with the setup after a schema change (D-075).
* **Application database (MariaDB).** `OPTIMIZE TABLE` on the sessions, the login attempts (`LoginIpAttempt`, `SessionCodeFailure`, `ConfirmationFailure`), the mail queue (`MailJob`) and the building lookups (`BuildingLookup`). Only when the status file of the housekeeping dump is readable, reports success and is at most two hours old.
* **Dump of the housekeeping (owner decision 2026-10-26).** A root unit (`docs/DEPLOYMENT.md`, section 12.5) writes `housekeeping-<UTC>.sql.gz` shortly before the run and the status file `/var/lib/leg-platform/housekeeping-backup.json` (`finished_at`, `ok`, `file_name`), atomically. The application only reads that status file. The daily backup, its retention and its status file are neither read, changed nor deleted by the housekeeping.
* **Deletion of dumps (owner decision 2026-10-26).** Only a root unit deletes `housekeeping-*.sql.gz`. With no open error it keeps the newest dump; while an error is open it keeps the newest two. It never deletes the only dump of an open error, and it removes `housekeeping-*.sql.gz.tmp` leftovers in every case. The application never creates or deletes a dump.
* **Error state (owner decisions 2026-10-26).** A failed step (address directory, application database, or a dump that is missing, failed, unreadable, invalid or too old) opens an error: `HousekeepingError` rows with the step, the fixed reason code and the dump file name only. While an error is open, the weekly run does not run again (a manual start is still allowed); the error is cleared only by a successful run or by the button "Acknowledge the errors" (right `addresses.run_housekeeping`, CSRF-protected POST; it changes only the flag, starts nothing, touches no dump, table or file; one security event `housekeeping_errors_acknowledged`). The admin page lists only these housekeeping errors.
* **Error notice (owner decision 2026-10-26).** There is no separate housekeeping mail: an opened error is notified through the log notice (D-120, D-122; source `housekeeping`).
* **Restore.** No restore button and no restore code. A restore is a manual root procedure (runbook: `docs/DEPLOYMENT.md`, section 12.2). Owner decision pending: whether a restore function is wanted later.
* **Concurrency.** A run takes a lease (three hours) under the row lock of `ImportRequest`, the import claim (D-090). `jobs.claim` refuses an import while the lease is active; a run is refused while an import runs. One run at a time.
* **Failures and record.** Each step records a fixed message code (`housekeeping.message_text`); a failing step stops nothing else. The result of a run is written once, in the same write that releases the lease, and only for the run that holds the lease (a late run cannot overwrite a newer result). One security event `housekeeping_run` per run: fixed text, no SQL, no table content, no file name.
* **Why.** `OPTIMIZE TABLE` locks the table for its duration; `VACUUM` needs free disk space and must not overlap an import; the web service user cannot read the backup directory (`docs/SECURITY.md`, section 9).
* **Consequence.** `HousekeepingStatus` lives in the application database; the schema of the directory file is unchanged. `run_scheduled_tasks` has the task `housekeeping`; the security event `housekeeping_run` exists.
* **Residual risk.** The optimisation locks the sessions and the mail queue while it runs (default time Sunday 04:30; the daily import at 03:00 must have finished). Dumps of failed runs stay under the retention rule above (newest two while an error is open). Leftover `housekeeping-*.sql.gz.tmp` files of killed runs are removed by the root cleanup in every case. The dumps are unencrypted database copies in the root-only backup directory, as the daily dump is. The SQLite and MariaDB behaviour cited in the code (`VACUUM`, `quick_check`, `OPTIMIZE TABLE`) not re-checked against the vendor documentation. The server units are not verified.

### D-133 Imports run in a worker service, not in the web process (2026-10-31)

* **Cause.** On stage an address import failed with "interrupted because the application stopped or restarted": it ran in a thread of the web worker, and gunicorn recycled that worker (`--max-requests`). The status page polled every 2 s, about 1800 requests an hour, so an import of more than 35 minutes (45 minutes to 1 h 40 on the 1 vCPU stage server) always hit the limit. Not an OOM kill.
* **Decision.** The web process runs no import. The buttons only enqueue (`jobs.enqueue`); the supervised service `manage.py process_import_queue --loop` (`addresses/worker.py`) claims the oldest entry (`jobs.claim(queued=True)`, D-090 single claim, D-132 queue) and runs the jobs one after the other with a heartbeat (`runner.execute_with_heartbeat`). `runner.start_queue`, `start_manual`, the web import thread and its `atexit` hook are removed; the command `process_address_imports` is replaced by `process_import_queue`. `run_queue` of the scheduled tasks stays as the fallback consumer.
* **Stop.** `SIGTERM` or `SIGINT` interrupts a running job at once (`jobs.WorkerStopped`, a `BaseException`, so no importer turns it into a file failure), records it with the reason `jobs.STOPPED` and the time, and puts the source at the front of the queue (`jobs.requeue_first`): it runs again when the service starts, the other entries keep their order. The live directory is untouched (an incomplete generation is invisible). A killed process leaves the job to the next claim, which finds the stale heartbeat (90 s) and stores `jobs.LEASE_EXPIRED`; that job is not queued again (a crash loop must not repeat a download).
* **Visible reason.** Every interruption stores the fixed reason and time in the result of its source (`last_*_error`, `last_*_finished_at`), in the import log (`ImportLogEntry`) and as a WARNING with the source in `application.log`. A requeued source shows the reason in its table row while it waits. Reasons: `jobs.STOPPED` (service stopped, requeued), `jobs.LEASE_EXPIRED` (no sign of life), `jobs.INTERRUPTED` (rows stored before this decision). No migration: the columns are free text of the fixed sentences.
* **Polling.** The status GET stays write-free (D-132). The script asks every 5 s (was 2 s), not while the tab is hidden, and asks at once when it is shown again (`document.visibilityState`).
* **Gunicorn.** `--max-requests` may stay; a recycle or restart of the web service no longer touches an import.
* **Deployment.** New unit `leg-platform-imports.service` (`docs/DEPLOYMENT.md`, 8.4): same hardening as the web unit, `PrivateTmp=yes` (the address SQLite import needs it), `TimeoutStopSec=60`, `Restart=always`. The deployment script must enable it once and restart it on every deployment.
* **Residual risk.** Without the service a queued import waits for the next tick of the scheduled tasks (at most 15 minutes); the page says so ("The import service is not running") when imports wait and `ImportRequest.worker_seen_at` is older than a minute (migration `addresses/0023`, `in_place`). A stop during the short bookkeeping of a finished job is left to the lease (`stopped responding`).
* **Amends** D-090 (thread of the web process, `atexit`, 2 s polling) and D-132 ("Queue": thread drains the queue; "Open": wait after a restart).

* **Cause.** The full import (addresses, PV plants, transformer scan) takes hours on the one-core server. The owner builds the file elsewhere and uploads it over SSH, not through GitHub.

### D-136 A new registration is confirmed with a code from the email (2026-11-01)

* **Owner decision.** Simplicity and trust: step 1 of the registration of a new address no longer mails a link but a six-digit code that the person enters in the same browser tab. Everything else stays link-based (password reset, email change, second address, invitations and the registration of an address staff invited, stop links, second-factor reset, recovery). Closing the tab means starting again; there is no link fallback. The password rule of the same day is D-004 (minimum 8).
* **Flow.** `/register/` ("Send code") -> `/register/code/` ("Enter code": "We sent an email to ... It contains a 6-digit code. If you received a link instead, open that link." (honest for every address, because a staff-invited address gets its invitation link, which now also says that no code is needed), "The code is valid for 15 minutes.", one field with the help "6 digits from the email", "Confirm", "Send new code", "Change address") -> steps 2 and 3 unchanged (`registration_method`, `registration_password`, `registration_complete`). The page after step 1 and its answers are identical for every address (D-058). The wrong-code messages are field errors (`aria-invalid`, `aria-describedby`). After a resend the page shows "We sent a new code. The old code no longer works." "Change address" fills the previous address into step 1 again (from the session, once, never in the URL).
* **Resend and the dead code (follow-up of the design review).** The pause of 60 s (server enforced) protects a LIVE code only. When the code is dead (five wrong entries or expired) the page enables "Send new code" at once and the server accepts it at once (`RegistrationResendView.pause`); the D-038 and per-IP limits still apply. "Live" is the state of the challenge row (not used, not expired, fewer than five wrong entries), so addresses with an account look the same.
* **Bot check.** A request caught by the honeypot or form timer gets the same page but NO challenge row (a decoy value in the session, `registration.DECOY_PREFIX`).
* **Code.** `secrets.randbelow(10**6)`, zero-padded; valid 15 minutes (`registration.CODE_LIFETIME`); single use; at most 5 wrong entries per challenge, the fifth kills the code ("This code is no longer valid. Request a new code."); a wrong entry says "This code is not correct. Please check it and try again."; a resend creates a new challenge and discards the old one. One text field, `autocomplete="one-time-code"`, `inputmode="numeric"`, no `maxlength`/`pattern`; spaces and hyphens are removed on the server (like `totp.normalize_code`); no script is needed.
* **Own model, not `VerificationToken`.** `RegistrationChallenge` (`accounts/models/registration_codes.py`): 10^6 codes would collide with the unique digest of `VerificationToken`. A random challenge id (`token_urlsafe(32)`) lives in the session, the table holds only its keyed digest (HKDF label "registration challenge v1") and the keyed digest of the code with the challenge id mixed in (own HKDF label "registration code v1"), compared with `hmac.compare_digest`. Fields: address (canonical), expiry, failed attempts, consumed, proof end, account. Not bound to the session key, so `cycle_key()` after the proof does not break it.
* **No account oracle.** A challenge row exists for EVERY entered address, also for addresses with an account. For active, temporarily locked and blocked accounts no code is made; the information mail (no code, once a day) goes out as before. The attempt counter works without a code, so the fifth wrong entry answers the same for every address. The worker serves the newest open challenge of an address; a retry of a job replaces the code (never two valid codes per challenge, at-least-once stays safe).
* **Account and proof.** The unverified account is created only when the code is confirmed (account row locked first, then the challenge row, D-072; challenge rows without an account alone, never `nowait`). After success: `cycle_key()`, the challenge row becomes the "address proven" state for 2 hours (`PROOF_LIFETIME`; the unverified account is deleted by `delete_expired_registrations` after it ends); the staged sign-in method (`registration_methods`) is bound to the digest of the challenge, as it was to the link digest. A new proof or choice deletes earlier staged data; "Change address" discards the challenge and the staged data. An uninvited unverified account of the address is replaced; an invited one is kept (D-087).
* **Mail.** HTML (the Graph backend sends one body, `contentType` HTML, no attachment) with a text variant (also used with `EMAIL_MODE=console`). The SUBJECT CONTAINS THE CODE: "<code> is your <instance name> code". Body: instance name small and grey; ONE box with only the digits (about 40 px, bold, monospace, centred); the line "Confirmation code · valid for 15 minutes"; small print ("If you did not request this, ignore this email.", "Never share this code. Enter it only on the page where you requested it."); the privacy link and an optional contact line. No other large number, button, link, image, script, tracking or external resource; inline CSS, table layout of at most 520 px, `color-scheme` meta. Everything is escaped (`accounts/code_mail.py`; instance values are operator data). The administrator-editable `EmailText` stays plain text: `{code}` (required in the subject and in the body, alone in a paragraph) and `{lifetime_minutes}` replace the link placeholders; the HTML wrapper is fixed in code. The information mail stays as it was.
* **Why the code is in the subject.** A subject shows on a lock screen. For registration only this is accepted: whoever reads the code still needs the session that asked for it (the code works only in the requesting session), so a bystander cannot use it. It is NOT accepted for password reset, login or any code that is not bound to a session.
* **Queue.** A registration job older than 5 minutes (`registration.JOB_MAX_AGE`) is dropped, so a code does not arrive nearly expired.
* **Limits.** D-038 limits stay (per address, client address, instance). Added: entries of codes per client address (30 in 10 minutes, 100 in an hour, `rate_limits.REGISTRATION_CODE_IP_LIMITS`); above it HTTP 429 with the existing "Too many requests" text. Security log: `REGISTRATION_COMPLETED` is reused; no new event, no personal data.
* **Amends.** D-037 ("plain text only": HTML only for this one mail), D-038 (the registration job carries no link and has a maximum age), D-058 (no registration link and no link lifetime for new addresses; the page "link no longer valid" remains for invitations and resets).
* **Expiry.** `expires_at` is set once at the request (15 min) for every address kind and not reset when the worker makes the code, so "expired" and the resend unlock come at the same moment for every address (no timing oracle). The queue drops registration jobs older than 5 minutes, so a mailed code arrives with at least 10 minutes left.
* **Risks.** Guessing: someone who enters a victim's address starts a challenge of their own and the code goes to the victim, bound to the attacker's session (the worker serves the newest open challenge of the address whatever session made it); the attacker has 5 blind guesses per mail. The address budget (12 an hour, 24 a day) allows at most 120 guesses per address and day (about 1.2e-4); the instance-wide limit of 300 requests an hour gives about 0.04 expected hits a day over all addresses. Accepted by design. A per-address cap on wrong entries is NOT added: it would let an attacker kill a victim's code. A staff-invited address that asks for a code sees the same page (whose text is honest for everyone) but receives the invitation link. Timing differences between the answers are not eliminated (D-058 limits the oracle to the sent mail).
* **Mail follow-ups.** A purpose line above the box ("Your code to create your account"), a hidden preheader that starts with the code (so a mail list preview shows it; not visible in the mail), the box with a 2 px grey edge. The contact line stays plain text: the rule "no link but the privacy notice" holds. The invitation mail (and an administrator-edited text of it, which does not change by itself) says "You do not need to enter a code. Open the link."
* **Password page wording.** Django's "too common" message is replaced by "This password is used very often. Please choose another one, for example a sentence of several words." (`accounts/password_validators.py`; no new rule).
* **Steps.** "Step 2 of 3" covers the choice of the sign-in method AND its setup (password, app or passkey page): sub-steps of one step, so the numbering stays.
