## D-003: User Interface

* Date: 2026-10-09 (updated)
* Status: Decided
* Decision: Tabler for the application interface and the Django admin for system administration. No second UI framework. The application interface is responsive and fully usable on mobile phones in phase 1 (`docs/PROJECT.md`, "Supported Devices").
* Rationale: No unnecessary combination of several dashboard frameworks. Tabler describes itself as an "admin dashboard UI kit" for "admin panels, dashboards and web apps" and can therefore also serve later administrative application views. Tabler is built on Bootstrap 5, which "is developed mobile first".
* Alternatives: AdminLTE 4 or CoreUI for administrative views (not pursued: a second UI framework would mean two sets of templates, styles, JavaScript dependencies and security updates without functional gain; several CoreUI components are only available in the paid PRO version).
* Sources: https://github.com/tabler/tabler, https://getbootstrap.com/docs/5.3/getting-started/introduction/, https://github.com/ColorlibHQ/AdminLTE, https://github.com/coreui/coreui-free-bootstrap-admin-template (checked on 2026-10-09)
* Consequences: Tabler states minimum browser versions (Chrome/Edge 123, Firefox 128, Safari 17.5, Opera 109); older devices whose browsers cannot be updated are not supported. This is documented for operators and users.
* Design language: `docs/DESIGN.md` (D-024).

## D-004: Authentication in Phase 1

* Date: 2026-10-09 (updated)
* Status: Decided
* Decision:
  * Phase 1 supports password login with the email address (D-021).
  * Two-factor authentication with an authenticator app (TOTP, e.g. Google or Microsoft Authenticator) is mandatory for staff users and system administrators and optional for users. An account that receives `is_staff` or `is_superuser` must set it up at its next login; until then its session has no privileges.
  * Single-use recovery codes are issued at setup and can be generated again after re-authentication.
  * Lost second factor without recovery code: for users, a system administrator may start the removal; the application sends a time-limited, single-use confirmation link to the registered email address, and the second factor is removed only after confirmation. The sender address of an incoming email is not accepted as proof, because it can be forged (RFC 7489). For staff users and system administrators, a system administrator resets it only after verifying the person's identity in person or by calling back a phone number known independently of the account; for the last system administrator only via a management command on the server. Every reset is logged and notified.
  * A password reset never removes or bypasses the second factor. Re-authentication requires the second factor if it is set up.
  * Password rules use Django's password validators: minimum length 15 characters for all accounts, maximum at least 64, no composition rules.
  * AGOV (the login service of the Swiss authorities) is intended as the second factor. The project owner has asked AGOV whether this use is permitted (status 2026-10-09: answer pending). Until then TOTP is used. If AGOV is permitted, the second factor is switched to AGOV, expected before going live, without changing the architecture or weakening security. Phase 1 therefore checks the completed second factor in one central place, independent of the method, and keeps the TOTP-specific parts separate (`docs/PROJECT.md`, "AGOV and Passkeys"). AGOV itself is connected only after the clarification.
  * Whether password login can later be disabled for system administrators once AGOV or passkeys are available is open.
  * Passkeys are a security goal and must be assessed together with account recovery and account protection.
* Verified facts:
  * `django-otp` provides TOTP devices that can be paired with Google Authenticator via the `otpauth` URL scheme, and static tokens usable as recovery codes. Its `OTPMiddleware` "adds `user.is_verified()` as a counterpart to `user.is_authenticated()`", and "Support for additional devices is handled by plugins" that subclass `django_otp.models.Device`; the verified state is therefore not tied to TOTP.
  * OWASP Authentication Cheat Sheet: minimum password length 15 characters without MFA and 8 with MFA, maximum at least 64; with MFA, re-authentication for email changes should use multi-factor verification. Because two-factor authentication is optional for users and can be removed, 15 characters apply to all accounts.
  * OWASP Multifactor Authentication Cheat Sheet: recovery codes and a "rigorous process" to verify identity for support-based resets are suggested methods; recovery mechanisms must not provide a way to bypass MFA.
  * Large providers restrict manual resets; GitHub, for example, states: "GitHub Support will not be able to restore access to accounts with two-factor authentication enabled if you lose your two-factor authentication credentials."
* Rationale for the lost-factor rule: users only have access to their own profile, and a password reset by email already gives access to accounts without a second factor; a confirmation through the registered mailbox is therefore proportionate. A security review on 2026-10-09 found that relying on the sender address of a request would allow an attacker who knows the password to forge it; the confirmation link closes this gap. Staff users and system administrators have extensive access and require a strict identity check; there are few such accounts, so the effort stays small.
* Not yet verified: how `django-otp` protects the Django admin; to be verified in its documentation before implementation.
* Security implications: system administrators have all permissions and staff users have extensive access; a password alone is not sufficient protection for these accounts. For users, the email account is the recovery anchor; its compromise together with the password allows removing the second factor through a system administrator.
* Sources: https://django-otp-official.readthedocs.io/en/stable/overview.html, https://pypi.org/project/django-otp/, https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html, https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html, https://www.rfc-editor.org/rfc/rfc7489, https://docs.github.com/en/authentication/securing-your-account-with-two-factor-authentication-2fa/recovering-your-account-if-you-lose-your-2fa-credentials (checked on 2026-10-09)

## D-005: Initial System Administrator

* Date: 2026-10-09 (updated)
* Status: Decided
* Decision:
  * The first system administrator account (Django superuser) of an instance is set up manually via a Django management command run in a terminal on the server. There is no fully automated setup and no setup function on the website.
  * The email address is read from the local, Git-ignored `.env` file of the instance. It is not recorded in the repository.
  * The command asks for the initial password interactively with hidden input. The password is never stored in `.env`, in other files or in logs.
  * The command only runs as long as no system administrator exists. It never overwrites or resets an existing account.
  * At the first login, the password must be changed and two-factor authentication must be set up before anything else is possible.
  * A separate management command restores access in an emergency (e.g. resetting the second factor of the last system administrator, unblocking a system administrator). It is run only on the server and its use is logged.
* Verified facts: Django's own `createsuperuser` command asks for the password interactively in the same way.
* Not yet verified: whether an established package provides the forced password change at first login; otherwise it is implemented as a small, tested component.
* Security implications: the password never exists in plain text in a file. A terminal on the server is required; the project owner expects it to be available for the Ittigen instance.
* Alternatives: initial password in `.env` (rejected: plain text in a file until it is removed manually); setup via the website (rejected: whoever opens the page first could take over the instance).
* Sources: https://docs.djangoproject.com/en/stable/ref/django-admin/#createsuperuser

## D-006: Email Delivery via Microsoft Graph

* Date: 2026-10-09 (updated)
* Status: Decided
* Decision:
  * Outgoing email is sent via Microsoft Graph: email verification, password reset, security notifications and account notifications where needed.
  * The system administrator maintains the configuration in a dedicated section of the Django admin: tenant ID, client ID, sender address, client secret and its expiry date, plus a test send with understandable feedback.
  * The client secret is write-only. After saving, only "set" and the expiry date are displayed; the admin warns before expiry.
  * The client secret is stored encrypted in the database. The key is derived from Django's `SECRET_KEY` with HKDF and a fixed, purpose-specific label; the secret is encrypted with Fernet. Both come from the established `cryptography` library. Keys derived from `SECRET_KEY_FALLBACKS` are tried for decryption, after which the secret is encrypted again with the current key. If no key matches, the admin clearly asks for the secret to be entered again.
  * The configuration is accessible only to system administrators; every change is logged.
  * In Exchange Online, the application is restricted to the sender mailbox with "RBAC for Applications"; no organisation-wide `Mail.Send` permission remains in Microsoft Entra ID. The installation guide explains this step by step.
  * The environment variable `EMAIL_MODE` controls delivery: `console` (default, output only), `allowlist` (only to `EMAIL_ALLOWED_RECIPIENTS`) and `graph` (unrestricted, only allowed with `APP_ENV=production`).
  * Security notifications tell the person to contact the operator if they did not request the change; they do not ask for a reply (changed on 2026-10-13, D-038: automatic emails expect no reply, and the sender is a noreply address by default). No separate reply address is configured.
* Verified facts:
  * The application permission `Mail.Send` "allows the app to send mail as any user without a signed-in user".
  * RBAC for Applications in Exchange Online allows restricting an application to specific mailboxes and replaces Application Access Policies. Permissions granted in Microsoft Entra ID and in RBAC for Applications are additive, so the unscoped Entra grant must be removed.
  * `SECRET_KEY` is used for cryptographic signing; Django supports rotation via `SECRET_KEY_FALLBACKS`.
* Not yet verified: the exact HKDF and Fernet API of the installed `cryptography` version; to be verified before implementation.
* Rationale: the database password alone does not protect against leaked backups or database exports, access by hosting staff or SQL injection. Deriving the key from `SECRET_KEY` adds this protection without additional effort for operators. HKDF with a purpose-specific label keeps this key separate from Django's other uses of `SECRET_KEY`.
* Alternatives: plain text storage (rejected: a leaked secret would allow sending mail as any user of the organisation); separate encryption key (rejected for now: additional burden for operators without in-depth IT knowledge); secret only in environment variables (rejected: the project owner wants the configuration in the admin); using `SECRET_KEY` directly as encryption key (rejected: no key separation).
* Open: whether certificate-based authentication is preferable to a client secret is to be checked in the Microsoft documentation.
* Sources: https://learn.microsoft.com/en-us/exchange/permissions-exo/application-rbac, https://docs.djangoproject.com/en/stable/ref/settings/#secret-key, https://pypi.org/project/cryptography/

## D-010: Language of Software, Documentation and User Interface

* Date: 2026-10-09
* Status: Decided
* Context: The software and its documentation should be uniform and maintainable internationally. The end users speak Swiss German. Multilingual support may follow later.
* Decision:
  * All software and project documentation are in English without exception: code, identifiers, database, stored key values, migrations, permission codenames, comments, docstrings, commit messages, branch names, logs, tests, configuration, URL paths, management commands and all documents in this repository.
  * Only the user interface is language-dependent. The default language is Swiss German, `LANGUAGE_CODE = "de-ch"`. The character "ß" is never used.
  * User-facing texts use Django's translation mechanism (English source texts, Swiss German translations in `locale/de_CH/LC_MESSAGES/django.po` under `LOCALE_PATHS`).
  * Texts that Django, its contrib apps or third-party packages deliver with "ß" are overridden in the project translation files. An automated check ensures that no displayed text contains "ß".
  * Phase 1 ships Swiss German only, without a language selection.
  * Communication between the project owner and the AI is in German. Instructions given in German are written in English when they go into the repository.
* Verified facts:
  * Django's `django/conf/locale/de_CH/` contains only `__init__.py` and `formats.py`, i.e. formats but no texts.
  * For a sublanguage without its own translation, Django falls back to the base language (`de-ch` → `de`).
  * Django's `de` translations contain "ß", e.g. "Schließen" (admin), "Datum außerhalb des zulässigen Bereichs", "Dieser Wert muss größer oder gleich … sein" (core), "Blockgröße" (auth).
  * Directories in `LOCALE_PATHS` have the highest precedence when Django looks up translations.
* Rationale: English is the common language for code, libraries and Django's documentation. The built-in translation mechanism allows multilingual support without restructuring.
* Security implications: none directly. Uniform identifiers make reviews and security checks easier.
* Alternatives: German identifiers in code (rejected); German user texts hard-coded in code (rejected, because multilingual support would then require restructuring); `LANGUAGE_CODE = "de"` (rejected, Swiss German is required).
* Sources: https://docs.djangoproject.com/en/stable/topics/i18n/translation/, https://docs.djangoproject.com/en/stable/ref/settings/#language-code, https://docs.djangoproject.com/en/stable/ref/settings/#locale-paths, https://github.com/django/django/tree/main/django/conf/locale (checked on 2026-10-09 on branch `main`; to be re-checked against the installed Django version)
* Consequences: Every user-facing text requires a Swiss German translation. Missing translations and "ß" in displayed texts are defects. Each Django upgrade and each new third-party package requires a check for new texts containing "ß".

## D-012: Role Model

* Date: 2026-10-09 (updated)
* Status: Decided
* Context: The concrete roles of the LEG are not yet known. Roles may be renamed later, and further roles will be added and linked to permissions over time.
* Decision:
  * Fixed access levels are the **system administrator** (responsible for the instance, implemented as Django `is_superuser` with `is_staff`, has all permissions), the **staff user** (`is_staff` without `is_superuser`, access to the admin with only the permissions assigned to it) and the **authenticated user** (logged in, no additional permissions, access to their own profile only).
  * All further roles are Django groups. They are created, named, renamed and linked to permissions in the admin. They are runtime data, not code.
  * No role is hard-coded. No code, migration or fixture creates, names or checks specific roles.
  * Authorization checks use permissions only, never group names.
  * Permissions for application functions are defined in code with English codenames.
  * New users receive no group memberships, no additional permissions, no `is_staff` and no `is_superuser`.
  * Only system administrators manage roles, permissions, role assignments, `is_staff` and `is_superuser`. This is enforced technically, including for staff users who have permissions to add or change users.
  * Staff users can never change, block, deactivate or delete the accounts of staff users or system administrators, including their own account in the admin, and never change the password, email address or second factor of another account.
  * Nobody can promote their own account. Promotions are performed only by an authorized superior; `is_superuser` is only granted by another system administrator.
  * System administrators can block other system administrators and remove their rights. At least one active, not blocked system administrator always remains; emergency access is restored via a management command on the server (D-005).
  * Example roles ("Content administrator", "Auditor", "Banker", "Moderator") are illustrations only and are not implemented.
* Verified facts:
  * A Django group is a generic way of categorising users to apply permissions; a user in a group automatically has the group's permissions.
  * The group name is a freely editable field (up to 150 characters).
  * `is_superuser` treats the user as having all permissions without assigning them individually.
  * `is_staff` allows access to the admin site; "by default, logging in to the admin requires that the user has the `is_staff` attribute set to `True`".
  * Django warns: "If you give a non-superuser the ability to edit users, this is ultimately the same as giving them superuser status because they will be able to elevate permissions of users including themselves!"
* Rationale: Django's built-in groups and permissions provide exactly the required flexibility without custom role logic.
* Security implications:
  * System administrators bypass all permission checks. The number of system administrator accounts is kept to a minimum, these accounts require strong authentication, and administrative actions are logged.
  * Anyone allowed to change users, groups or permissions without restriction can grant themselves further rights (privilege escalation). The admin therefore restricts these functions to system administrators, and delegating role assignment to other roles requires a separate, reviewed decision. Every promotion is logged.
  * A system administrator can always create a second account and promote it; "nobody can promote their own account" does not limit system administrators. Logging makes such actions traceable.
  * Later financial functions may require separation of duties (e.g. a four-eyes principle). A system administrator who can do everything conflicts with this. This must be assessed before financial modules are planned.
  * Because roles are data, tests must create the groups and permissions they need themselves and must not rely on predefined roles.
* Alternatives: hard-coded roles in code or migrations (rejected, because roles must be renamable and extensible at runtime); custom role model (rejected, Django's built-in model suffices).
* Terminology: see `docs/PROJECT.md`, section "Terminology".
* Sources: https://docs.djangoproject.com/en/stable/topics/auth/default/, https://docs.djangoproject.com/en/stable/ref/contrib/auth/, https://docs.djangoproject.com/en/stable/ref/contrib/admin/
* Consequences: Every protected function defines and checks a permission. Roles become meaningful only once a system administrator creates them in the admin and assigns permissions.

## D-013: Deployment Model – One Instance per Municipality

* Date: 2026-10-09
* Status: Decided
* Context: The application is built for the LEG in Ittigen. Other municipalities (e.g. Bolligen) may later want to use the same software. A multi-tenant design (several municipalities in one instance with tenant administrators) was discussed in detail and rejected in favour of separate instances.
* Decision:
  * The application is not multi-tenant. Each municipality runs its own, independent instance.
  * Each instance has its own database, configuration, secrets, users and system administrators. Instances share no data.
  * A person who uses several instances has a separate, independent account in each and may use the same email address in each.
  * The same code base serves all instances. Instance-specific values (e.g. name of the community or municipality, domain, canonical base URL, sender address, contact details) are part of the instance configuration and are never hard-coded in code, templates or migrations.
  * A new instance is set up from the same code base using only the documented installation steps and its own configuration.
  * Operation, updates, backups and data of an instance are the responsibility of its operator.
* Verified facts:
  * By law, an LEG covers at most the area of one political municipality (Art. 17d para. 3 StromVG). One instance per municipality therefore matches the legal maximum extent of an LEG.
  * Postal codes do not match municipal boundaries: according to the official directory of localities (swisstopo), one postal code can cover several municipalities (e.g. 3048 Worblaufen: 81.9 % of addresses in Ittigen, 18.1 % in Bern). This was relevant for the rejected multi-tenant design and becomes relevant again when locations are introduced.
  * Django's permission framework does not implement object permissions in its core. A multi-tenant design would have required a custom, central tenant separation mechanism.
* Rationale:
  * Multi-tenancy is not needed for the current goal (one LEG in Ittigen); other municipalities are only potential future users. The project rules forbid overloading the foundation with speculative functionality.
  * Separate instances with separate databases are the strongest form of data separation. A programming error cannot disclose data of one municipality to another.
  * Considerably less complexity in the data model, authorization and tests.
* Security implications:
  * Positive: no cross-municipality data disclosure is possible within the application.
  * Every instance must be kept up to date with security updates. An instance that is not maintained is a risk for its own data. Update and operating responsibilities must be clarified with every additional operator.
  * `ALLOWED_HOSTS` lists only the instance's own domains; links in emails are built from the canonical base URL of the instance.
* Alternatives: multi-tenant platform with tenants, tenant administrators and tenant switching (rejected: high complexity and a primary security boundary inside the application, without a current need).
* Sources: StromVG Art. 17d (https://fedlex.data.admin.ch/filestore/fedlex.data.admin.ch/eli/cc/2007/418/20260401/de/pdf-a/fedlex-data-admin-ch-eli-cc-2007-418-20260401-de-pdf-a-1.pdf, version of 1 April 2026), swisstopo "Amtliches Ortschaftenverzeichnis" (https://www.swisstopo.admin.ch/de/amtliches-ortschaftenverzeichnis, dataset checked on 2026-10-09), https://docs.djangoproject.com/en/stable/topics/auth/customizing/, https://docs.djangoproject.com/en/stable/ref/settings/#allowed-hosts
* Consequences:
  * No tenant concept in the data model, authorization or user interface.
  * Combining several municipalities in one instance later would be a significant redesign.
  * There is no central administration across instances.

## D-015: Supported Versions and Versioning

* Date: 2026-10-09 (updated)
* Status: Decided
* Decision:
  * Only minimum versions of Python, Django, the database (MariaDB since 2026-10-11, D-030) and all packages are specified: the oldest versions that are technically possible and still receive security updates from their vendor.
  * The minimum versions result from the functions used and from the requirements of the packages used (e.g. `django-axes` requires Python ≥ 3.10). They are determined from official sources and proven by automated tests, not estimated.
  * No package with known security vulnerabilities is used in order to support old versions.
  * When a minimum version reaches its vendor's end of security support, the minimum version is raised.
  * Declared versus used versions (project owner, 2026-10-11, applies to the whole development): the minimum versions are declared and tested, but whenever a version is chosen for use (development environment, dependency installation, continuous integration "latest" jobs, recommendations for operators), the newest possible version is used: the newest release that is compatible with the other components and, for components with long-term support tracks (e.g. MariaDB), the newest release of the long-term support track, so that instances can stay on a stable version for as long as possible.
  * The software uses semantic versioning. Raising the minimum major version of Python, Django or MariaDB can lead to a new major version of the software.
* Verified facts: Django 4.2 no longer receives security updates since 7 April 2026; Django 5.2 LTS receives them until April 2028 (checked on 2026-10-09). `django-axes` 8.3.1 still declares Django 4.2, so package declarations alone do not determine the minimum version.
* Support periods of MySQL and Python: checked on 2026-10-11 against the vendors' official pages; results and proposed minimum versions in D-026. Since 2026-10-11 the database is MariaDB; its minimum version (10.11) and support periods are in D-030.
* Update (project owner, 2026-10-11): the minimum is raised to Django 6.0 (latest patch 6.0.9) and Python 3.12, because the project uses Django's built-in Content Security Policy support, which Django 6.0 introduced (D-026, D-028). Django 6.0 receives security fixes until April 2027 (https://www.djangoproject.com/download/, checked on 2026-10-11); the minimum must be raised to a supported release line by then at the latest.
* Open: how the minimum versions are proven by tests (e.g. a test matrix in continuous integration over the declared minimum and current versions); decided together with the minimum versions.
* Rationale: "as old as possible" alone would allow versions without security updates; declaring them as supported contradicts security by default.
* Sources: https://semver.org/, https://www.djangoproject.com/download/

## D-016: Account Lifecycle

* Date: 2026-10-09 (updated)
* Status: Decided
* Decision:
  * A person can log in once their email address is verified and a password is set. There is no approval step.
  * The password is set only after verification, via the verification link. Unverified accounts and their data are deleted automatically when the verification link expires; a new registration with the same address replaces a pending one. Reason (security review 2026-10-09): if the password were chosen at registration, an attacker could register with someone else's address and a known password, and the victim would activate the attacker's account by clicking the link.
  * Account states: unverified, active, blocked, deactivated; in addition, the abuse protection temporarily locks accounts after too many failed attempts (`docs/PROJECT.md`, "Account States").
  * System administrators can block and unblock accounts, including those of other system administrators. Blocked accounts cannot log in or reset their password. During a temporary lockout, a password reset remains possible.
  * Every account has a retention obligation flag. It is unset at registration. Later functions set it when the account is used for something subject to a retention obligation. It can only change from unset to set; the application rejects any attempt to unset it, including in the Django admin.
  * Deleting an account, by the user or by a system administrator, without a retention obligation removes all of its data; security log entries are kept without personal reference until they expire (D-018).
  * Deleting an account with a retention obligation deactivates it. A deactivated account cannot log in or reset its password; responses do not reveal its existence. The user cannot reactivate it.
  * Email addresses are unique among accounts that are not deactivated. The same email address can therefore be used for a new registration. Uniqueness is enforced by the database with a nullable column and a normal unique index, because MariaDB does not support conditional unique constraints (`docs/ARCHITECTURE.md`, "User Model and Login Identifiers").
  * A system administrator can reactivate a deactivated account unless an active, temporarily locked or blocked account with the same email address exists.
  * At least one active, not blocked system administrator always remains: the last one can neither be deleted, deactivated or blocked nor lose superuser status.
  * Users can change their email address. The change takes effect only after the new address has been verified; until then the old address remains valid. After verification the old address is replaced and the account continues under the new address. The change requires re-authentication, and the old address is notified. A change to an address of an active, temporarily locked or blocked account is not performed; the response is the same as for a successful request, and the new address receives an information email.
  * Registration with an address of an active, temporarily locked or blocked account creates no account; the response is the same as for a new registration, and the address receives an information email.
  * Confirming an email address change or reactivating an account deletes a pending unverified registration with the same address, so that a pending registration cannot block either.
  * Every path that deletes, deactivates, reactivates, blocks, unblocks, promotes or demotes accounts, changes the email address or changes the retention flag goes through the central account logic, including admin bulk actions; Django's "delete selected objects" action does not call the model's `delete()` method.
  * In phase 1, no function sets the retention obligation yet; the flag and the deactivated state are part of the foundation so that later functions can build on them.
  * Profile data and purposes: customer number (generated when the registration is completed, i.e. when the password form is submitted successfully via the verification link, D-021), name, postal address and email address (all required; the email address is given at registration, the rest after the verification link when the registration is completed, project owner 2026-10-13) for identification and invoices by post or email; phone number (optional) for queries. The profile is complete from the start as a basis for the later LEG functions.
  * Backups are the responsibility of the operator. Deleted data can remain in backups until they expire; the documentation states this.
* Verified facts:
  * OWASP Authentication Cheat Sheet: account creation uses a generic response such as "A link to activate your account has been emailed to the address provided."; email changes send confirmation emails to both the old and the new address.
  * Django's password reset sends no email to inactive users and users without a usable password, and shows no error message ("This prevents information leaking to potential attackers.").
  * Django does not support conditions on MariaDB: "The `condition` argument is ignored with MySQL and MariaDB as neither supports conditional indexes" (Django documentation, "Model index reference"), and its system check `models.W036` reports "<database> does not support unique constraints with conditions" (Django documentation, "System check framework", 6.0); MariaDB unique indexes permit multiple `NULL` values ("A `UNIQUE` constraint allows multiple `NULL` values because in SQL, `NULL` is never equal to another `NULL`", MariaDB documentation, "MariaDB Indexes Guide", checked on 2026-10-11 after the switch to MariaDB, D-030).
* Security implications: the one-way rule for the retention obligation is enforced at application level; persons with direct database access can bypass it. Database privileges are therefore restricted (`docs/SECURITY.md`, section 9).
* Open: which concrete retention obligations apply and for how long is determined later from official legal sources.

## D-017: Protection Against Automated Login Attacks

* Date: 2026-10-09 (updated)
* Status: Decided (login protection and limits confirmed by the project owner on 2026-10-12; registration and recovery limits remain open)
* Decision:
  * Login abuse protection uses `django-axes` for temporary lockouts per normalised account identifier and a separate, transactional MariaDB counter for client IP addresses. The separate counter is required because Axes stores account and IP values in the same rows, and resetting rows by account also lowers IP failure counts.
  * Project owner decision (2026-10-12): five failed attempts in a rolling 15-minute window for both the account and the IP address. Successful completion of all required authentication factors releases the reserved IP slot; failed authentication retains the attempt until the window expires. An account reset clears only Axes account rows; it never touches the separate IP counter.
  * Account identifiers and IP addresses are canonicalised, then stored only as separate HMAC-SHA256 digests with keys derived from `SECRET_KEY` using HKDF and distinct purpose labels (D-023). Secret-key rotation resets these counters, as already accepted in D-023.
  * Axes account attempt rows store the keyed username, never the raw email or IP. The raw IP is used only in request memory to calculate its independent HMAC bucket; Axes success access logs are disabled. The POST fields `password`, `otp_token` and `otp_device` are masked. Axes' own admin is disabled until its records can be exposed through a read-only system-administrator-only view (D-018).
  * Lockouts are temporary (15-minute cool-off), so attackers cannot lock out other users permanently; password reset remains possible during an account lockout. A successful reset clears only the account lockout and leaves all IP counters unchanged.
  * Login with a nonexistent email address shows the same response and lockout behaviour as a wrong password.
  * Remaining risk: attackers who know an email address can repeatedly cause temporary lockouts of that account and use up the per-address email limit. Accepted, because lockouts are temporary, the most recent link sent to the owner's mailbox stays valid when the limit is exceeded (the attacker's own requests also deliver valid links to the owner), and new emails are possible after the time window.
  * Failed attempts are counted per normalised email address. The customer number is not a login identifier (D-021).
  * Client IP resolution defaults to `REMOTE_ADDR` and ignores forwarded headers (`AXES_IPWARE_PROXY_COUNT=0`). An instance behind proxies must set the exact trusted proxy count; IPware applies strict proxy-chain validation. Client-controlled headers are never accepted as IP identities by default.
  * Registration, password reset and email change requests are also rate-limited, per IP address and per normalised target email address (updated 2026-10-09: a limit per IP alone does not prevent flooding a mailbox from many addresses or repeatedly replacing another person's pending registration). The per-address limit restricts the emails sent; above it, a request is not processed and replaces nothing, so the most recent link sent stays valid. Neither the response nor the response time changes. The counters are kept only for the time window (`docs/SECURITY.md`, section 3).
  * Operators behind reverse proxies must configure their actual proxy count before relying on per-IP login protection.
* Verified facts:
  * `django-axes` "keeps track of failed login attempts in Django-powered sites"; release 8.3.1 (2026-02-11); declares Django 4.2, 5.2 and 6.0; requires Python ≥ 3.10.
  * `django-axes` provides `AXES_IPWARE_PROXY_COUNT` and related settings and warns that "the client can spoof IP addresses by just setting the header in their request".
  * Installed version 8.3.1 and its official documentation support independent username and IP lockout buckets with `AXES_LOCKOUT_PARAMETERS = ["username", "ip_address"]`, and `AXES_USERNAME_CALLABLE(request, credentials)` can canonicalise the submitted identifier.
  * In the installed database handler, one `AccessAttempt` row contains both username and IP address. Failure counts are sums over the rows matching each independent bucket. `reset_username` deletes rows by username, so deleting those rows also lowers the corresponding IP failure counts. The package's username reset therefore does not meet the requirement that a successful password reset leave IP counters unchanged.
  * The installed Axes admin exposes a cleanup action for attempts and does not override the default change/delete permissions. Its records require a read-only, system-administrator-only admin integration to meet D-018. Attempt query data masks `password` and configured sensitive fields; future OTP form fields must be added to `AXES_SENSITIVE_PARAMETERS`.
  * Runtime tests on Django 6.1.2, django-axes 8.3.1 and MariaDB verify five failed attempts across distinct usernames lock one IP; password-only `authenticate()` keeps its IP slot reserved, a subsequent successful Django `login()` releases it, expired attempts are ignored, and account resets do not lower IP counts. Separate IP tests verify that forwarded headers are ignored with proxy count 0 and a configured one-proxy chain resolves to the client.
  * `django-ipware` 8.0.0 declares Python 3.10+ and Django 5.2+; its package metadata declares MIT. `python-ipware` 4.1.1 is installed transitively and declares MIT.
  * OWASP Authentication Cheat Sheet: lockout mechanisms must not allow a denial of service by locking out other users' accounts; password recovery may remain possible for locked accounts.
* Open: the TOTP login flow must invoke Django `login()` only after all required factors succeed; add account/IP failure tests for OTP errors before enabling it. Also open are scheduling of the `cleanup_login_ip_attempts` management command and the Axes attempt-retention cleanup; the read-only administrator security-log view; rate limits for registration, password reset and email change; and timing-equivalent generic responses for those functions. Until those functions and OTP are wired, the admin and deployment remain restricted to `APP_ENV=local`.
* Sources: https://pypi.org/project/django-axes/, https://github.com/jazzband/django-axes, https://django-axes.readthedocs.io/en/latest/2_installation.html, https://django-axes.readthedocs.io/en/latest/3_usage.html, https://django-axes.readthedocs.io/en/latest/4_configuration.html, https://django-axes.readthedocs.io/en/latest/5_customization.html, https://pypi.org/project/django-ipware/, https://cryptography.io/en/latest/hazmat/primitives/key-derivation-functions/, https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html

## D-018: Security Logging

* Date: 2026-10-09 (updated)
* Status: Decided
* Decision:
  * Security-relevant events are logged; the list is in `docs/SECURITY.md`, section 10.
  * Logs never contain passwords, tokens, secrets or complete security links, and only as much personal data as necessary.
  * Only system administrators can view security logs.
  * Log entries of deleted accounts are kept without personal reference (e.g. only an internal number instead of name and email address).
  * Retention is configured per instance in the server configuration, not in the admin, with minimum values that cannot be undercut. Default: 1 year for changes of roles, permissions, `is_staff` and `is_superuser`, resets of the second factor of staff users and system administrators, blocking and unblocking of staff users and system administrators, changes by system administrators to the password or email address of another account, deletion, deactivation and reactivation of accounts by system administrators, use of emergency management commands and changes to the Microsoft Graph configuration, because misuse of privileges is often noticed late; 30 days for all other log entries, including the failed-attempt records of the abuse protection package. Expired entries are deleted automatically.
  * The security log, including the failed-attempt and lockout records of the abuse protection package, is append-only within the application; nobody, including system administrators, can create, change or delete entries through the admin or other application functions. Otherwise logging would not be an effective control over system administrators (D-012).
  * Log entries use an internal number, not the customer number, because the customer number appears on invoices.
  * The design follows established practice with good usability; the OWASP Logging Cheat Sheet is used as the basis and verified before implementation.
* Rationale: the project owner does not want to review logs daily and does not need entries older than about a month for operational errors. DSG Art. 6 para. 4 requires personal data to be destroyed or anonymised as soon as it is no longer required for the purpose.
* Open: how the automatic deletion is scheduled; decided at implementation together with the hosting.

## D-019: Agent Workflow

* Date: 2026-10-09 (updated)
* Status: Decided
* Decision:
  * `developer` implements. `tester` plans and runs tests and checks, including Django's security checks. `security-reviewer` reviews read-only.
  * `security-reviewer` is restricted technically via its `tools` list to `Read, Grep, Glob, WebFetch, WebSearch`: it cannot edit files, run commands, start subagents or instruct other agents.
  * `developer` and `tester` have no tool restrictions. They may start subagents for clearly bounded, simpler tasks (e.g. with a less expensive model) under the delegation rules in `AGENTS.md`, section 11. The delegating agent remains responsible and must review the result before using it.
  * Deliberately accepted deviation (project owner, 2026-10-09): `developer` keeps the unrestricted `Agent` tool and `tester` keeps `Edit` and `Write`, although a `tools` list or `disallowedTools` could restrict them. This is an accepted decision of the project owner, although such a restriction would be an effective technical control: it removes the tool completely and does not depend on anyone reading a permission prompt. Risks:
    * `developer` can start the `security-reviewer` or other agents itself and thereby influence the review of its own code.
    * `tester` can technically change application code, which its instructions forbid.

  * All agents and subagents follow the rules of conduct in `CONDUCT.md` ("don't be evil").
  * Self-improvement (project owner, 2026-10-09): agents may improve their agent files and the project instructions (`CLAUDE.md`, `AGENTS.md`) and record lessons learned, always under `CONDUCT.md` and never weakening security (`AGENTS.md`, section 12.2). Agent files are therefore not write-protected.
  * Protection of the premise "don't be evil" (project owner, 2026-10-09: it must never be deleted): the rules of conduct are kept in a separate file `CONDUCT.md`, because a single section of a file cannot be protected without protecting the whole file. Edit deny rules in `.claude/settings.json` cover `CONDUCT.md` and `.claude/settings.json` itself, so that the rule cannot be removed with Claude's file tools. Only the project owner changes these files. Limit (Claude Code documentation, "Configure permissions"): Edit deny rules apply to Claude's file tools and to file commands Claude Code recognises in Bash, but not "to arbitrary subprocesses that read or write files indirectly, like a Python or Node script that opens files itself"; whether they apply to PowerShell commands is not verified. The protection is therefore a technical barrier against accidental or casual changes, not a complete protection; `CONDUCT.md` itself forbids working around it. Further limits: the deny rules apply only to Claude Code, not to Codex (D-007); `.claude/settings.local.json` is not covered, and hooks configured there could run arbitrary commands (a deny rule for it is proposed to the project owner); the rule is only effective as long as `CLAUDE.md`, `AGENTS.md` and the agent files refer to `CONDUCT.md`, so these references are listed in `AGENTS.md`, section 12.2, as items that are never removed. Verified in the actual environment (2026-10-09): the Edit tool and `sed` were refused on `CONDUCT.md` and `.claude/settings.json`, also while the session's working directory was `.claude/agents`.
  * The Git repository (initialised on 2026-10-11) provides the baseline to compare changed control files against.
  * The main session coordinates: it passes review findings to the developer, has a new review run check the corrections, and reports findings, corrections and re-checks to the project owner. Critical findings and decisions go to the project owner.
  * Each agent reads only the documents it needs (listed in its agent file), to keep token usage low; `CLAUDE.md` is loaded into every subagent automatically.

  * Project subagents are stored in `.claude/agents/`; `name` and `description` are required.
  * If `tools` is omitted, a subagent inherits every available tool; a `tools` list restricts it to the listed tools.
  * By default, a subagent can spawn subagents of its own, up to three layers below the main conversation; omitting `Agent` from the `tools` list prevents this.
  * Each subagent starts with its own context and receives the delegation prompt written by the main session and the CLAUDE.md hierarchy.

Exceptions: the first agent file in a newly created `agents` directory, agent files in directories added with `--add-dir`, and sessions started with `--disable-slash-commands`.

User-level agents with other names (e.g. `critical-reviewer`) are also available in this project; they are not part of this workflow.

According to the documentation, changes are picked up without a restart; the cause of the observation is unknown. It was observed again on 2026-10-09 after a restart: agent files changed later in the same session were not picked up. After every change to an agent file, the session is therefore restarted and the loaded definitions are checked before the agents are relied on.
* Limits: the agents do not guarantee an independent security review. They use the same model, receive the same project instructions, and their task is formulated by the main session. Subagents started by agents are subject to the same limits. Critical changes additionally require a human review.

## D-021: User Model and Login Identifiers

* Date: 2026-10-09 (updated)
* Status: Decided
* Decision:
  * The project uses a custom user model from the first migration.
  * Every account receives a customer number exactly once, when the registration is completed (password form submitted successfully via the verification link), not at registration; email address changes and reactivation keep it, and the initial system administrator receives it from the setup command: six digits, random (cryptographically secure generator), unique, never reused, stored as text. Unverified accounts have no customer number. It is displayed in two blocks of three digits (e.g. `482 915`). Numbers of deleted accounts are kept in a list of retired numbers without personal reference. The customer number is read-only for everyone.
  * Login is possible only with the email address. The customer number identifies the account (e.g. later on invoices) but is not a login identifier.
  * Email addresses are normalised with Unicode NFKC, removal of surrounding white space and lower case. Internationalised domains are mapped to lowercase IDNA ASCII using UTS #46; the local part is ASCII only and the canonical form is stored (D-035; security review findings Q-1 and N-1, implementation in D-034).
* Reason for the update (project owner, 2026-10-09, after a consistency check):
  * Assigning the number at registration would let registrations that are never verified use up the at most one million numbers permanently, because numbers are never reused.
  * With login by email address and customer number, failed attempts would have to be counted per account across both identifiers. An attacker could then find out, from the earlier lockout, whether an email address and a customer number belong to the same account, which contradicts the rule that responses do not reveal the existence of accounts. Login with the email address only removes this side channel.
* Why retired numbers stay blocked even after a complete deletion: the number is shown to the person in the profile and may appear in their correspondence; a reused number could lead to mix-ups with a former holder (e.g. payments or enquiries quoting an old number). The list contains only numbers, without any link to a person, and does not limit capacity in practice once only verified accounts receive numbers. Confirmed by the project owner on 2026-10-09.
* Verified facts:
  * Django recommends setting up a custom user model when starting a new project; changing `AUTH_USER_MODEL` after database tables have been created "can be complex" and requires manual schema changes.
  * OWASP Authentication Cheat Sheet: email addresses may be used as usernames if verified; user IDs should ideally be randomly generated rather than sequential.
* Security implications: the customer number is an identifier, not a secret; it will later appear on invoices. Because it cannot be used to log in, knowing it gives no possibility to cause lockouts or to try passwords. With six digits there are at most one million numbers; this is sufficient for one LEG and is monitored if an instance grows.
* Sources: https://docs.djangoproject.com/en/stable/topics/auth/customizing/, https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html (checked on 2026-10-09)

## D-023: Password Hashing and Keyed Hashes

* Date: 2026-10-09
* Status: Decided
* Context: The project owner wants a high but not excessive work factor, because it is not yet known whether the hosting is billed by CPU usage or at a flat rate (D-008).
* Decision:
  * Passwords are hashed with Django's default password hasher (PBKDF2-HMAC-SHA256) and the default work factor of the installed Django version. The work factor is never lowered below this default and never below the OWASP recommendation of 600,000 iterations. It is not raised above the default for now.
  * Once the hosting is decided, the time for one password hash is measured on the actual server; per OWASP it should stay below one second. Only if the measurement and the cost model allow it is a higher work factor considered (a new decision).
  * The counters of the per-address rate limits (`docs/SECURITY.md`, section 3) store, where the package allows it, an HMAC-SHA256 of the normalised address instead of the address. The key is derived from `SECRET_KEY` with HKDF and its own purpose-specific label, as in D-006, using the `cryptography` library. A keyed hash needs no work factor: its protection comes entirely from the secret key, and its CPU cost is negligible. Before implementation it is checked whether Django provides a documented public function for this (e.g. `django.utils.crypto.salted_hmac`), which is then preferred over own code.
  * Consequences: rotating `SECRET_KEY` resets the running per-address counters once (acceptable; attackers cannot trigger a rotation, no fallback keys are needed for counters). If `SECRET_KEY` leaks, the hashes can be reversed cheaply with a list of known email addresses; the short retention limits the impact. When the rate-limit package is chosen, it is recorded whether plain addresses end up in its storage.
* Verified facts:
  * Django "uses PBKDF2 by default", has "chosen a reasonable default (and will increase it with each release of Django)", and re-hashes passwords when the number of iterations changes.
  * OWASP Password Storage Cheat Sheet: "PBKDF2-HMAC-SHA256: 600,000 iterations (recommended)"; "When you choose a work factor, strike a balance between security and performance"; "If the work factor is too high, the performance of the application may be degraded, which could be used by an attacker to carry out a denial of service attack"; "As a general rule, calculating a hash should take less than one second."
  * OWASP recommends Argon2id first ("minimum configuration of 19 MiB of memory, an iteration count of 2, and 1 degree of parallelism"); Django supports it but "it requires a third-party library" (`argon2-cffi`).
* Not yet verified: the default iteration count of the Django version that will be installed; checked at implementation against the Django release notes and source.
* Rationale: Django's default is maintained by the vendor and rises with each release, which matches "high but not excessive" without project-specific tuning. Abuse protection (D-017) limits how many hashes an attacker can trigger.
* Security implications: a higher work factor makes offline attacks on leaked hashes more expensive but increases CPU load per login and the risk of denial of service.
* Alternatives: Argon2id (OWASP's first recommendation; not chosen for now because it adds a dependency and memory use per login whose cost on the unknown hosting cannot be assessed yet; can be reconsidered with the hosting decision); a custom higher PBKDF2 work factor (not chosen until measured on the target server).
* Sources: https://docs.djangoproject.com/en/5.2/topics/auth/passwords/, https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html (checked on 2026-10-09)

## D-025: Portal Entry Point and Host Name

* Date: 2026-10-11 (security implications refined on the same day after a security review)
* Status: Decided
* Context: The project owner wants a single public website per LEG (for Ittigen: `leg-ittigen.ch`) with all information about the LEG. People log in to the application from there. The project owner originally considered the path `leg-ittigen.ch/login`.
* Decision:
  * The application has no public home page. Its entry point is the login page, which offers login, password reset and registration, and links to the privacy notice and to the instance's website.
  * Information about the LEG and public figures (e.g. number of members, production and use within the LEG) are not part of the application. They are provided by the instance's website. Publishing figures from the application on the website would require a public interface with its own security design; this is not part of phase 1.
  * The application runs on its own host name (e.g. a subdomain such as `portal.leg-ittigen.ch`), never under a path of the instance's website. The host name is part of the instance configuration. The operator chooses between a subdomain of the website's registrable domain and a host name under a separate registrable domain; the installation guide states the residual risk of a subdomain (see "Security implications").
  * The minimum number of participants from which aggregated figures may be published is deliberately left open; each operator decides it for its instance when such figures are introduced.
  * Onboarding per building or location after registration is intended for phase 2.
* Verified facts:
  * RFC 6454, section 3.2: two URIs are part of the same origin "if they have the same scheme, host, and port"; the path is not part of the origin. A website and the application under the same host therefore share one origin.
  * RFC 6265, section 8.5: "Cookies do not always provide isolation by path." Section 8.6: servers "SHOULD NOT both run mutually distrusting services on different paths of the same host and use cookies to store security-sensitive information."
  * Django documentation, CSRF, "Limitations": "Subdomains within a site will be able to set cookies on the client for the whole domain." A subdomain of the website's registrable domain is a different origin but still the same site as the website.
* Rationale: A vulnerability in the website (e.g. its content management system or a plugin) must not be able to act within authenticated sessions of the application. A separate host name provides origin isolation: the same-origin policy separates the DOM, scripts and `localStorage` of the website and the application. For users nothing changes, as the website links to the login page.
* Security implications:
  * Origin isolation is not site isolation. If the application runs on a subdomain of the website's registrable domain (e.g. `portal.leg-ittigen.ch` below `leg-ittigen.ch`), a compromised website can still set cookies for the parent domain that the browser also sends to the application (cookie tossing). Residual risks are session fixation and injection of a CSRF cookie. The `SameSite` cookie attribute gives no protection between subdomains of the same site.
  * Countermeasures (`docs/SECURITY.md`, sections 3 and 6): `SESSION_COOKIE_DOMAIN` and `CSRF_COOKIE_DOMAIN` are not set, so that the cookies are host-only (Django's default; to be verified against the installed version); `CSRF_TRUSTED_ORIGINS` never contains the instance's website or a wildcard for the parent domain; in stage and production the session and CSRF cookie names use the `__Host-` prefix, which supporting browsers accept only for cookies that are `Secure`, have `Path=/` and no `Domain` attribute, so that a cookie set by the website for the parent domain cannot take its place. The `__Host-` prefix is defined in draft-ietf-httpbis-rfc6265bis, an Internet-Draft, not in RFC 6265; browser support and compatibility with Django's cookie handling are verified at implementation.
  * A host name under a separate registrable domain is a different site and removes the cookie risks above. The operator chooses; the installation guide states the residual risk of a subdomain.
  * `ALLOWED_HOSTS` lists only the host names of the application, not the instance's website. This clarifies "the instance's own domains" in D-013.
* Alternatives: application under a path of the website (rejected for the reasons above); public home page in the application (rejected by the project owner: one public website per LEG); a mandatory separate registrable domain (not made mandatory: the operator chooses, and the residual risk of a subdomain is documented).
* Sources: statements of the project owner (2026-10-11); https://www.rfc-editor.org/rfc/rfc6454.html, section 3.2; https://www.rfc-editor.org/rfc/rfc6265.html, sections 8.5 and 8.6 (checked on 2026-10-11); https://docs.djangoproject.com/en/5.2/ref/csrf/, "Limitations"; draft-ietf-httpbis-rfc6265bis (https://datatracker.ietf.org/doc/draft-ietf-httpbis-rfc6265bis/), cookie name prefixes (both as cited in the security review of 2026-10-11, not yet re-checked in this document update; re-checked against the installed Django version and the current draft revision at implementation)
* Consequences: `docs/PROJECT.md`, `docs/ACCEPTANCE.md` and `README.md` replace the public home page with the login page as entry point. The privacy notice is linked on all pages accessible without login (D-022).

## D-027: Local Database, Public Repository and Continuous Integration

* Date: 2026-10-11
* Status: Decided; the local database part is superseded by D-030 (project owner, 2026-10-11: MariaDB instead of MySQL)
* Note (2026-10-11, D-030): the local database is now MariaDB 12.3 LTS, installed with the Chocolatey package `mariadb.install` below `%ProgramFiles%`, and continuous integration tests MariaDB 10.11 and 12.3. * Context: Tests depend on MySQL behaviour (D-016), and the minimum versions must be proven by tests (D-015, D-026). The development machine had neither MySQL nor Docker, and only Python 3.13.
* Decision:
  * Local development and tests use MySQL installed with Chocolatey (project owner, 2026-10-11). The local server runs MySQL 9.7 LTS, not the minimum version 8.4: the minimum version (D-026) states what the software must support, not what an instance runs. 9.7 is supported longer, and the Chocolatey package is closer to Oracle's latest patch for 9.7 (9.7.2 vs. 9.7.3) than for 8.4 (8.4.6 vs. 8.4.12). The project owner asked on 2026-10-11 why 9.7 LTS was not used.
  * The local setup is done by `scripts/local/setup-dev-windows.ps1`, which the developer runs once as administrator (installation of a Windows service requires elevation). The settings read their configuration from environment variables, the method shown in Django's deployment checklist (`SECRET_KEY = os.environ["SECRET_KEY"]`). Locally, the script stores the configuration as user environment variables without printing generated values; how `.env` is loaded into the environment on servers is decided with the hosting (D-008). AI tools therefore never need to read a secret file.
  * Continuous integration tests both the minimum version (MySQL 8.4) and the latest LTS (MySQL 9.7). Whether Django 6.0 and 6.1 work correctly with MySQL 9.7 is not stated by Django (minimum supported versions in the installed sources: MySQL 8.0.11 for Django 6.0.9, MySQL 8.4 for Django 6.1.2, `minimum_database_version` in `django/db/backends/mysql/features.py`) and is proven by these tests (updated on 2026-10-11 after the minimum was raised to Django 6.0, D-026).

* Verified facts:
  * The Chocolatey package `mysql` (community package, not maintained by Oracle) offers 8.4.6 as its latest 8.4 version (Oracle: 8.4.12, 2026-08-18) and 9.7.2 as its latest 9.7 version (Oracle: 9.7.3, 2026-08-18).
  * MySQL 9.7 is an LTS series: Oracle's reference manual names the repository `mysql-9.7-lts-community` for 9.7.x releases, and the 9.7.0 release notes (2026-04-21) refer to "consecutive LTS versions higher than 9.7.0". An LTS series receives "5 years of premier support and 3 years of extended support"; no end date is stated for 9.7. 9.7 is the last release line before calendar versioning (YY.M). It downloads the official zip archive from `cdn.mysql.com`, checks a SHA-256 checksum, installs a Windows service and initialises the data directory with `--initialize-insecure`, i.e. the `root` account has no password. The package sets no bind address.
  * Commits use the GitHub no-reply address as author email; no private email address is published with the history.
* Security implications:
  * Local MySQL (since the update below, the settings are written before the first start instead of afterwards): without hardening, `root` has no password and the server listens on all interfaces, both with the classic protocol (`bind_address` default `*`) and with X Plugin, which is enabled by default and listens on port 33060 on all interfaces (`mysqlx_bind_address` default `*`). The setup script therefore binds the server to `127.0.0.1`, disables X Plugin (`mysqlx=OFF`; Django does not use the X Protocol), verifies the listening sockets after the restart, sets a `root` password, verifies a login with it, and creates an application account with only the privileges Django needs (`SELECT, INSERT, UPDATE, DELETE, CREATE, DROP, ALTER, INDEX, REFERENCES`) on the project database and its test database (`docs/INSTALLATION.md`, "Database privileges"). The root password is validated before anything is installed; if a later step fails, the script stops and disables the MySQL service and prints recovery steps (security review of 2026-10-11, M-2 to M-4, L-3, L-4). 9.7.2 lacks the fixes of 9.7.3; it is used only for local development, bound to the loopback interface, and is upgraded once the Chocolatey package offers a newer patch.
  * Residual risk of user environment variables: they are inherited by every process of the Windows user, including AI tools and their subprocesses, which can therefore read `DB_PASSWORD` and `DJANGO_SECRET_KEY` of the local environment. These are local development credentials only (no stage or production secrets on development machines, D-020). The environment is never printed (`AGENTS.md`, section 8).
  * Public repository: all documents, including the security policy, become public. They contain no secrets (checked with a pattern search before publishing). Security through obscurity is not relied upon. GitHub's secret scanning with push protection and Dependabot alerts are enabled.
  * Continuous integration: workflow permissions are read-only, no repository secrets are used, and third-party actions are pinned to full commit SHAs (GitHub documentation "Security hardening for GitHub Actions").
* Update (project owner, 2026-10-11, after the first run of the setup script failed right after `choco install mysql`):
  * Cause: the package registers the service with `mysqld --install MySQL`, so its command line is `C:\tools\mysql\current\bin\mysqld MySQL` (no quotes, no `.exe`, no `--defaults-file`; verified on the development machine with `Win32_Service.PathName`). The script took `C:\tools\mysql\current\bin\mysqld` as the program path, which does not exist as a file, and stopped. The option file is `C:\tools\mysql\current\my.ini` (`BASEDIR\my.ini`), so the existing fallback to the base directory was correct.
  * Fix: the program path is resolved from the service command line by trying the white-space separated prefixes from the shortest to the longest (the order Microsoft documents for `CreateProcess`) and, for a path without extension, the path itself and then the path with `.exe`. `datadir` values in `my.ini` are unescaped (`\\` stands for `\`), because the package writes `datadir=C:\\ProgramData\\MySQL\\data`.
  * New switch `-RemoveFailedInstallation`: removes a failed installation (stop the service, `choco uninstall mysql`, `sc.exe delete MySQL`, delete leftover `my.ini` files) and then runs the normal setup. The data directory is deleted only if it is the package default `C:\ProgramData\MySQL\data`, looks like a MySQL data directory (or is empty), and the user types `DELETE`; any other `datadir` is reported, never deleted. Without the switch, the script stops before changing anything if a service, the package, the data directory or a leftover `my.ini` exists, and shows the one-line command to run.
  * Security review of 2026-10-11 (M-1, M-2, L-1): the removal works only on an installation of the Chocolatey package: the service program must lie under `<tools>\mysql` (Chocolatey's tools directory, normalised full paths compared case-insensitively) and `--defaults-file` must be absent or point to `<tools>\mysql\current\my.ini`; only `<tools>\mysql\current\my.ini` and `my.ini.before-leg-setup` are deleted. Otherwise the script stops without changes and refers to the manual steps. If `C:\ProgramData\MySQL`, the data directory, `<tools>\mysql` or `<tools>\mysql\current` is a reparse point (symbolic link, junction, mount point), the script stops. Every removal requires typing `DELETE` after a list of all items. The removal first stops the service and sets it to `Disabled`. The data directory is re-checked (reparse points, MySQL data directory) immediately before it is deleted with `[IO.Directory]::Delete(path, true)`, which "does not recurse through the reparse point" (Microsoft Learn, "Directory.Delete Method"). Without the switch, the script warns if an existing `MySQL` service is running.
  * Security re-check of 2026-10-11 (N-1, N-2): the removal re-checks the ownership of the service at its start and the reparse points of `<tools>\mysql`, `<tools>\mysql\current` and the option files immediately before deleting the option files.
  * File permissions (main session finding of 2026-10-11, verified with `icacls` and `Win32_Service.StartName`): `C:\tools`, `C:\tools\mysql` and `C:\tools\mysql\current\bin` inherit "Authenticated Users: Modify" from `C:\`, and `C:\ProgramData\MySQL` inherits "Users: write data, append data, write attributes" (container inherit) from `C:\ProgramData`. The service runs as `LocalSystem` ("The default user for running the MySQL service is LocalSystem", MySQL Reference Manual, "Starting MySQL as a Windows Service"), so any local user could replace `mysqld.exe` and gain system rights at the next service start (local privilege escalation). A first fix that hardened these folders after the installation was not reliable (security re-check of 2026-10-11, H-1 to H-3: ordinary users can rename `C:\tools`, `icacls /grant:r` keeps foreign explicit permissions, and `icacls /t` may follow junctions) and was replaced by the layout below.
  * Layout of the local installation (project owner, 2026-10-11; replaces the later hardening of `C:\tools\mysql` and `C:\ProgramData\MySQL`): before `choco install mysql`, the script creates `C:\LEG-MySQL` with the subfolders `server` and `data` (no spaces, because the package registers the service with an unquoted path). Each folder is created with its security descriptor set at creation (`DirectoryInfo.Create(DirectorySecurity)` in .NET Framework, `FileSystemAclExtensions.Create` in .NET): inheritance from the parent blocked, full control for Administrators (`S-1-5-32-544`) and SYSTEM (`S-1-5-18`), read and execute for Users (`S-1-5-32-545`) on `server` only, owner Administrators. The script stops if `C:\LEG-MySQL` exists. It writes `server\mysql\current\my.ini` (`basedir`, `datadir=C:/LEG-MySQL/data/mysql/data`, `port`, `bind-address=127.0.0.1`, `mysqlx=OFF`) before the installation and installs with the package parameters `/installLocation:C:\LEG-MySQL\server /dataLocation:C:\LEG-MySQL\data`. The package installs to `<installLocation>\mysql\current`, writes `my.ini` only if it does not exist, creates `<dataLocation>\mysql\data`, initialises it with `mysqld --defaults-file=<that my.ini> --initialize-insecure`, registers the service with `mysqld --install MySQL` and starts it (`tools\chocolateyInstall.ps1` of mysql 9.7.2 on the development machine; the parameters are listed on https://community.chocolatey.org/packages/mysql). The server therefore listens only on `127.0.0.1` with X Plugin off from its first start. The script stops if one of the global option files `%WINDIR%\my.ini`, `%WINDIR%\my.cnf`, `C:\my.ini` or `C:\my.cnf` exists, because mysqld reads them before `BASEDIR\my.ini` (MySQL Reference Manual, "Using Option Files").
  * Owner (security re-check of 2026-10-11): the owner of objects created by members of the Administrators group depends on the policy "System objects: Default owner for objects created by members of the Administrators group" (values "Administrators group" or "Object creator"); its effective default on Windows 10 and 11 was not found stated on Microsoft Learn. If the installing user became the owner, a non-elevated process of that user could change the permissions. After writing `my.ini` and again after the installation, the script therefore enumerates `C:\LEG-MySQL` without following reparse points (any reparse point fails before anything is changed), checks each item again and sets its owner to Administrators with `ObjectSecurity.SetOwner` and `Set-Acl` (Microsoft Learn). Files that mysqld creates later while running as `LocalSystem` (tables, logs, `mysqld-auto.cnf`) get the owner of the service's token; which owner that is was not verified. They inherit the protected permissions of `data` (Administrators and SYSTEM only) in any case, and the allowlist check runs only during the setup.
  * Verification after the installation (allowlist): `my.ini` is unchanged and `mysql.ibd` exists in the data directory; every file and folder below `C:\LEG-MySQL` is enumerated without following reparse points (each reparse point fails), its owner must be Administrators or SYSTEM, and every allow entry must be Administrators or SYSTEM, or Users without any write right (generic rights count as write rights) and only below `server`; `C:\LEG-MySQL` may contain only `server` and `data`. Any violation fails into the existing failure path (service stopped and disabled).
  * `-RemoveFailedInstallation` handles both layouts: the service program must lie under `C:\LEG-MySQL\server\mysql` or `<tools>\mysql` with no other option file; `C:\LEG-MySQL` may contain only `server` and `data`, `<tools>\mysql` only `current` and `mysql-*-winx64` (other content of `<tools>` is never touched); `C:\ProgramData\MySQL\data` must look like a MySQL data directory. Everything is checked before the typed confirmation and again immediately before the removal; the trees are deleted with `[IO.Directory]::Delete(path, true)`, which "does not recurse through the reparse point". The removal also deletes the MySQL `bin` folders from the user `PATH` (the package adds them with `Install-ChocolateyPath`, default `PathType` User), because ordinary users can create folders directly below `C:\` (`Authenticated Users: (AD)` on `C:\`, verified with `icacls`) and could otherwise place programs where `PATH` points.
  * Security re-check of 2026-10-11 (M-A, L-B to L-I): before a tree that ordinary users may have been able to change is deleted (`<tools>\mysql`, `C:\ProgramData\MySQL\data`, or a `C:\LEG-MySQL` the script did not create), it is locked down top-down without following reparse points (per folder: fail on a reparse point, owner Administrators, protected DACL with Administrators and SYSTEM only, then its entries), verified with the allowlist (no Users entries) and checked again, then deleted; a foreign owner of `C:\LEG-MySQL` is reported before the confirmation. `server\mysql`, `current` and `my.ini` are created with their security descriptor and owner set at creation (`FileSystemAclExtensions.Create` for files in .NET, the `FileStream` constructor with `FileSecurity` in .NET Framework), and `my.ini` is compared again right before `choco install`. After the installation, the service is stopped while the owners are set and the allowlist is checked, and the setup fails if `BASEDIR\my.cnf` or `DATADIR\mysqld-auto.cnf` exists ("Even with --defaults-file, mysqld reads mysqld-auto.cnf"). The tools root of the earlier layout is the machine-wide `ChocolateyToolsLocation` or exactly `C:\tools`, never a process or user value. The script removes the earlier `PATH` entry `C:\tools\mysql\current\bin` from `HKCU\Environment` in every run, reading the value with `RegistryValueOptions.DoNotExpandEnvironmentNames` and writing it back with its original kind (the user `PATH` on the development machine is `REG_EXPAND_SZ`); MySQL entries in the machine `PATH` are only reported; a new terminal is needed to see the change (no broadcast). The mysql client is called with `--defaults-file=<temporary option file>` ("Read only the given option file") or `--no-defaults`; because clients still read `%APPDATA%\MySQL\.mylogin.cnf`, the script stops if that file exists (MySQL Reference Manual, "Command-Line Options that Affect Option-File Handling").
  * Security re-check of 2026-10-11 (N-1, decision of the main session, option c): `Lock-DirectoryTree` is removed, because `Set-Acl` works by name and could follow a swapped junction, and setting an inheritable DACL propagates into existing children. The script no longer removes the earlier layout (`<tools>\mysql`, `C:\ProgramData\MySQL`) or a `C:\LEG-MySQL` that fails the allowlist; it changes nothing and prints the manual commands (see the M-1 update below), to be run in an elevated PowerShell while no other user is signed in. `-RemoveFailedInstallation` removes automatically only a `C:\LEG-MySQL` that passes the allowlist (it was created protected, so ordinary users cannot have changed it), after the typed confirmation, with the service stop, `choco uninstall`, `sc.exe delete` and `PATH` cleanup as before. Residual risk accepted for the one-time manual cleanup on the developer's own machine: a junction planted inside the legacy folders is not followed by `Directory.Delete`, but the cleanup relies on no other user acting at the same time. The legacy tools root is the machine-wide `ChocolateyToolsLocation` or `C:\tools`.
  * Security re-check of 2026-10-11 (M-1, L-a to L-c): the earlier layout is detected by `<tools>\mysql` and `C:\ProgramData\MySQL\data` (not the parent, because MySQL's own installer uses `C:\ProgramData\MySQL\MySQL Server <version>`). The printed commands delete `C:\ProgramData\MySQL\data` recursively and the parent only non-recursively, which fails if it is not empty (tested with a mocked second installation). Service commands are printed only for the service of the earlier layout; for another service, the script warns. Before printing delete commands, the script checks that the tools root, `<tools>\mysql`, `C:\ProgramData\MySQL`, its `data` folder and (if present) `C:\LEG-MySQL` are not reparse points, and prints only a warning otherwise; the printed block starts with the same check for the user. The manual cleanup is run while no other user is signed in and no scheduled tasks or services of other users run.
  * Security re-check of 2026-10-11 (L-1, L-2, L-4): before the first client call, the script removes `MYSQL_TEST_LOGIN_FILE`, `MYSQL_HOST`, `MYSQL_TCP_PORT`, `MYSQL_PWD`, `MYSQL_UNIX_PORT`, `MYSQL_HOME`, `MYSQL_GROUP_SUFFIX`, `LIBMYSQL_PLUGIN_DIR`, `LIBMYSQL_PLUGINS` and `LIBMYSQL_ENABLE_CLEARTEXT_PLUGIN` from its own process (MySQL Reference Manual, "Environment Variables"; values are never printed), and passes `--protocol=TCP --host=127.0.0.1 --port=3306` on the command line, which takes "precedence over values specified in option files and environment variables". After the root password is set, `mysql.user` may contain only the reserved accounts `root`, `mysql.sys`, `mysql.session` and `mysql.infoschema` (all `@localhost`; MySQL Reference Manual, "Reserved Accounts"); the application account is created afterwards. `PATH` cleanup and user environment variables apply to the account that runs the elevated script (`HKCU`); the script warns if it differs from the console user (`Win32_ComputerSystem.UserName`).
  * Residual risks and open points of the local installation: after the initialisation, `root` has no password until the script sets it a few seconds later; the server listens only on the loopback interface during that time, so only processes on the same computer can use it. The service runs as `LocalSystem` (MySQL's default); running it with MySQL's documented `--local-service` option (`LocalService` account) is an open point, because the package installs the service itself. Folders created by ordinary users below `C:\` (e.g. a stale `C:\tools`) are outside the scope of the script. The creation with owner Administrators and the installation itself were not run by the AI (they need an elevated PowerShell); the helper functions were tested without elevation.

## D-028: Baseline Settings of the Django Project Skeleton

* Date: 2026-10-11
* Status: Decided. The Content Security Policy and local email delivery were decided by the project owner on 2026-10-11. On 2026-10-12 the project owner delegated the remaining parts to established practice with priority on security; the main session reviewed them against the sources listed below (checked on 2026-10-11, not re-fetched on 2026-10-12) and kept them unchanged.
* Context: README "Current Status", next step: create the Django project skeleton. `docs/SECURITY.md` (sections 3 and 6) requires secure defaults, but leaves several details of the settings open.
* Decision:
  * The environment variables are validated in one place (`leg_platform/environment.py`); invalid or unsafe values prevent the start. Beyond `APP_ENV`, `DJANGO_DEBUG` and `EMAIL_MODE`: outside `APP_ENV=local`, `DJANGO_SECRET_KEY` and every fallback key must meet the criteria of Django's deployment check `security.W009` (at least 50 characters, at least 5 unique characters, no `django-insecure-` prefix), `DJANGO_ALLOWED_HOSTS` must be set, and `DJANGO_CSRF_TRUSTED_ORIGINS` accepts only `https://` origins. Wildcards (`*`, leading `.`) are rejected in `DJANGO_ALLOWED_HOSTS` and `DJANGO_CSRF_TRUSTED_ORIGINS` in all environments.
  * HSTS in stage and production with a default of one year (`DJANGO_SECURE_HSTS_SECONDS`, can be lowered for testing but not disabled).
  * `SECURE_HSTS_INCLUDE_SUBDOMAINS` is off by default and can be enabled by the operator with `DJANGO_SECURE_HSTS_INCLUDE_SUBDOMAINS=True`: the policy would also apply to every host below the application's host name, which only the operator can assess. The deployment warning `security.W005` is silenced only while it is off (security review of 2026-10-11, L-1).
  * `SECURE_HSTS_PRELOAD` is never set and `security.W021` is always silenced. Preloading puts the domain into lists built into browsers; removal depends on the list maintainers and on browser releases, so it is effectively irreversible for an operator and not offered as a setting. Silencing keeps `check --deploy --fail-level WARNING` meaningful for every other warning.
  * `EMAIL_MODE` per `APP_ENV` (`docs/SECURITY.md`, sections 8 and 11): `local` allows `console` (its default) and `allowlist`, `stage` requires `allowlist`, `production` requires `graph`; outside `local`, a missing `EMAIL_MODE` prevents the start (security review of 2026-10-11, M-1).
  * Local email (project owner, 2026-10-11, to test Microsoft Graph delivery locally): `allowlist` is allowed locally; `graph` (unrestricted) stays production-only. Local `allowlist` delivery requires a dedicated development app registration and sender mailbox whose credentials are separate from stage and production (D-020, `docs/SECURITY.md`, section 7). The allowed local recipient addresses are kept only in the user environment variable `EMAIL_ALLOWED_RECIPIENTS` on the developer machine, never in the repository. `docs/SECURITY.md` sections 8 and 11 were aligned accordingly, which resolves the earlier contradiction between them ("controlled by default" versus "restricted to test output"); the project owner consented to this change.
  * Automated tests never send real email: Django's test runner sets the locmem backend (`django/test/utils.py`: `EMAIL_BACKEND` in 6.0.9, every alias of `MAILERS` in 6.1.2), verified by a test in both versions. Tests and examples use only addresses under reserved domains (RFC 2606: `example.com`, `example.net`, `example.org`, `.test`, `.invalid`); `leg_platform/tests/test_repository.py` scans the text files of the repository (not `.env`) for other addresses.
  * `allowlist` with an empty `EMAIL_ALLOWED_RECIPIENTS` refuses the start in every environment (re-review of 2026-10-11, N-5; security review of 2026-10-11, L-3). Each entry must be exactly one complete address (exactly one `@`, a domain with at least two labels, no white space, wildcards or domain-only entries); entries are stored in lower case. Error messages name only the position of an invalid entry, never an address. The Microsoft Graph backend must still deliver only to these addresses (to be tested when it is built).
  * `DEFAULT_EXCEPTION_REPORTER_FILTER = "leg_platform.debug.ExceptionReporterFilter"`: a subclass of Django's `SafeExceptionReporterFilter` whose `hidden_settings` pattern adds `RECIPIENTS` to Django's default (`API|AUTH|TOKEN|KEY|SECRET|PASS|SIGNATURE|HTTP_COOKIE`, identical in 6.0.9 and 6.1.2), so that debug pages and error reports mask `EMAIL_ALLOWED_RECIPIENTS` in the settings and in `request.META` (Django documentation, "How to manage error reporting": `hidden_settings` matches "settings and `request.META` values considered as sensitive"). The setting keeps its name, which matches the environment variable.
  * Numeric values (`DB_PORT`, `DJANGO_SECURE_HSTS_SECONDS`) accept only ASCII digits; ports must be in the range 1 to 65535, also in `DJANGO_CSRF_TRUSTED_ORIGINS`.
  * `CSRF_COOKIE_HTTPONLY = True`: no JavaScript reads the CSRF cookie. Django's documentation states that this "doesn't offer any practical protection" but is "sometimes required by security auditors"; `docs/SECURITY.md` (section 3) requires `HttpOnly` where possible. Scripts that need the token read it from the form field rendered by `{% csrf_token %}` (Django documentation "How to use Django's CSRF protection").
  * `SECURE_PROXY_SSL_HEADER` is set only through `DJANGO_SECURE_PROXY_SSL_HEADER`, never by default.
  * Email delivery via Microsoft Graph is not implemented yet. In the modes `allowlist` and `graph`, a placeholder backend (`leg_platform.mail.GraphNotImplementedEmailBackend`) raises an error on every send attempt, so that email is never dropped silently and never sent through Django's default SMTP backend or to the console. Django 6.1 deprecates `EMAIL_BACKEND` in favour of `MAILERS`, which Django 6.0 does not know; the settings set `MAILERS` on Django 6.1 and later and `EMAIL_BACKEND` otherwise.
  * Database connection (MariaDB through Django's MySQL backend since 2026-10-11, D-030): `isolation_level` "read committed" (Django's default, set explicitly; MariaDB's own default is `REPEATABLE-READ`), `charset` utf8mb4, test database with utf8mb4 and `utf8mb4_uca1400_ai_ci` (until 2026-10-11 `utf8mb4_0900_ai_ci`, which MariaDB has only as an alias from 11.4.5 on and 10.11 not at all). `sql_mode` is set for every connection with `OPTIONS["init_command"]` (Django documentation, "Setting sql_mode"; security review of 2026-10-11, L-6) to MariaDB's documented default `STRICT_TRANS_TABLES,ERROR_FOR_DIVISION_BY_ZERO,NO_AUTO_CREATE_USER,NO_ENGINE_SUBSTITUTION` (MariaDB documentation, "Server System Variables"), so that a changed server default cannot weaken it; Django's check `mysql.W002` (run in CI with `--database default`) and tests (tag `mariadb`) verify strict mode and the exact session value. Collations of identifier columns: D-031.
  * Logging: warnings and errors to standard error; no email to `ADMINS`.
* Verified facts:
  * Django's MySQL notes (which apply to MariaDB, D-030): "Django works best with and defaults to read committed rather than MySQL's default, repeatable read. Data loss is possible with repeatable read."; "The default value of the `sql_mode` option contains `STRICT_TRANS_TABLES`." MariaDB's default for `transaction_isolation` is also `REPEATABLE-READ` (MariaDB documentation, "Server System Variables"). Django connects with `charset` utf8mb4 by default (source `django/db/backends/mysql/base.py`, 5.2.18 and 6.1.2).
  * Django's SecurityMiddleware documentation: "it's a good idea to first use a small value for testing, for example, `SECURE_HSTS_SECONDS = 3600` [...] (31536000 seconds, i.e. 1 year, is common)"; "The HSTS policy applies to your entire domain".
  * Django's settings reference on `SECURE_HSTS_INCLUDE_SUBDOMAINS`: "Setting this incorrectly can irreversibly (for the value of `SECURE_HSTS_SECONDS`) break your site."
  * Django's settings reference on `CSRF_COOKIE_HTTPONLY`: "If you enable this and need to send the value of the CSRF token with an AJAX request, your JavaScript must pull the value from a hidden CSRF token form input instead of from the cookie."
  * Django 6.1 release notes: `EMAIL_BACKEND` and related settings "are deprecated. Replace them with a `MAILERS` configuration"; new deployment check `mail.E001` against development-only backends in `MAILERS`; "The check management command now supplies all databases if not specified."
  * Django 6.0 and later provide `django.middleware.csp` and `SECURE_CSP` (present in 6.1.2); Django 5.2.18 has no built-in Content Security Policy support (no `django/middleware/csp.py`). `django/middleware/csp.py` is identical in 6.0.9 and 6.1.2.
  * None of Django's password validators sets a maximum length (source `django/contrib/auth/password_validation.py`, 6.1.2).
* Rationale: fail early and closed on configuration errors; operators without in-depth IT knowledge get secure defaults (`docs/SECURITY.md`, section 1).
* Content Security Policy (project owner, 2026-10-11: use Django's built-in support; minimum raised to Django 6.0, D-026):
  * `django.middleware.csp.ContentSecurityPolicyMiddleware` directly after `SecurityMiddleware`, and in all environments `SECURE_CSP = {"default-src": [CSP.SELF], "script-src": [CSP.SELF], "style-src": [CSP.SELF], "img-src": [CSP.SELF], "font-src": [CSP.SELF], "object-src": [CSP.NONE], "base-uri": [CSP.NONE], "form-action": [CSP.SELF], "frame-ancestors": [CSP.NONE]}`, rendered as `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`. No `'unsafe-inline'`, no nonces, no report-only policy. `X-Frame-Options: DENY` stays as a fallback for browsers without `frame-ancestors`.
  * Directive names: W3C Content Security Policy Level 3 (`default-src`, `script-src`, `style-src`, `img-src`, `font-src` and `object-src` are fetch directives; `base-uri` is a document directive; `form-action` and `frame-ancestors` are navigation directives; "frame-ancestors will not fall back to the default-src directive's value"). Value constants: `django.utils.csp.CSP` (`SELF` = `'self'`, `NONE` = `'none'`); Django's documentation uses directive names as string keys, e.g. `"default-src": [CSP.SELF]`.
  * Django admin under this policy (checked in the installed sources of 6.0.9 and 6.1.2): the admin templates contain no inline `<script>` (every `<script>` has a `src`; configuration is passed in `data-` attributes), no `style` attributes, no event handler attributes and no `javascript:` URLs; the admin CSS contains no `data:` or external URLs; the admin JavaScript outside `vendor/` contains no `eval`, `new Function` or `setAttribute("style")`. One exception: `admin/change_list.html` contains an inline `<style>` block (`#changelist table thead th:first-child {width: inherit}`) that is rendered only when a change list shows no actions (`actions_on_top` and `actions_on_bottom` both off). Django 6.1 adds `{% csp_nonce_attr %}` to it, Django 6.0 does not; without a nonce in `style-src`, browsers block it in both versions. The effect is cosmetic (width of the first column); the policy is not relaxed for it. A test verifies that the admin login page contains no inline code and carries the header. The admin was not checked in a browser.
  * Django's CSRF failure page (`csrf_403.html`) has an inline `<style>`; under this policy it is displayed without its styles (cosmetic). Django's debug pages (only with `DEBUG=True`, local) disable the policy for themselves with `csp_override({})`.
  * Tests: the header on responses with production settings (including a 500 error response) and on the admin login page with the local settings of the test run, the settings in a separate process with `APP_ENV=production`, and the absence of `'unsafe-inline'`, `'unsafe-eval'`, `'unsafe-hashes'`, nonces, wildcards and `data:`.
* Security implications: Encrypted transport to the database in stage and production (`docs/SECURITY.md`, section 9) is not configured yet and depends on the hosting (open).
* Alternatives: `SECURE_HSTS_INCLUDE_SUBDOMAINS = True` by default (rejected: could break other hosts of the operator's domain; left to the operator); silencing `mail.E001` instead of a placeholder backend (rejected: it would hide that production cannot send email); Django's dummy backend (rejected: drops email silently).

* Security implications:
  * Phase without a root password (security review of 2026-10-11, M-1 and L-4). It begins when the installation starts the service (the MSI starts it, `ServiceControl Start='install'`, and the package runs `NET START MySQL`) and ends with the `ALTER USER` statement of the hardening. It covers the rest of the Chocolatey installation, locating the installation and disabling the firewall exception, the permission checks (with the service stopped), and, after the restart, the pipe check and the wait for other connections. Its length was not measured. During the phase, `root@localhost` has no password and the server listens only on its named pipe; the server treats pipe connections as `localhost`. Because of the pipe's DACL (Everyone read and write, low integrity label), any local process can connect; because `PIPE_REJECT_REMOTE_CLIENTS` is not set, users of other computers who can authenticate to this computer over SMB (port 445, File and Printer Sharing) can connect as well. The installation guide therefore asks to check the firewall for port 445 and to run the script only when no untrusted user or program is active.
  * Checks against misuse of the phase: (a) the server holds the pipe exclusively only while its process runs (`FILE_FLAG_FIRST_PIPE_INSTANCE`, no `FILE_CREATE_PIPE_INSTANCE` for others); a client that is `root` during the phase could shut the server down and create a pipe with the same name. The script therefore checks that the pipe's server process is the service immediately before it connects (`GetNamedPipeServerProcessId`; the pipe is opened with `SECURITY_SQOS_PRESENT` and `SECURITY_IDENTIFICATION`, so that its server cannot impersonate the elevated script) and that the service process is unchanged after the account creation. ## D-031: Collations

* Date: 2026-10-11
* Status: Decided (project owner, 2026-10-12; proposed after the security review of 2026-10-11, M-2). Applies when the custom user model and the token tables are implemented (D-021).
* Context: The databases use the character set `utf8mb4` with the collation `utf8mb4_uca1400_ai_ci` (D-028, D-030), which is case- and accent-insensitive ("_ai" accent insensitive, "_ci" case insensitive). Comparisons in such a collation treat different strings as equal, e.g. `josé@example.org` and `jose@example.org`. For identifiers this would make a unique index reject a different address and a lookup find another account.
* Decision:
  * Columns that hold identifiers and are compared exactly use the binary collation `utf8mb4_bin` through Django's `db_collation` field option: the normalised email address of the uniqueness column (D-016), token and keyed-hash values (D-023), and the customer number (D-021). Normalisation (D-021: NFKC, surrounding white space removed, lower case, IDN domain mapped to ASCII) stays in the application.
  * All other text columns keep the database default `utf8mb4_uca1400_ai_ci`.
  * Every database of an instance is created with `CHARACTER SET utf8mb4 COLLATE utf8mb4_uca1400_ai_ci` (the local setup script does so; the installation guide states it for operators); Django's test database receives the same through `TEST["CHARSET"]` and `TEST["COLLATION"]`.
* Verified facts:
  * Django: `CharField.db_collation` and `TextField.db_collation`: "Optional. The database collation name of the field." "Collation names are not standardized." (Django documentation, "Model field reference", 6.0).
  * MariaDB: `utf8mb4_bin` (id 46) and `utf8mb4_uca1400_ai_ci` are listed in "Supported Character Sets and Collations" (list "from MariaDB 11.4.5"); the UCA-14.0.0 collations exist from 10.10.1. For 10.11, the existence of both is proven by a database test that applies both collations (`COLLATE`), run in CI against 10.11 and 12.3.
  * Defaults: `character_set_server` is `latin1` up to MariaDB 11.5 and `utf8mb4` from 11.6; the default collation of `utf8mb4` is `utf8mb4_general_ci` up to 11.4 and `utf8mb4_uca1400_ai_ci` from 11.5 (MariaDB documentation, "Server System Variables" and "Supported Character Sets and Collations"). A database created on MariaDB 10.11 without explicit options would therefore be `latin1`; the project always sets both explicitly. A database test checks the default character set and collation of the (test) database.
  * `utf8mb4_bin` uses PAD SPACE (trailing spaces are ignored in comparisons; `utf8mb4_nopad_bin` would not ignore them). The values of these columns never end with spaces (normalised addresses, URL-safe tokens and hashes, digits), so PAD SPACE does not matter for them.
* Alternatives: an accent- and case-sensitive UCA collation (rejected: still linguistic, not byte-exact); `utf8mb4_nopad_bin` (equivalent for these values; `utf8mb4_bin` chosen as the established binary collation named in the review).
* Sources: https://docs.djangoproject.com/en/6.0/ref/models/fields/, https://mariadb.com/docs/server/reference/data-types/string-data-types/character-sets/supported-character-sets-and-collations, https://mariadb.com/docs/server/server-management/variables-and-modes/server-system-variables (checked on 2026-10-11)
* Consequences: `docs/ARCHITECTURE.md` ("User Model and Login Identifiers") and `docs/INSTALLATION.md` describe the collations; tests of the user model must cover addresses that differ only in accents or case.

## D-032: Profile Data Structure Based on eCH-0010

* Date: 2026-10-12
* Status: Decided (project owner, 2026-10-12). Applies when the custom user model is implemented (D-021). Amended by D-036 (2026-10-12): the structure stays; unused fields are hidden, the shown fields have everyday labels and forms show one postal code field.
* Context: The profile needs the name and postal address for invoices (`docs/PROJECT.md`, "Profile Data and Purpose"). Accounts may represent a private person or an organisation (e.g. a property management). Unmarried couples with different names want both names on the invoice. Owners or property managements may live abroad.
* Decision:
  * The profile fields follow the person, organisation and address structure of eCH-0010 (postal address). All fields of these parts are created, even if some are rarely used (project owner: better to have them than to need a migration later).
  * Person: salutation (optional; "Mrs", "Mr", "Family" or empty), title (optional), first name, last name.
  * Organisation: organisation name and two name add-ons (optional).
  * Either the organisation name or first and last name are required. With an organisation name, the person's salutation, title, first and last name are optional (contact person).
  * Address: two free address lines (optional, e.g. a second person on the invoice such as "and Beat Example", or "c/o"), street, house number (text, e.g. "12a"), dwelling number, post office box number and text, locality, town, postal code, country (default Switzerland). Swiss postal codes have four digits (1000-9999); foreign postal codes are text of up to 15 characters.
  * Required address fields: postal code, town, country and either a street or a post office box; the house number is optional, so that addresses without a house number and post office box addresses are possible (project owner, 2026-10-12; eCH-0010 itself makes only the town and the country mandatory).
  * The postal address uses the town ("Ort") of the postal address, not the political municipality (see D-013).
  * One account belongs to exactly one person or organisation; there are no shared accounts. A second person is named in an address line, not in the name fields.
* Verified facts (eCH-0010 XML schema `eCH-0010-8-0.xsd`, published with version 8.1.0, approved 14 July 2025):
  * `personMailAddressInfoType`: `mrMrs` (optional, values 1 and 2 only), `title` (optional, max. 50), `firstName` (optional, max. 30), `lastName` (required, max. 30).
  * `organisationMailAddressInfoType`: `organisationName` (required, max. 60), `organisationNameAddOn1` and `organisationNameAddOn2` (optional), `mrMrs`, `title`, `firstName`, `lastName` (all optional).
  * `addressInformationType`: `addressLine1`, `addressLine2` (optional, max. 150), `street` (max. 150), `houseNumber` (max. 30), `dwellingNumber` (max. 30), `postOfficeBoxNumber`, `postOfficeBoxText` (max. 15), `locality` (max. 40), `town` (required, max. 40), `swissZipCode` (1000-9999) with optional add-on and ID, or `foreignZipCode` (max. 15), `country` (ISO 3166 alpha-2 code and short name).
* Deviations from eCH-0010: the salutation "Family" does not exist in `mrMrs`; it is lost in a future eCH export. Whether eCH-0010 intends the address lines for a second person was not verified (the main document could not be read).
* Security and data protection: all additional fields are optional and serve the stated purpose (postal address for invoices; DSG Art. 6 para. 3). Field lengths are limited; the eCH lengths are the reference.
* Alternatives: two accounts for a couple (rejected: both names would still not appear on one invoice); both names in the first and last name fields (rejected: breaks sorting and search by name); a shared account (rejected: shared credentials, no traceability).
* Sources: https://www.ech.ch/de/ech/ech-0010 (version 8.1.0), https://www.ech.ch/sites/default/files/imce/eCH-Dossier/0001-0030/eCH-0010/8.1.0/Beilagen/eCH-0010-8-0.xsd (checked on 2026-10-12)
* Consequences: `docs/PROJECT.md` ("Profile Data and Purpose") lists the fields; the privacy notice of the instance must name the purposes.

## D-033: Address Validation and Autocompletion with the Official Directory of Building Addresses

* Date: 2026-10-12
* Status: Decided in principle (project owner, 2026-10-12); details open (see below).
* Context: The project owner wants entered addresses to be validated and an autocompletion to be offered, as part of phase 1 (creating, updating and deleting the profile are fully covered in phase 1).
* Decision:
  * The official directory of building addresses (swisstopo) is downloaded regularly and stored in an optimised form in a separate database (project owner, 2026-10-12). It is public data and is not part of the application's backups, so backups stay small; stage and production (and several instances) on the same server may use the same address database.
  * Each environment and instance accesses the address database with its own account that may only read (`SELECT`). Only a separate import account may write. The application has no foreign keys into the address database; the profile stores the address as entered.
  * Swiss addresses are checked against it during registration and profile editing, and an autocompletion is offered. The check warns but does not block: foreign addresses and very new buildings are not in the directory.
  * Entered addresses are never sent to an external service; the autocompletion queries only the local copy.
* Verified facts (swisstopo data catalogue, data.geo.admin.ch, STAC API, checked on 2026-10-12):
  * "Official directory of building addresses" (ID 197 of the catalogue of basic geodata): contains all official building addresses of Switzerland and Liechtenstein and is binding for public authorities.
  * Assets per country as CSV (ZIP), FileGDB and INTERLIS, each with a SHA-256 multihash checksum; the Swiss data set was last updated on 2026-10-11.
  * The licence link refers to the swisstopo terms of use for open government data (https://www.swisstopo.admin.ch/ogd-conditions).
* Open and not yet verified:
  * the content of the terms of use (e.g. attribution);
  * the columns of the CSV file (whether postal code and town are included per address) and the update interval;
  * how the import is scheduled per server and how its integrity is verified (checksum from the catalogue over HTTPS);
  * the Django configuration: a second database alias with a database router, migrations for that alias, and a test database for it (the local setup script and continuous integration must provide it);
  * rate limiting of the autocompletion endpoint, which is reachable without login during registration.
* Security implications: the directory contains no personal data. Sharing the address database deliberately crosses the separation of stage and production (`docs/ARCHITECTURE.md`, "Environments"): a compromised stage could read it but not change it, because every environment has its own read-only account and separate credentials (`docs/SECURITY.md`, section 7); a compromised import account could change addresses shown to all environments, which affects only suggestions and warnings, never stored profiles. The import is an outbound HTTPS download from a federal service; the downloaded file is verified before use. The autocompletion endpoint must be rate-limited and must not reveal anything about accounts.
* Sources: https://data.geo.admin.ch/api/stac/v0.9/collections/ch.swisstopo.amtliches-gebaeudeadressverzeichnis and `/items` (checked on 2026-10-12)
* Consequences: `docs/PROJECT.md` lists the function in phase 1.

## D-034: Data Model of the Custom User Model

* Date: 2026-10-12
* Status: Decided (project owner, 2026-10-12: data model only; profile fields directly on the user model; countries with `django-countries`, default Switzerland; optional phone number, validated and stored in E.164 with `django-phonenumber-field` and `phonenumberslite`). The other points implement D-016, D-021, D-031 and D-032 and are recorded for traceability.
* Context: README "Current Status", next step 3 (D-021). The custom user model must exist before any persistent database is migrated.
* Decision:
  * Scope of this step: the app `leg_platform.accounts` with the models, the first migration and tests. No views, forms, URLs, templates, admin registration of the user model, login backend, `django-axes` or `django-otp` wiring.
  * The profile fields of D-032 are fields of the user model `accounts.User`; there is no separate profile table. Lengths follow eCH-0010. The Swiss postal code is an integer from 1000 to 9999, the post office box number an integer of at most 8 digits. Rules that depend on several fields (organisation name or first and last name; street or post office box; post office box text for a post office box number; town and country required; Swiss postal code for Switzerland, foreign postal code otherwise) are checked in `User.clean()`, which Django's model forms call. Amended by D-036: no rule requires a hidden field (no post office box text for a post office box number); the postal code rules are checked in `User.clean_fields()`.
  * Country: `CountryField` of `django-countries` (ISO 3166-1 alpha-2 code), default `CH`; country names come from the package's translations.
  * Phone number: optional `PhoneNumberField` of `django-phonenumber-field`; `PHONENUMBER_DEFAULT_REGION = "CH"` (numbers without international prefix are read as Swiss numbers) and `PHONENUMBER_DB_FORMAT = "E164"` (the package default, set explicitly). `phonenumberslite` is declared directly instead of the extra `django-phonenumber-field[phonenumberslite]`, so that the minimum CI job pins it; the lite variant omits the geocoder, carrier and time zone metadata, which are not needed.
  * Customer numbers (D-021): the table `IssuedCustomerNumber` holds every number ever issued, as primary key, without reference to a person. A number is drawn with `secrets.randbelow(10**6)` and inserted in a savepoint; a collision is retried, at most 100 times; when all numbers are issued, issuing fails without drawing. Rows of this table cannot be changed or deleted through the model or its queryset; `save()` always inserts (`force_insert`), so an existing number is never overwritten, and `bulk_create()` is rejected. `User.customer_number` is a one-to-one foreign key to this table (`on_delete=PROTECT`, column `customer_number`), so the database accepts only issued numbers; `customer_number_id` holds the six-digit string and `customer_number_display` the display format. A foreign key column takes the type and collation of the referenced column (Django source `ForeignKey.db_parameters()`, installed Django 6.1.2), here `utf8mb4_bin`; a test reads `information_schema.COLUMNS` to confirm it (security review finding L-3). The number is set only by `assign_customer_number()`, for a saved, active account without a number (L-5).
  * String representation (project owner, 2026-10-12, Q-3, clarified after re-review): `User.__str__()` never shows an email address or customer number; it is "Account 17" using the internal primary key (Swiss German "Konto 17"). The ID provides a way to find the corresponding user during support; the later admin must expose the internal ID in the user list. Changed by D-036 (2026-10-12): the account display and the admin user list use the customer number; admin log entries keep only the internal number (D-018), which the change form shows as "internal number".
  * Deleting an account deletes its admin log entries (`LogEntry.user` cascades); accepted by the project owner on 2026-10-12 (Q-4).
  * Compiled translations (`.mo`) are committed next to their `.po` files; CI compiles each `.po` with GNU `msgfmt --check` and compares the decompiled result with the committed `.mo` (`msgunfmt`). Developers regenerate them with `python manage.py compilemessages`, which needs GNU gettext.
  * Login identifier (D-016, D-021, D-031): `normalized_email` is the `USERNAME_FIELD`: unique, nullable, not editable, collation `utf8mb4_bin`. `email` holds the canonical address (D-035) and `normalized_email` is derived from it in `save()` with `normalize_email_address()`; it is `NULL` while the account is deactivated. Validation rejects non-ASCII local parts (D-035), quoted local parts, domain literals, IP addresses, `localhost` and characters of the Unicode categories C, Z and M; it validates the canonical address with Django's `EmailValidator`. `idna` is a direct dependency so Unicode and Punycode domain spellings use the same unique key. Whether mail providers deliver all mapped variants to the same mailbox has not been verified.
  * Invariants enforced by the model, independent of any view or admin: `is_active` is derived from the status (only active accounts are active); unverified accounts have neither a customer number nor a usable password; `create_user()` creates an unverified account without usable password and rejects a password and the fields only the account logic sets (status, privileges, groups, permissions, customer number, retention flag); `create_superuser()` refuses while any account with `is_superuser` exists (`docs/PROJECT.md`, "First System Administrator"); a customer number never changes; the retention flag can only change from unset to set, checked against the stored row read with `SELECT ... FOR UPDATE`; `QuerySet.update()` of protected fields (status, `is_active`, email, normalised email, retention flag, `is_staff`, `is_superuser`, customer number, password), `QuerySet.delete()` and `bulk_create()` are rejected (`bulk_update()` uses `update()`; related managers such as `group.user_set` use the same queryset). The protecting queryset is also the base manager (`Meta.base_manager_name = "objects"`), so that `_base_manager` does not bypass it.
  * Central account logic (Q-2): status, email address (with the normalised column), `is_active` (derived), `is_staff`, `is_superuser`, customer number and retention flag change only through `set_status()`, `change_email()`, `set_privileges()`, `assign_customer_number()` and `set_retention_obligation()`. Every `save()` of an existing account compares these fields with the row locked with `SELECT ... FOR UPDATE` and rejects changes that were not made through these methods, which also rejects a full `save()` of a stale instance. `update_fields` that contain one of email, status, normalised email or `is_active` are extended to all four (M-1). New accounts are always inserted (`force_insert`), the primary key of a loaded account cannot change, and `create_user()` rejects `id`/`pk` and the controlled fields (M-2). `delete()` refuses accounts with a retention obligation and the last active system administrator (M-4).
  * `create_superuser()` requires a password, runs Django's password validators, refuses inside a transaction and serialises concurrent calls with a MariaDB named lock (`GET_LOCK`), because no row exists yet that could be locked; a concurrency test covers it. Django's `createsuperuser` command is replaced by one that refuses (D-005) (M-5).

## D-035: Canonical Form of Account Email Addresses

- Date: 2026-10-12
- Status: Decided by the project owner (2026-10-12). Re-confirmed by the project owner on 2026-10-13 with knowledge of the risk statement below (lower case for the whole address, including the local part); no open owner decision remains.
- Context: The security re-review (findings L-2 and Q-1/N-1, see D-034) showed that the documents said accents in the local part are kept while the validator rejected them. The question was whether to store the entered address or a canonical form.
- Decision:
  - The local part of an account email address is ASCII only. Internationalised local parts (SMTPUTF8) are not accepted. Internationalised domains are accepted and stored as IDNA ASCII (D-034).
  - The canonical form is stored in `email`: Unicode NFKC, surrounding white space removed, lower case for the whole address, domain in IDNA ASCII (UTS #46). It is derived in `save()` (`_apply_derived_fields()`), which all account changes go through.
  - `normalized_email` holds the same value while the account is not deactivated, so both columns are equal for active accounts. It is `NULL` while deactivated (D-034).
  - Lookups, counters and rate limits use `normalize_email_address()` unchanged (D-021).
  - Local parts are stored in lower case and compared case-insensitively. This deviates from RFC 5321 section 2.4 (see Verified facts and Risks).
- Reason: One canonical value avoids two stored spellings of the same account. ASCII local parts avoid SMTPUTF8 transmission failures and accent look-alikes. The project owner's rationale: domains are not case-sensitive, and the owner assumes that the same name cannot be reserved in two cases, so all comparisons are done in lower case. This assumption is not verified (see Not verified).
- Verified facts:
  - RFC 6531 sections 3.2 and 3.5: non-ASCII local parts require SMTPUTF8. Section 3.4: SMTPUTF8 carries a transmission-failure risk. Section 3.2 and 3.7: IDNA domains can be used without SMTPUTF8.
  - RFC 5321 section 2.4 (fetched 2026-10-12): "The local-part of a mailbox MUST BE treated as case sensitive". Domains are not case sensitive. Lower-casing the local part therefore conflicts with this MUST.
- Not verified: Whether the mail services used by the municipalities treat local parts case-insensitively. Not tested against a real mail server.
- Risks:
  - Lower-casing the local part (RFC 5321 section 2.4) can send verification mail to a different mailbox on a host that distinguishes case, for example `Max@x` and `max@x`. The owner of that mailbox can then complete verification of a pending account or, once password reset exists, reset the password of an active account (account takeover). This needs a case-distinguishing host and two differently cased mailboxes; neither is verified. Because both spellings map to one account key, registering one spelling blocks the other (denial, not takeover). The security review of 2026-10-12 (finding H-1) found the first version of this risk text incorrect. The project owner must re-confirm the lower-casing decision with the corrected risk. Secure alternative (not chosen): keep the local part as entered, use the lower-case form only as lookup and uniqueness key, and send mail only to the stored address.
  - The stored address can differ from the entered one (Punycode domain, lower case). The user interface must show the stored form where it is shown.
- Alternatives: Keep the local part case-sensitive as RFC 5321 requires (not chosen by the project owner). Allow SMTPUTF8 for accented local parts (not chosen; see RFC 6531 section 3.4). Store the entered address and compare the canonical form only (not chosen; two stored spellings).
- Consequences: No schema change and no migration. Existing rows with a non-canonical `email` are not converted by this decision; check before any deployment with data. Tests and docs updated. The redundant `normalized_email` column remains; its removal would need a migration and is not decided.
- Sources: https://www.rfc-editor.org/rfc/rfc6531 (sections 3.2, 3.4, 3.5, 3.7); https://www.rfc-editor.org/rfc/rfc5321 (section 2.4), both checked 2026-10-12.

## D-037: Registration, Verification Links, Login Views and Instance Links

* Date: 2026-10-13
* Status: Proposed (implemented for review; the points under "To be confirmed by the project owner" are not decided yet). * Decision:
  * Pages: `/` (leads to the login page, or to the profile when logged in), `/login/`, `/logout/` (POST only), `/register/`, `/register/sent/`, `/register/verify/<token>/`, `/register/complete/`, `/profile/` (read only, always `request.user`, no identifier in the URL). Pages with forms, tokens or personal data send `Cache-Control: no-store` (Django `never_cache`).
  * Registration: a form with an explicit field list (email address and the profile fields of `docs/PROJECT.md`, one postal code field, D-036), so that other submitted values are ignored. The response is always a redirect to the same generic page. A new or still unverified address creates an unverified account and a token and sends the link; a pending registration of the same address is replaced (the old link stops working).   * Verification token: 256 bits from `secrets.token_urlsafe(32)` (43 characters), stored only as an HMAC-SHA256 digest with a key derived from `SECRET_KEY` via HKDF with its own label (D-023), in the table `VerificationToken` (purpose, digest, expiry, user). The token is consumed, and the account activated, only when the form with the password is submitted successfully; two concurrent submissions are serialised with a row lock and only one succeeds. The form shows the verified address read-only and lets the person correct the profile and choose a password (Django password validators, minimum length 15, `docs/SECURITY.md`, section 3).   * Token redaction: a logging filter on the handler of all loggers replaces the token in `/register/verify/<token>/` in log messages, arguments and exception texts (Django logs the path of every response with status 400 or higher, and the development server logs every request line). Links are built from `INSTANCE_BASE_URL`, never from the request. A failing send is logged by exception class only (no address, link or message), and the response stays generic; the person can register again.

  * Login: Django's `LoginView` with a form that shows one message for every failure (wrong password, unknown, unverified, blocked or deactivated account): `EmailModelBackend` returns no user for inactive accounts, so they are indistinguishable. `redirect_authenticated_user` stays off (docs/ARCHITECTURE.md, "Deliberately Open"). Redirect targets are checked by Django against the request host. The lockout page of Axes is a template without the submitted value (`AXES_LOCKOUT_TEMPLATE`). Logout accepts POST only (Django `LogoutView`).

## D-038: Password Reset, Request Limits, Background Sending and Sender Address

* Date: 2026-10-13
* Status: Proposed (implemented for review; the values under "To be confirmed by the project owner" are proposals). Real email delivery could not be tested on the development machine; everything is tested with Django's in-memory email backend only.
* Context: open points of D-037 and of the review of the duplicate registration: per-address and per-IP limits (D-017), response time independent of the state of an address (`docs/SECURITY.md`, section 3), password reset, the sender address. Decisions of the project owner of 2026-10-13: limits as best practice for this kind of application, sending in the background, the sender address is configured by the administrator (otherwise `noreply@<domain>`), the reset flow is implemented.
* Decision:
  * Outbox: a request for registration or password reset counts the request and stores one `MailJob` (kind, normalised address, attempts, next due time). It reads no account and sends nothing, so the response and its time do not depend on the address. The response is the same redirect and generic page as before. The worker (`manage.py process_mail_queue`, `--loop` for a service) takes a job under a lock (attempt counter raised and next due time moved forward; this is the lease and the retry delay of 2 minutes times the attempts), lets the handler look up the address and store what it needs in one transaction, sends outside any transaction and deletes the job. Raw tokens are created by the worker and sent at once; they are never stored in a job. Delivery is at least once; after 3 attempts a job is given up, and unprocessed jobs of requests are deleted after 1 hour and unprocessed notifications after 24 hours by `cleanup_mail_requests`. A database error while claiming ends the round without raising.
  * Limits (proposed values; OWASP's Forgot Password Cheat Sheet names the controls, not the numbers): per normalised address 12 requests per hour and 24 per 24 hours (project owner, 2026-10-13: the first hour must allow a person at the device several attempts; first version: 3 and 10), shared by registration and password reset (and later email change); per client IP address 20 per hour (IPv6 counted by its /64 prefix, RFC 6177; no determinable address: one shared bucket, a warning is logged); instance wide 300 per hour for registration and 300 per hour for password reset, counted separately (reaching it is logged). A request counts only if every limit has room, in one transaction with ordered row locks, so that a refused client does not use up the budget of someone else's address and parallel requests cannot exceed a limit. A refused request is stored as a job without the address and processed as "send nothing", so it changes nothing visible and replaces no pending registration. The information email to an existing address is sent at most once per address per 24 hours, checked in the worker. Counters are rows in `RateLimitBucket` and `RateLimitEvent` under a row lock per key, with keyed digests (HKDF from `SECRET_KEY`, D-023) instead of addresses or IP addresses; unused buckets are deleted after 24 hours. Deviation from D-026: a database table instead of Django's cache framework, because cache counters are not atomic and the same pattern is already used for the login IP counter (D-017).
  * Password reset: pages `/password-reset/`, `/password-reset/sent/`, `/password-reset/verify/<token>/` and `/password-reset/new-password/` follow the registration pattern (token only as keyed digest, the link stores the digest in the session and redirects, the token is consumed only when the form with the new password is submitted successfully, `no-store`, `no-referrer`, token redaction in logs). The email is sent only to an account with the status active (a temporarily locked account has this status, so reset works during a lockout; unknown, unverified, blocked and deactivated addresses receive nothing, and the person typing cannot tell). The lookup uses the normalised unique column. The link is valid for 24 hours, equal to the longest limit window, so that a person who cannot request another email because someone else used up the budget can still use a link already in the mailbox; several links can be outstanding, and a completed reset removes all of them. A reset ends all other sessions (Django derives the session hash from the password) and the temporary lockout of the account only, never the counters and lockouts of IP addresses (D-017); the second factor is untouched. The account receives a notification of the changed password.
  * Information email for existing addresses now says that an account exists, links the login page and tells the person that a new password can be requested on the login page if the password is unknown (identical text for active, temporarily locked and blocked accounts).
  * Sender: `EMAIL_SENDER_ADDRESS` (environment, optional) checked against a strict address pattern without control characters; default `noreply@<host of INSTANCE_BASE_URL>`, locally `noreply@localhost`. The emails never state that replies are read (project owner, 2026-10-13: automatic emails expect no reply); the notification of a changed password names the contact information of the instance (`INSTANCE_WEBSITE_URL`) where configured. SPF, DKIM and DMARC are DNS settings of the sending domain and are documented in the installation guide, not enforced by the code.
  * Management commands: `process_mail_queue`, `cleanup_mail_requests` and `delete_expired_registrations`; their scheduling is open (deployment gate).
  * Customer number warning (project owner, 2026-10-13): from 90 % of the six-digit numbers issued (`CUSTOMER_NUMBER_WARNING_PERCENT`), every issue of a number logs a warning ("N of 1000000 customer numbers have been issued (P%)", no personal data), and the user list of the administration shows a notice to system administrators (not to staff users). The count is the one `issue()` already makes. The notice is visible only where the administration is reachable (`APP_ENV=local` for now, D-004); until then the log line is the alarm and the operator must watch for it. Reaching 100 % still fails the completion of a registration with an error (D-037, M-1).
* Verified facts:
  * Django 6.1 refuses `EMAIL_TIMEOUT` together with `MAILERS`, so the setting was removed; a Graph backend has to set its own timeout. Django 6.1's `check` command accesses the database.
  * All tests pass with Django 6.1.2 and with the minimum Django 6.0.9, MariaDB 12.3, Python 3.14, deprecation warnings as errors: 455 tests (2026-10-13). `manage.py check --deploy` with a production-like environment reports no issue; `makemigrations --check` finds no changes; the Swiss German catalogue has no "ß" and passes `msgfmt --check`.
  * Tests cover: identical responses for every state of the address, an identical set of database statements for every state (compared as a set, because the buckets are locked in digest order), no database transaction open while sending, leases and retries, crash and database error behaviour, parallel requests against a limit, IPv6 prefixes, the suppressed jobs, sender validation, reset single use, session end, lockout handling and the unchanged IP counters.
* Security review (agent `security-reviewer`, started by the main session): its findings on the first version led to: ordered bucket locks and a single transaction for the three limits, jobs of refused requests without an address, the lease and the sending outside any transaction, catching database errors in the worker, and the lock order account before token. The corrected version was not reviewed again yet.
* Security implications and open points:
  * Plain-text addresses are held in unprocessed jobs for at most one hour. A database dump taken in that time contains them.
  * Delivery is at least once; an email can arrive twice after a crash. Tokens are single use, so a duplicate is harmless.
  * If the worker does not run, no email is sent and nobody learns why; monitoring of the queue age is not implemented. Requests within the limits are counted even when the worker is down.
  * An attacker who knows an address can use up its budget (12 per hour, 24 per day) and so keep the owner from requesting a new email for a while; the 24-hour link lifetime and the per-address limit of the information email limit the effect (D-017, accepted).
  * The IP limit depends on the correct number of trusted proxies (`AXES_IPWARE_PROXY_COUNT`); an office behind one address shares the budget.
  * The request rate of the pages themselves is not limited by the application; the reverse proxy must do it.
* Decided by the project owner on 2026-10-13: the hourly per-address limit of 12 (the daily value of 24 and the other limits are my proposals and still to be confirmed); no explicit sender is required: without `EMAIL_SENDER_ADDRESS` the default `noreply@<host>` applies in every environment; no separate instance contact value (the information email has no contact line; the sender address is the only instance address, and it is not announced as a reply address unless set explicitly); the customer number stays six digits (D-021, D-037 M-1); the lower-casing of the local part stays (D-035); `data:` images stay disallowed (D-037, D-028). Still to be confirmed: the 24-hour lifetime of the reset link and the daily and IP limits.

## D-039: Editable Email Texts in the Administration

* Date: 2026-10-13
* Status: Decided by the project owner (the answers below, 2026-10-13); implemented; security review of 2026-10-13 below.
* Context: the project owner wants to change or rewrite the texts of the emails that the application sends (registration link, information for an existing address, password reset link, password change notification) in the administration, with a list of the placeholders that can be used and a check of the placeholders when saving.
* Decision (project owner, 2026-10-13):
  * Only the default language of the instance (Swiss German) is editable; one text per email. Subject and body are editable.
  * The editor refuses to save a text without the personal link of the email (`{verification_url}` for the registration, `{reset_url}` for the password reset).
  * System administrators and staff users with the permission "change email text" may edit (permission `accounts.change_emailtext`, assigned to a role at runtime as for every permission, D-012; nothing is hard-coded). The history of an email text is visible to system administrators only, as for accounts.
  * Every text can be reset to the default (a checkbox, or an empty text), and every change is recorded in the administration log with the name of the email and the changed field names, never with the text.
  * Web and email addresses cannot be typed into a text or subject: after NFKC normalisation and removal of format characters, the editor rejects schemes (`https:`, `mailto:`, `tel:` and others), `//`, backslashes, `@` and any word with a dot followed by two letters (so also `www.`, bare domains and email addresses). It is a deny-list and cannot be complete (look-alike letters of other scripts pass); the permission to edit is the protection against a person who wants to bypass it. Addresses reach a text only through placeholders.
* Implementation:
  * Table `EmailText` (one row per email, created empty on first view of the list; an empty subject or body means the default). The defaults stay in the application (the four templates and the subjects); a text equal to the default is stored as empty, so that later improvements of the default reach the instance.
  * Placeholders are written `{name}`. All emails: `{instance_name}`, `{contact_url}` (the instance's website, empty if not configured), `{privacy_url}`, `{login_url}`; the registration and password reset emails also `{lifetime_hours}` and their own link. The subject can use `{instance_name}` only. The list and the editor show them (the list for all emails, the editor for the email being edited).
  * The saved text is never run through the template engine: the markers are replaced in a single pass from a fixed list of values by a regular expression, so a text cannot read variables, call anything or expand a value again. A text with `{{ ... }}`, `{% ... %}` or any unknown or unbalanced bracket is refused (the name of the offending placeholder is shown).
  * Protection at sending time: if a saved text no longer passes the validation (for example after a later change of the placeholders), the default is used and a warning with the name of the email (not the text) is logged, so that a missing link never reaches a person.
  * Maximum 5000 characters for the text, 150 for the subject; no control, format or separator characters (Unicode categories C* and Zl/Zp; the text may contain line breaks and tabs).
* Verified facts: the full test suite (510 tests) passes with Django 6.1.2 on MariaDB 12.3; it was not run with Django 6.0.9 after this change. The `ModelAdmin` hooks used (`changelist_view`, `has_*_permission`, `history_view`, `change_list_template`) exist in both versions. The administration stays restricted to `APP_ENV=local` (D-004).
* Security implications and risks:
  * Anyone who may change the texts decides what the emails say, including emails that carry real links. They cannot add other addresses (rule above), but they can write misleading text. The permission is therefore not part of any default role; give it only to people who are trusted with the communication of the instance, and review it in the access review.
  * The system-administrator-only history and the log entries without text keep the audit trail free of personal data (D-018).
  * Not implemented: language variants and a diff between versions.
* Further decisions of the project owner on 2026-10-13: the password change notification gets no special treatment (the same permission as every other text); a preview and a test email are wanted; a version history is wanted; no approval by a second person (too few administrators; the instance will often be run by one person).
* Preview and test email: the button "Preview" in the editor validates the typed text like a save and shows the subject and text as they would be sent, with example links (the token in them does not exist), without saving, logging or sending anything. From the preview, "Send a test email" sends the typed text to the address of the logged-in account only (never to a typed address), with the prefix "[Test]" and a note that the personal link does not work; a failing send is reported without details and logged by exception class only. Both need the change permission. No limit (project owner, 2026-10-13): only an administrator with the change permission can send it, and only to the own address.
* Versions: every save or restore that changes the subject or text writes an `EmailTextVersion` (subject, text, time, internal account for the audit, cleared when the account is deleted). The page "Versions" (view permission) lists them newest first with the text and marks the current one; "Restore" (change permission, POST only) puts an earlier text or the default back after validating it with the current rules (a version that is no longer valid is refused) and writes a new version and a log entry. The account is not shown; the full history with accounts stays for system administrators (D-018). The latest 100 versions per email are kept.
* Security review of 2026-10-13 (agent `security-reviewer`, read only, started by the main session; no critical or high finding) and how it was handled: M-1 (fixed: stricter deny-list, also for the subject, see above; a fixed non-editable footer was considered and not done); M-2 (fixed: a restore is always logged, also if a preview field is posted); M-3 (accepted by the decision of the project owner that the password change notification gets no special treatment: an administrator can rewrite its warning sentence; the default text contains it); M-4 (open: a refused request still creates one counter row and one suppressed job, so the growth follows the request rate; the reverse proxy must limit the request rate, `docs/INSTALLATION.md`); M-5 (fixed: separate instance-wide budgets for registration and password reset); L-1 (fixed: one check of character categories for subject and text); L-2 (fixed: 100 versions per email); L-3 (fixed: the row is locked when saving); L-4 (fixed: notification jobs are kept 24 hours, D-038); L-5 (open, accepted as low: if sending the information email to an existing address fails, the retry finds its daily budget used and the email is lost); L-6 (accepted by the project owner: no limit for test emails; only an administrator with the change permission can send them, and only to the own address); L-7 (fixed: the editor default has no contact branch if the instance has no website); L-8 (accepted: the list creates the four empty rows on first view, idempotent). Tests for the findings were added and the whole suite passes (519 tests); the corrected version was not reviewed again.
* To be confirmed by the project owner: nothing open for this decision; the permission is not part of any default role (see risks).

## D-040: Password Change and Two-Factor Authentication with an Authenticator App

* Date: 2026-10-13
* Status: Proposed (implemented and reviewed twice by the `security-reviewer`; the values under "To be confirmed by the project owner" were decided on 2026-10-13, see below). Real email delivery could not be tested; everything is tested with Django's in-memory email backend only.
* Context: README "Current Status", items 1 and 2: password change, the TOTP flow, central two-factor enforcement, recovery codes, re-authentication and OTP-protected admin access (D-004, D-016, D-017, D-018).
* Decision:
  * Password change (`/profile/password/`): asks for the current password and the new one twice (same policy as everywhere). The current password is checked through Django's `authenticate()`, so the check runs under the login abuse protection (Axes account counter and separate IP counter, D-017): a hijacked session cannot guess the password through this form. After saving, Django's `update_session_auth_hash()` renews the session ID and keeps this session; every other session ends because Django derives the session hash from the password. The account receives the existing notification (D-038). The administration's own password change page redirects to this one.
  * Second factor: own device models that follow the interface of `django-otp` (`Device`; its `OTPMiddleware` and device functions work with them): `AuthenticatorDevice` (TOTP: 30 seconds, six digits, SHA-1, which is what authenticator apps support; one step of tolerance; a used code cannot be used again) and `RecoveryCodeDevice` with `RecoveryCode`. The security values are not stored in plain text and cannot be shown again (project owner, 2026-10-13: "analogous to the Graph secret, no security value directly visible"): the TOTP key (160 bits) is encrypted with Fernet under a key derived from `SECRET_KEY` with HKDF and its own label (`leg_platform/accounts/encryption.py`, the same scheme as D-006; keys from `SECRET_KEY_FALLBACKS` are tried for decryption and a key found under an old key is encrypted again with the current one when it is used; a key that cannot be decrypted verifies nothing and is logged); a recovery code is stored only as an HMAC-SHA256 digest with a purpose-specific key (D-023), which is stronger than encryption for a value that is only ever compared. Replacing `SECRET_KEY` without keeping the old one in `SECRET_KEY_FALLBACKS` makes the second factors unusable, so that those accounts need a reset. The device throttling of django-otp is not used (see "Security review", M-1); the number of failures is limited by the login abuse protection. The issuer shown in the app is `INSTANCE_NAME`. An account has at most one authenticator app; only a confirmed authenticator app counts as a second factor (recovery codes alone do not).
  * Central check (`leg_platform/accounts/second_factor.py`): `requires_second_factor()` (staff users and system administrators), `has_second_factor()`, `is_second_factor_complete()` (django-otp's `is_verified()`; fails closed if the middleware is missing). `SecondFactorMiddleware` (after `OTPMiddleware` and the messages middleware) gives a session of an account that must use a second factor no privileges without it: only logging out and the setup pages are open; an account with a second factor whose session did not complete it is logged out; an account without one is sent to the setup page. A promotion takes effect in an open session. The administration additionally checks the completed second factor in `PortalAdminSite.has_permission()`, so it stays closed if the middleware is removed by mistake. The administration has no login page of its own: it leads to the portal login. TOTP-specific parts are in `totp.py`.
  * Login in two steps (D-017): the password is checked by the login form; if the account has a second factor, no `login()` is called. The session ID is renewed and a pending login (account, time, safe redirect target) is stored in the session; the IP slot of the password attempt is released. `/login/two-factor/` asks for the code (or a recovery code). Each code attempt goes through the Axes lockout check (`AxesStandaloneBackend`), reserves its own IP slot, and a wrong code is a failed attempt of the account and the IP address (Django's `user_login_failed` signal); Django's `login()` is called with the device only after the code was verified, which renews the session ID again and lets django-otp store the device in the session. The pending login lasts 5 minutes (proposal), ends if the account is no longer active or has no second factor, and the code field is named `otp_token`, which Axes masks.
  * Setup (`/profile/two-factor/setup/`): requires the current password again; creates an unconfirmed secret (160 bits) and shows the QR code and the secret for manual entry; the factor is turned on only after a correct code from the app. The QR code is served as an SVG image of its own (`/profile/two-factor/setup/qr.svg`, `no-store`, only for the logged-in account's unconfirmed secret), because the policy allows images only from the own origin and no `data:` images (D-028, D-037). Ten recovery codes (40 bits each) are created and shown once. The session that confirmed the app counts as completed and its ID is renewed. A staff user or system administrator without a second factor can do this in the restricted session.
  * Re-authentication: password and, if a second factor is set up, a code, both under the abuse protection, in the forms for new recovery codes and for turning the second factor off. New recovery codes make the previous ones invalid. Users can turn their second factor off; staff users and system administrators cannot (the function refuses it as well).
  * Notifications (no link, `docs/SECURITY.md`, section 3): four new editable emails (D-039): second factor set up, removed, recovery codes renewed, recovery code used; queued like the password change notification and kept 24 hours if not processed.
  * Logging: until the security log of D-018 exists, setup, removal, renewal and use of a recovery code are written to the logger `leg_platform.security` with the internal account number and nothing else.
  * Budget of wrong codes (project owner, 2026-10-13: best practice and customer friendliness, a small residual risk is accepted; designed with the `security-reviewer`): `AuthenticatorDevice` counts the wrong codes of the account in a window of 24 hours from the first one (`failed_codes`, `failed_codes_since`; no new table; it disappears with the factor). Only a wrong code that reaches the check counts (code step, re-authentication forms, wrong recovery codes), under the account lock; attempts that Axes or the pause refuse and wrong passwords do not count, so that someone who knows only the email address can neither pause an account nor trigger the email. At 10 the owner gets one email without a link per window (the fifth notification, queued in the transaction; it does not use the request budgets of D-038) and one log line. At 15 code entry is paused, also for a correct code, until the window ends: the response is the lockout page with a text about the pause and the link to the password reset; like an Axes refusal it records nothing, so the Axes lockout is not extended, and the IP attempt is kept. A completed password reset ends the pause and leaves at most 10, never more attempts than before, and only once per window (`code_budget_relieved`; a mailbox thief gets at most the 5 attempts that the Axes reset gives, once per window). A successful login does not clear the budget: NIST SP 800-63B-4, section 3.2.2 says failures should be disregarded after a success, but then the budget of an attacker would grow with every login of the owner; deviation accepted. Escalating cool-off times were rejected: they would hang on the shared Axes counter and let someone who knows only the email address lock an account for a long time (D-017). NIST SP 800-63B-4, section 3.2.2 allows at most 100 consecutive failures per authenticator, this is far stricter; the estimate of the reviewer for the former limit (about 175,000 guesses per year) shrinks to at most 15 per account and day (about 5,500 per year, about 1.6 % chance of one right code per year in the extreme case, own arithmetic with three valid codes in 10^6, not checked against a source).
  * The pending login stores the session hash of the password and ends when the password changes. `cleanup_login_ip_attempts` also deletes abandoned unconfirmed setups and expired Axes attempts, and takes the IP buckets one by one with `skip_locked`, so that it cannot deadlock with a request (the order of locks is the same).
  * The devices are not in the administration, so that no secret can be shown and no staff user can add a device to an account.
