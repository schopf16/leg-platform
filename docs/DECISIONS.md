Raise a minimum when vendor support ends. Versions chosen for use: newest compatible release, for LTS tracks the newest of the track (owner, 2026-10-11). Never support an old version through a package with known vulnerabilities.

## 2. Language and translation

* **English repository** (D-010): code, identifiers, schema, stored keys, migrations, permission codenames, comments, commits, logs, tests, configuration, URL paths, documents. Only the UI is localized: `LANGUAGE_CODE = "de-ch"` is the instance default; French, Italian and English can be chosen (D-056, below).
* **UI texts** (D-010, D-036): translatable (English source), Swiss German in `locale/de_CH/LC_MESSAGES/django.po` (`LOCALE_PATHS`).
  * Never the German sharp s (eszett): `de_CH` falls back to `de`, so the catalogue overrides every such text (Django, contrib, third-party; e.g. UK country name, D-034). Automated check; recheck at each Django upgrade and new package.
  * Missing translations and sharp s are defects. Commit `.mo` next to `.po`; CI: `msgfmt --check`, compare `msgunfmt` (D-034). Keep every placeholder. A literal "%" in `{% translate %}` needs "%%": use placeholders (D-080).
* **Wording** (D-036, owner): everyday terms ("company name", "address addition", "post office box", "account", "system administrator"), no invented technical terms; admin titles "LEG Platform"/"Administration", never "Django". LEG-specific texts are catalogue content that another instance replaces.
* **Languages** (D-056, D-074; changed 2026-10-19): `LANGUAGES` are `de-ch` (Deutsch, the instance default), `fr`, `it`, `en`; every server-rendered text follows the chosen language. `en` is the English source text and has no catalogue. `locale/fr` and `locale/it` hold `django.po` and `djangojs.po` with the entries of `locale/de_CH` (translated separately; `REQUIRE_COMPLETE_CATALOGS` in `accounts/tests/test_translations.py` switches the completeness test on). No native-speaker review planned; do not call the texts drafts.
  * Only the language cookie chooses (`leg_platform.language.ChosenLanguageMiddleware`, a subclass of Django's `LocaleMiddleware`); the `Accept-Language` header of the browser never does, so a browser set to French does not change the default of an instance. A text without a translation is shown in English (`install_english_fallback`: Django would otherwise fall back to the Swiss German catalogue), never in German.
  * Emails, the mail worker and every text outside a request stay in the instance default language (`translation.override(settings.LANGUAGE_CODE)`).
* **Fact-based work** (D-011): no assumptions; sources are project state and official documents (vendor, law, OWASP/IETF/W3C, owner); never blogs, forums, news, SEO, AI text. Ask when in doubt (`AGENTS.md` section 3).

## 3. Instances, configuration, hosting

* **One instance per municipality** (D-013): not multi-tenant; own database, configuration, secrets, users, system administrators; no shared data or central administration; one account per person and instance. One code base; instance values (names, domain, base URL, sender, contacts) are configuration, never in code, templates or migrations. Operation, updates, backups: operator's duty. Source: StromVG Art. 17d para. 3 (an LEG covers at most one municipality).
* **Host name** (D-013, D-025): `ALLOWED_HOSTS` only own hosts; never read `Host` from `request.META` (use `request.get_host()`); email links from `INSTANCE_BASE_URL`.
  * Own host name (e.g. `portal.leg-ittigen.ch`), never a website path (shared origin, RFC 6454, RFC 6265 8.5/8.6). Subdomain or separate registrable domain is the operator's choice (the latter avoids cookie tossing). `SameSite` does not protect between subdomains.
  * `SESSION_COOKIE_DOMAIN`/`CSRF_COOKIE_DOMAIN` unset. `CSRF_TRUSTED_ORIGINS` never holds the website or a parent wildcard. Stage/production cookies use the `__Host-` prefix.
* **Entry point** (D-025): no public home page; the entry is the login page (login, reset, registration, links to privacy notice and instance website). Public LEG figures belong on the instance website.
* **Environment configuration** (D-027, D-028, D-037): environment variables validated in `leg_platform/environment.py`; invalid or unsafe values stop the start.
  * Outside `APP_ENV=local`: `DJANGO_SECRET_KEY` and fallback keys meet `security.W009` (>= 50 chars, >= 5 unique, no `django-insecure-`); `DJANGO_ALLOWED_HOSTS` required; `DJANGO_CSRF_TRUSTED_ORIGINS` only `https://`. Wildcards (`*`, leading `.`) rejected; numbers ASCII digits only; ports 1..65535.
  * `SECURE_PROXY_SSL_HEADER` only via `DJANGO_SECURE_PROXY_SSL_HEADER`. HSTS in stage/production, default one year (`DJANGO_SECURE_HSTS_SECONDS`, lowerable, not disableable); `SECURE_HSTS_INCLUDE_SUBDOMAINS` only with `DJANGO_SECURE_HSTS_INCLUDE_SUBDOMAINS=True` (`security.W005` silenced only while off); `SECURE_HSTS_PRELOAD` never (irreversible); `security.W021` silenced.
  * Logging: warnings/errors to stderr; no email to `ADMINS`. `DEFAULT_EXCEPTION_REPORTER_FILTER = "leg_platform.debug.ExceptionReporterFilter"` masks `EMAIL_ALLOWED_RECIPIENTS`.
* **Instance values** (D-037): `INSTANCE_NAME` (default "LEG Platform", max 100, no control or line-separator characters); `INSTANCE_BASE_URL` (`https://` origin without path or credentials; `http://` only with `APP_ENV=local`; required elsewhere; host in `DJANGO_ALLOWED_HOSTS`); `INSTANCE_PRIVACY_URL` (absolute `https://`, required outside local); `INSTANCE_WEBSITE_URL` (optional). The privacy notice is linked on every page without login, also the lockout page. Branding: section 12.
* **Environments** (D-070): `APP_ENV=stage` is only a label; no code branches on it. Stage must not differ from production (owner 2026-10-16; approved deviation from `docs/SECURITY.md` section 8): HTTPS, cookies, HSTS, CSP, limits, validation, secret rules.
  * Stage and production require `EMAIL_MODE=graph` and refuse `console`, `allowlist` and a non-empty `EMAIL_ALLOWED_RECIPIENTS`. Stage has own database, `DJANGO_SECRET_KEY`, Graph app registration and certificate; no production data or secrets (D-013, D-020). Real personal data on stage counts like production.
  * Accepted risks: real mail to typed addresses (not recallable); the registration form allows up to 300 mails/hour to third parties (production limits apply, section 8).
  * Procedures (`docs/DEPLOYMENT.md` 5.3/5.4, `docs/OPERATIONS.md`): testers use own addresses; mark stage in `INSTANCE_NAME` (e.g. "<municipality> STAGE (test system)"); restrict the stage host at the proxy (IP allow-list or basic auth, recommended); name who reads the stage sender mailbox; purge/check queued `MailJob` rows before the first restart; revert environment files with the code.
* **Hosting** (D-008, D-074): Ittigen production runs on an Infomaniak "VPS Lite 1" with MariaDB; Infomaniak operates stage and production (owner statement; assume nothing else). Other instances: operator's choice. SSH needed for management commands. Vendor facts: official images only, no security software, no SLA, no Infomaniak backup, outgoing port 25 not openable, key authentication.
* **Deployment** (D-053, D-064, D-076): `docs/STARTUP.md` is the one local-environment document (agents never print the environment, never read `.env`, never delete seeded accounts, stop processes only by process ID). `docs/DEPLOYMENT.md`: direct deployment without containers (venv, Gunicorn, nginx, MariaDB 12.3 from the MariaDB Foundation repository, Certbot, systemd units and timer; secrets only in root-owned 0600 environment files); a proposal not yet run on a server; section 0.5 is the entry for a deployment request.
  * Distinguish update from initial install; keep a non-secret instance record; verify both CI variants for the exact SHA. Stage without explicit revision: the release branch resolved once to a SHA. Production: the release accepted on stage (same full SHA) with explicit per-deployment approval.
  * Update: quiesce writers; wait for the importer, never interrupt it; back up and validate on stage too; migrate; refresh static files; restart; verify. Destructive migrations, restores and security exceptions stay approval boundaries. A code-only rollback does not prove schema compatibility.
  * Forbidden: unattended-password pseudo-terminal script, fake privacy URL default, automatic self-signed TLS fallback, skipping the stage backup, treating the importer as one-shot. Owner decisions O-1..O-23: `docs/DEPLOYMENT.md` section 1.
  * One reverse proxy on the same host: `AXES_IPWARE_PROXY_COUNT=0` resolves every visitor to `127.0.0.1`; count 1 works only with a header of exactly two entries, so nginx overwrites `X-Forwarded-For` with `"$remote_addr, 127.0.0.1"`.
  * Facts: Ubuntu 26.04 LTS until May 2031 (python3 3.14.3), 24.04 until June 2029 (3.12.3); Debian 13 until 2028-08-09, LTS 2030-06-30. MariaDB repository key fingerprint `177F 4010 FE56 CA33 3630 0305 F165 6F24 C74C D1D8`.
* **First start** (D-005, D-076; owner 2026-10-16): no manual account creation; empty database + environment file + start = working instance.
  * `manage.py setup_instance` is idempotent, runs on every start under one named MariaDB lock (`GET_LOCK`, hashed name, waits at most 600 s): `migrate --noinput` (never `flush`); initial system administrator; `migrate addresses --database=addresses`. Prints no secrets.
  * Administrator: locked `create_superuser()` from `BOOTSTRAP_SYSTEM_ADMIN_EMAIL`/`BOOTSTRAP_SYSTEM_ADMIN_PASSWORD`, `password_change_required=True`, security log entry; only when `accounts_user` has no row. Accounts but no superuser: create nothing, write `System administrator: NONE EXISTS, but accounts exist ...` to stderr, exit 0 (advice: restore a backup or run interactive `setup_initial_administrator`; `emergency_access` grants no admin rights). Missing or weak password, email without password, password without email on an empty table: fail the unit.
  * Password: project validators (min 15 chars); never in messages or arguments; not read while a superuser exists (the start prints a reminder to remove it); not a Django setting (`environment.parse_bootstrap_administrator()`); `PASS` in the name so reports mask it; only letters, digits, `-`, `_`, `.` (systemd `EnvironmentFile=` quoting). A human types it; an AI never generates or sees it.
  * The directory step never blocks the start (failure: stderr with class only, exit 0, retried next start); a failure of the main database or of a configured administrator fails the command.
  * Units (`docs/DEPLOYMENT.md` 8.0): `Type=oneshot` `leg-setup.service` (`Restart=on-failure`, `RestartSec=60s`, `StartLimitIntervalSec=15min`, `StartLimitBurst=5`, systemd >= 244); web and mail worker `Requires=`+`After=`, importer `Wants=`+`After=`, cleanup `After=` only. Never `systemctl stop|restart leg-setup` (`start` is safe; `reset-failed` after the limit); never `StartLimitIntervalSec=0`. Migrations run at every start without backup: change code only via the update runbook (12.3, backup first).
  * Alert on a failed `leg-setup` and on `journalctl -u leg-setup | grep -c 'NONE EXISTS'` (expect 0). Not automatable: empty MariaDB database and account, HTTPS/DNS/proxy, the environment file.
* **Initial administrator** (D-005, D-041): only by server command, never via the website (a first visitor could take over); only while no system administrator exists; never overwrites or resets an account. `setup_initial_administrator` reads `BOOTSTRAP_SYSTEM_ADMIN_EMAIL`, asks twice for the password with `getpass` (refuses without a terminal that hides input), refuses while any `is_superuser` exists. `createsuperuser` stays disabled.
  * `password_change_required`: only password change and logout work (`SecondFactorMiddleware`); admin closed (also `PortalAdminSite.has_permission()`); the new password must differ. Password change or reset by link clears the flag; then the second factor must be set up.
  * Accepted risk (owner): the initial password sits in the environment file (0600 root), no expiry; whoever knows it and logs in first can take over (change password, enrol own second factor). The instance must not be publicly reachable (nginx closed or `allow`/`deny`) until the owner has logged in, changed the password and enrolled the second factor; restart services after removing the variable. A take-over shows as a failed first login or an unexplained `PASSWORD_CHANGED`. Accepted: the security log entry is written after commit.
* **Emergency commands** (D-005, D-041, D-044): `manage.py emergency_access`: `reset-second-factor N` (any account, also the last system administrator), `unblock-account N`, `reencrypt-second-factor-keys`. Typed confirmation (`--no-input` skips; owner 2026-10-13); prints only the internal number; every use logged for the long retention; server only (`docs/INSTALLATION.md`).
* **Seed accounts** (D-019, D-042): `seed_design_accounts` (owner 2026-10-13) creates throw-away accounts of every access level for local design work. Refuses outside `APP_ENV=local`; writes credentials only to a file outside the repository, never prints them; creates no role or permission. Risk: that file is readable by anyone who can read the user's files.
* **Scheduled tasks** (D-041, D-068): `manage.py run_scheduled_tasks` runs `delete_expired_registrations`, `process_application_deadlines` (reminders and deadlines of the customers' applications, D-103: it queues mails and deletes only drafts), `cleanup_mail_requests` (includes `delete_expired_reset_tokens`, `mail_queue.delete_stale_jobs`), `cleanup_login_ip_attempts`, `cleanup_security_log`, `cleanup_confirmation_failures`, `clearsessions`, `cleanup_address_lookups` (expired stored building searches, D-066) and, last, `scheduled_address_import` (the daily address directory run, section 10; it can take minutes). A failing task does not stop the others and fails the command. A test requires every `cleanup_*`/`delete_expired_*` command of the accounts app to be included. The scheduler (systemd timer) is part of hosting (`docs/INSTALLATION.md`).
* **Backups** (D-016, D-075): operator's duty; deleted data may persist in backups until expiry (documented). Backup = MariaDB + environment file; the address directory is in no backup. Replacing `SECRET_KEY` without `SECRET_KEY_FALLBACKS` invalidates pending links and makes encrypted values unreadable (second-factor keys, IBANs, Graph key); backups need the key.

## 4. Roles and access

* **Three fixed access levels** (D-012): system administrator (`is_superuser` + `is_staff`, all permissions), staff user (`is_staff`, assigned permissions only), authenticated user (own profile only). Other roles are Django groups created at runtime in the admin.
  * Never hard-code roles: no code, migration or fixture creates, names or checks a group. Authorization checks permissions, never group names; codenames English; tests create their own groups. No predefined role or rights set (D-061).
  * New users have no groups, permissions, `is_staff`, `is_superuser`. Nobody promotes themselves; `is_superuser` only by another system administrator; every promotion is logged.
  * Only system administrators manage roles, permissions, assignments, `is_staff`, `is_superuser`, enforced technically, also against staff holding add/change-user permissions (Django: equals superuser). Delegation needs a separate reviewed decision.
  * Staff never change, block, deactivate or delete staff or system administrator accounts (also not their own in the admin), nor another account's password, email or second factor. System administrators can block each other and remove rights; at least one active, unblocked system administrator always remains (emergency: section 3) (D-016).
* **Rights only with a second factor** (D-042, D-043; owner 2026-10-14): the administration grants `is_staff`/`is_superuser` only to an account with a confirmed authenticator app (`second_factor.has_second_factor()`; an unconfirmed app or recovery codes do not count). The form refuses with a translated message; `save_model()` rechecks on the locked account row (403). Removing rights is always possible; groups and direct permissions are not restricted.
  * The rule lives only in the administration (`UserAdminForm._clean_privileges`, `UserAdmin.save_model`). Other code granting `is_staff`/`is_superuser` must implement the same check with a test; every review checks this. The administrator confirms with the person that they set up the factor themselves (`docs/SECURITY.md` section 4).
  * Gaps: the initial administrator and staff after a second-factor reset set up the factor at next login. A password reset keeps `is_staff`, `is_superuser`, groups, permissions. If permissions are later used outside the administration for non-staff, decide again whether they need a second factor.
* **Management area exception** (D-086, D-087; owner 2026-10-17; approved deviation from D-012; wins over D-077/D-079/D-080/D-081/D-084): `/management/` uses NO Django permissions. Every active staff user or system administrator with a completed second factor may use every page and function there (policy: `leg_platform/management/access.py`, section 13). The rest of D-012 stays; the Django admin and functions outside the area stay permission-protected.
  * Staff may change customer profile data there, never password, login email, second factor, status, `is_staff`, `is_superuser`, groups, permissions, retention flag or customer number of any account (D-087). A later financial module may need four-eyes separation: assess before building (D-012, D-086).

## 5. Accounts and lifecycle

* **Lifecycle** (D-016): login after email verification and password set; no approval. The password is set only via the verification link, never at registration (attackers could register a victim's address with a known password). States: unverified, active, blocked, deactivated (plus temporary lockout, `docs/PROJECT.md`).
  * Unverified accounts are deleted when the link expires; a new registration with the same address replaces a pending one. System administrators block/unblock any account. Blocked accounts cannot log in or reset passwords; during a temporary lockout reset works.
* **Retention flag** (D-016, D-086): one-way (unset to set only; otherwise rejected, also in the admin; DB privileges restricted, `docs/SECURITY.md` section 9). Deleting an account without it removes all data (security log entries lose the personal reference, D-018). With it the account is deactivated: no login or reset, responses never reveal existence, the user cannot reactivate; a system administrator can, unless an active/locked/blocked account has the same email. Assigning a person to a metering point with an assignment in force sets it (section 13); so does accepting the contract (D-103).
* **Email uniqueness** (D-016, D-034): unique among non-deactivated accounts via nullable `normalized_email` + a normal unique index (MariaDB has no conditional unique constraints; UNIQUE allows several NULLs); NULL while deactivated.
* **Protection rules** (D-016): the last active, unblocked system administrator cannot be deleted, deactivated, blocked or lose superuser status.
  * Email change: effective after verifying the new address (old valid until then), needs re-authentication, old address notified.
  * Registration or change to the address of an active, locked or blocked account does nothing; the response equals success and that address gets an information email. Confirming an email change or reactivation deletes a pending unverified registration for that address.
  * Every delete/deactivate/reactivate/block/unblock/promote/demote/email-change/retention-flag path uses the central account logic, also admin bulk actions (Django's "delete selected" skips `delete()`).
* **Deletion by the user** (D-055; amended by D-105, owner 2026-10-19): the page and the message are the same for every account **except** that an account that will only be deactivated (retention obligation or a metering point assignment) is told so before the proof and in the result ("Ihr Konto wird deaktiviert. Ihre Angaben bleiben aus Aufbewahrungsgründen erhalten."); no artificial delay. Without the flag account and data are erased; with it the account stays `deactivated` and the email is released; the admin shows "Deleted (retention obligation)" and offers "Restore account". The deletion is released only after the deregistration of every running metering point is started (D-105). Legal assessment of the wording (DSG Art. 6, 19, 25) unverified, owner's responsibility.
* **Customer number** (D-021, D-034, D-038): six random digits (`secrets.randbelow(10**6)`, max 100 retries), unique, never reused, text, shown `482 915`, read-only. Assigned once at completion of registration (or by the setup command for the initial administrator) by `assign_customer_number()` for a saved, active account without one; kept on email change and reactivation; unverified accounts have none.
  * `IssuedCustomerNumber` holds every number ever issued without person reference (immutable). `User.customer_number` is a one-to-one FK (`PROTECT`, `utf8mb4_bin`). An identifier, not a secret.
  * Max 1,000,000 numbers: from 90 % issued (`CUSTOMER_NUMBER_WARNING_PERCENT`, owner 2026-10-13) each issue logs a warning and the admin user list shows a notice to system administrators only; at 100 % registration completion fails (500; no error page defined). Login is by email only: counting failures across email and number would reveal whether they belong to one account.
* **Email canonical form** (D-021, D-035): local part ASCII only (no SMTPUTF8, RFC 6531 section 3.4). `email` stores NFKC, trimmed, whole address lower case, IDN domain as IDNA ASCII (UTS #46), derived in `save()`; `normalized_email` equals it unless deactivated. Lookups, counters, rate limits use `normalize_email_address()`. Validation rejects non-ASCII local parts, quoted local parts, domain literals, IPs, `localhost`, Unicode categories C/Z/M. `idna` is a direct dependency.
  * Owner decision 2026-10-12 (re-confirmed 2026-10-13 with the risk): the local part is lower-cased although RFC 5321 section 2.4 calls it case sensitive. Risk: on a case-distinguishing host mail could reach another mailbox; mitigated because all mail goes to the canonical stored address.
* **User model** (D-034, D-051): `leg_platform.accounts`, `accounts.User` from the first migration; profile fields on it. `USERNAME_FIELD = normalized_email` (unique, nullable, not editable, `utf8mb4_bin`).
  * Invariants in the model: `is_active` derived from status; unverified accounts have no customer number or usable password; `create_superuser()` refuses while any `is_superuser` exists; customer number never changes; retention flag only unset -> set.
  * Status, `is_active`, email, normalised email, retention flag, `is_staff`, `is_superuser`, customer number and password change only via `set_status()`, `change_email()`, `set_privileges()`, `assign_customer_number()`, `set_retention_obligation()`/`create_user()`. `QuerySet.update()` of these fields, `delete()`, `bulk_create()` are rejected (also base manager, `Meta.base_manager_name = "objects"`). `save()` of an existing account compares them with the `FOR UPDATE`-locked row. `delete()` refuses accounts with a retention obligation and the last active system administrator.
  * Not covered (DB privileges, `docs/SECURITY.md` section 9): raw SQL, `QuerySet._update()`, `loaddata`, many-to-many managers (`user.groups.add()`); no fixtures with accounts. Deleting an account deletes its admin log entries (owner accepted 2026-10-12).
* **Profile data** (D-032, D-034, D-036): fields follow eCH-0010 8.1.0 (https://www.ech.ch/de/ech/ech-0010; lengths per `eCH-0010-8-0.xsd`); all fields exist even if hidden.
  * Person: salutation (Mrs/Mr/Family/empty), title, first and last name. Organisation: name + two add-ons. Organisation name OR first+last name required. One account = one person or organisation.
  * Address: two lines, street, house number (text), dwelling number, PO box number (integer up to 8 digits) and text, locality, town, postal code, country (`CountryField`, default `CH`). Swiss postal code integer 1000-9999, foreign text up to 15. Required: postal code, town, country, and street or PO box (owner 2026-10-12); postal town, not political municipality. At registration only email; the rest after the verification link (owner 2026-10-13).
  * Phone optional (`PhoneNumberField`, `PHONENUMBER_DEFAULT_REGION = "CH"`, `PHONENUMBER_DB_FORMAT = "E164"`; declare `phonenumberslite`). Cross-field rules in `User.clean()`/`clean_fields()`.
  * Forms hide title, organisation add-ons, address line 2, dwelling number, PO box text, locality; validation never requires a hidden field, saving keeps stored values. An eCH export must fill the PO box text (e.g. "Postfach") when a PO box number exists. One "postal code" field: `CH` -> `swiss_postal_code` (4 digits 1000-9999); other countries (also `LI`, until eCH/owner clarify) -> `foreign_postal_code` (required, up to 15); the other is cleared.
* **Admin neutrality** (D-018, D-036): `User.__str__` = "Account 686 821" or "Unconfirmed account", never email or name. `LogEntry.object_repr` = "Account with internal number N" (`UserAdmin` overrides `log_addition`, `log_change`, `log_deletions`, not `log_actions()`); future admin code logging an account as related object keeps this, with a test. Account history: system administrators only (`UserAdmin.history_view()` 403 before any lookup). The user list shows/sorts/searches by customer number, not internal ID. The duplicate-email message exists only for the later email change; registration answers duplicates generically (`docs/SECURITY.md` section 3).
* **Collations and connection** (D-028, D-031): create every instance database with `CHARACTER SET utf8mb4 COLLATE utf8mb4_uca1400_ai_ci` (MariaDB default charset is `latin1` up to 11.5); Django test DB via `TEST["CHARSET"]`/`TEST["COLLATION"]`. Exactly compared identifier columns use `utf8mb4_bin` (`db_collation`): normalised email, tokens/keyed hashes, recovery codes, customer number.
  * Connection: `isolation_level` "read committed" (repeatable read can lose data), `charset` utf8mb4, `sql_mode` via `OPTIONS["init_command"]` = `STRICT_TRANS_TABLES,ERROR_FOR_DIVISION_BY_ZERO,NO_AUTO_CREATE_USER,NO_ENGINE_SUBSTITUTION`. Check `mysql.W002` (CI `--database default`); tests tagged `mariadb` verify it. Source: Django "Model field reference" (`db_collation`); MariaDB "Supported Character Sets and Collations".
* **Password hashing** (D-023): Django default PBKDF2-HMAC-SHA256 at the installed version's default work factor; never below it or OWASP's 600,000 iterations. Not raised for now (measure one hash on the real server; OWASP: under one second; higher needs a new decision). Argon2id not chosen. Source: Django passwords docs; OWASP Password Storage Cheat Sheet.
* **Keyed hashes** (D-017, D-023): counters and tokens store HMAC-SHA256 digests under a key derived from `SECRET_KEY` via HKDF with an own label per purpose (`cryptography`; prefer `django.utils.crypto.salted_hmac`; `keyed_digest` also reads with `SECRET_KEY_FALLBACKS`). Rotation resets counters (accepted). A leaked `SECRET_KEY` lets hashes be reversed with address lists; short retention limits the impact. Raw IPs and identifiers exist only in request memory.
* **Encrypted secrets** (D-006, D-040, D-087): secrets read back (Graph private key, TOTP key, IBAN) are Fernet-encrypted under an HKDF key from `SECRET_KEY` with an own label (`LEG-Platform Microsoft Graph certificate key v1`, `LEG-Platform person IBAN v1`; `leg_platform/accounts/encryption.py`). `SECRET_KEY_FALLBACKS` keys are tried; the value is re-encrypted on use or by the re-encrypt commands. An undecryptable value shows nothing and is logged without content.

## 6. Authentication, second factor, confirmation links

* **Login** (D-004, D-021, D-037): email + password via Django `LoginView`; one message for every failure; a nonexistent email behaves like a wrong password; no user for inactive accounts; `redirect_authenticated_user` off; `/logout/` POST only. Pages with forms, tokens or personal data send `Cache-Control: no-store`.
  * Passwords (OWASP Authentication Cheat Sheet; NIST SP 800-63B-4 Appendix A): Django validators, minimum 15 characters for ALL accounts, maximum at least 64, no composition rules. Texts shown to users state only the real policy.
* **Second factor policy** (D-004): TOTP (authenticator app) mandatory for staff and system administrators, optional for users (they may turn it off; staff and administrators cannot). A password reset never removes or bypasses it; recovery must not bypass MFA (OWASP MFA Cheat Sheet). D-106: administrators may use a passkey-only account instead.
  * Library `django-otp`; the completed factor is checked centrally, independent of method. Passkeys: D-106 (`docs/PROJECT.md`, "Passkeys").
* **Central check** (D-040, D-041): `leg_platform/accounts/second_factor.py` (`requires_second_factor()`, `has_second_factor()`, `is_second_factor_complete()`, fails closed without the middleware). `SecondFactorMiddleware`: such a session has no privileges without the factor (only logout/setup open); promotion applies in an open session; `PortalAdminSite.has_permission()` checks it too; the admin has no own login page.
  * The mandatory factor is set up in the restricted session at first login (owner 2026-10-13). Accepted: anyone knowing the password of a newly promoted account or the initial administrator can enrol first (no privileges; the owner is notified by email; reset is the recovery).
* **Devices and secrets** (D-040, D-054, D-062): `AuthenticatorDevice` (TOTP 30 s, 6 digits, SHA-1, one step tolerance, a used code is not reusable; one app per account, DB-enforced; only a confirmed app counts) and `RecoveryCodeDevice`/`RecoveryCode`. `django-otp` device throttling is NOT used (someone knowing the password could lock the owner out). Issuer = `INSTANCE_NAME`. Devices are not in the administration.
  * TOTP key (160 bits) Fernet-encrypted (section 5). Ten recovery codes (8 chars `a-z2-7`, 40 bits, shown once, a new set invalidates the old), keyed digests only, unique per device (`accounts_recovery_code_unique_per_device`), single use by one `DELETE`. The term is "recovery code".
  * Setup asks for the password unless the session is recent. An unconfirmed secret is valid 15 min, bound to the starting session. The QR code is an own SVG (`no-store`, no `data:` image). The factor is on only after a correct code. Recovery codes appear once in the POST answer that creates them (never stored plain or in the session; `no-store`, `sensitive_post_parameters`) with a server-checked "I saved the codes" checkbox. Notifications without link for setup, removal, renewed codes, used recovery code.
* **Two-step login** (D-040): no `login()` after the password if a factor exists. The pending login (account, time, safe redirect, password session hash) lives in the session for 5 minutes and ends if the account becomes inactive, the factor is gone or the password changed. `/login/two-factor/` takes an app or recovery code (`otp_token`, masked by Axes). Each attempt passes the Axes lockout check and takes its own IP slot; a wrong code is a failed attempt of account and IP, under the account row lock. Session ID renewed at each step. "Stay signed in": D-100.
* **Wrong-code budget at login** (D-040; owner 2026-10-13, small residual risk accepted): `AuthenticatorDevice` counts wrong codes in 24 h from the first (`failed_codes`, `failed_codes_since`); only wrong codes that reach the check count (not Axes/pause refusals or wrong passwords).
  * At 10: one email without link per window + log line (outside the mail budgets). At 15: code entry paused until the window ends, also for a correct code (lockout page with reset link; does not extend the Axes lockout). A completed password reset relieves to at most 10, once per window.
  * A successful login does not clear the budget (deviation from NIST SP 800-63B-4 section 3.2.2, accepted). No escalating cool-off (someone knowing only the email could lock an account). Accepted: anyone knowing only the password can pause code entry for 24 h.
* **Automated attacks** (D-017; owner 2026-10-12): `django-axes` for temporary lockouts per normalised account identifier + a separate transactional MariaDB counter per client IP (Axes shares rows, so account resets would lower IP counts).
  * Limits: 5 failed attempts in a rolling 15 minutes for account and IP each; 15-minute cool-off (`LOGIN_COOLOFF`; the lockout page names the real duration). Completing all factors releases the IP slot; failures keep it until the window ends. An account reset clears only Axes account rows, never the IP counter.
  * Identifiers and IPs only as keyed digests. POST `password`, `otp_token`, `otp_device` masked (`AXES_SENSITIVE_PARAMETERS`). Axes admin disabled until a read-only, system-administrator-only view exists.
  * Client IP = `REMOTE_ADDR`, forwarded headers ignored (`AXES_IPWARE_PROXY_COUNT=0`); behind proxies the operator sets the exact trusted proxy count first. A lockout is recorded only when the failure reaching the limit is counted (Axes 8.3.1 also signals refused attempts during a lockout).
  * Accepted risk: someone knowing an email can repeatedly trigger temporary lockouts and use up the per-address mail limit. Sources: django-axes 8.3.1 docs, django-ipware; OWASP (a lockout must not enable denial of service; recovery stays possible while locked).
  * Lockout response `AXES_LOCKOUT_CALLABLE = "leg_platform.accounts.axes_handler.lockout_response"` (lockout template, `AXES_HTTP_RESPONSE_CODE` 429, never-cache, same HTML for XHR and for the second-factor pause; never shows the submitted value). No middleware or `AxesMiddleware` subclass: django-axes' JSON answer echoes the username and sets `Access-Control-Allow-Origin` from `AXES_ALLOWED_CORS_ORIGINS` (default `"*"`).
* **Lock order** (D-072): account row first, then counter rows (`LoginIpBucket`/`LoginIpAttempt`, `SessionCodeFailure`, `ConfirmationFailure`); an inverted order caused MariaDB 1213 deadlocks. Cleanup commands lock per account with `skip_locked`, never wait. No `nowait`: waits end at `innodb_lock_wait_timeout`, then 1205/1213 = HTTP 500, nothing accepted, no oracle, no retry. Do not widen the application DB account with `PROCESS`. Operators check the `EXPLAIN DELETE` plans (`docs/DEPLOYMENT.md` 12.4).
* **Registration** (D-016, D-037, D-058; owner 2026-10-13: six-digit number): three steps.
  * Step 1 asks the address only. New/unverified address -> unverified account + token + link (a pending registration is replaced, the old link dies). Active, temporarily locked or blocked account -> no account, one identical information email without link (no IP/agent/time; no reply asked). Deactivated accounts do not hold their address. Duplicates never give a form error. The next page is identical for every address. "Send again" after a 60 s pause enforced on the server; D-038 limits apply to every resend.
  * Mail goes to the canonical stored address, never the entered spelling (IDNA 2003 vs UTS #46 mismatch could bind an account to a domain the attacker does not control).
  * Step 2 sets the password. The verified address is shown as plain text (no form control, so no password manager can overwrite it); a hidden read-only `username` field (`autocomplete="username"`, out of the tab order, `aria-hidden`) gives the password manager the account context and the server ignores its posted value; both password fields are `new-password` (Chromium "Create Amazing Password Forms"; WHATWG HTML autofill field names). The same for the new password after a reset link (`accounts/_account_name.html`). The password is held only as a hash in the session, bound to the link digest. Step 3 collects names, street, house number, postal code, town, privacy checkbox (stored: `privacy_accepted_at`, `privacy_accepted_url`).
  * Only the last step activates the account: status, customer number, password in one transaction with locks on account (first) and link, then login. `User.complete_registration()` is the only place a customer number is issued.
  * The link stays valid until step 3 completes or 24 h pass (mail scanners, back button; no text may call it single use). Opening it calls `cycle_key`.
* **Token links** (D-037, D-038, D-058, D-067): token = `secrets.token_urlsafe(32)`, stored only as keyed digest (`VerificationToken`, own HKDF label). Opening a link stores the digest in the session and redirects to the form page (scanners cannot consume it); the token is consumed only when the form succeeds (row lock; `sensitive_post_parameters`).
  * Token pages send `Referrer-Policy: no-referrer` and `never_cache`; no form is served under `no-referrer` (POST would send `Origin: null`, which CSRF refuses); form views after the redirect use `same-origin`.
  * Every invalid, expired, used or replaced token, non-active account, stop link without open request, or removal link without usable second factor answers `302` to a fixed page (`/email-change/expired/`, `/email-change/stop-expired/`, `/two-factor-reset/expired/`; registration and reset to "link no longer valid" with an address field). Status, `Location`, headers, body identical for every cause; no token, no flash message; fixed paths must not match a token route.
  * `TOKEN_URL_PATTERN` (`leg_platform/log_filters.py`, also used by the session-timeout middleware so tokens never reach `next`) matches every token route incl. `/email-change/stop/<token>/`; a logging filter redacts tokens on all handlers; a test walks the resolver (a regex route with `token` fails). Proxy/web-server access logs are the operator's job (nginx error logs can keep token URLs). Response time is not equalised (`docs/SECURITY.md` section 11).
  * Accepted: `APPEND_SLASH` 301 for a token URL without slash; a stale-session cookie returned; `SecondFactorMiddleware` redirects an incomplete staff session before a verify view; rotating `SECRET_KEY` invalidates pending links.
* **Password reset** (D-038, D-044): "Forgot password?" -> single-use link valid 24 h (= the longest limit window; a completed reset removes all outstanding links) -> new password -> normal login, no automatic login. Mail only to status active (a temporarily locked account is active: reset works during a lockout); other states get nothing (unblock a blocked account with `emergency_access unblock-account N`).
  * Reset ends all other sessions and that account's temporary lockout only (never IP counters or lockouts), leaves the second factor untouched, notifies the account. `process_reset_request()` locks the account row and checks status under the lock; `complete_reset()` accepts only purpose `PASSWORD_RESET`. A request below the per-address limit deletes earlier reset links first (retries during a mail outage each replace the link: accepted).
* **Password change** (D-040, D-062): `/profile/password/`; session ID renewed, other sessions end, notification sent, outstanding reset links removed; refused under the lock if the session auth hash changed since request start. "New equals current" is checked only after a valid proof, via `check_password(new, user.password)`; before a proof the answer is identical whatever the new password is (it was a guessing oracle).
* **Login after registration, recent authentication** (D-055, D-063): completing registration calls `login()` with `second_factor.LOGIN_BACKEND` and goes to the start page; no privileges; a used/expired/replaced link logs nobody in.
  * `second_factor.recently_authenticated(request, max_age=timedelta(minutes=5))` is true only if the session holds the server-side `authenticated_at` (epoch seconds, number not bool, not in the future, at most 5 min old), written only by the `user_logged_in` receiver `remember_authentication` (after password and 2FA, and registration completion); never by activity, key cycling, password change/reset or client input; ends with the session. Not bound to an account id; safe only because a session never changes account without a flush; a future path changing a session's account must bind the time to the account.
  * Accepted Low risks: within 5 min of a login an unattended browser can start 2FA setup without the password (consequence: owner locked out); `ENROLMENT_LIFETIME` 15 min; "Copy codes" uses the clipboard; the 5 minutes are the owner's choice, not an OWASP rule.
* **One proof per confirmation, "2FA wins"** (D-062; owner 2026-10-15): every profile re-authentication asks exactly one proof: the 6-digit app code if 2FA is active, otherwise the current password, never both. Applies to email changes (incl. second address), password change, new recovery codes, turning off 2FA, account deletion, forced password change. Staff without 2FA give the password; 2FA setup after more than 5 min asks the password.
  * A posted `current_password` with 2FA is ignored; the code is checked after all other fields are valid. After `totp.normalize_code` only exactly six digits count; anything else is refused as "not a code", not counted against the wrong-code budget (a habit-typed password cannot pause the account), never echoed.
  * A recovery code is no proof in any profile confirmation; it counts only at login and in "phone lost". `totp.verify_code()` needs the caller to hold the account row lock.
* **"Phone lost"** (D-062): card "turn off 2FA", `POST /profile/two-factor/lost-phone/`, works without script: password AND a recovery code, both right; wrong password and wrong code give the same message; the code is used up only if everything before was right. Success in one transaction under the account row lock (of two parallel posts one wins): 2FA off, other sessions end, every address mailed, security events `recovery_code_used` and `two_factor_removed_phone_lost` (long retention). Not for staff/administrators, not without 2FA. People with neither app nor code go through the operator.
* **Wrong entries in confirmations** (D-062): counted per session, not at the account budget, Axes or IP counter (an existing Axes lockout or pause still refuses). `SessionCodeFailure`, keyed by a keyed digest (purpose `LEG-Platform session code failures v1`) of a random `confirmation_counter_id` kept in the session across `cycle_key`; changed under the account row lock.
  * `SESSION_CODE_LIMIT` = 5 ends the session, event `session_ended_wrong_codes`, one notice to every address. A correct code deletes the row; a right password restarts the count except in "phone lost"; format errors count nowhere.
  * Account cap (`ConfirmationFailure`): 15 wrong entries over all sessions in 24 h end all sessions (`end_all_sessions`), event `all_sessions_ended`, one notice, count restarts (login not paused); a running request is refused (`confirmation_refused`). `cleanup_confirmation_failures` removes rows older than 30 days.
  * A session holder cannot trigger the account budget or Axes; with session and password the code can still be guessed (5 per session, 15 per 24 h). Residual risk: with 2FA an app code alone suffices to change email/password or delete the account (phished code, unlocked phone). Mitigations: notifications to all addresses, other sessions end, 24 h pending address change with stop link, budgets, Axes.
  * Accepted low points (next change of this area): L-1 `verify_password`/`verify_second_factor(per_session=True)` do not check the caller is the logged-in person (a new caller without login needs `request.user.pk == user.pk`); L-2 under an Axes lockout the check still sends the failed-login signal (counts against the holder's IP only); L-3 a login in a logged-in session also restarts the session count for accounts without 2FA; L-4 session counts are cleaned only via `run_scheduled_tasks`.
* **Profile cards, second address, stop link** (D-059): `/profile/` has five cards (personal details, email addresses, password, 2FA, delete account); state server-rendered (`?edit=...&step=...`); GET changes nothing. Mandatory-2FA accounts see only the 2FA card; the forced password change keeps its own page.
  * Second address: `User.secondary_email`, `PendingEmailChange` (account, kind login/secondary, address, 24 h deadline, one per account and kind). A request stores a row for every target address whether or not it belongs to another account (same answer, no enumeration); the worker re-checks. Two-step link (page, then POST). A login-address change ends all other sessions and mails old and new address. The second address never logs in or resets a password, is not unique, is stored only after confirmation, removable at once.
  * Notifications go to every address (`User.notification_addresses()`, `mail_queue.enqueue_for_account`): password changed, address changed/removed, 2FA on/off, new recovery codes, deletion; queued before the confirmation link.
  * Stop link `/email-change/stop/<token>/`, sent to the old login address and a confirmed second address with every change request: works without login, two-step; cancels all pending changes, deletes all confirmation and stop tokens, ends every session, records `email_change_stopped`, recommends a new password; refuses a link without an open request. `User.discard_email_change_requests()` runs after password reset/change, on any status change away from active and in `remove_second_factor`; confirming a login address deletes all stop links.
  * Limits are checked for every posted kind before password/code (`RequestRefused`, HTTP 429 only for client-address and instance limits); bot hits and repeats count per client address (`SCOPE_MAIL_SILENT`, 30/h). Events `email_change_cancelled`, `email_change_stopped`, `secondary_email_changed`, `registration_completed` carry no personal data. All mail templates have `autoescape off`.
  * The delete card shows the legal notice (`legal/VORGABEN.md` section 7) with privacy link, re-authentication, a never pre-ticked checkbox. Open owner question (not built): an attacker with password and session who confirms a new login address in their own mailbox at once leaves no window for the stop link; an undo window needs a product decision.
* **Lost second factor** (D-004, D-041, D-044): users: a system administrator requests removal in the administration (action "Reset two-factor authentication", system administrators only, 403 otherwise, also for the own account). The worker mails a single-use link (24 h, keyed digest, never in the job); the owner confirms with a button; then devices are deleted, all sessions end, the owner is notified, the event is logged. A newer link replaces the older; it dies if the account is inactive, became staff or has no factor.
  * Staff and system administrators: immediate reset after the administrator ticks that identity was verified in person or by callback to a number known independently of the account; the factor is set up again at next login. The last system administrator: only `emergency_access reset-second-factor N`. An incoming email's sender is never proof (forgeable, RFC 7489).
  * Rationale: users reach only their own profile and a mailbox reset already opens accounts without a second factor, so confirmation through the registered mailbox is proportionate; staff need a strict identity check.
* **Bot protection stage 0** (D-058, D-069): hidden field `contact_fax_number` (class `hp-field`, `aria-hidden`, `tabindex="-1"`, `autocomplete="off"`) + signed `form_started` (`django.core.signing`, min age 2 s `MAIL_FORM_MINIMUM_SECONDS`, max 3 days) on step 1, the invalid-link form and the reset request; a hit shows the same confirmation without a job. A read-only pre-check of client-address and instance limits (`mail_queue.requests_refused`) runs before storing anything: refusal creates no `MailJob`/session and answers HTTP 429 with a visible message; only these two limits are shown (no account oracle); the per-address limit stays silent. Proof of work (ALTCHA) is not built; reconsider only if abuse is observed (needs designer approval and study of licence, data protection, self-hosted widget under the CSP).

## 7. Security log and sessions

* **Security log** (D-018, D-041): events per `docs/SECURITY.md` section 10. Never passwords, tokens, secrets or complete links; only necessary personal data; accounts by internal number (not customer number); entries of deleted accounts lose the personal reference.
  * `SecurityEvent` = time, event (fixed list), internal numbers of the account concerned and the actor (no FKs), long-retention flag; no email, no free text. Append-only in the application (update, delete, bulk create refused, also for Axes failure/lockout records). Admin: read-only, system administrators only (not by permission). Also logged to `leg_platform.security`, in the change's transaction (exceptions: initial administrator, lockout, re-encryption).
  * Retention is server configuration: `SECURITY_LOG_RETENTION_DAYS` / `SECURITY_LOG_LONG_RETENTION_DAYS`, defaults and minimums 30 / 365 days (lower value stops the start); `cleanup_security_log` deletes expired entries.
  * Long retention: changes of rights/roles/`is_staff`/`is_superuser`, initial administrator, emergency commands, 2FA reset of staff and system administrators, blocking/unblocking of staff and administrators, administrator changes of another account's password/email, deletion/deactivation/reactivation by administrators, Graph configuration and portal settings changes, staff changes of customer data, grid operator changes, printing. Everything else 30 days.
  * No stricter protection against persons with server/DB access (owner 2026-10-13). Basis: DSG (SR 235.1) Art. 6 para. 4; OWASP Logging Cheat Sheet. Events of functions not yet built are logged when they exist.
* **Sessions** (D-041, D-056): see D-100 (idle timeout only; "stay signed in" 14 days; no step-up code). **Log files and log page** (D-099): see D-099.

## 8. Mail

* **Delivery** (D-006, D-028, D-070): all mail via Microsoft Graph with a certificate (client credentials, signed client assertion), not a client secret (owner 2026-10-14; Microsoft advises against secrets in production).
  * `EMAIL_MODE`: `console` (default, local), `allowlist` (local, `EMAIL_ALLOWED_RECIPIENTS`), `graph` (stage, production; section 3). Outside local a missing value stops the start.
  * Local `allowlist` (owner 2026-10-11): dedicated development app registration and mailbox with credentials separate from stage/production (`docs/SECURITY.md` section 7); recipients only in the user environment variable, never in the repository; empty list refuses the start; each entry one full lower-cased address (one `@`, domain with >= 2 labels, no wildcards); errors name only the entry position.
  * Tests never send real mail (locmem), use only reserved domains (RFC 2606: `example.com/.net/.org`, `.test`, `.invalid`); `leg_platform/tests/test_repository.py` scans text files for other addresses.
  * `leg_platform.mail.GraphNotImplementedEmailBackend` raises on every send until the real backend is configured; never silence `mail.E001`. Django 6.1 refuses `EMAIL_TIMEOUT` with `MAILERS`; the Graph backend sets its own timeout.
* **Graph configuration** (D-006, D-048): system administrators maintain tenant ID, client ID, sender, certificate, private key in a Django admin section with test send (`accounts.GraphConfiguration`; superusers only view/change, no add/delete). Changes logged; expiry shown (certificate-expiry warning not built).
  * Private key write-only, Fernet-encrypted (section 5); a non-ASCII key is refused; a stored one gives a generic `GraphEmailError` without token request; an `OSError` from MSAL tenant discovery becomes a generic error. Certificate: key size at least 2048 bits, expiry checked; `GRAPH_UPLOAD_MAX_BYTES` = 16 KiB, and the proxy must limit the body too (`docs/INSTALLATION.md`).
  * Test send: superuser only, only to the requester's own address, refused in console mode, every attempt logged (`GRAPH_TEST_EMAIL_REQUESTED`), reuses the per-address budget (D-051).
  * Loggers `msal.oauth2cli.oauth2` and `msal.oauth2cli.assertion` are CRITICAL, `propagate` False (MSAL logs token response bodies at ERROR).
* **Graph backend** (D-006, D-048): `msal`, `POST /v1.0/users/{sender}/sendMail` (202 = accepted, not delivered). Fail closed if the message sender differs from the configured sender. Never follow redirects (bearer token).
  * No `Auto-Submitted` header (Graph allows custom headers only on creation, named "x-"; SMTP sends `Auto-Submitted: auto-generated`, RFC 3834 section 5.2): switch off automatic replies of the sender mailbox (`docs/INSTALLATION.md` step 6).
  * Exchange Online: restrict the app to the sender mailbox with "RBAC for Applications" (filter `EmailAddresses -eq 'smtp:<sender>'`, verify with `Test-ServicePrincipalAuthorization`); no organisation-wide `Mail.Send` in Entra ID. Source: Microsoft Learn (application-rbac, v2-oauth2-client-creds-grant-flow, user-sendmail, message resource).
* **Mail content** (D-037, D-038, D-054, D-058): plain text only in phase 1 (HTML adds link spoofing, tracking, rendering risk). Acceptance after the real Graph test send: click a link mail in Outlook, Apple Mail, Gmail and a Swiss webmail; if a link breaks, add a line asking to copy the whole line into the address bar.
  * Links only from `INSTANCE_BASE_URL`, never from the request (`docs/SECURITY.md` section 4), on their own line. Sender `EMAIL_SENDER_ADDRESS` (optional, strict pattern), default `noreply@<host of INSTANCE_BASE_URL>` (locally `noreply@localhost`).
  * Emails never say replies are read (owner 2026-10-13); notifications invite no reply and tell the person to contact the operator if not requested; link mails end with a contact line from `INSTANCE_WEBSITE_URL`. SPF/DKIM/DMARC are DNS settings. A failing send is logged by exception class only. Pages after a request show identical conditional text for every address.
* **Queue** (D-038): registration, reset and invitation requests only count the request and store one `MailJob`; nothing is read or sent in the request (no address-dependent response or timing). Worker `manage.py process_mail_queue` (`--loop`) claims under lock (retry after 2 min), sends outside any transaction, deletes the job; raw tokens are created by the worker, never stored. At-least-once; given up after 3 attempts. `cleanup_mail_requests` deletes unprocessed request jobs after 1 h and notifications after 24 h; jobs of a deleted account go with it (CASCADE).

* **Purpose** (D-033, D-066, D-069): Swiss addresses are checked and autocompleted against a local copy of the swisstopo "Official directory of building addresses" (public federal data) where a postal address is edited: registration step 3 (country fixed to CH) and profile edit (owner 2026-10-15); not in the read-only profile or the Django admin.

Logging: only DB errors and `ValueError` of the limit check, fixed texts.
* **Source and licence** (D-049, D-022, D-066, D-074): STAC collection `https://data.geo.admin.ch/api/stac/v0.9/collections/ch.swisstopo.amtliches-gebaeudeadressverzeichnis`, asset `amtliches-gebaeudeadressverzeichnis_ch_2056.csv.zip` (UTF-8 with BOM, `;`, 143 MB zipped, 3.3 million lines). The import verifies the SHA-256 multihash (prefix `1220`) from the catalogue.

The reference belongs into the privacy notice and imprint of every instance, written by the operator (D-074); no attribution in the UI.
* **Stored columns** (D-049): only `STN_LABEL` (street), `ADR_NUMBER`, `ZIP_LABEL` (split at the first space into postal code and locality; the postal locality, not `COM_NAME`), `BDG_EGID` (building identifier) and `ADR_EDID` (entrance identifier), the last two since 2026-10-19 (owner approval, see below); no others (`BDG_NAME` may contain names; data minimisation, FADP art. 6). * **Building identifier (EGID)** (owner 2026-10-19, KONZEPT 3a; amends D-049, D-066): a building is identified by its EGID, not by address text.
  * Column: `BDG_EGID` (swisstopo, "Amtliches Verzeichnis der Gebaeudeadressen", product information table 1 "Attribute", column CSV; also the first line of the published file, checked 2026-10-19: `ADR_EGAID;STR_ESID;BDG_EGID;ADR_EDID;STN_LABEL;ADR_NUMBER;...`). KONZEPT 3a names it "EGID": the file has no column of that name. Stored as `Address.egid` (nullable integer, 1 to 999,999,999, anything else refuses the file), `Address.entrance_id` (column `ADR_EDID`, product information table 1, SHORT; nullable, 0 to 32767, anything else refuses the file; owner approval 2026-10-19 for the "Hauseingang und EGID" choice; in the file of 2026-10-19 values 0 to 90, none empty) and `Directory.has_egid`. One `Address` row per row of the file: an address with several buildings has several rows, a building with several addresses shares its EGID over several rows (in the file of 2026-10-19: 15,603 addresses with more than one EGID, 54,875 EGIDs with more than one address). A file without a column is refused ("Missing EGID column.", "Missing entrance column.", `jobs.SAFE_FAILURES`), the published generation stays. A published generation without identifiers (`has_egid` false; migration `addresses.0005` also resets it for a generation imported before the entrance existed) is replaced by the next import even if the checksum is unchanged.
  * Search `addresses/buildings.find_buildings(street, house_number, postal_code, town, user=)`: (1) the local directory, exact on the folded keys, no internet; (2) a stored answer (`BuildingLookup` in the application database, so an import does not replace it and request threads may write it; keyed digest of the normalised address, never its text; negative answers 7 days, positive 90 days, `cleanup_address_lookups`); (3) one request to swisstopo, only for a signed-in active account and within the budgets (6/min and 10/h per account, 30/min and 300/h per instance; `limits.allow_external_lookup`), and not while the circuit breaker is open (below). Result: `found` (candidates: one per EGID and entrance, each with `egid`, `entrance_id`, house number, street, postal code, locality; the wizard shows "Hauseingang und EGID" and lets the person choose when there are several), `not_found` (every attempt made), `unavailable` (`reason` not_signed_in, limit, circuit_open or failed: nothing stored, no flag) or `invalid`.
  * Outbound request (`addresses/swisstopo.py`, the only module besides the importer that imports `requests`; `docs/SERVICES.md` S-4): `GET https://api3.geo.admin.ch/rest/services/api/MapServer/find` (swisstopo product information chapter 3, https://docs.geo.admin.ch/access-data/find-features.html): layer `ch.swisstopo.amtliches-gebaeudeadressverzeichnis`, `searchField=zip_label`, `searchText` the postal code, `layerDefs` `adr_number ilike '<number>' and stn_label ilike '<street>'` (the service filters only these attributes). Only the house number (ASCII, `[0-9A-Za-z][0-9A-Za-z.\-/]{0,11}`) and street (anything outside letters, digits, space, point and hyphen becomes the wildcard `_`) reach the filter; hits are compared again on the folded text.   Fixed https URL, no redirect, `Accept-Encoding: identity`, JSON content type, strict checks of every field (nested JSON that exhausts the parser is a failure, not a crash), at most 200 features (a full answer without the address is no conclusion), no proxy variables or `.netrc`, 256 KiB. **Time:** one wait is limited to 3 s (connect) and 4 s (read; a normal answer takes 0.2 to 0.6 s), and the **whole request has a hard deadline of 8 s** (a quarter of the 30 s of a Gunicorn worker): the request runs in a helper thread, the caller waits at most 8 s, and on expiry every socket of the request is shut down (the blocked read ends at once) and the helper thread is gone. A socket timeout alone would not do: a server sending one byte every few seconds never times out. Proved against a local server that sends one byte every 0.3 s in the body, in the headers and not at all (`DeadlineTests`; the tests replace only the URL constant). **Circuit breaker:** 5 failures (timeout, error status, invalid answer; not a refused input) within 5 minutes pause the search for everybody (`limits.circuit_open`, counted in the transactional rate-limit tables, so every worker sees it); a success clears the count; while it is open nobody is asked and no budget is used up (the result is `unavailable`, reason `circuit_open`). A failure carries a fixed sentence; the address is never logged.
    * **Review path:** `BuildingSearch.needs_review` is true for `not_found` and for an `unavailable` search whose reason is `limit`, `circuit_open` or `failed`: the caller notes the address for the review by the LEG and lets the person go on (nobody is stuck by swisstopo or the budget). **Today** (`community/buildings.find_candidates`) every `unavailable` raises the application error `directory_unavailable` and nothing is noted: the wizard still has to use `needs_review`.

### D-090 Address import in the web process (2026-10-17)

* Decision (owner wants visible progress and errors): the admin button and an automatic refresh start the import in a daemon thread of the web process (`runner.py`). No extra service or cron job. Worker `process_address_imports` stays an optional alternative. Why: the button only queued a request that nothing consumed.
* Claim: `jobs.claim` locks the single `ImportRequest` row (`claim_token`): one import over all web workers and the worker. The thread has its own DB connection. Gunicorn runs sync workers (`docs/DEPLOYMENT.md` 8.1). Recycle (`--max-requests`), restart or kill ends the thread; `atexit` marks the job interrupted where it still runs, else the next claim finds the stale heartbeat.
* Heartbeat: a second thread writes phase, bytes, rows every 2 s. Without it for 90 s (`jobs.HEARTBEAT_STALE_AFTER`) the job is dead; the next claim takes over and frees the lease. The old thread checks its claim at every phase (D-101). The live directory is untouched until the new generation is complete.
* Writer: only the import thread writes the SQLite file (`storage.mark_thread_writer`, thread-local). `mark_writer` stays forbidden in `wsgi.py`/`asgi.py`.
* Status: JSON at `admin/addresses/importrequest/status/` (session + `addresses.request_directory_import`, GET only, `no-store`); `static/js/import-status.js` polls every 2 s while queued or running (stops at a login redirect or 401); the poll is no session activity (D-100). Only the fixed sentences of `importer.ImportFailure` (`jobs.SAFE_FAILURES`) reach row, page and logs; anything else is "failed unexpectedly" (trace in the application log).
* Logs: logger `leg_platform.addresses`; security events `address_import_succeeded`/`address_import_failed` (kind and fixed reason or count); the request keeps `address_import_requested`.
* Automatic refresh (replaced 2026-10-19): the call `runner.maybe_start_automatic()` from the administration start page and the management overview, and `runner.AUTOMATIC_CHECK_INTERVAL`, are removed; the daily run of the scheduled tasks replaces them (section 10, "Import", Schedule). The thread of the web process stays for the button (`runner.start_manual`).
* Sources (2026-10-17): Python `threading` ("Daemon threads are abruptly stopped at shutdown", `threading.local`); Django `django/db/utils.py` (`ConnectionHandler.thread_critical = True`); Gunicorn design https://gunicorn.org/design/ (pre-fork, `sync` = one request per worker).

### D-098 Request budgets and back-off (2026-10-17)

* Decision: person search (`management:metering_points_person_search`) is counted per staff account (`rate_limits.PERSON_SEARCH_LIMITS`, 300 per minute); text under two characters is not counted. Beyond the limit: 429 with `Retry-After: 30` and `{"results": [], "limited": true}`.
* Why 300: at 120 ms, typing without a pause sends about 8 requests per second (the running request is cancelled); normal work stays far below; a hijacked session cannot keep the database busy for long.
* Bounds: text cut to 100 characters (`PersonAssignForm.person` `max_length=100`); only the first five words filter (`person_search.MAX_WORDS`).
* Back-off: `combobox.js` and `address-directory.js` send no request after a 429 until the `Retry-After` time has passed (30 s, at most 120 s; 60 s for the address lookup). The combobox says "Too many searches. Please wait a moment." and searches the text again after the pause.
* Address lookup budget unchanged: 60 per minute per client address, 600 per minute per instance. At 200 ms with cancellation at most five requests per second. A refused request means "no suggestions". Not measured against real typing.
* Amends D-094 "the person search has no request limit".

### D-099 Logs and log hardening (2026-10-17; replaces D-092)

* Decision: logs go to standard error (journald in production) and, with `LOG_DIRECTORY`, to `application.log` and `security.log` (rotating, 10 MB x 5, files 0600 in a 0700 folder). Defaults: local `~/.leg-platform-dev/logs`; stage and production `/var/log/leg-platform` with `LogsDirectory=leg-platform`. `off` = standard error only. An unusable folder means no files.
* Page "Protokolldateien" in the administration (`admin:logs*`; `is_superuser` only, no right): lists files, shows one live (poll of an offset, pause/follow), streams a download. Fixed keys `application`/`security` plus backup number 0-5, never a client path. Every line is redacted when read (tokens, emails, IBANs, database error values). Events `log_viewed`/`log_downloaded` (long retention); the same page again within 300 s in one session is no new event; a download always is.
* Hardening: `log_filters.SafeFormatter` escapes CR, LF, other control characters and U+2028/U+2029, so a path like `%0a` cannot forge a line; tracebacks stay multi-line. Files open with `O_NOFOLLOW` and are checked as regular file on the descriptor (Windows has no `O_NOFOLLOW`; the descriptor check remains). Download redaction reads in pieces with a 512-character overlap cut at a blank; the local part of `EMAIL_PATTERN` is bounded to 64 characters.
* `portal_upload_rejected` is written once per session and minute with an app-code proof (the upload is judged before the code is checked); with a password proof every rejection is written.
* Residual risk: several processes write one file; `RotatingFileHandler` does not coordinate rotation (Python `logging` cookbook), so rotation can reorder or drop older lines; size stays bounded. Run `manage.py` as the service user (`docs/OPERATIONS.md` section 5).

### D-100 Sessions and long sessions (2026-10-17; replaces D-088)

* Session end (owner 2026-10-13, changed 2026-10-17; deliberate deviation from OWASP's absolute timeout): server-side `SessionTimeoutMiddleware`. Idle timeout: users 30 min, staff and system administrators 15 min; every request extends it (written at most once a minute). No absolute limit for an ordinary session. A session without stored times ends (fails closed).
* Background polls (`session_timeout.PASSIVE_VIEWS`: import status, live log) neither extend nor survive the idle timeout (401, no redirect). After a timeout: login page with a message; return after GET only; a POST changes nothing; the redirect never puts a link token into the login URL.
* `SESSION_COOKIE_AGE` (8 h) only bounds the cookie and row of an abandoned session; `clearsessions` removes them. The session hash covers the password and `User.session_version`; `User.end_all_sessions()` raises it.
* Cause of "logged out every 5 minutes" (owner): the portal settings page refused a save when the login was older than `RECENT_AUTHENTICATION_WINDOW` (5 min). Replaced by one proof at the save (app code, else password; wrong entries counted per session, D-062). The window remains for setting up the second factor only.
* Stay signed in (owner: for everyone, also staff and system administrators): off by default. Ticked gives `STAY_SIGNED_IN_DURATION` (14 days, owner may change) as absolute end and idle timeout (a `timedelta`, so it does not slide). The wish lives on the request object or in the pending login, never in the session. A privileged account without a second factor gets none.
* Second factor: checked once per login; the persistent session exists only after the code was accepted; the 14 days then need no new code. Residual risk (owner-accepted): a stolen persistent session of a staff account has its privileges, incl. IBAN and PDF lists, for up to 14 days. Operator: staff log out on foreign devices.
* Mitigations: every persistent session of a staff or system administrator account writes security event `persistent_session_started` (long retention); no email (owner 2026-10-19: security proportionate to the effort of users, normal level; too many mails make users ignore all mails). A system administrator ends all sessions of another account ("End all sessions", `lifecycle/end_sessions/`, event `account_sessions_ended_by_admin`, long retention); the own account is excluded (as the 2FA reset, D-041).
* No step-up code (owner, D-102): whoever is signed in is authenticated; an unattended device is the operator's responsibility.
* Amends D-041 absolute timeouts; D-056 "stay signed in not for staff"; D-055/D-073 five-minute rule; wording of D-086.

### D-102 Metering point number, menu, unchanged items (2026-10-17; replaces D-093)

* Source: VSE/AES "Metering Code Schweiz (MC-CH 2025)", 4 December 2025, section 4.2.3 "Bildungsregel", tables 4 and 5 (<https://www.strom.ch/de/media/13608/download>, read 2026-10-17). Same composition: VSE/AES "Handbuch Messdatenmanagement HB-MDM-CH", November 2017, section 2.4 (<https://www.strom.ch/de/media/8287/download>).
* Composition: 33 characters. Positions 1-2: country (ISO 3166 alpha-2, "CH"). 3-13: identifier (grid number in 3-8, reserved placeholder in 9-13, assigned by VSE/AES). 14-33: the number the grid operator assigns (20 characters, unique in its area, not temporary). Empty positions are zero; optical separators only inside the 20.
* The 20 characters (table 5, ISO 8859-1: "Grossbuchstaben A-Z, die Ziffern 0-9 sowie der Bindestrich"): A-Z, 0-9 and "-", ASCII only. The owner follows the standard (replaces the digits-only rule of D-093).
* Rule, one place `numbers.normalise_entered_number` (form class, check route `management:metering_points_check_number`, `field-check.js`): shorter than 20: zeros on the left (`zfill` would put them behind a hyphen); longer than 20: only leading zeros are removed, as many as needed, otherwise invalid ("The metering point number is invalid: it is too long. …" with the count); more than 200 characters (`MAX_ENTRY_LENGTH`): invalid; forbidden character and empty: own messages; no other character is ever removed; all zeros are valid.
* Small letters are accepted and stored as capitals (the column is binary and unique; `ab-12` and `AB-12` are one number). The character check runs before upper-casing (`ß` would become `SS`).
* Field: no `maxlength` (a paste is never cut), no `inputmode`, `autocapitalize="characters"`; internal name `number_digits`. Country (2 capitals) and identifier (11 capitals/digits, looser than grid number plus placeholder) come from `ManagementSettings` (D-077). Complete number `[A-Z]{2}[A-Z0-9]{11}[A-Z0-9-]{20}`, unique, nullable; duplicates found on the normalised value. The script pads on leaving the field, shows the complete number, looks it up.
* Column 33 characters, unique, binary collation (no migration). Lists and search use `contains` on the upper-cased word. History holds ids only. `format_metering_point_number` groups by four. The IBAN-like log redaction may over-redact a number (harmless).
* Power fields and LEG quota: `form_fields.DecimalInputField`: digits and one decimal point or comma (stored as point), no sign, at most two decimals, at most 999999.99 (`DECIMAL(8,2)`); quota `DECIMAL(5,2)`, at most 999.99 (D-089). Checked while typing and on the server.
* Menu "System administration" (amends D-097): shown in the left and phone menu only to an active staff account for which `admin.site.get_app_list(request)` is not empty (`navigation.system_administration_visible`; Django's own check of view/add/change/delete rights, plus the log files for a system administrator). Superuser: always; staff with one admin right: yes; staff without any, customers: no. No group name or role is read. Hiding is not security: the administration refuses every request without the right. "Mail texts" needs `accounts.view_emailtext` or `accounts.change_emailtext` (`navigation.EMAIL_TEXT_PERMISSIONS`).
* Unchanged: the location of a metering point stays optional; the warning "This metering point is not assigned to a location." is in the list and the banner of the point with "Set location". An invited person stays unassignable (D-081: no person until it has a customer number); the text after inviting says so. The bottom bar is unchanged.
* No step-up code: no new code before IBAN, PDF lists or any other action; an unattended device is the operator's responsibility.
* Amends D-093, D-096, D-088, D-100.

## 20. Decisions of 2026-10-21 (D-106)

### D-106 Passkeys: registration, switching, recovery and reset (2026-10-21; amends D-004, D-040, D-044)

* **Login methods.** A user registers with a password. A password account may add an authenticator app (2FA) and may switch to a passkey. A passkey account has no password and no app. The switch needs re-authentication with the current proof, ends all other sessions, notifies every address of the account and deletes the password, the app and the recovery codes. Password and passkey are never combined on one account.
* **Passkeys.** Passkeys are discoverable, so sign-in needs no username. The email address stays the account identifier for registration, notices and reset. Passkeys are voluntary for users. A second passkey on another device (for example computer and phone) is recommended. The portal refuses to remove the last passkey.
* **Administrators.** `is_staff` and `is_superuser` may use a passkey-only account. They first register two passkeys on two devices, then the password and the app are removed. The passkeys then meet the second-factor requirement of D-004 (amended).
* **Recovery codes.** Password accounts keep 10 codes of 8 characters, unchanged. Passkey accounts have no recovery codes (amends D-040).
* **Back to password.** Self-service with a current passkey as proof: the user sets a new password. The change takes effect only after the user clicks a link sent to every address. Until then the passkeys stay valid, afterwards they are deleted. The app is offered; it stays optional for users and is required for administrators (D-004).
* **Lost passkey.** With a second passkey the user signs in with that one. Without any passkey, the user receives instructions by email to contact the LEG administrator and prove identity with an official ID document, sent by email. The administrator checks it and starts the reset manually. Owner decision: convenience over an in-person check, accepted and recorded.
* **Reset.** Started by a staff user or a system administrator (`is_staff` or `is_superuser`, amends D-044). Staff may reset other staff. The administration shows a red button; after a warning dialog that names the consequences, the reset starts. Identity check: the person sends an official ID document by email; the administrator compares the name with the stored values. The same applies to staff and system administrators (simplicity chosen over an in-person check, owner decision). A single-use link (24 hours) goes to the registered address. The old passkeys stay valid until the link is clicked; then they are deleted and the user chooses the login method again, exactly as at registration (users: password, password and app, or passkey; administrators: password and app, or passkey). The email verification is replaced by the link. Every reset is notified to all addresses and logged.
* **Guidance (2026-10-21, designer specification accepted, team lead decisions).** A person is helped to choose, in plain language, never with "2FA" in a heading:
  * The choice step is called "Sign-in method" ("Anmeldemethode"). One component (an explainer, a static decision helper "Which fits me?" and one card per method with "You need" and "If you lose it") is shown at four places: the registration follow-up (the start tile, which stays hideable and disappears once a second factor exists), the profile card, after a reset, and at the first login of an administrator (restricted session, then the page joins `second_factor.UNRESTRICTED_VIEWS`).
  * The options come from one server function (`accounts/login_methods.py`, `available(user)`): users are offered password only, password and app, passkey; administrators password and app, passkey (no password only, D-004). An administrator with only one option has no choice page. The posted method is validated against that list on the server; a method that is not offered, such as a forged `passkey`, is refused. The choice leads into the existing flows and adds no security logic.
  * Recommendation: users "password and app" ("Not sure? We recommend ..."; the app has the most precise recovery path, the recovery codes); administrators the passkey on two devices once passkeys exist. The explainer names no app brands ("an authenticator app from your phone's app store").
  * The passkey option, its explainer paragraph and its helper line are hidden by the setting `PASSKEYS_ENABLED` (default False; a plain Django setting, not read from the environment) until passkeys are built: no page mentions a passkey while it is off. Turning the setting on before a passkey flow exists must not promise what the server cannot keep: while `login_methods.PASSKEY_FLOW_BUILT` is False (flipped in the change that builds the flow), `PASSKEYS_ENABLED=True` fails the system check `accounts.E001` (an Error, so `check`, `migrate` and `runserver` refuse it).
  * Source: designer specification of 2026-10-21; D-004, D-040, D-056 (Clear register).
